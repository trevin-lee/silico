# Sketch editing

The sketch edits M4 left out (docs/design/m4.1-command-api.md, section 5's *Not in M4*):
- adding and removing a point, a curve, or a constraint;
- splitting a curve at a point;
- trimming a curve back to its neighbours;
- pulling a shared point apart;
- deleting a curve while keeping its neighbours' shared point;
- merging ends that touch (decision 17's `--merge-touching`).

M5's sketch mode needs them, and the draft M5 plan (#196) puts them in a step of their own, M5.10. This note is the study it starts from. It says what FreeCAD does, the edge cases, the fixes in FreeCAD's history, the tests to port, and where Silico's shared points make it differ. **This note decides nothing.** The decisions at the end are open, each with a recommendation, for M5.0's design and the maintainer to take or change. Wherever the note says what Silico does, "recommended" or a column headed *Silico*, it's that recommendation, not a settled rule.

## 1. The model each side edits

**FreeCAD.** Every curve has its own ends: `start`, `end`, and `mid` (a centre). A joint is a `Coincident` constraint between two ends, or an endpoint-to-endpoint `Tangent` or `Perpendicular`, which imply one. Geometry and constraints are addressed by **index**, so every deletion renumbers what follows (`changeConstraintAfterDeletingGeo`, `SketchObjectConstraints.cpp:1439-1475`), expressions included (`testIssue3245`). A lone `GeomPoint` is geometry of its own.

**Silico** (D2, approved 2026-10-16):
- A sketch lists its points. A line goes `from` one point `to` another; an arc has `center`, `start` and `end` points, counter-clockwise; a circle has a `center` point and a `radius`.
- <a id="se-share-a-point"></a>Two curves that meet **share a point**, so there is no coincidence constraint. Every reference is an 8-character ID, so nothing renumbers.
- The fixed references `origin`, `x_axis` and `y_axis` can be named but not edited.
- The gate (D2, *The gate's rules for sketches*) refuses, among other things:
  - a line whose ends are one point;
  - an arc whose start or end is its centre, or whose start and end are one point;
  - geometry of size 1e-7 mm or less;
  - <a id="se-a-curve-s-own-point-constrained"></a>a curve's own point constrained onto that curve;
  - an edge `tangent` between two curves that share an end, which must be `tangent_at`.

  <a id="se-every-edit-s-result-has-to"></a>Every edit's result has to pass it.

**What follows for the port:** FreeCAD's whole joint-repair layer has no counterpart in Silico. That layer is `transferConstraints`, `delConstraintOnPoint`'s search for a replacement point, `getDirectlyCoincidentPoints`, and renumbering. About a dozen of FreeCAD's fixes below repair that layer, and they don't apply as code. The rules they protect still apply, and each becomes a test.

## 2. Adding and removing

### Add a point, a curve, a constraint

**What FreeCAD does:**
- **`addGeometry`** (`SketchObjectGeometry.cpp:148-207`) checks nothing ("a sketchobject managed operation", :150, :186). It copies each geometry with a fresh tag (`71a555a6bb`, so adding one Python object twice makes two curves, with two tags *(1.1.3)*) and appends it. The list form appends the whole list in one `setValues`.
  - **Construction** is one flag for the call, so the list form sets it on every member *(1.1.3)*. Since `3db4633f9d` (2024) a point is construction only when asked; before it every new point was forced to construction *(1.1.3: a point added alone isn't)*.
  - **Degenerate input** is refused only where Part won't make it: a line's ends within `gp::Resolution` raise "Both points are equal" (`Part/Geometry.cpp:4822`) before the sketch sees the line *(1.1.3)*. A circle of radius 0 and a line 1e-12 mm long are added, and the sketch solves them (status 0) *(1.1.3)*.
  - Since `0e174da56d` and `f32d5e5fd9` (2026), the Gui's tools refuse non-finite positions and zero-size rectangles before they add anything.
- **Python's `addGeometry`** (`SketchObjectPyImp.cpp:69-196`) takes one geometry or a list:
  - In a list, an item that isn't a geometry is **skipped silently**: `[line, 5, circle]` adds two curves *(1.1.3)*.
  - A geometry of a type the sketch doesn't take (an unbounded `Part.Line`) raises `TypeError`, "Unsupported geometry type", **before any is added**, so that list adds nothing *(1.1.3)*.
  - A `Part.Arc`, a trimmed circle, is taken as an arc of a circle (`d974d6897b`, #1713).
- **`addConstraint`** (`SketchObjectConstraints.cpp:930-962`) and its list form **`addConstraints`** (:858-893) check nothing either. Each new constraint has its form completed **from the current geometry**:
  - a tangency's or perpendicularity's kind at an end, 0 or π, by `AutoLockTangencyAndPerpty` (:2674, from `3838bddcdb`, 2014);
  - on main only, a distance's or a line-circle tangent's side, by `setOrientation` (:1407; `3c8a254356`, 2025-12, for distances; `f432d1c6a7` and `5a6be36bc3`, 2026-04, for tangency, #29007). 1.1.3 records no side *(1.1.3: its `Constraint` has no orientation attribute)*.
- **Python's `addConstraint`** (`SketchObjectPyImp.cpp:370-439`) checks index ranges (`evaluateConstraint`, `SketchObjectConstraints.cpp:2172-2233`), since `7d8b1f30c3` (2014, #1720: invalid sketches crashed FreeCAD):
  - **One constraint** out of range raises `IndexError`, "Constraint has invalid indexes", and adds nothing *(1.1.3)*. A constraint can only name geometry the sketch already holds, so a shape's geometry and its constraints take two calls *(1.1.3: a `Horizontal` of geometry 0 on an empty sketch is refused)*.
  - **A list is checked whole before any of it is added.** One constraint out of range refuses the whole list, with "The constraint has invalid index information and is malformed." (`0e85b24348`, 2023's wording) and one message for the list *(1.1.3: `[Horizontal(0), Horizontal(5)]` on a sketch of one line adds neither)*. Items that aren't constraints are skipped silently.
  - **Only the range is checked.** A position a curve hasn't, like a line's `mid`, is added, and the solve then reports it malformed *(1.1.3: status −5, `MalformedConstraints` [1])*. That has been an error at recompute since `150e50c700`.
  - **One constraint is solved as it's added,** so its geometry moves before the command is committed. `e1dd86f0a9` (2015, #2281) recomputes the initial solution after that solve. **A list isn't solved** *(1.1.3: a `Horizontal` on a line from (0, 0) to (10, 1) moves it at once when added alone, and added as a list leaves it at (10, 1) until the next solve)*.
  - **A conflicting constraint is kept,** alone or in a list. The solve reports the conflict (status −3), and the sketch holds every constraint *(1.1.3: two `DistanceX` of 10 and 12 on one line)*. Only main's Coincident command rolls back a worse solve (`cb2780e2fa`, below).
- **Setting the properties directly** (`sketch.Constraints = …`) is an "unmanaged" operation. Since `c35d8be9a3` (2020) its indices are checked too, and a bad constraint is shown empty, with an error in the report, but not refused.
- **The Gui's tools** add a shape's geometry and its constraints in one transaction, and abort it on any exception (`Gui/DrawSketchHandlerLine.h:130-158`: "This prevents constraints from being applied on non existing geometry"). So a tool's batch is made whole or not at all.
  - **Before they commit,** the tools drop the auto-constraints they inferred (a snap's coincidence, a tangency, a horizontal) that the solver finds redundant, and abort on a redundancy or conflict that isn't one of those: `removeRedundantAutoConstraints` and `diagnoseWithAutoConstraints` (`Gui/DrawSketchDefaultHandler.h:752-798`, from `677694b0ba`, 2023). Silico's add keeps a redundant constraint, which the edit's solve flags with a warning, so M5's drawing tools must carry the same filter before they send the batch.
- **The Coincident command** (`Gui/CommandConstraints.cpp:5310-5782`, from `e38154474a`, `084379651a` and `cb2780e2fa`, 2025–2026) refuses:
  - <a id="se-points-already-coincident-even-through-other"></a>points already coincident, even through other points ("already coincident");
  - <a id="se-a-coincidence-that-would-bring-two"></a>a coincidence that would bring two ends of one curve together, directly or through a chain ("would collapse geometry to zero length", #20771);
  - <a id="se-any-result-whose-solve-is-worse"></a>any result whose solve is worse than before, which it rolls back.
  - Its tests are the six in `SketcherTests/TestCoincidentCommandGui.py`.
- <a id="se-tangency-substitution"></a>**Tangency substitution:** adding a tangency between curves whose ends are joined gives an endpoint tangency, and adding a coincidence where an edge tangency exists does the same (`180d722a53`, `620188073e`, #3299).

**Edge cases:**
- **An empty list** adds nothing, and both list forms return an empty tuple *(1.1.3)*.
- **The same object added twice** gives two curves with different tags (`71a555a6bb`).
- **A constraint before its geometry** is refused for its index (above).

**What Silico does differently** (docs/design/m5.0-app.md, `sketch_add`):
- **One batch of every kind,** as the document writes them: points, lines, circles, arcs and constraints, each member with its own ID. A constraint may name a member added in the same batch, because the batch is checked as the sketch it makes. FreeCAD's two calls, geometry then constraints, become one.
- **Whole-batch checking.** The batch is checked whole before any of it is added, as Python's list `addConstraint` and the Gui's transactions do, but by every rule of the gate, not only index ranges:
  - The gate runs on the sketch with every member added, and refuses it with **all** its errors at once.
  - Each error names its field by ID path (`circles.cb000003.radius`). A new member has the same path in the sketch as in the request, so each error points at the request's own field.
  - A wrong form, a dangling ID (with candidates), a curve of 1e-7 mm or less (the circle of radius 0 and the 1e-12 mm line that FreeCAD adds), a curve's own point constrained onto it, an edge `tangent` between curves that share an end, a value out of range: each is refused when it's made, never at the next solve. Nothing in the batch is skipped silently.
- **ID paths.** A member's ID that the sketch already holds is refused at the request's field (`circles.cb000003.id`), naming the member that holds it (M4.1 §2, *An edit that repeats an ID*). An ID given twice in the batch is refused at the later member's place (`circles.1.id`), where the gate names a later holder. Both are checked before the gate, which would name the untouched member by its place. There is no tag to copy: the ID is the member's identity, so `71a555a6bb`'s rule becomes a refusal, not a renaming.
- **An ID a removal freed** may be given again, and the member added with it is the removed one's to every stored name: a feature's name made from it finds the new member, wherever it lies, as after a `replace_text` that keeps the ID (decided 2026-10-29). The saved file is the truth, and reusing an ID is the writer's choice of identity; refusing it only until `commit` would make the result depend on the edit's path. Clients give each new member a fresh random ID.
- **Shared points** (M3.2's D2). A new line may run from a point the sketch already holds, so it's joined to that point's curves by construction, where FreeCAD adds a curve with ends of its own and a `Coincident`.
- **D4.** `side` and `direction` are given, never recorded from the geometry as `setOrientation` and `AutoLockTangencyAndPerpty` record them. A `tangent` given `right` where the drawing shows the circle on the line's left is added as `right`. What the rebuild's solve then finds depends on the form; the edit is applied either way (SD7):
  - **A line's `left` or `right`** (a `tangent`'s, a `point_line_distance`'s): the solve never moves the drawing across. 1.1.3's PlaneGCS measures a point's or a circle's distance from a line unsigned, so it solves the drawing on the side it's on, and M3.3 reports the result as `invalid_result` (`wrong_sides`), naming the constraint: the sketch reads invalid.
  - **`inside` or `outside`, and a `direction`**: the solve moves the drawing to the side given, or fails, and the sketch reads as the failure (M3.3).
- **`construction` is per member,** as given, for points too (D7; `3db4633f9d`).
- **The add doesn't solve, and isn't refused for what the solve then finds** (M5.0's SD7). Once the gate takes the batch, it's applied; the rebuild's solve is the sketch's state, so a conflicting or redundant constraint reads as such, and the features that sweep the sketch fail loudly. FreeCAD keeps a conflicting constraint and reports it, so this follows it. Only the edits that write geometry (split, trim, merge, unjoin, extend, and a drag's release) refuse a conflict their solve finds, around the edit, as the merge's check does (decision 10).
- **An empty batch changes nothing:** nothing is added, and the sketch is as it was, so the command's `changed` is false, as for `set_field` to a field's own value. FreeCAD's empty lists add nothing too.
- **`added`** lists the members by kind (points, lines, circles, arcs, constraints), each kind in the request's order, which is the order the edit makes them. `modified` and `removed` are empty.
- **Tangency substitution** is already the gate's rule (`tangent_at` where two curves share an end), so an edge `tangent` added between curves that share an end is refused, naming its field, never converted.

### Remove a constraint

`delConstraint(s)` (`SketchObjectConstraints.cpp:964-1019`) erases by index and shifts the rest. Deleting a `Coincident` unjoins two ends **without moving them**.

<a id="se-in-silico-a-constraint-is-removed"></a>In Silico a constraint is removed by ID and nothing shifts. There's no coincidence constraint to delete: unjoining is its own edit (§5). So removing a `tangent_at` leaves its point shared, where FreeCAD's endpoint `Tangent`, which joins the ends in place of a `Coincident`, leaves them apart when deleted *(1.1.3, the sketch-edit oracle's sweep, seed 42: `edit_42_214`, its delete leaving them apart in 10 of 10 runs)*.

### Remove a curve

**What FreeCAD does** (`delGeometry`, `SketchObjectGeometry.cpp:226-288`; the Gui's batch form `delGeometries`, `SketchObjectOperations.cpp:115-167`):

1. **Joints.** For each of the curve's `start`, `end` and `mid`, `getDirectlyCoincidentPoints` (`SketchObjectConstraints.cpp:2002-2042`) lists the ends joined to it, in constraint order: through `Coincident`s, and since `f8f159c4d3` through endpoint-to-endpoint `Tangent`s too. If any are listed:
   - `delConstraintOnPoint(onlyCoincident)` (:1036-1159) picks the partner of the **first** `Coincident` as a replacement, re-points every other coincidence to it, and drops the one between them. So at a joint of three or more curves the others stay joined.
   - `transferConstraints` (:1161-1229) moves the deleted end's other constraints onto the first listed partner: locks, `PointOnObject`, `Symmetric` (its third element since `51cf34a596`), and point-form horizontal and vertical.
     - An endpoint `Tangent` or `Perpendicular` becomes a `Coincident` (`9ce5756011`, #3291: a tangency nobody asked for was imposed on the neighbour).
     - An `Angle` is dropped (`e66849378b`, #3589).
2. **Dropping.** Every constraint naming the curve in any slot is dropped, and every later index shifts (`0016d6f2f8`, `aeabffeed8`). An end used by no other curve disappears with the curve, and so do its constraints.
3. **One solve,** after the whole edit (`65310f00ab`, `339717c96f`).

| Deleting the middle of a chain, or a curve at a joint of three *(1.1.3)* | Result |
|---|---|
| D between A and B, each joint its own (`Coincident(A.e, D.s)`, `Coincident(D.e, B.s)`) | Both coincidences go. A and B are free. D's lock on its start moves to `A.e` |
| D the hub of a three-way joint with A and B | `Coincident(A.e, B.s)`: they stay joined |
| Two arcs whose centres are joined through a deleted circle's centre | The arcs' centres stay coincident |
| A lone point joining two line ends | The lines stay coincident; the point's lock moves to `A.e` |

**FreeCAD's defects here, observed in 1.1.3:**
- <a id="se-the-result-depends-on-the-order"></a>**The result depends on the order of the constraints.** When an endpoint `Tangent` is listed before the `Coincident`, the replacement (from the first `Coincident`) and the transfer target (the first listed partner) differ. The coincidence is dropped, the tangency isn't moved, and **the two neighbours end up unjoined**. With the constraints listed the other way round, they stay joined.
- <a id="se-an-endpoint-to-edge-tangent-on"></a>**An endpoint-to-edge `Tangent` on the deleted end becomes a malformed `Coincident(point, edge)`,** still carrying its angle value.

**What Silico does differently:**
- <a id="se-shared-points-do-all-of-this"></a>**Shared points do all of this by construction.** A point that another remaining curve uses survives, and every constraint on it stays as it is: no re-pointing and no transfer.
- <a id="se-a-tangent-at-naming-the-deleted"></a>A `tangent_at` naming the deleted curve is removed, never moved onto a neighbour (`9ce5756011`'s intent).
- <a id="se-a-deleted-line-s-midpoint-becomes"></a>**A deleted line's `midpoint` becomes a `symmetric`** of its ends about the point, while the point and both ends stay. FreeCAD stores a midpoint as a `Symmetric` of the line's ends, so deleting the line leaves it on the ends its neighbours keep *(1.1.3, the sketch-edit oracle: `remove_line_with_midpoint`)*. Silico's `midpoint` names the line, so it's rewritten, keeping its ID, as split rewrites one (§3).
- Nothing depends on constraint order.
- **What Silico has to decide** is what happens to a point **only** the deleted curve used. FreeCAD's end disappears with the curve. Recommended (decision 7): the same. A point no remaining curve uses is deleted with its constraints, as a line's endpoints go with it in SolidWorks, unless it was a standalone point before the curve used it. With shared points that can't be told apart, so the rule is simply "used by no curve after the edit".
- **Batch delete:** deleting a set equals deleting its members one by one. It tolerates duplicates and members that depend on others in the set, and it's solved once (`41c91574cf`, `4ffb6c5e2a`).
- **Refused:** deleting `origin`, `x_axis` or `y_axis` (`2a401ee895`, `83d14b785e`).

### Remove a point

<a id="se-freecad-s-gui-delete-on-a"></a>FreeCAD's Gui Delete on a vertex does one of two things (`Gui/ViewProviderSketch.cpp:4885-4952`):
- <a id="se-on-a-geompoint-it-deletes-that"></a>On a `GeomPoint`, it deletes that geometry. Its constraints move onto a joined end if it had one *(1.1.3)*.
- <a id="se-on-any-curve-s-end-it"></a>On any curve's end, it *unjoins* that end (`delConstraintOnPoint`, §5).

<a id="se-freecad-has-no-delete-a-point"></a>FreeCAD has no "delete a point that curves end at". In Silico such a point *is* those curves' end, so deleting it would have to delete the curves too. Recommended (decision 7): delete a point only if no curve uses it, and otherwise refuse, naming the curves that use it.

## 3. Split

**What FreeCAD does** (`split`, `SketchObjectOperations.cpp:1151-1282`):

1. <a id="se-split-index-refusals"></a>**Refusals.** Only the index is checked: out of range raises "Not able to split curve with the given index". The kind isn't checked: the curve is taken by a `static_cast` (`SketchObject.h:285-288`), and splitting a `GeomPoint` **segfaults** *(1.1.3, in `GeomCurve::getFirstParameter`)*. Main has the same path, by reading; trim's equivalent was fixed by `5efb8e5e76`, and split never got the check. Only the Gui restricts kinds.
2. <a id="se-split-position"></a>**The split position** is the given point's projection onto the curve (`closestParameter`). A point off the curve splits at its projection *(1.1.3: (4, 3) on the x axis splits at (4, 0))*.
3. <a id="se-at-or-beyond-an-end-it"></a>**At or beyond an end, it fails inside OCCT,** with "Geom_TrimmedCurve::U1 == U2", and the sketch is left unchanged *(1.1.3)*. `82633fb5df` (2022) refused this with "Split point is at one of the end points of the curve."; the refactor `215fbc5187` (2025) lost the check.
4. <a id="se-near-an-end-nothing-is-refused"></a>**Near an end, nothing is refused:** a split 1e-12 mm from the start makes a 1e-12 mm line *(1.1.3)*.
5. **Pieces.**
   - An open curve gives two pieces: the start side keeps the curve's index and geometry ID (`82610ca8fa`, a refactor that changed behavior), and the other is appended.
   - <a id="se-a-circle-gives-one-arc-from"></a>**A circle gives one arc from the split angle to the same angle plus a full turn,** whose start and end are at one place and aren't joined *(1.1.3)*. At some angles it gives an arc with no sweep instead (first and last parameter 5.12777734235934 and 5.127777342359341, a circle split at about 293.8°), and a second split of it raises "Geom_TrimmedCurve::U1 == U2" *(1.1.3, the sketch-edit oracle's sweep, `edit_32_410`)*.
6. <a id="se-constraints-on-the-curve-s-ends"></a>**Constraints on the curve's ends** stay with the outer ends (`transferConstraints` with `doNotTransformTangencies`). The refactors `6c8cb8e58d` (lines, 2022) and `c6f5739763` (arcs, 2024) turned an end tangency into a coincidence, and `6d06b61c7e` fixed it on main; 1.1.3 still turns it into a `Coincident` *(1.1.3)*.
7. **Constraints on the curve itself** go through `deriveConstraintsForPieces` (`SketchObjectConstraints.cpp:1506-1747`), shared with trim. The table below gives the rules.
8. **The joint between two pieces:**
   - Arcs get a `Coincident` at the split point and one between the centres.
   - <a id="se-split-lines-main-tangent"></a>Lines on main get an endpoint **`Tangent`**, which holds them collinear (`6d06b61c7e`, 2026-09).
   - <a id="se-split-lines-113-coincident"></a>Lines in **1.1.3 get a `Coincident`**: the pieces can kink unless a direction constraint was copied to both.
9. **No expression is kept** on a constraint split rebuilds *(1.1.3: a length's `5*2` was lost)*; trim keeps them.
10. **One solve** at the end (`c6c084f22c`, #23711: a solve halfway through moved geometry before the pieces were built).

|---|---|---|---|
| <a id="se-split-direction-constraints"></a>`horizontal`, `vertical`, `parallel` on a line | on both pieces; with `parallel` too, one redundant constraint | on the first piece only; the tangent joint carries it | as main (decision 1) |
| <a id="se-split-perpendicular"></a>`perpendicular` (in D4, between two lines' directions, never a contact) | on both pieces *(probed with a line it doesn't touch)* | dropped when neither piece touches the other line: it goes through the edge-contact test (:1563-1590, marked "TODO: Actually check that there was perpendicularity earlier"), a bug | on the start-side piece, with the direction constraints (decision 1); main's drop isn't copied |
| <a id="se-split-angle-segfault"></a>`angle` between lines | **segfault**: a piece not yet in the sketch reached `78e5729520`'s angle branch as a null (`std::ranges::any_of` over `newGeos`, in the crash report) | on the first piece; the crash is fixed by `bbbff1f8f1`, which passes the new pieces in | as main (decision 1) |
| `length` | `distance` between the outer ends | the same (`4d6b1f3eb8`, `2779f0b29f`) | `distance` between `from` and `to` |
| `equal` on a line | dropped | dropped (`857190a20a`, #25008; `edb87a0663`) | dropped |
| `radius`, `diameter`, `equal` on an arc or circle | first piece only | the same (`f0d30cb570`) | on one piece: the pieces share the centre, so their radii are equal anyway |
| <a id="se-split-on-dropped"></a>`on`, `point_line_distance` to the curve | **dropped** (#28240) | to the piece whose span holds the point's projection; outside every span, the nearer end's piece (`closestParameter`'s fallback, `Part/App/Geometry.cpp:1073-1083`) (`bbbff1f8f1`, `263331f6fb`) | as main, but on an arc a point outside both spans goes to the nearer end's piece, where `closestParameter` takes its antipode when that's on the arc *(1.1.3: 330° on an arc from 0 to 270°, split at 90°, goes to 150°, the second piece)*. With decision 1 the pieces lie on the original's line, or share its circle, so the constraint means on either piece what it meant before |
| <a id="se-split-edge-tangent"></a>edge `tangent` | on both pieces | to the piece that touches the other curve, else dropped (`6d06b61c7e`, `c823a6b270`) | to the piece whose span holds the contact; else the start-side piece, whose line or circle is the original's (decision 2) |
| `midpoint` of the line | kept on the outer ends, as a `Symmetric` | the same | `symmetric` of `from` and `to` about the point |
| <a id="se-split-symmetric-about-the-line"></a>`symmetric` about the line | dropped | dropped | on the start-side piece, whose line is the original's (decision 2) |
| <a id="se-split-tangent-at-an-end"></a>`tangent_at`, `tangent_on` at an end of the split curve (it's `a`) | made `Coincident` (the regressions above) | kept | kept: the end is the same point |
| <a id="se-tangent-on-onto-the-split-curve"></a>`tangent_on` onto the split curve (it's `b`: another curve's end `at` lies on it) | on a line, on both pieces, one copy then redundant; on a circle or arc, dropped *(1.1.3, the sketch-edit oracle: `split_line_tangent_on_second_half`, `split_circle_tangent_on`)* | a point-located constraint goes to the piece holding its point (`findPieceContainingPoint`, :1490-1504; `0800791a0f` for an angle via a point) | `b` becomes the piece whose span holds `at`. When `at` is the split point itself, it becomes `tangent_at` between `a` and that piece, its `direction` mapped from the stored one, never derived, since the gate refuses a `tangent_on` whose `at` is an end of `b` |

**What Silico does differently:**
- **The pieces share one new point** at the split position, and two arc pieces share the original centre point. Nothing is added to join them, so there's no joint constraint.
- <a id="se-constraints-on-the-original-end-points"></a>Constraints on the original end points don't move, because those points are the pieces' outer ends.
- <a id="se-splitting-at-a-point-the-sketch"></a>**Splitting at a point the sketch already has** (a point held `on` the curve): the pieces share that point, and its `on` constraint is removed, since the gate refuses a curve's own point `on` it. A `tangent_on` whose `at` is that point becomes a `tangent_at` (the table's last row).
- <a id="se-the-start-side-piece-keeps-the"></a>**The start-side piece keeps the curve's ID** (`82610ca8fa`): from `from` for a line, counter-clockwise from `start` for an arc. The other piece gets a new ID. Both keep `construction`, and so does the new point. FreeCAD 1.1.3 keeps it on a line's and an arc's pieces, but its circle split drops it: a construction circle gives a normal arc *(1.1.3, the sketch-edit oracle: `split_construction_circle`)*: a circle's pieces are new arcs (`GeomCircle::createArc`) where a line's or an arc's copy the curve, and split never got trim's fix (`23ecf94ab6`): `215fbc5187`'s refactor dropped the commented-out `setConstruction` calls, and `41c750be47` (#21504) removed the flag it read and never used. Silico keeps it on every piece.
- **A circle can't split as FreeCAD splits it,** since an arc whose start and end are one point is refused (decision 3).
- **An edge `tangent` with a curve that ends at the split point** (that end held on the curve by a `tangent_on`) never reaches a split from a checked document: the gate refuses an edge tangency beside a `tangent_on` of the pair (#258), as it does one beside an `on` of an end (`3a656d8597`). Given one unchecked, it would leave two curves sharing an end with an edge tangency, which the gate refuses. The split is refused, naming it. A merge converts such a tangency (§6), but here the `tangent_on` beside it already becomes the `tangent_at` it would be (the table's last row), so the edge `tangent` only repeats it, perhaps the other way round. FreeCAD's split makes the pieces new ends and never shares the point, so it has no such case; it reports the input itself redundant *(1.1.3: `redundant [1]` before the split)*, and removing the edge `tangent` is the fix.
- <a id="se-split-refusals-as-data"></a>**Refusals, as data naming the curve:** a point (the gate's kinds); a split position at, beyond, or within 1e-7 mm of an end (`82633fb5df`'s rule restored, with the gate's size floor); a position farther than 1e-7 mm off the curve (decision 4).

## 4. Trim

**What FreeCAD does** (`trim`, `SketchObjectOperations.cpp:921-1149`; the cut search in `Part/Part2DObject.cpp:104-261`):

1. <a id="se-what-may-be-trimmed"></a>**What may be trimmed:** any sketch curve that isn't internal geometry. A `GeomPoint` finds no cut and **is deleted** *(1.1.3)*. Before `5efb8e5e76` (#19425) it crashed.
2. **What cuts:** every other curve, including construction (`715f98d1f3`, #624) and external geometry. The axes cut only with main's opt-in `includeSketchAxes` (`196da068a0`), and then as infinite lines. **A sketch point never cuts** *(1.1.3)*. A cut is found three ways:
   - OCCT's curve-curve intersections at 1e-12;
   - both ends of an overlap or tangent-contact segment (`3cbe309330`);
   - every end of another bounded curve that lies on the trimmed curve within 1e-7 mm (`e10068a648`, #2463), because OCCT misses an end touching tangentially.

   **Tangency counts as a cut** *(1.1.3)*.
3. **Which cuts are used:** the nearest on each side of the picked point's projection, or for a closed curve the two nearest around it.
   - A cut within 1e-8 **in the curve's parameter** (`Precision::PApproximation`: mm on a line, radians on an arc, so r · 1e-8 mm) of an open curve's own end is no cut (`226d24792d`, :638-643), so a neighbour joined at the end doesn't make a zero-length piece.
4. **When the whole curve is deleted** (through delete, so joints are kept; `2d817128d0`):
   - no cut on either side (`testTrimWithoutIntersection`);
   - two cuts within **5e-5 mm** of each other *(1.1.3: two cutters 3e-5 mm apart, picked between them)*;
   - a circle with fewer than two distinct cuts (`testTrimCircleEnd`). Main reaches this by writing into an empty vector, which is undefined behaviour that happens to give the right answer.
5. **Pieces.**
   - A cut on one side shortens the curve.
   - Cuts on both sides of an open curve give two pieces.
   - A circle gives one arc, counter-clockwise from the cut after the pick to the cut before it.
   - The first piece keeps the index and ID (`7d8a8b7cc8`, `226d24792d`). Every piece keeps `construction` (`23ecf94ab6`, #12715).
6. **Each new end at a cut** is joined to the cutter. Each cut is decided on its own and from geometry (`7d9cfeb2c5`, `07cf5b10d7`):
   - If the cut is within **5e-5 mm** of the cutter's start or end (`dec01d1df0`, 2020: "needed in order to not falsely distinguish points calculated with seekTrimPoints"), the new end is made `Coincident` with that end.
   - Otherwise it gets `PointOnObject` on the cutter.
   - A cutter end already held `PointOnObject` on the trimmed curve at that cut becomes the `Coincident` (`6e6a0ccfb4`).
7. **A tangency between the cutter and the trimmed curve** (edge to edge) becomes an endpoint tangency at the new end (`dec01d1df0`). This applies only to the cutter at that cut: a tangency to an unrelated curve stays edge to edge (`08a66afbc8`, AstoCAD #24, `testTrimEndEffectOnUnrelatedTangent`).
   - <a id="se-a-perpendicular-with-the-cutter"></a>**A `Perpendicular` with the cutter** is treated the same way, by the same code (`transformPreexistingConstraintForTrim`, `SketchObjectOperations.cpp`): it becomes an end-to-edge perpendicular at the first cut by that cutter, on the piece whose end is there, and no other piece gets it *(1.1.3, the sketch-edit oracle: `trim_perpendicular_cutter`, `trim_perpendicular_cutter_into_two`)*.
8. **Constraints on a kept end** move with it. Those on a removed end are dropped. A constraint naming **both** ends survives only if both do (`f0d30cb570`, `502b7b9a3f`; `testTrimEndEffectOnFullLengthConstraints`, `testTrimEndEffectOnSymmetricConstraints`).
   - <a id="se-trimming-away-an-end-that-a"></a>Trimming away an end that a neighbour shares detaches the neighbour *(1.1.3)*.
9. <a id="se-constraints-on-the-curve-itself"></a>**Constraints on the curve itself:** as for split (§3's table), with three differences:
   - `horizontal`, `vertical`, `parallel`, `perpendicular` (but one with a cutter, item 7), an edge `tangent` on a line, and `angle` go to **every** line piece (`assumeTangency = false`, :1547-1552) *(1.1.3: a `Perpendicular` to a line it doesn't touch is on both pieces)*. Nothing joins two line pieces, which haven't been collinear since `2d817128d0`.
   - A `tangent_on` onto the trimmed curve goes to the piece holding `at`, and is dropped when `at` is on the removed part.
   - An `on` whose point lies on the removed part is dropped (`333ca836c0`).
   - Two arc pieces get coincident centres but **no `equal`** (`f0d30cb570`: it made constraints redundant), so the second arc's radius is free.
10. **Expressions follow** the constraints they're on (`bb5afb911a`, #27505; *1.1.3 keeps them*).
11. **One solve** at the end, never in between (`350a416708`, `fa2e5cd5fe`, `1dcde4e4cc`).

**Worked example** *(1.1.3)*. Line 0 runs from (0,0) to (10,0), with `Horizontal`, a length of 10 and `Equal` to line 3:
- cutter 1 crosses it at x = 3;
- cutter 2 *starts* on it at x = 7, held by `PointOnObject`;
- neighbour 6 is joined at its start;
- point 4 is `on` it at x = 5, on the part that's removed;
- point 5 is `on` it at x = 9.

Picked at x = 5, the result is:
- the pieces are 0 from (0,0) to (3,0) and 7 from (7,0) to (10,0);
- `Horizontal` is on both, and the length becomes `Distance(0.start, 7.end) = 10`;
- piece 7's start is joined to cutter 2's start;
- piece 0's end gets `PointOnObject` on cutter 1;
- point 5's `on` moves to piece 7;
- the neighbour stays joined;
- `Equal` and point 4's `on` are dropped.

**What Silico does differently:**
- <a id="se-the-piece-s-end-is-the"></a>"Coincident with the cutter's end" becomes **the piece's end is the cutter's point**, shared, but only when a constraint holds the cutter's end on the trimmed curve (decision 5). FreeCAD's own tests draw the cutter there with no constraint, and Silico departs from them (§9).
- "PointOnObject on the cutter" becomes **a new point with an `on` constraint** to the cutter. The cutter isn't split.
- Two arc pieces share the centre point.
- <a id="se-trimming-away-a-shared-end-gives"></a>Trimming away a shared end gives the piece a new end point; the neighbour keeps the shared point.
- **FreeCAD's 5e-5 mm "at the cutter's end" test merges points that aren't the same.** That's the snapping Silico's exactness rule refuses (decision 5).
- **Where intersections come from:** FreeCAD uses OCCT. Silico's curves are lines and circular arcs, whose intersections are closed-form (decision 6).
- **Line pieces stay independent,** with direction constraints on each, as FreeCAD's trim does. Unlike split, nothing joins them.
- <a id="se-where-nothing-can-take-a-constraint"></a>**Where nothing can take a constraint,** because the trim's pieces really are independent (an arc's edge `tangent` that no piece touches, `symmetric` about the trimmed line), FreeCAD drops it; Silico refuses the trim, naming it (decision 2). A contact past the arc's ends, on its circle beyond the arc, touches no piece either: it isn't taken by the nearer end's piece, as an `on` past the ends is.
- <a id="se-a-perpendicular-with-a-cutter"></a>**A `perpendicular` with a cutter** goes to the piece at that cut alone, as FreeCAD's does (item 7), and the new end gets its `on` the cutter as at any cut: D4's `perpendicular` is between two lines' directions, so the `on` and it together are FreeCAD's end-to-edge perpendicular. Copied to both pieces, it would be redundant when another direction constraint is on both.
- <a id="se-a-line-only-shortened-keeps-a"></a>**A line only shortened keeps a `symmetric` about it,** since the one piece is the same line. FreeCAD 1.1.3 drops it, because `deriveConstraintsForPieces` has no `Symmetric` case. Trimmed into two pieces, it's refused (decision 2).
- <a id="se-of-cuts-within-1e-7-mm"></a>**Of cuts within 1e-7 mm of one another, the new end is held on one cutter alone, the one the sketch already holds to the curve there,** ranked by what joining it adds, least first:
  1. a cutter's end held on the curve (an `on`, or a `tangent_on` with the curve as `b`): the new end *is* that point, its `on` implied. This replaces FreeCAD's 5e-5 mm merge (decision 5);
  2. a cutter held edge-`tangent` to the curve: a new point, the tangency made a `tangent_on` there, and no `on`;
  3. any other: a new point, `on` the cutter.

  Within a rank, the nearest is taken, then the first in the cuts' order (along the curve, then by cutter ID). That order is the bound: two cuts of one rank at one place are told apart by nothing else, and the result's `on` names the cutter taken, the end at the cut either way. The new end is never held on two cutters: what it lies on is the cut, one fact per new end. Holding it on a second cutter invents a relation the sketch never drew, and isn't harmless: a horizontal line edge-tangent to a fixed circle, trimmed back to a fixed upright through the contact, would get `on(end, upright)` beside `tangent_on(piece, end, circle)`, three equations on the end's two unknowns and the piece's direction, which the solve reads as redundant and refuses. A held tangency outranks a crossing because FreeCAD's answer there (the end `on` the upright, the tangency left edge-to-edge) holds the piece's carrier tangent somewhere but not the end at the contact, so the trim's result is lost at the next move; FreeCAD's own code wants the single end tangency instead (the TODO at `SketchObjectOperations.cpp:668-673`). A held end outranks a held tangency because it adds no point, and the other cutter's tangency carried edge-to-edge loses nothing the sketch held. **FreeCAD settles the tie by noise:** `seekTrimPoints` keeps the cut with the strictly greater (or smaller) parameter (`Part2DObject.cpp:210-232`, `param > param1`), so the lowest GeoId wins an exact tie, and otherwise whichever OCCT's parameter puts a bit nearer. Silico departs from that, and follows the rule above.
- <a id="se-an-arc-s-pick-outside-its"></a>**An arc's pick outside its sweep is placed at the end nearer in angle,** as its projection is. FreeCAD 1.1.3 removes a middle piece instead: on an arc from 0 to 270° cut at 90° and 180°, a pick at 300°, 315° or 359° removes 90°–180°.
- <a id="se-a-pick-at-a-round-s"></a>**A pick at a round's centre is refused,** naming the pick. FreeCAD 1.1.3 throws "Unknown C++ exception".
- **A `tangent` turned into an end tangency** needs a `direction` (`tangent_at` or `tangent_on`), which D4 stores and never derives from geometry (decision 8).

## 5. Pulling a shared point apart

**What FreeCAD does.** It has no shared points, and **no gesture to unjoin**: dragging a joint moves the whole coincident group. Two things unjoin ends:

- **Deleting the `Coincident` constraint.** Both ends stay where they are, now independent.
- **Selecting a vertex and pressing Delete** (`Gui/ViewProviderSketch.cpp:4922-4952`). This runs `delConstraintOnPoint(geo, pos)`:
  - <a id="se-that-one-curve-s-end-leaves"></a>That one curve's end leaves its group, and the rest stay joined, through re-pointed coincidences (`0358ff7ce2`, 2024: before it, every coincidence at the point was dropped, so a three-way joint fell apart).
  - <a id="se-the-end-s-other-constraints-stay"></a>The end's other constraints stay with that curve.
  - <a id="se-the-same-commit-also-drops-the"></a>**The same commit also drops the curve's own length** (`Distance`, `DistanceX` or `DistanceY` on the whole curve) when it unjoins either end *(1.1.3)*. Nothing asked for that, and Silico doesn't port it.
  - <a id="se-on-a-point-with-no-coincidence"></a>On a point with no coincidence, main does nothing since `bc4d463cdf` (#2275); 1.1.3 raises "Not able to delete a constraint on point" *(1.1.3, the sketch-edit oracle)*. Silico refuses it either way (decision 9).

**What Silico does differently.** Unjoining is an explicit edit: one curve's use of a shared point moves to a new point at the same coordinates. Recommended (decision 9):
- <a id="se-the-other-curves-keep-the-point"></a>The other curves keep the point and every constraint on it.
- <a id="se-the-detached-curve-gets-the-new"></a>The detached curve gets the new point with no constraints.
- <a id="se-a-tangent-at-between-the-detached"></a>A `tangent_at` between the detached curve and another at that point is removed, since they no longer meet. This is refused if the point isn't shared, naming the point (`bc4d463cdf`).
- <a id="se-every-dimension-of-the-detached-curve"></a>Every dimension of the detached curve stays (not `0358ff7ce2`'s side effect).
- With `origin` as the shared point, the detached curve gets a new point, and `origin` stays.
- Afterwards the two points are at one place. `check` then warns of them as `ends_not_joined` until something moves them, which is true and intended.

## 6. Merging touching ends

**What FreeCAD does.** The *Validate sketch* task (`Gui/TaskSketcherValidation.cpp`) and `SketchAnalysis` (`detectMissingPointOnPointConstraints`, `SketchAnalysis.cpp:505-550`):

- **Tolerance.** 1e-4 mm by default (`Confusion × 1000`; the task offers 1e-9 to 1e-2 and takes typed text). It's compared **per axis**, inclusive: a square, not a distance *(1.1.3: ends 0.9e-4 apart in both x and y are found)*. The history shows it is a user's tolerance, not a modelling rule: 0.1 mm in `957cedc1ff` (2013), then 0.001 (`b29fbc5f93`), then a choice defaulting to 1e-4 (`97a2b516bb`).
- **Clusters.** Ends are sorted with a tolerance (not a strict weak order). A cluster is the ends within tolerance of its **first** end, **not chained** *(1.1.3: ends at x = 0, 0.6e-4 and 1.2e-4 give one missing, not two)*.
- **Which ends count:** line, arc and conic ends only. **Not** arc or circle centres, not `GeomPoint`s, and not an end lying on a full circle *(1.1.3: 0 for each)*. External geometry never counts. Construction counts in Python's default, but the task's "Ignore construction geometry" is checked by default (`0d21e94d3f`, `10c0af4a8a`).
- **Joined** is meant to be `Coincident`, or an endpoint `Tangent` or `Perpendicular` (`7463aa7efd`, #2994). That fix also judged two curves sharing both ends per end.
  - `c036128aa0` (2022) made the grouping transitive, with k groups giving k − 1 coincidences (`testThreeLinesWithCoincidences_1`/`_2`).
  - The same commit starts the list from **every** constraint. So, *(1.1.3)*, two touching ends report **0 missing** whenever one of these holds:
    - a `Distance`, `Horizontal` or `Vertical` sits between them;
    - a deactivated `Coincident` joins them;
    - one of them carries an `on` to an unrelated curve or a lock (the end is dropped from the analysis).
- **Fix** (`makeMissingPointOnPointCoincident`) adds k − 1 `Coincident`s in one go, each chained from the first end of the previous group, ordered by (GeoId, PosId). **The solver then decides where the ends land.** Its one-by-one form solves after each and throws on failure.
  - `5696ee821c` (#14240): Fix once used a different analysis from Find and added nothing.
- **`autoconstraint`** first deletes every constraint. Not relevant to a merge.

**What Silico has already:** `check`'s `ends_not_joined` (crates/silico-core/src/warnings.rs, #189):
- profile curves' ends that are separate points, strictly closer than FreeCAD's **wire-joining** distance, 1e-7 mm, Euclidean;
- chained as `BRepLib_MakeWire` chains them, one warning per cluster;
- construction never warns.

That is deliberately not Validate's 1e-4 box. Ends 1e-7 to 1e-4 mm apart, which Validate would flag, are what M3.5's open-profile refusal names when a feature sweeps the sketch. **Silico doesn't carry `c036128aa0`'s bug:** joined means the same point, and no other constraint hides an end. Those cases warn where 1.1.3 says 0, and that divergence is deliberate.

**What Silico does differently.** The merge is an explicit edit that makes several points one, never a constraint the solver satisfies. Recommended (decision 10):
- **The request names the points.** `--merge-touching` names each `ends_not_joined` cluster's points.
- <a id="se-the-first-point-the-request-names"></a>**The first point the request names survives,** at its own coordinates; `--merge-touching`, whose points are within 1e-7 mm, keeps each cluster's least ID. The others' curves and constraints are re-pointed to it, and the others are removed. (A FreeCAD coincidence is solved, not placed: it lands where the solve takes it, at its `First` point in a two-line probe either way round *(1.1.3)*; Validate chains from the first end by (GeoId, PosId), creation order, which Silico's random IDs don't keep.)
- **Refused, naming them:**
  - <a id="se-points-that-are-already-one-point"></a>points that are already one point (`cb2780e2fa`);
  - <a id="se-a-merge-after-which-a-curve"></a>a merge after which a curve would use one point twice (a line's ends, an arc's centre and an end, or its two ends; `084379651a`, #20771, through any chain);
  - <a id="se-a-merge-after-which-a-constraint"></a>a merge after which a constraint would name one point twice (a `distance` or `horizontal_points` between merged points);
- <a id="se-an-on-the-merge-makes-hold"></a>**An `on` the merge makes hold a line's or an arc's end on that curve is removed as implied,** listed in `removed` (docs/design/m5.0-app.md, open item 13b): a T drawn at a line's end, which `--merge-touching` meets. The shared point is the end, so the `on` holds by construction, as trim drops one at a shared cut (decision 5). FreeCAD keeps the `PointOnObject` and its solve flags it redundant; the gate refuses a curve's own point held on it. Any other constraint the merge puts on its own curve (an `on` of a centre, a `midpoint`, a `point_line_distance`, a mirrored `symmetric`) would conflict, not repeat, and stays refused.
- <a id="se-an-edge-tangent-between-two-curves"></a>**An edge `tangent` between two curves that then share an end becomes a `tangent_at` there,** keeping its ID, listed in `modified` (docs/design/m5.0-app.md, open item 13), as FreeCAD's coincident command substitutes an endpoint tangency for an edge one (`620188073e`, *Endpoint to endpoint tangency was applied instead*; main's `substituteConstraintCombinationsCoincident`). Its `direction` keeps the tangent's `side` (decision 8): a round on the line's left, or two rounds one inside the other, turn the same way where they touch, an angle of 0 between the curves' own directions; on its right, or outside each other, π. That angle is written as the `direction` the solve reads it from, by which ends the point is. FreeCAD's edge tangency holds no side, so its command locks the angle the unmerged drawing shows at the point (`AutoLockTangencyAndPerpty`). Where the merged points touch, the point is the contact, and the two agree *(the sketch-edit oracle: `merge_leaves_edge_tangent`)*. Merged from apart, the drawing at the point can show the other side, and FreeCAD then flips it: a line from (0, 0) to (10, 0) and an arc about (10, 10) from (15, 1.3397) to (18.6603, 15), tangent `left`, merged with the arc's end kept, FreeCAD locks π, the arc on the line's right *(1.1.3, the port review's probe)*; Silico keeps `left`, as the file says (found by the robustness and port reviews; `a_line_merged_onto_an_arcs_far_end_keeps_the_side_freecad_would_flip`). Curves that would share both ends, which have no one point for it, stay refused, by the gate's `tangent_at` rule.
- <a id="se-the-merged-sketch-is-gated"></a>**The merged sketch is gated,** and refused as the merge's, naming the points and what the gate names: a merge places points by ID, so a curve it leaves with no size (a line's ends, or an arc's end and centre, drawn at one place) and a sketch its `tangent_at`s take past the solver's 10,000 values are the gate's to find (found by `/break-it`; main's merge returned the first as `Ok`), as is a merge that would leave an edge `tangent` beside a `tangent_on` of the same pair, which the gate refuses, naming the pair (#290: the `tangent_on` already makes them tangent where the end lies; `edit_45_93`, where FreeCAD's merge solves in 8 of 10 runs, at a different place nearly every run, so the oracle shows it as FreeCAD varying).
- <a id="se-no-automatic-fix-up"></a>**No automatic fix-up:** the solve after the merge is the edit's, and one worse than the sketch's solve before it refuses the edit as data (M3.3), as FreeCAD's command rolls back a worse solve.
  - <a id="se-so-does-any-refusal-of-the"></a>So does any refusal of the solve's result. Three cases come from points merged from apart, where Silico's placed point doesn't solve and FreeCAD 1.1.3 does one of two things: its coincidences solve, or its solve is worse and the Coincident command rolls the merge back, the sketch just as it was: it fails (-1; the sketch-edit oracle's sweep: `edit_32_184`, 10 of 10 runs), or finds constraints redundant (-2; `edit_44_310`, 39 of 40 runs, once one conflicting as well, so the oracle shows it as FreeCAD varying, the geometry its solve leaves before the rollback different each run) or conflicting (-3; `edit_45_243`, 10 of 10 runs, the same). Where a line collapses, FreeCAD isn't the same run to run: `edit_32_154` solves most runs, to a line 5e-13 mm long, and fails about 4 of 36 (alone in a script, 3 of 20, its other 17 solves at three different places), a FreeCAD fragility (a possible upstream issue) the oracle lists as known and doesn't compare: <a id="se-the-reverse-comes-too-points-merged"></a>The reverse comes too: points merged from apart whose solve Silico takes clean from the kept point's place, where FreeCAD's, from the points apart, finds constraints conflicting (-3) and its Coincident command rolls the merge back, though its own solve of the same merge from the kept point's place is clean (`edit_90_328`; Worker 1's FreeCAD probe, 2026-10-30): a merged point at a double root, such as a tangent contact, lands within PlaneGCS's convergence of it (20–30 nm here), as FreeCAD's does. Where FreeCAD's arc can't hold the end Silico places (an arc's end merged onto a point off its circle), no solve of FreeCAD's from the kept point's place exists to compare, and FreeCAD's from the points apart isn't the same run to run: `edit_78_52` fails (-1) now and then and is clean otherwise, a case the oracle lists as known, compared only where FreeCAD makes the merge too.
    - <a id="se-a-tangent-at-or-tangent-on"></a>a `tangent_at` or `tangent_on` whose side the solve would flip (decision 8), as when a corner moves to a circle's centre (the oracle's sweep, `edit_14_13`);
    - <a id="se-a-line-the-solve-shortens-to"></a>a line the solve shortens to nothing, which M3.3's unbuildable result names with its length (`edit_32_154`). The up-front refusal covers only a curve made to use one point twice; one the constraints collapse is the solve's.
    - <a id="se-a-solve-that-fails-or-conflicts"></a>a solve that fails or conflicts from the kept point's place (`edit_43_229`, `edit_90_370`), refused as `solve_failed` or `over_constrained` (Fable, 2026-10-29: the request's order is the seed, and Silico tries no other; a solve that doesn't succeed refuses the edit); a failed solve's refusal suggests what the request can change: name the point the constraints hold first, or move the points together, then merge.
  - <a id="se-merge-built"></a>**Built** (the geometry edits' commands, docs/design/m5.0-app.md, section 7's common rules; refines SD7: pre-existing conflicts): each command solves the sketch after the edit, and, where that isn't clean, before it, on the session's sketch solvers, and refuses an edit whose solve is worse as FreeCAD main's `shouldRejectCoincidentSolve` ranks it (`getCoincidentSolveStatusSeverity`, with `getCoincidentSolveStatus` reading a negative DoF count first): solved 0, solved with redundant constraints 1, in conflict 2, over-constrained 3 (in conflict with the diagnosis's DoF below 0, as PlaneGCS counts it), no solution 4, a result the file can't hold 5 (always refused). Not a clean success, and ranking worse or flagging a constraint redundant or in conflict that the solve before didn't, refuses it, naming them; an edit that leaves the conflict the sketch had, at its rank, is made. One rule for split, trim, unjoin, and merge (and extend, and a drag's release, as they're wired). Redundancy is FreeCAD's full redundancy (`getLastHasRedundancies`), not its partial one; the flags are read from the diagnosis, which a solve that failed has too, and matched by constraint ID, where FreeCAD matches them by content (`getConstraintDiagnosticIdentity`), so a constraint an edit retypes under its ID (a length become a distance) is the same constraint. A deliberate divergence: an edit that takes a sketch whose solve can't be built (rank 5 before it) to any other rank is accepted, unless it flags a constraint the solve before didn't, where FreeCAD's `abortIfCoincidentSolveRejected` refuses any edit whose sketch before is `InvalidGeometry`. FreeCAD's `InvalidGeometry` is a constraint list naming geometry that isn't there, which Silico's gate refuses before any edit runs; Silico's rank 5 is a solve reaching geometry the file can't hold, which an edit may mend.

## 7. Extend

**What FreeCAD does** (`extend`, `SketchObjectOperations.cpp:503-549`): lines and arcs only.
- <a id="se-extend-lines"></a>**Lines.** A line's chosen end moves by `increment` along the line, through the solver's drag, so constraints win: a line with a length of 10, extended by 5, slides instead of growing *(1.1.3)*.
- <a id="se-extend-arcs"></a>**Arcs.** An arc's start or end angle moves by `increment` **radians**, written straight into the geometry, then solved.
- <a id="se-extend-unchecked"></a>**Unchecked:** a negative increment may shrink past the other end and flip a line *(1.1.3: −15 on a 10 mm line)*, or invert an arc. One that takes a free line to nothing (−10 on a 10 mm line) fails the drag ("Invalid solution from DogLeg solver"), leaves the sketch as it was, and still returns success *(1.1.3, the sketch-extend oracle: `extend_free_line_to_nothing`)*; so does a drag that would collapse a neighbour onto its far end (`extend_collapses_neighbour`). Where `moveGeometry` reports its drag's failure, `extend` raises "Not able to extend geometry" instead, the same for the same sketch run to run *(1.1.3, the sketch-extend oracle's sweep, seed 32: `extend_32_132`, a frame Silico can't build, and `extend_32_140` and `extend_32_387`, lines flipped)*. An arc also wraps past a whole turn, its range trimmed periodically by OCCT: a 90° arc's end on by 300° gives a 30° arc, and by −120° a 330° one *(1.1.3)*. A turn that leaves it no sweep at all raises `Geom_TrimmedCurve::U1 == U2` *(1.1.3, the sketch-extend oracle: `extend_arc_to_nothing`, by −90°)*.
- <a id="se-other-kinds-and-the-mid-position"></a>**Other kinds and the `mid` position.** 1.1 refused these. Main returns success and does nothing (`d8cf415e4f`, `a502762119`, 2026), a regression by reading.
- <a id="se-the-gui-extends-to-the-cursor"></a>The Gui extends to the cursor and then adds the auto-constraints the cursor suggests at the moved end (`createAutoConstraints`, `DrawSketchHandlerExtend.h`: a coincidence, a point on a curve, a tangency, as the snap finds). The App layer never looks for the next curve. FreeCAD has no App test of extend.

**What Silico does differently.** Moving an end is moving its point. Every curve that shares it follows, as FreeCAD's drag pulls a coincident neighbour. The order matters: dragging the end to its target and letting the solve follow gives FreeCAD's result, but writing the end there and then solving doesn't *(1.1.3: a 10 mm horizontal line with its length, extended by 5: (5,0)–(15,0) by the drag, (3.5706,0)–(13.5706,0) by write-then-solve)*. Recommended (decision 11):
- <a id="se-a-line-s-end-goes-through"></a>A line's end goes through the sketch worker's drag session (M3.7's begin, move, end), as FreeCAD's `moveGeometry` does; an arc's range is written and the sketch solved, as FreeCAD does. Where the arc's end is shared, writing it moves the shared point, so the neighbour's end moves with it before the solve; FreeCAD's `setRange` moves only the arc's end, and the solve then pulls the neighbour to it through their coincidence. After the solve the two agree where FreeCAD's result is the arc-first one (below); FreeCAD's own result there also varies from run to run *(1.1.3, the sketch-extend oracle: `extend_arc_start_with_tangent`)*, and in one measured case its solve fails (-1) in some runs and not others *(`extend_32_115`, seed 43's `extend_43_274`, and seed 42's `extend_42_165`, 5 of 10 runs each; `extend_arc_start_with_tangent`, `extend_arc_order_probe`, and the seed-32 sweep's 22 other shared-end cases solved in 10 of 10)*. FreeCAD's arc result depends on the order its geometry was added: with the arc listed first, its end lands at the turned angle and a joined free line follows; listed after the line, the solve undoes most of the turn and moves the centre *(1.1.3: an arc of radius 10 from 0° to 90°, a line from its end to (−10, 10), the end on by 30°: (−5, 8.660254) arc first, (−0.0396, 9.9909) line first)*. Silico writes the point, so it takes the arc-first result whatever the order. (FreeCAD's arc branch also edits the geometry in place without marking the sketch for a solve, so a joined line stays where it was until an explicit `solve()` *(1.1.3)*: an upstream bug Silico doesn't carry.)
- <a id="se-refuse-anything-but-a-line-or"></a>Refuse anything but a line or an arc, at anything but its two ends, as 1.1 did.
- <a id="se-refuse-a-result-of-size-1e"></a>Refuse a result of size 1e-7 mm or less, or a flip: the request's own (an increment that would take the line or arc there, before any drag) and the drag's.
- Express an arc's increment as an angle (`Angle`, exact) and a line's as a `Length`, or either's target as a point on its carrier (`To`, below).

<a id="se-extend-built"></a>**Built** (`silico_core::extend`, run by the `sketch_extend` command, docs/design/m5.0-app.md, section 7 and open item 12c: from the revision's sketch as solved and written back, as a drag begins, the line's move under the command's stop, `cancel` naming it stopping it, and the edit's solve then judging what it wrote). Its result is a function of the sketch as stored and the increment (or the point) alone: the drag begins from the stored sketch, moves once to FreeCAD's target (the other end, along the line, plus the new length), and ends, all in one request to the sketch worker (`MoveOnce`). An extend isn't a drag, so it's held to a solve's limits and time, as FreeCAD's `extend` has no cap of its own, not to `MAX_DRAG_UNKNOWNS`, which bounds each of a drag's many moves for the cursor's sake (a chain of 282 unknowns extends; its real-worker test). The frame's values seed the rest of the edited sketch, and the moving end is written at the target exactly, after the frame's checks (PlaneGCS's SQP stops on its step and never checks the pin's residual, so the drag leaves the end about 1.6e-7 mm short, which would leave an end extended to a neighbour's point unjoinable). The edit's solve then settles them, as a drag's end does, moving the end back only where constraints pull it: a free end lands on its target bit for bit (Fable, 2026-10-29: an edit writes exactly what its request names). Every point the drag moved is `modified`. The 1.1.3 probe above is its real-worker test: (5,0)–(15,0). Beyond the recommendations, it also refuses:
- <a id="se-an-increment-of-0-since-it"></a>an increment of 0, since it changes nothing;
- <a id="se-a-frame-that-isn-t-a"></a>a frame that isn't a success, as an invalid result, where FreeCAD leaves the sketch as it was and returns success (above);
- <a id="se-an-increment-whose-target-is-1e"></a>an increment whose target is 1e-7 mm or less from the other end, or past it, before any drag, whatever the line's constraints would make of it. FreeCAD drags toward that target and keeps what its constraints leave, which can be a valid line short of it *(the extend oracle's sweep, seed 32, nine of 500: `extend_32_129` and others)*; Silico refuses what the request asks for, a line shortened to nothing or flipped, rather than taking a result the request didn't name;
- <a id="se-a-drag-that-leaves-the-line"></a>a drag that leaves the line 1e-7 mm or less, or flipped;
- <a id="se-an-arc-swept-a-whole-turn"></a>an arc swept a whole turn or more; and, once the edit's solve runs, a solve that fails from the written end (`extend_43_212`), refused as `solve_failed`: turn it less, or unjoin the end first.

<a id="se-each-result-is-checked-by-the"></a>Each result is checked by the gate before it's returned: a neighbour the move collapses, or an arc's radius that rounding far from the origin takes to the floor, is refused as the edit's, naming what the gate names. `modified` lists the points moved, then a circle whose radius the drag changed, then a reference dimension it re-measured. A line's end its constraints hold where it is, and an arc's end a turn too small to move, are refused as changing nothing, where FreeCAD reports success.

**Extend to the next curve** (`next_crossing` and `By::To`; docs/design/m5.0-app.md, open item 12c). SolidWorks' Extend Entities extends a line or an arc to the nearest curve it meets. FreeCAD has nothing like it: its Extend tool takes the cursor through its snap manager and sends the increment printed to six places (`DrawSketchHandlerExtend.h:293`), and its App layer never looks for the next curve (above). So this follows SolidWorks.
- `next_crossing` gives the nearest crossing past the end: along a line's line, or around an arc's circle short of its other end. It finds it from the stored coordinates in closed form, with trim's carriers and `crossings`, so it counts what trim cuts at (decision 6). That's every other curve, construction too, where the carriers cross on it, or touch within 1e-7 mm, or where one of its ends is within 1e-7 mm of the carrier. In that last case the end's stored point is the answer, so the extended end lands on it exactly.
- Past the end means farther than 1e-7 mm from it, and from the curve's other end. A crossing past the sketch's reach isn't offered.
- A curve the extension would run along to the point isn't met there: one within 1e-7 mm of the halfway place, on it. That's a collinear neighbour, whose far end extending to would collapse it or overlap it, or a round the curve runs into nearly tangent, whose contact lies a few microns on (found by `/break-it`).
- A curve built on the moving end's point isn't met: one that starts or ends there, or a round about it. It moves with the end, so its crossing does too; offered, the edit would drag it onto itself or cut it short (found by the port review).
- The nearest wins: a line's by distance, an arc's by angle. At the same distance, the least ID wins.
- `By::To` puts the end at a point within 1e-7 mm of the carrier, exactly. For a line, that's the line's one move sent there, and its constraints win, as for a length. For an arc, the end is put there.
- `By::To` measures the carrier as `next_crossing` does (trim's), so it takes every point `next_crossing` gives. That includes an arc whose end a solve left off its start's radius, and a line's start, whose foot is found from the same end.
- The edit adds nothing to hold the end where it lands, as FreeCAD's App `extend` adds nothing: an `on` to the curve met, or a shared point with an end it lands on, is the tool's or the caller's, as FreeCAD's Gui adds its auto-constraints after the edit (docs/design/m5.0-app.md, automatic relations). Until one is added, an end landing on another curve's end is two points `ends_not_joined` reports.
- An increment couldn't do this. `Length` is whole nanometres and `Angle` whole nanodegrees, so an end moved by the nearest increment misses the other curve by up to half of one, more than the 1e-7 mm the gate and trim count as touching.
- `By::To` is refused for a point past the reach (before anything else is measured), a point farther from the carrier, the end's own point (nothing changes, a zero of either sign alike), and a point that leaves the curve 1e-7 mm or less, or a line flipped. Both refuse an arc whose ends are at one angle from its centre, which has no circle to go around. Its tests are hand-computed crossings that land on exact binary values, plus a real-worker line taken to a circle at an irrational crossing, which it then touches within 1e-7 mm.

- `SketcherTests/TestCoincidentCommandGui.py`'s six tests become the merge command's tests: already one point, collapsing a curve (directly and through a chain), and a merge whose solve conflicts, refused.
- `TestSketchValidateCoincidents.testSingleMissingCoincidentCase` and `TestSketcherSolver.testThreeLinesWithCoincidences_1`/`_2` are already ported for `ends_not_joined` (#189). They become the merge's cases too: merging the found cluster leaves no warning.
- `testDegenratedGeometryCase` waits for a degenerate-curve warning (curves of 1e-7 mm or less that are distinct points), reported, never removed.

**Not ported, by kind:**
- `testConstraintAfterDeletingGeo` and `testIssue3245` test renumbering. Silico's IDs avoid it, though `testIssue3245_2`'s rule returns with expressions: a deleted constraint takes its expression and no other.
- The ellipse and B-spline variants.
- `testValidateConstraintsCase`, which the gate covers.

### Silico's own

FreeCAD has no test for how constraints move on split, for extend, or for most of the transfer rules. Silico's tests, with values worked by hand:

- **Split:**
  - a line with `horizontal` and `parallel` splits with no redundancy (1.1.3 reports one);
  - an `angle` on the split line survives (1.1.3 segfaults);
  - a point `on` each half goes to its own piece;
  - a `point_line_distance` from beside the second half goes to that piece;
  - a `length` becomes the `distance` between the outer points;
  - an arc's `radius` lands on one piece;
  - `tangent_at` at both of an arc's ends survives;
  - a `perpendicular` to a line neither piece touches survives, on the start-side piece (main drops it);
  - a `tangent_on` whose `at` lies on the second half moves to that piece; one whose `at` is the split point becomes `tangent_at`;
  - a point `on` the line's extension beyond `to` goes to the end piece;
  - refused, naming the curve: a split at `from`, at `to`, beyond an end, within 1e-7 mm of one, off the curve, or of a point;
  - after a split of a fully constrained sketch, every untouched point keeps its exact coordinates.
- **Add:**
  - a batch of each kind, `added` by kind and in the request's order;
  - a line from a point the sketch already has (shared points);
  - a batch with one bad member refused whole, nothing added, every problem at its ID path;
  - an ID the sketch has, at the request's field; one given twice in the batch, at the later member's place;
  - a constraint naming a member of the same batch; one naming no member, with candidates;
  - `construction` kept, on points too;
  - `side` and `direction` as given, against the drawing;
  - an empty batch changes nothing;
  - a conflicting constraint is added, and the sketch's solve then finds the conflict (the real worker).
- **Delete:**
  - at a three-way joint every other curve still shares the point;
  - with a `tangent_at` to the deleted curve listed first or last, the result is the same (1.1.3 differs);
  - deleting one of two lines with an `angle` removes it;
  - deleting a `symmetric`'s `about` line removes it;
  - a point no curve uses after the edit is gone;
  - a batch equals one by one;
  - `origin` and the axes are refused.
- **Unjoin:**
  - the others stay joined;
  - the detached line keeps its `length`;
  - unjoining an unshared point is refused.
- **Merge:**
  - ends with a `horizontal_points`, an `on` to another curve, or a lock still warn and merge (1.1.3 reports 0 missing);
  - a merge that collapses a line through a chain is refused;
  - a merge that leaves an edge `tangent` at a shared end makes it a `tangent_at` keeping the tangent's `side`, at every end and either way round, merged touching or from apart, which the real worker then solves keeping the side (the other `direction` gives the other side, or moves it).
- **Trim:**
  - a tangent line cuts a circle, and one off by more than decision 6's contact tolerance doesn't (both sides of it, and of the end-on-curve tolerance);
  - collinear overlapping lines cut at the overlap's ends;
  - a sketch point doesn't cut;
  - a cutter end held `on` the trimmed curve becomes the piece's shared end, and its `on` is removed;
  - an `on` on the removed part is dropped;
  - undoing a trim restores the document byte for byte.
- **Extend:**
  - a line with a `length` slides rather than grows, to (5,0)–(15,0), as 1.1.3 does;
  - a shrink past the other end is refused;
  - a circle is refused.

## Open decisions

Open: none is decided. Each has a recommendation, for M5.0's design to propose and the maintainer to approve, change, or refuse, as M4.1's decisions were. They follow FreeCAD where it gives one answer, choose between 1.1.3 and main where they differ, and follow Silico's exactness rule where FreeCAD's tolerances would snap.

1. <a id="se-a-split-line-s-two-pieces"></a>**A split line's two pieces.** 1.1.3 leaves them free to kink and copies `horizontal`, `vertical`, `parallel` and `angle` to both, which makes a constraint redundant when two are present. Main, since `6d06b61c7e`, holds them collinear with an endpoint tangency and puts those on the first piece. **Recommended: main's.** Join the pieces with `tangent_at` (`same`) at the split point, and put direction constraints on the start-side piece only. The shape and its freedoms are what they were, plus the split point's slide along the line, and nothing is redundant. Trim's pieces stay independent, as FreeCAD's do.
2. <a id="se-a-constraint-that-no-piece-can"></a>**A constraint that no piece can take.** With decision 1, a split's pieces lie on the original's line or share its circle, and D4's `on`, `point_line_distance`, edge `tangent` and `symmetric` about a line act on the whole line or circle, so every such constraint means on a piece what it meant before. **Recommended:** in a split, each goes to the piece whose span holds its point, else the nearer end's, else the start-side piece; nothing is refused or dropped. In a trim, where the pieces really are independent, a constraint no piece can take (an arc's edge `tangent` that no piece touches, `symmetric` about the trimmed line) is refused, naming it, so the person or agent removes it first. FreeCAD drops these silently.
3. <a id="se-splitting-a-circle"></a>**Splitting a circle.** FreeCAD gives one arc whose ends are one place, which the gate refuses. **Recommended: a circle splits at two points into two arcs**, as SolidWorks's Split Entities needs two points on a closed curve. A circle split at one point is refused, naming it.
4. <a id="se-decision-split-position"></a>**The split position.** FreeCAD projects any point onto the curve. **Recommended:** the request gives a position, and the new point goes at its projection onto the curve. A position farther than 1e-7 mm from the curve is refused, naming the distance: the gate's floor, not a snap. So is a position at, beyond, or within 1e-7 mm of an end.
5. <a id="se-trim-s-the-cut-is-the"></a>**Trim's "the cut is the cutter's end".** FreeCAD merges at 5e-5 mm. **Recommended: share the cutter's point only when the cutter's end is held on the trimmed curve by a constraint** (an `on`, a `tangent_on` with the trimmed curve as `b`, which then becomes `tangent_at` by decision 8, or the end is already a point of the trimmed curve). Then it's exact, and the `on` is removed as implied. Otherwise the piece gets a new point `on` the cutter. A cutter end that's merely drawn there leaves two points at one place, which `ends_not_joined` names when they're within 1e-7 mm and `--merge-touching` merges. Likewise "two cuts at one place" means within 1e-7 mm, not 5e-5. This departs from five of FreeCAD's trim tests, whose cutters are only drawn (§9).
6. <a id="se-where-trim-finds-intersections"></a>**Where trim finds intersections.** **Recommended: in the core, in closed form,** with the libm shim's math, the same on every platform. Lines and circular arcs are the only curves, so no worker is needed and nothing depends on OCCT's intersector. FreeCAD's three sources of cuts (crossings, tangent contacts and overlaps, other curves' ends on the curve) each become a case of that computation, with tests. Each needs a stated tolerance, since exact comparison finds a solved tangency only when rounding falls the right way. FreeCAD's intersector cuts a circle by a line at y = 5 + δ for δ = 1e-12 but not 1e-10 *(1.1.3, radius 5)*, and takes another curve's end within 1e-7 mm (`e10068a648`). Recommended: a tangent contact or an overlap counts when the gap is at most 1e-7 mm (`LENGTH_TOLERANCE`, the gate's floor), and so does an end on the curve, each tested on both sides. `x_axis` and `y_axis` don't cut, as by default in FreeCAD (main's opt-in, `196da068a0`, isn't in 1.1.3).
7. **Deleting points.** **Recommended:** deleting a curve deletes each of its points that no curve uses afterwards, with their constraints. Deleting a point is allowed only when no curve uses it; otherwise it's refused, naming the curves.
8. **A tangency at a new or merged shared end.** Trim turns the cutter's edge tangency into an end tangency, and a merge can make an edge `tangent` illegal (the gate's `tangent_at` rule). Both forms carry a `direction` that D4 stores and never derives. **Recommended:** the edit writes the `direction`, an act of the edit, done once, and stored. Where an edge `tangent` with a `side` becomes it (a merge, §6), the `side` decides it: what the file says, whatever the merge moves. Where no side says it (trim's cutter, whose new end lies at the contact on the sketch as last solved), the edit writes what the sketch as last solved shows, the way FreeCAD's tool records it. At a contact the two agree. Merged from apart, FreeCAD's lock reads the unmerged drawing and can flip the side (§6); Silico keeps it. The edit's solve must then agree, or the edit is refused as M3.3 refuses a side that flips.
9. **Unjoining.** **Recommended** (§5): the curves that stay keep the shared point and every constraint on it. The detached curve's end gets a new point at the same coordinates with none. A `tangent_at` between the detached curve and another at that point is removed. Unjoining a point no other curve shares is refused.
10. **Merging.** **Recommended** (§6): the request names the points (or `--merge-touching` names each `ends_not_joined` cluster). The first point named survives at its own coordinates (`--merge-touching`: the cluster's least ID, its points being within 1e-7 mm); the others' curves and constraints are re-pointed to it. Refused, naming them: points already one, a curve using one point twice, a constraint naming one point twice. An edge `tangent` left at a now-shared end becomes a `tangent_at` there, keeping its `side` (decision 8; FreeCAD `620188073e`). The edit's solve decides the rest, and a merge whose solve is worse than the one before it is refused: a constraint it finds redundant, conflicting, or malformed that the solve before didn't, naming it, or a solve that fails. That's main's Coincident command, which rolls such a merge back (`shouldRejectCoincidentSolve`, `Gui/CommandConstraints.cpp`, from `cb2780e2fa`, 2026-09, after 1.2 branched). 1.1.3's command has no rollback: merging two locked ends, it makes the merge, and its solve lists the second lock redundant *(1.1.3, the sketch-edit oracle: `merge_two_locked_ends`)*. Silico follows main. It's the command's check, around the edit: the merge itself doesn't solve.
11. **Extend.** **Recommended:** a line's end is dragged by a `Length` along the line through the sketch worker's drag session (M3.7), so constraints win as in FreeCAD; an arc's start or end moves by an `Angle`, written, then the sketch solves. Refused: other kinds, the `center`, and a result of 1e-7 mm or less or flipped (FreeCAD doesn't check). Extending to the next curve, as SolidWorks's Extend Entities does, is the core's: `next_crossing` finds the point and `By::To` puts the end there, since an increment can't reach it within 1e-7 mm (§7).

## The oracle

`silico-oracle` compares the edits with FreeCAD 1.1.3 (`crates/silico-oracle/src/sketch_edit.rs`, and `sketch_edit` in `oracle.py`). It cites this note by the anchors on the lines it relies on (each an `a` tag with an `id` such as `se-merge-built`, cited as `sketch-edit.md#se-merge-built`), never by line number, so an edit of the note moves no citation; a report gives each anchor's line as it stands, and a test fails on any anchor cited that the note lacks or defines twice. A case is a sketch and one edit: `tests/oracle/sketch-edits/` holds them (`sketches.silico`, and `cases.json` naming a sketch and an edit for each: 131 cases, extend 38, trim 36, split 26, merge 13, remove 12, unjoin 6), and `pixi run oracle` runs them with the rest; `pixi run oracle-sketch-edit-sweep -- --seed S` makes 500 random ones from seed `S` (`generate::sketch_edit_cases`; `--only INDEX` takes one of them, and `--dump DIR` writes each case's sketch, edit, and Silico's edited sketch as JSON), and `oracle-sweep.yml` runs that when started with `sketch_edits: true` (and a `seed`, to repeat one).

**How a case maps across.** The sketch goes to FreeCAD's model as the sketch oracle builds it (each shared point a group of ends joined by coincidences), each constraint named after its ID. The edit is FreeCAD's own call:

| Silico | FreeCAD |
|---|---|
| `remove` | `delConstraints` of the constraints named, then `delGeometries` |
| `unjoin` | the vertex Delete, `delConstraintOnPoint(curve, position)` |
| `merge` | a `Coincident` from the first point to each other one, as the Coincident command adds it: an end-to-end `Tangent` instead where the two curves have an edge tangency ([se-tangency-substitution](#se-tangency-substitution), `180d722a53`) |
| `split` | `split(curve, position)`; a circle, at its two positions in turn |
| `trim` | `trim(curve, pick)` |
| `extend` (`silico_core::extend`) | `extend(curve, increment, position)`: a line's end through `moveGeometry`'s drag, an arc's range by `setRange`, each then solved; an arc's increment in radians, Silico's in degrees (§7) |

Both results are solved, and FreeCAD's geometry is matched to Silico's by its geometry IDs, which its edits keep (the start-side piece keeps the curve's, as Silico's keeps its ID), new pieces in the order each made them.

**What's compared:** each curve and lone point, its kind and `construction`; which ends are one point (a Silico shared point is FreeCAD's ends joined by a `Coincident` or an end-to-end tangency, D2); every point after the edit and after the solve, to 1e-8 mm; the constraints, by kind and by what they name in Silico's terms (a curve, a point, or a curve's end), so a constraint kept, dropped, or moved to another piece shows, and each dimension's value; the degrees of freedom; the conflicting, redundant, and partially redundant constraints; and whether each side refuses. A refusal on both sides agrees only where Silico's is one the note gives, checked against the refusal itself (its code, the elements it names, and the request's field) and against the sketch, and where the note doesn't give FreeCAD another outcome for it. FreeCAD crashing or hanging is its own outcome, never a refusal: it agrees only where the note says 1.1.3 crashes, splitting a point ([se-split-index-refusals](#se-split-index-refusals)), FreeCAD crashed by a segmentation fault (killed by SIGSEGV on macOS; on Linux, where 1.1.3's handler catches it, exiting with status 1 after its line "Program received signal SIGSEGV, Segmentation fault.", `src/App/Application.cpp:1815-1825`, `src/Base/SystemHandler.cpp:123-131` on main; not otherwise, not status 1 without that line, and not by hanging), and Silico refuses it ([se-split-refusals-as-data](#se-split-refusals-as-data)); anywhere else it's a difference. Every case runs FreeCAD: where FreeCAD has no edit for one, it's given the gesture the note says it has instead (deleting a point curves use, its Delete on that vertex, [se-freecad-s-gui-delete-on-a](#se-freecad-s-gui-delete-on-a) to [se-on-a-geompoint-it-deletes-that](#se-on-a-geompoint-it-deletes-that); a point merged with itself, the coincidence its Coincident command refuses as already coincident, [se-points-already-coincident-even-through-other](#se-points-already-coincident-even-through-other)), and FreeCAD run on a case and giving no outcome is a difference. A result of Silico's edit the gate refuses is always a difference, since every edit's result has to pass it ([se-every-edit-s-result-has-to](#se-every-edit-s-result-has-to), [se-split-refusals-as-data](#se-split-refusals-as-data)). Only FreeCAD's own edit call raising is its refusal: the harness's code around it failing is reported as the harness's.

**Modulo the note.** Where this note says Silico deliberately differs, FreeCAD's result is brought to the note's form after its edit, and each report lists the lines it was compared modulo:
