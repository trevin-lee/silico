# M2.1 design: the document's types and canonical JSON

**Status: accepted.** The maintainer took every recommendation below (2026-10-14), and chose JSON with Silico's own strict reader over a notation of Silico's own: a `.silico` file is JSON inside, as a `.ipynb` or `.gltf` is. M2.1 builds it (`silico-core`'s `document` module).

M2.1 builds the Rust types for a `.silico` document, a parser that reads them from strict JSON exactly, a writer that produces canonical form, and a JSON Schema for agents. It doesn't validate references between features (M2.2) or recompute anything (M2.3 on).

## Already decided (ARCHITECTURE.md)

M2.1 builds these as they stand: strict JSON; `"silico": 1`; the `units` header, accepting only `{"length": "mm", "resolution": "1nm"}`; the timeline as the order of `features`; random 8-character IDs; `v` on every feature; `note` as a data field; unknown keys rejected; lengths and angles as `i64` nanometres and nanodegrees, parsed from the decimal text, never through a float; NaN, infinity, `-0`, too many decimals, and out-of-range values rejected; canonical form with keys in schema order, LF, and a trailing newline.

## Decisions for the maintainer

### D1. Which features a document can hold in M2

The kernel can make primitives, move a shape, run booleans, fillet and chamfer edges, and extrude or revolve a polygon. A fillet or chamfer refers to edges by name, and the syntax of names is the open question the naming study (`docs/ports/naming.md`) settles. Extruding a polygon is a stopgap until sketches (M3).

- **Recommended:** primitives (`box`, `cylinder`, `sphere`, `cone`, `torus`) and booleans (`fuse`, `cut`, `common`) in M2.1. Fillet and chamfer join when the naming study has fixed the syntax of an edge reference (M2.7–M2.8). Extrude and revolve wait for sketches, as `pad` and `revolve` (M3.6), so the format never carries the polygon stopgap.
- Alternative: add fillet and chamfer now with references as edge numbers (`"edges": [3, 5]`), replaced by names later. That's quicker to test, but it puts in the file exactly the unstable references naming exists to remove.

### D2. What a document's result is

Booleans take shapes made by earlier features. Something has to say which shapes the model ends up with.

- **Recommended:** every feature makes one solid. A feature that takes solids as inputs (a boolean's `base` and `tool`) consumes them, as SolidWorks' Combine consumes its bodies. The document's bodies are the solids no later feature consumes, in timeline order. A solid used as an input twice is an error (M2.2), since it's been consumed.
- Alternative: FreeCAD's way, where every feature's result stays available and booleans hide their inputs only in the view. That makes "what does this model contain" depend on view state, which a text format can't diff.

### D3. Where primitives sit

The kernel makes each primitive at the origin and can move it (no rotation yet).

- **Recommended:** a required `position` on each primitive, `[x, y, z]` in millimetres: the box's lowest corner, the centre of the cylinder's and cone's base, and the centre of the sphere and torus, as the kernel makes them. A rotation becomes a further field when the kernel can rotate, in a later format version. Primitives are FreeCAD's (SolidWorks has none), and FreeCAD gives each a placement.
- Alternative: primitives always at the origin, and a separate `move` feature, as SolidWorks moves bodies. Every placed primitive becomes two features, and the diff of a move lands away from the thing moved.

### D4. How numbers may be written

- **Recommended:** a length or angle is written as a plain decimal: an optional `-`, digits, and an optional fraction (`10`, `-2.5`, `0.000001`). No exponent (`1e-3` is refused, suggesting `0.001`), since one value has one spelling. Trailing zeros are accepted (`10.50` is exactly 10.5 mm) and `silico fmt` drops them. A length allows 6 decimals (nanometres) and an angle 9 (nanodegrees). A non-zero digit past that is refused; zeros past it are accepted, since they add no precision.
- Alternative: refuse anything but canonical spelling (no trailing zeros). Hand edits would then fail for writing `10.0`.

### D5. Format version before the first release

- **Recommended:** `"silico": 1` stays 1 until Silico's first public release, and the schema may change under it, with every change to the schema snapshot and the golden documents (both protected) agreed with the maintainer. After the release, any change a reader of the previous version couldn't read bumps the version, and a reader refuses a version newer than its own, saying which Silico reads it.
- Alternative: bump the version on every schema change from now on. That costs migrations for documents nobody has yet.

### D6. Absent optional fields

- **Recommended:** omitted, never `null`. The only optional fields in M2.1 are `note` (and, from M2.6, `fingerprint`). Every other field is required and always written: no defaults, so a document says everything it means.

### D7. Canonical layout

ARCHITECTURE.md says "one leaf entity per line". Precisely:

- **Recommended:** an object or array is written on one line when it holds no object (`{"length": "mm", "resolution": "1nm"}`, `[0, 0, 0]`); otherwise it's written one member per line, indented two spaces. Members on one line are separated by `, `, keys by `: `. So a primitive or boolean is one line, and a one-parameter edit changes one line of the file. A feature that holds an object (a fingerprint, from M2.6) is written one member per line, the fingerprint on its own line. Strings are UTF-8 as written, escaping only `"`, `\`, control characters (C0, DEL, and C1), and the line and paragraph separators U+2028 and U+2029, so no string breaks a line for a tool that reads the file by lines.

### D8. Names in the file

- **Recommended:** field names in lower case, as FreeCAD's properties mean them: `box` has `length` (x), `width` (y), and `height` (z), as `Part::Box` does; `cylinder` has `radius` and `height`; `sphere` `radius`; `cone` `radius1` (base), `radius2` (top), and `height`; `torus` `radius1` (ring) and `radius2` (tube), as `Part::Torus` does. Booleans are three types, `fuse`, `cut`, and `common`, each with `base` and `tool` (feature IDs), as FreeCAD's `Part::Fuse`, `Part::Cut`, and `Part::Common`. Every feature also has `id`, `type`, `v`, and `name` (a non-empty display name), in that order, first.

### An example in canonical form

```json
{
  "silico": 1,
  "units": {"length": "mm", "resolution": "1nm"},
  "features": [
    {"id": "k7f2qx3m", "type": "box", "v": 1, "name": "Block", "position": [0, 0, 0], "length": 40, "width": 20, "height": 10},
    {"id": "a91cw0de", "type": "cylinder", "v": 1, "name": "Pin", "position": [20, 10, -1], "radius": 2.5, "height": 12},
    {"id": "m3tq8v0z", "type": "cut", "v": 1, "name": "Hole", "base": "k7f2qx3m", "tool": "a91cw0de", "note": "Clearance for an M5 bolt"}
  ]
}
```

## How M2.1 is built

- **Where:** a `document` module in `silico-core`, which ARCHITECTURE.md gives the document model and serialization.
- **`Length` and `Angle`:** newtypes over `i64` (nanometres, nanodegrees), with no float in parsing or equality. `Length::mm()` gives the `f64` the kernel takes, `nm as f64 / 1e6`: one correctly rounded division, the same on every platform, and exact in its integer part up to 2⁵³ nm (9,000 km), far past the kernel's 1 km limit. Range checks against the kernel's limits are the validation gate's (M2.2); the parser refuses only what `i64` can't hold.
- **The reader is Silico's own, not serde_json's.** Serde can't give a number's text to a field inside an enum tagged by `"type"` (it buffers the value, parsing the number into a float first), so a strict reader of its own (a few hundred lines) parses the bytes into a tree that keeps each number's text, each key's order, and each value's line and column. It refuses duplicate keys, trailing commas, comments, a byte-order mark, invalid UTF-8, and nesting deeper than a fixed limit (so hostile input can't exhaust the stack). The typed document is decoded from the tree, refusing unknown keys and naming the field.
- **The writer** writes the typed document in canonical form (D7) directly; nothing is kept from the bytes read.
- **Errors** are `invalid_input` (no new error code, so the error contract doesn't change), with `feature` (the feature's ID, or its position in `features` when the ID itself is bad), `parameter` (the field, dotted: `position.2`), and the line and column in the message. Parsing stops at the first error; the gate (M2.2) reports every invalid reference at once.
- **IDs** are 8 characters of Crockford's base32 in lower case (`0`–`9` and `a`–`z` without `i`, `l`, `o`, `u`), matching the examples in ARCHITECTURE.md. The parser checks the form; uniqueness is the gate's. New IDs come from the command API (later) from the OS's randomness, through a generator tests can seed. An ID is a value the document stores, never recomputed, so its randomness doesn't touch the determinism invariant.
- **Schema:** the types derive `schemars::JsonSchema`, `Length` and `Angle` as numbers with `multipleOf` their resolution, and the generated schema is snapshotted as `crates/silico-core/tests/contract/document-schema.json` (protected, as agents rely on it). The parser is the authority where the schema can't say enough (an exponent, a duplicate key).

## Tests

From the roadmap: a byte-stable round trip; `0.1` reads as exactly 100,000 nm; too many decimals, out-of-range values, `NaN`, `Infinity`, and `-0` refused with structured errors; units other than `mm`/`1nm` refused; unknown keys refused; a fuzzed parser never panics; a stable schema snapshot. Also:

- canonical bytes read and written back are identical, and any valid document written, read, and written again is identical to the first writing (property tests over generated documents);
- `silico fmt`'s core (read, then write) is idempotent;
- every refusal names its feature and field, and gives line and column;
- duplicate keys, an exponent, a byte-order mark, invalid UTF-8, and deep nesting are refused, not panicked on;
- `Length::mm()` of a value read from text equals the analytic value (`0.1` gives the `f64` nearest 0.1);
- the first golden documents (`tests/golden/`, protected: added with the maintainer).

## Not in M2.1

References between features checked (M2.2), parameters and expressions (not yet on the roadmap: the parameter UX is an open question), fingerprints (M2.6), sketches (M3.2), fillet and chamfer (D1), rotation of primitives (D3), and the CLI (M2.9).
