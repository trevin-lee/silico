# M5.0 design: the app

**Status: draft, awaiting Trevin.** It is written on the recommended answers to the open decisions of the draft M5 plan (docs/roadmap/m5-app.md, #196). Each answer taken is marked *pending Trevin, decision N*, where N is #196's number. The sketch edits' rules are the recommendations of docs/ports/sketch-edit.md (#208), marked *pending Trevin, sketch-edit N*, by that note's number. What #196 and the port note leave open, and what this design finds the app forces, is listed in section 12, each item open, none taken here. Where a list item there carries a recommendation, it's only offered.

Like M4.1, this design comes before anything else in M5 is built. It gives:

- the app's state;
- how the app polls its commands without waiting;
- each new command's request, result, and errors as JSON;
- each amendment to an approved M4.1 decision, written as text and marked as an amendment;
- the layout, as docs/ux/fusion.md gives it;
- each tool's behavior, as docs/ux/solidworks.md gives it.

It describes shapes, and changes none. No schema or contract file changes with it. Each step changes its own snapshots and examples with Trevin's approval, as M4.1 section 8 requires. Suppression and a sketch's face plane are document schema changes, and they go to Trevin with M5.1 and M5.9.

Two topics are being studied separately, so this design only points to them. The viewport (`re_renderer`: its paint callback, outline and picking passes, and per-instance IDs measured on the corpus) is in docs/study/viewport.md. The toolkit (`eframe`, `egui_tiles`, `re_ui`, `egui_kittest`, at the versions `re_ui` 0.38.1 pins, and `re_ui`'s tree under `cargo-deny`) is in docs/study/toolkit.md. Both studies are in progress (Worker 3).

## 2. The app's state

The app is one process, `silico-app`, which holds:

- one `command::Sessions`, whose sessions share its kernel pool, sketch solvers, render worker, and caches, as `silico serve`'s do (M4.1 section 3);
- one tab for each document it has open.

### What a tab holds

| Held | What |
|---|---|
| The session | Its `SessionId`, and the path it opened |
| The model it draws | `Sessions::published(&id)`'s model, read each frame, and its revision (M4.1, decision 33) |
| Its meshes | The newest `meshes` answer for the view, with the model revision and the mesh level it's of, uploaded to the GPU once (M5.6) |
| Its status | The newest `status` answer: its revision, transaction, rebuild, drag, and disk |
| The outline and problems | The newest `outline` and published `check` answers, for the browser, the timeline, and the error marks (M5.4) |
| The selection | A list of element names, each with its `stable`, as an agent could write them (M5.7) |
| The commands under way | Each command's `Running` handle, with what it's for (section 3) |
| The dialog open | The feature dialog's inputs, and how many edits it has made (M5.8) |
| The drag | The drag open, if one is, and the newest frame drawn (M5.3) |
| The camera | The viewport's camera, which is the app's own and never a command's, as decision 29 has it |

The model, the meshes, the outline, and the problems are each of a revision, and the app draws each one as of its own revision. It never waits for them to agree. A frame can draw the published model of revision 8 under a timeline of revision 9's outline. The rebuild indicator shows that a rebuild is running (`status.rebuild`). This is what decision 33 allows: the app reads `published` and never stalls.

### The unsaved state (pending Trevin, decision 1)

The app keeps its unsaved changes as a transaction, begun at a document's first edit, not when it opens.

- **No edits held** (no transaction open): the session reloads what an agent commits, as decision 2 does today, at the next command that reads the file (section 4).
- **Edits held** (a transaction open): the document is unsaved, and its tab is marked with an asterisk, as SolidWorks marks a changed document (docs/ux/solidworks.md, §6). Its file isn't reloaded (M4.1 section 4). `status.disk` says whether the file changed on disk (section 6, `status`), and the app offers what decision 3 says (section 4).
- **Save** is `commit`. **Revert** is `rollback`.
- **Close** asks, if the tab holds edits, then rolls back and closes. Decision 22 refuses `close` inside a transaction.
- A dialog's edits are made inside the same transaction. The dialog's Cancel undoes only its own edits, through M5.2's `undo`, never `rollback`, which would drop the unsaved edits made before the dialog (M5.8).

Whether the tab's edits are unsaved is `status.transaction.changed` (section 6). The flag is false once undo returns to the state `begin` saw, so the asterisk goes.

## 3. The frame loop: polling, never waiting

The UI thread calls only what answers at once. M4.1 section 3 names these:

- `Sessions::published(&id)`;
- `status` and `read_logs`;
- the `Running` handle's `try_take`, `progress`, and `cancel` (section 6).

Every other command is started on the UI thread, and its whole body runs off it. The command returns a `Running` handle at once, before its file read, gate, rebuild, save, or export (M4.1 section 3). Each frame:

1. **Status.** For each tab, `status` (it reads only what the session holds) and `Sessions::published(&id)`.
2. **Results.** Every `Running` handle is polled with `try_take`. A finished command updates the tab's state: an `outline` updates the browser and timeline, a `meshes` answer its meshes, an edit's result its undo count, and a refusal shows its errors where SolidWorks shows them (section 8). A handle not finished is left until the next frame. The app never calls `wait` or `wait_timeout` on the UI thread.
3. **Input.** Each user action starts its command and keeps the handle.
4. **Repaint.** While any handle is pending, or a rebuild is running (`status.rebuild.state` is `running`), the app asks the toolkit for the next frame. So a result is taken up within a frame of its landing, without input to wake the loop. How a repaint is asked for is the toolkit's (per docs/study/toolkit.md).

### When the app reads

- **The model to draw** is the published one, read each frame. Its revision is `published(&id)`'s.
- **Meshes** are read when the published revision changes, or when the view's half pixel crosses a level of the ladder (a power of two, M4.6). Each read is a `meshes` read of the published model (section 6). It's a published read, so it's counted against the eight a session may run (M4.1 section 6), and the app keeps at most one in flight a tab. Until it lands, the viewport draws the meshes it has (M5.6). A model's buffers are uploaded once, never once a frame.
- **The outline and the problems** are read with each published revision: `outline`, and `check` with `"model": "published"`. The browser, the timeline, and the error marks are drawn from them (M5.4).
- **Pre-selection and the Measure tool** read the published model (`elements`, `query`, `distance`, `angle`), as decision 33 intended.

### Bursts of edits

The session's queue is unbounded (an M4 low, #196's *What M4 leaves for M5*), so the app never queues edits one by one. A tab has at most one edit in flight. An edit made while one is in flight waits in the tab, and a newer edit of the same field replaces it (typing in a dialog's value box, say). When the edit in flight answers, the waiting one is sent, against the revision the answer gave (decision 12). A drag's moves are coalesced the same way (section 6, `drag_move`).

### Stop, and the rebuild indicator

The timeline's rebuild indicator is `status.rebuild` (M4.1 section 9's table): `done` of `steps` while one is running, and its state otherwise. Its stop button is `cancel`, naming `status.running`, or a published read named in `status.reads` (decision 34). Esc does the same, as Esc interrupts a SolidWorks rebuild (docs/ux/solidworks.md, §5, *Rebuild*). A cancelled render still answers `internal` (M4.6's open item, #196's *What M4 leaves for M5*). M5.4 makes it `cancelled` so the stop button can show it.

### How this is tested (pending Trevin, decision 7)

The tests use a frame counter that keeps climbing while the fake kernel holds a request. Each of these is held in turn:

- a rebuild (M5.4);
- a `meshes` read (M5.6);
- a drag's move in the fake sketch worker (M5.3, M5.11);
- an export (M5.12).

In each case, frames keep coming and the panels keep answering. The app is driven through `egui_kittest`'s accessibility tree (labels, roles, values), per docs/study/toolkit.md. The viewport is checked through its ID buffer against projections by hand, as M4.6's tests are. A screenshot is never compared with a stored image.

## 4. Files: open, save, revert, close, and a file changed on disk

| Action | Command | Notes |
|---|---|---|
| New | `open` with `"create": true` | Needs a path first. A SolidWorks document asks for a name only at its first save (docs/ux/solidworks.md, §6), and a session always has a file (open item 20) |
| Open | `open` | A document the gate refuses still opens, with its problems shown (decision 21) |
| Save (Ctrl+S) | `commit` | Writes only if the transaction's document differs from `begin`'s. Ctrl+S is SolidWorks' (docs/ux/solidworks.md, §6) |
| Revert | `rollback` | Restores the file's text byte for byte (M4.1 section 4) |
| Close (Ctrl+W) | `rollback` if edits are held and the person agrees, then `close` | Closing a changed document asks whether to save it (docs/ux/solidworks.md, §6). Decision 22 refuses `close` inside a transaction |
| Quit | As Close, for each tab | Closing several changed documents lists them, to save all, some, or none (docs/ux/solidworks.md, §6) |
| Accept drift | `format`, naming the features | Allowed inside a transaction (pending Trevin, decision 8; amendment A6) |

### A file changed on disk (pending Trevin, decisions 1 and 3)

Live co-editing follows decision 30's (a) for M5 (pending Trevin, decision 3). A person and an agent share a part through its file, not at once.

- **With no edits held**, the next command that reads the file reloads it (decision 2): `outline`, which the app sends when `status.disk` says `changed`. Its envelope says `"reloaded": true`, at a new revision. A published read reloads nothing (M4.1 section 4). That's why the app sends `outline`, which reads the document, rather than relying on its per-frame reads.
- **With edits held**, `status.disk` says `changed` (or `gone`), and the app offers two choices:
  - **Reload**, dropping its edits: `rollback`, after which the next command reloads the file.
  - **Keep its edits**: its `commit` is then refused as a `conflict` (decision 2) until it reloads. "Save elsewhere", which decision 3's (a) also names, needs a command no step builds (open item 9).

  SolidWorks' *Reload* likewise marks a reload that would lose unsaved changes (docs/ux/solidworks.md, §6). Its help says nothing about a document open for writing that another program changes on disk (§6), so the choice offered is decision 3's, not SolidWorks'.
- **The comparison runs off the UI thread.** `status` answers from the session's last comparison and starts the next if none is running and the last ended at least `DISK_CHECK_INTERVAL` ago (1 s; section 5, A4). It compares bytes, not times, as decision 2 does. Each comparison reads the whole file, up to 16 MiB (open item 10).

## 5. Amendments to M4.1

Each amendment changes the text of M4.1's design, in the section or decision it names, when M5.0 is approved. The step that builds it changes that text in the same PR, as M4.1's *as built* notes did.

**A1. Section 3, *One command at a time, per session*** (pending Trevin, decision 9). The paragraph "Four kinds don't queue behind the session's other commands …" becomes:

> Five kinds don't queue behind the session's other commands.
> - `status`, `read_logs`, and `cancel` answer at once, because they only read what's held or stop what's running.
> - Reads of the published model run beside the queue, on the read lane where they need a worker (section 2), and never wait for a rebuild.
> - A drag's commands (`drag_begin`, `drag_move`, `drag_end`) run on the session's drag, outside the queue:
>   - `drag_begin` reads the current revision's solve of its sketch, waiting for that solve but not for any queued command.
>   - Each `drag_move` is solved on the sketch worker the drag holds. Only the newest is solved: a move that arrives while one is solving waits, and a newer one replaces it.
>   - `drag_end`'s edit waits for the queued command running, if one is, and is applied before the commands queued behind it.
>
> `status` lists the published reads running and the drag open, and `cancel` can stop the reads. Commands of different sessions run at the same time.

The Rust API's calls that answer on the caller's thread stay `Sessions::published(&id)`, `status`, and `read_logs`.

**A2. Section 3, *What a session holds*** (pending Trevin, decisions 1, 2, and 9). The table gains three rows:

> | The undo stack | Inside a transaction: each edit's state before it (its text, checked form, and what edits reached), and the states undone since, for `redo`; bounded (section 6) |
> | The drag | If one is open: its sketch and point, the begin state, the sketch worker it holds, and the newest cursor solved |
> | The disk comparison | The last comparison of the file with the bytes the session last read or wrote (`unchanged`, `changed`, `gone`, `unreadable`), and whether one is running |

And *Per-client generations*, on sketch workers, gains:

> A drag holds a sketch worker of the session's `SketchSolvers` from its begin to its end. While it does, the worker serves only the drag, so a rebuild takes another, and it isn't stopped for a superseded generation (ARCHITECTURE.md, *Sketches solve in the sketch worker*, which these rules make built). A move is still a request like any other, under its timeout and the crash and hang handling. A move that hangs or crashes ends the drag.

**A3. Section 4, *Transactions*** (pending Trevin, decisions 1, 2, and 8).

- The bullet "Inside a transaction, an edit is applied once the gate takes it …" gains:

  > It's pushed on the transaction's undo stack, and the stack's redo states are dropped.

- The bullet "After a commit there is no undo in the API (decision 9) …" becomes:

  > Inside a transaction, `undo` and `redo` step back and forth through its edits, each at a new revision whose state equals an earlier one (section 7, `undo`). A commit or a rollback empties the stack. After a commit there's no undo in the API (decision 9, amended): the committed states are the file's history, which is git's.

- In *A file changed outside the session*, "inside a transaction, only `commit` reads it" becomes:

  > Inside a transaction, only `commit` reads it to decide anything. `status` compares it off the caller's thread, at most once each `DISK_CHECK_INTERVAL`, and reports what it found in `disk`, reloading nothing.

- `format` inside a transaction: see A6.

**A4. Section 6, *Limits*** (pending Trevin, decisions 2, 6, and 9). The table gains:

> | A transaction's undo stack | 100 edits, and 256 MiB of the texts it holds (open item 6) | `undo`, `redo`, every edit inside a transaction | not refused: the oldest is dropped and counted (`status.transaction.dropped`) |
> | A disk comparison | at most one running a session, each at least 1 s (`DISK_CHECK_INTERVAL`) after the last ended | `status` | not refused: `disk` is the last comparison's |
> | Drags open in one session | 1 | `drag_begin` | `invalid_input`, naming `session`: end the drag open first |
> | A drag's moves solving | 1, the newest waiting behind it, the rest dropped | `drag_move` | not refused: a move replaced before it's solved answers `dropped` |
> | A drag's part | 256 unknowns (`MAX_DRAG_UNKNOWNS`, M3.7) | `drag_begin` | `invalid_input`, naming `point` |
> | A display mesh read's size | 1 to 4,096 pixels a side, as `render`'s | `meshes` | `invalid_input`, naming `width` or `height` |

`version`'s `limits` gain `undo_edits`, `undo_bytes`, `disk_check_ms`, and `drag_unknowns`, in that order, after `sketch_seconds`.

**A5. Section 10, *Determinism*** (pending Trevin, decision 9).

- The bullet "Not results, and described so in their schemas" gains:

  > a drag's frames (`drag_begin`'s and `drag_move`'s answers: which moves are solved and which dropped depends on the worker's speed), and `status`'s `disk` and `drag` (the file system's state, and when the drag was last seen).

- New bullet:

  > **A drag's edit.** `drag_end`'s edit is a function of the begin state and the final cursor alone. It solves the sketch dragged to the final cursor from the begin state, never from the last frame that happened to be solved. If that fails, it keeps the begin state and says so. However many moves were dropped, the same begin, cursor, and end give the same document byte for byte.

- New bullet:

  > **Display meshes** (`meshes`) are results: the kernel's tessellation at the level the ladder gives, from the request's view and size. A mesh made by the deterministic kernel is the same on every checked platform. Which published revision a published read answers from depends on when it's asked, as for every published read.

**A6. Decision 31, and section 7's `format`** (pending Trevin, decision 8). "Refused inside a transaction (commit or roll back first); M5 revisits that …" becomes:

> Inside a transaction, it accepts the drift it names into the transaction's state: the transaction's document gains each accepted feature's fingerprint and each sketch's solve, as one edit (undoable, as every edit inside one is), and its commit saves them like any edit's. It writes nothing itself. With `"write": false`, it says whether the canonical text would differ, as outside one. Outside a transaction it's as before.

Decision 31's last sentence ("Refusing `format` inside a transaction is for M5 to revisit …") becomes "*Amended (M5.0):* allowed inside a transaction, accepting drift into the transaction's state (section 7)." The error "a transaction open" goes from `format`'s errors.

**A7. Decision 9** (pending Trevin, decision 2). "No undo stack in the API" becomes:

> No undo across commits. Inside a transaction, `undo` and `redo` step through its edits (M5.2), each a new revision equal to an earlier state, the stack bounded (section 6). Once committed, history is git's: the file's history is the history of committed states, and an agent that wants to try something opens a transaction.

The reasons for decision 9 stand, and so does invariant 3: an undo only in the app would let the app do what the API can't.

**A8. Decision 33, and section 2's *Reading the current or the published model*** (pending Trevin, decisions 6 and 9).

- The commands that read a model gain `meshes`, which takes `"model": "current" | "published"` as the others do.
- "What a published read costs" gains:

  > `meshes` needs a worker for a level it hasn't meshed (`tessellate`), on the read lane as `render`'s meshes are. A level the cache holds needs none. It's counted against the eight published reads a session runs, beside the Measure tool's.

- The decision's text gains: "The app's viewport reads `meshes` of the published model (M5.5)."

**Also:**

- Section 5's *Not in M4* gains: "*M5:* inserting and moving (M5.1, `add_feature`'s `before`, `move_feature`), suppressing (M5.1, `suppress_feature`), and the finer sketch edits (M5.10)."
- Section 9's table, in its *App (M5)* column:
  - the `begin`, `commit`, `rollback` row reads "the unsaved state: begun at the first edit; Save, Revert, Close (decision 1, M5.0)";
  - the `render` row stays "(the viewport draws itself, from `meshes`)";
  - the new commands' rows are added, with their MCP tools of the same names.
- `silico fmt --merge-touching` (decision 17) becomes a thin client of `sketch_merge`, one for each `ends_not_joined` cluster (section 7).

## 6. `status`, amended

`status` (M4.1 section 7) gains `drag` and `disk`, and its transaction gains its counts. The request is unchanged.

```json
{
  "features": 9,
  "gated": true,
  "transaction": {"base": 4, "changed": true, "undo": 3, "redo": 0, "dropped": 0},
  "running": null,
  "reads": ["meshes"],
  "rebuild": {"revision": 9, "state": "running", "done": 3, "steps": 9},
  "drag": {"sketch": "s0000001", "point": "pa000003"},
  "disk": "unchanged"
}
```

- `transaction` gains four fields:
  - `changed`: whether its document differs from the one `begin` saw. It's false after undoing back to that state. A commit then writes nothing.
  - `undo`: the edits it can undo.
  - `redo`: the edits it can redo.
  - `dropped`: the oldest edits the stack's bound dropped, which can't be undone.
- `drag`: the drag open, its sketch and point, or `null`.
- `disk`: the last comparison of the file with the bytes the session last read or wrote:
  - `unchanged`;
  - `changed`;
  - `gone` (no file at its path);
  - `unreadable` (not a regular file this user may read, or past what Silico reads of a document);
  - `null` before the first comparison has ended.

  It's a diagnostic (A5): it says what the file system held when the comparison ran. It reloads nothing.

## 7. The commands

Each command's request, result (the envelope's `result`), and errors (each one member of the envelope's `errors`), in M4.1's form. Every request also refuses what any request refuses (M4.1 section 7).

The examples use the bracket M4.9 builds (`crates/silico-cli/tests/bracket/session.jsonl`):

- `s0000001`, the L profile on `xz`: points `pa000001` to `pa000006`, lines `na000001` to `na000006`, constraints `ka000001` to `ka00000c`;
- `p0000001`, the pad;
- `s0000002`, the base's holes on `xy`: centres `pb000001` and `pb000002`, circles `cb000001` and `cb000002`;
- `h0000001`, the pocket through them;
- `s0000003` and `h0000002`, the upright's holes;
- `f0000001`, the inside corner's fillet.

Every edit outside a transaction is its own transaction and gives the commit's result, as M4's edits do (decision 1). Inside one, `commit` is `null`.

### `add_feature`'s `before` (M5.1)

`add_feature` takes `before`: the ID of the feature to add the new one before, or `null` to add it at the end, as M4 does. Inserting a feature before the end of the timeline is M4.1 section 5's *Not in M4*. Every field of a request is required (M4.1 section 2), so a request without `before` is refused. This changes `add_feature`'s snapshot, its MCP tool, and its examples, with Trevin, as M4.1 section 8 requires before the first release.

```json
{
  "session": "s1",
  "revision": 12,
  "before": "h0000002",
  "feature": {
    "type": "chamfer",
    "name": "Base edge",
    "base": "h0000001",
    "edges": [
      "p0000001.pad.Edge(G s0000001.sketch.Vertex.pa000002)"
    ],
    "size": {"distance": 1}
  }
}
```

The result is `add_feature`'s, with `index`, the new feature's place in the timeline from 0:

```json
{
  "feature": {
    "id": "c0000002",
    "type": "chamfer",
    "v": 1,
    "name": "Base edge",
    "base": "h0000001",
    "edges": [
      "p0000001.pad.Edge(G s0000001.sketch.Vertex.pa000002)"
    ],
    "size": {"distance": 1}
  },
  "index": 6,
  "changed": true,
  "commit": null
}
```

In the bracket, `h0000002` consumes `h0000001`'s solid. A chamfer of `h0000001` added before `h0000002` would consume it too, and the gate refuses two features consuming one solid (M2.2). Whether an insert takes the place of the later feature's base is open item 1, so this example's insert is refused today, as the error below shows. An insert whose base no later feature consumes (a feature on a body no later one uses, a new primitive) is placed only.

Errors: those of `add_feature`, and `before`'s.

```json
{"code": "invalid_input", "message": "the document has no feature z0000001 to add this one before", "feature": null, "elements": [], "elements_total": 0, "parameter": "before", "cause": null, "suggestion": "name a feature by its ID, or give null to add at the end", "candidates": []}
```

```json
{"code": "invalid_input", "message": "h0000001's solid is consumed by both c0000002 and h0000002", "feature": "c0000002", "elements": [], "elements_total": 0, "parameter": "base", "cause": null, "suggestion": "use a solid no other feature consumes", "candidates": []}
```

A feature added before something it uses (a pocket before its sketch) is refused by the gate, naming both features (below).

### `move_feature` (M5.1)

This moves a feature to another place in the timeline, placed only: no reference changes. A child feature can't be moved before its parent (docs/ux/solidworks.md, §5, *Editing upstream*). The gate refuses a move that puts a feature before what it uses, or after what uses it, and names both features.

Request: the feature, and the feature to move it before (`null` for the end).

```json
{"session": "s1", "revision": 12, "feature": "s0000003", "before": "s0000002"}
```

Result: where it was and where it is, from 0. Whether the document changed (a move to where it is changes nothing). Outside a transaction, the commit's result. A move reaches nothing (decision 28), since no feature's values change, so its commit writes no fingerprint.

```json
{"feature": "s0000003", "from": 4, "to": 2, "changed": true, "commit": null}
```

Errors:

```json
{"code": "invalid_input", "message": "h0000002 would come before h0000001, which it uses as its base", "feature": "h0000002", "elements": [], "elements_total": 0, "parameter": "before", "cause": null, "suggestion": "move it after h0000001, or change its base first", "candidates": []}
```

```json
{"code": "invalid_input", "message": "s0000003 would come after h0000002, which uses it as its sketch", "feature": "s0000003", "elements": [], "elements_total": 0, "parameter": "before", "cause": null, "suggestion": "move it before h0000002, or move h0000002 with it", "candidates": []}
```

Reordering features within one body's chain (two pockets swapped) needs their bases changed too, which a move doesn't do (open item 2).

### `suppress_feature` (M5.1)

Suppression behaves as SolidWorks' does (docs/ux/solidworks.md, §5, *Editing upstream*):

- suppressing a feature suppresses the features that depend on it;
- unsuppressing it leaves them suppressed;
- unsuppressing a dependent unsuppresses what it depends on.

A feature depends on the features its fields name: its base, its tool, its sketch, a fillet's edges' features, and a sketch's face (A4). It also depends on each of those features' dependencies. In the document, a suppressed feature is marked by a field, a schema change that goes to Trevin with M5.1 (open item 4). The gate refuses a document in which a feature that isn't suppressed depends on one that is, naming both. A suppressed feature:

- isn't built;
- consumes nothing, so the solid it would have consumed is a body again;
- keeps its stored fingerprint;
- is reported by no `check`.

A read of its solid is refused, saying it's suppressed. Suppression reaches nothing (decision 28): no feature's own values change, so unsuppressing a feature rebuilds it to its stored fingerprint, and unsuppressing each in turn restores the model's fingerprints exactly (M5.1's tests).

Request: the feature, and whether it's to be suppressed.

```json
{"session": "s1", "revision": 12, "feature": "h0000001", "suppressed": true}
```

Result: the feature, the features this edit suppressed and unsuppressed (in timeline order, the feature itself among them), whether the document changed, and the commit's result outside a transaction. Here the pocket's dependents go with it: the upright's pocket, which consumes its solid, and the fillet on that.

```json
{"feature": "h0000001", "suppressed": ["h0000001", "h0000002", "f0000001"], "unsuppressed": [], "changed": true, "commit": null}
```

Unsuppressing the fillet afterwards unsuppresses what it depends on, and leaves alone what depends on it:

```json
{"session": "s1", "revision": 13, "feature": "f0000001", "suppressed": false}
```

```json
{"feature": "f0000001", "suppressed": [], "unsuppressed": ["h0000001", "h0000002", "f0000001"], "changed": true, "commit": null}
```

Suppressing a feature already suppressed, or unsuppressing one that isn't, changes nothing: `"changed": false`, both lists empty, no new revision. In Silico, a pocket's base is a dependency, so suppressing an early feature of a body's chain suppresses the rest of that chain. A SolidWorks body would instead go on without it (open item 3).

Errors: a feature the document hasn't, as `remove_feature`'s, and a stale revision.

### `undo` and `redo` (M5.2; pending Trevin, decision 2)

These work inside a transaction only. `undo` restores the state before the transaction's last edit not yet undone. `redo` restores the state after the last edit undone. Each is at a new revision equal to that state, as `rollback` restores at a new revision (section 3: revisions never go back).

An edit is any command that changed the transaction's document (`"changed": true`):

- the typed edits and `replace_text`;
- `add_feature`, `move_feature`, `suppress_feature`;
- `drag_end`;
- the sketch edits;
- `format` inside a transaction (A6).

Each is one step. An edit after an undo drops the redo states. A commit or a rollback empties both.

What's restored:

- the text, byte for byte;
- what edits reached, exactly;
- the checked form.

The model is rebuilt, its steps found in the cache, so its names and fingerprints equal the earlier state's (invariant 5). It isn't kept, as `rollback` keeps `begin`'s (open item 5).

Request: the session, and the revision the client last saw (decision 12).

```json
{"session": "s1", "revision": 15}
```

Result: the revision whose state is restored, and what's left to undo and redo. The envelope's revision is the new one.

```json
{"restored": 13, "undo": 2, "redo": 1}
```

Errors:

```json
{"code": "invalid_input", "message": "no transaction is open in session s1", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": "undo steps through a transaction's edits: outside one, each edit was saved as it was made", "suggestion": "edit inside a transaction to undo; a saved file's history is git's", "candidates": []}
```

```json
{"code": "invalid_input", "message": "nothing to undo in session s1's transaction", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": null, "suggestion": "roll back to return to the state the transaction began from", "candidates": []}
```

```json
{"code": "invalid_input", "message": "nothing to redo in session s1's transaction", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": "an edit after an undo drops what was undone", "suggestion": null, "candidates": []}
```

A stale revision is a `conflict`, as for any edit. Past the stack's bound, the oldest edit is dropped and counted in `status.transaction.dropped`. Undo then stops at the oldest edit kept, and `rollback` still returns to `begin`'s state.

### `drag_begin`, `drag_move`, `drag_end` (M5.3; pending Trevin, decision 9)

A drag of one of a sketch's points, through the sketch worker's drag session (M3.7). With shared points (D2), every point a drag takes is a point by its ID: a line's end, an arc's start, end, or centre, a circle's centre, a lone point. Dragging a curve whole, or a circle's edge to change its size, isn't in M3.7's port (open item 14). A drag's commands don't queue (A1). A drag ends:

- at `drag_end`;
- at an edit or reload of the session (any new revision);
- when the session closes;
- when its worker is restarted (a move that crashed or hung).

A move after the drag ends is refused. The client begins again.

#### `drag_begin`

Request: the revision, the sketch, and the point.

```json
{"session": "s1", "revision": 12, "sketch": "s0000001", "point": "pa000003"}
```

The begin state is the current revision's solve of the sketch, which `drag_begin` waits for. The worker diagnoses the whole sketch once, and keeps the part its pins move (M3.7).

Result: the sketch's degrees of freedom left, and the points and circles of the part the drag moves. Every other member stays where it began. `moves` is a diagnostic (A5).

```json
{"sketch": "s0000001", "point": "pa000003", "dofs": 1, "moves": ["pa000002", "pa000003", "pa000004"]}
```

A point no constraint leaves free still begins a drag: its frames don't move it. SolidWorks' help doesn't say what dragging fully defined geometry does (docs/ux/solidworks.md, §3), and FreeCAD's drag behaves this way.

Errors:

```json
{"code": "over_constrained", "message": "the sketch's constraints conflict: these 2 can't all hold", "feature": "s0000001", "elements": ["ka000009", "ka00000d"], "elements_total": 2, "parameter": null, "cause": "a drag starts only from a sketch that solves, as FreeCAD refuses to drag one with conflicts", "suggestion": "remove or change one of the constraints named", "candidates": []}
```

```json
{"code": "invalid_input", "message": "the part of the sketch the drag moves has 300 unknowns, and a drag takes at most 256 there: each move of a larger part takes too long", "feature": "s0000001", "elements": [], "elements_total": 0, "parameter": "point", "cause": null, "suggestion": "drag a point of a smaller connected part, or set the value with a dimension", "candidates": []}
```

```json
{"code": "invalid_input", "message": "a drag is already open in session s1, of pa000003 in s0000001", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": null, "suggestion": "end it first: drag_end with to null leaves the sketch as it was", "candidates": []}
```

A point the sketch hasn't: `invalid_input`, naming `point`. A feature that isn't a sketch: `invalid_input`, naming `sketch`. A stale revision: `conflict`.

#### `drag_move`

Request: the cursor, in the sketch's coordinates (two `Coordinate`s, as a sketch's points hold them, M3.2's D3). A move carries no revision, since it's not an edit.

```json
{"session": "s1", "to": [62.5, 7]}
```

Result: the cursor solved for, and how the frame ended:

- `solved`: the part's new values;
- `failed`: the solver didn't reach the cursor;
- `invalid`: it reached geometry that can't be built (a line of no length, a radius not above 0), as M3.7's `SolvedInvalid`;
- `dropped`: a newer move replaced this one before it was solved.

The values come only with `solved`. Otherwise the client keeps its last frame. A frame is a diagnostic, never a result (A5).

```json
{
  "to": [62.5, 7],
  "frame": "solved",
  "points": [
    {"id": "pa000002", "x": 62.5, "y": 0},
    {"id": "pa000003", "x": 62.5, "y": 7},
    {"id": "pa000004", "x": 5, "y": 7}
  ],
  "radii": []
}
```

`radii` are the part's circles and arcs whose radius moved, each `{"id": …, "radius": …}`. Points and radii are listed by ID. A frame that didn't solve:

```json
{"to": [62.5, 7], "frame": "dropped", "points": [], "radii": []}
```

Errors:

```json
{"code": "invalid_input", "message": "no drag is open in session s1", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": "a drag ends at drag_end, at an edit or reload of the session, or when its worker restarts", "suggestion": "begin the drag again", "candidates": []}
```

A cursor that isn't finite or is out of reach is refused by M3.7's `check_drag_target`, naming `to`.

#### `drag_end`

Request: the final cursor, or `null` to end the drag with no edit (Esc).

```json
{"session": "s1", "to": [62.5, 7]}
```

The edit is a function of the begin state and the final cursor alone (A5). From the begin state, the sketch is moved to the final cursor and then solved as a whole, as M3.7's closing solve is. Its points' coordinates, as solved, become the sketch's (M3.4: a sketch's file holds its solve). The edit goes through the gate at a new revision against the begin's revision, and is one undoable edit.

If the final cursor's move fails, the begin state is kept and the result says so. The last frame that happened to be solved is never kept. This changes M3.7's closing solve, which kept the last good frame, so a released drag no longer depends on which frames were solved. Dimensions hold during a drag, as SolidWorks' do (docs/ux/solidworks.md, §3), since the drag only pins the point at a lower priority.

Result: the sketch, which state was kept (`cursor` or `begin`), whether the document changed, and the commit's result outside a transaction.

```json
{"sketch": "s0000001", "kept": "cursor", "changed": true, "commit": null}
```

```json
{"sketch": "s0000001", "kept": "begin", "changed": false, "commit": null}
```

With `"to": null`, `kept` is `begin` and nothing changes. Errors: no drag open, as for `drag_move`; the gate's errors for the dragged sketch (a point dragged past what a coordinate holds, say), the drag then ended with no edit. `drag_end` waits for the queued command running, if one is, and runs before those queued behind it (A1). An edit queued against the begin's revision then meets a `conflict`, and the app sends it again against the new revision (section 3).

### `meshes` (M5.5; pending Trevin, decision 6)

The display meshes of a model's bodies for a view, on M4.6's mesh ladder: each body meshed at the largest power of two no coarser than half a pixel, from the same cache `render` meshes into. So the viewport and an agent's `render` of one view mesh a body once, and look the same (R1). Each mesh face and edge is named by the element map, with its stability.

Request: as `render`'s, without `highlight`, `to`, or `replace`. The model, a named view or a camera (not both), the size in pixels, and the features (`null` for every body; a feature's ID for its solid).

```json
{
  "session": "s1",
  "model": "published",
  "view": null,
  "camera": {"projection": "orthographic", "eye": [100, -50, 95], "target": [30, 20, 25], "up": [-0.4082482904638631, 0.4082482904638631, 0.8164965809277261], "view_height": 80, "field_of_view": null},
  "width": 1600,
  "height": 1000,
  "features": null
}
```

Result: the camera, as `render` gives it. Then, for each body in timeline order:

- `feature`;
- `body`, its number in the model, as the ID buffer writes it (M4.6);
- `level`, the deflection asked, and `deflection`, the one the kernel used (a body's floor can raise it, `meshes.rs`);
- `positions`, `normals`, `triangles`: the kernel's mesh (`silico_protocol::Mesh`);
- `faces`, each `{"name", "stable", "triangles"}`, its triangle count, in face order (`Face1` first);
- `edge_points`, and `edges`, each `{"name", "stable", "points"}`, its polyline's point count, in edge order.

Positions are lengths as the kernel made them (`f64`, written as a `Coordinate` is). Normals are `f32`, written as the shortest decimal that reads back as the same `f32`. The arrays hold no objects, so each is on one line.

```json
{
  "camera": {"projection": "orthographic", "eye": [100, -50, 95], "target": [30, 20, 25], "up": [-0.4082482904638631, 0.4082482904638631, 0.8164965809277261], "view_height": 80, "field_of_view": null},
  "bodies": [
    {
      "feature": "f0000001",
      "body": 1,
      "level": 0.03125,
      "deflection": 0.03125,
      "positions": [[0, 0, 0], [60, 0, 0], [60, 40, 0]],
      "normals": [[0, 0, -1], [0, 0, -1], [0, 0, -1]],
      "triangles": [[0, 2, 1]],
      "faces": [
        {"name": "p0000001.pad.Face(G s0000001.sketch.Edge.na000001)", "stable": true, "triangles": 1}
      ],
      "edge_points": [[0, 0, 0], [60, 0, 0]],
      "edges": [
        {"name": "p0000001.pad.Edge(G s0000001.sketch.Vertex.pa000001)", "stable": true, "points": 2}
      ]
    }
  ]
}
```

(The example's arrays are cut to one triangle and one edge, for its shape.) For the published model, a level the cache holds asks the kernel nothing (A8). A body of a feature that failed, or a kernel fault, is answered as `render` answers it: the failure once, and the fault in `model.fault`.

Errors: `render`'s, for the view, the camera, and the size (M4.1 section 7, *`render`*); a response past 128 MiB, `invalid_input` naming `features` (ask for fewer bodies) or `width` and `height` (a smaller view, a coarser level). The Rust client takes the mesh from the typed answer, never through JSON. How MCP carries the meshes is open item 11.

### The sketch edits (M5.10)

Each sketch edit names its sketch by ID and its members by their IDs (M4.1 section 2: a request names a sketch's members by ID only). Each goes through the gate, and then the sketch's solve: a conflict that the solve finds refuses the edit as data (M3.3), and a bad edit is refused whole.

The rules are the port note's recommendations (docs/ports/sketch-edit.md), each pending Trevin by its number there. The IDs of the members an edit makes (a split's new line and point, an unjoin's new point) come from the request's `ids` if it gives them, or from the core's generator if it gives `null` (open item 7, decision 20). Each result lists every member the edit added and removed, by ID, in the sketch's list order (points, lines, circles, arcs, constraints), each list sorted by ID.

#### `sketch_add`

Adds members as the document writes them (pending Trevin, sketch-edit 7, for what removal leaves). A batch is checked whole before any member is added (docs/ports/sketch-edit.md, §2). `side` and `direction` are given, never decided from geometry (D4).

```json
{
  "session": "s1",
  "revision": 12,
  "sketch": "s0000002",
  "points": [
    {"id": "pb000003", "x": 40, "y": 20, "construction": false}
  ],
  "lines": [],
  "circles": [
    {"id": "cb000003", "center": "pb000003", "radius": 2.75, "construction": false}
  ],
  "arcs": [],
  "constraints": [
    {"id": "kb000007", "type": "equal", "a": "cb000001", "b": "cb000003"}
  ]
}
```

```json
{"sketch": "s0000002", "added": ["pb000003", "cb000003", "kb000007"], "removed": [], "changed": true, "commit": null}
```

Errors: the gate's for the sketch with the members added, all at once, each naming the field by its ID path (`circles.cb000003.radius`). An ID already in the document is refused at the field the request named (M4.1 section 2).

#### `sketch_remove`

Removes members by ID (pending Trevin, sketch-edit 7):

- a constraint;
- a curve, with each of its points that no curve uses afterwards, and every constraint that names a member removed;
- a point, only if no curve uses it, with its constraints.

Deleting a set equals deleting its members one by one: duplicates, and members that depend on others in the set, are taken (docs/ports/sketch-edit.md, §2). The sketch is solved once. A curve's points that another curve uses stay, with every constraint on them, so neighbours stay joined. A `tangent_at` naming the removed curve is removed.

```json
{"session": "s1", "revision": 12, "sketch": "s0000001", "members": ["na000003"]}
```

```json
{"sketch": "s0000001", "added": [], "removed": ["na000003", "ka000003"], "changed": true, "commit": null}
```

Errors:

```json
{"code": "invalid_input", "message": "point pa000004 is used by lines na000003 and na000004", "feature": "s0000001", "elements": ["pa000004", "na000003", "na000004"], "elements_total": 3, "parameter": "members.0", "cause": "a point that curves use is those curves' end", "suggestion": "remove the curves that use it, or unjoin it first", "candidates": []}
```

```json
{"code": "invalid_input", "message": "origin is one of the sketch's fixed references, which can't be removed", "feature": "s0000001", "elements": [], "elements_total": 0, "parameter": "members.0", "cause": null, "suggestion": "remove the constraints that name it instead", "candidates": []}
```

#### `sketch_split`

Splits a curve at one position, or a circle at two, into two pieces (pending Trevin, sketch-edit 1 to 4):

- **The new point** goes at the position's projection onto the curve.
- **A line's pieces** are joined by a `tangent_at` (`same`) at the split point, held collinear as FreeCAD's main holds them (`6d06b61c7e`). Its direction constraints go on the start-side piece only.
- **A circle** splits at two positions into two arcs, as SolidWorks' Split Entities needs two points on a closed curve (docs/ux/solidworks.md, §4).
- **Constraints on the curve** go to the piece whose span holds their point, else the nearer end's, else the start-side piece. Nothing is dropped.

```json
{"session": "s1", "revision": 12, "sketch": "s0000001", "curve": "na000001", "at": [[30, 0]], "ids": ["pa000007", "na000007", "ka00000d"]}
```

Result: the pieces (the original's ID first, on the start side), and what was added and removed.

```json
{"sketch": "s0000001", "pieces": ["na000001", "na000007"], "added": ["pa000007", "na000007", "ka00000d"], "removed": [], "changed": true, "commit": null}
```

Errors, each naming the curve:

```json
{"code": "invalid_input", "message": "the split position is 0.25 mm from line na000001, farther than 1e-7 mm", "feature": "s0000001", "elements": ["na000001"], "elements_total": 1, "parameter": "at.0", "cause": null, "suggestion": "give a position on the curve", "candidates": []}
```

```json
{"code": "invalid_input", "message": "a circle splits at two positions into two arcs, got 1", "feature": "s0000001", "elements": ["cb000001"], "elements_total": 1, "parameter": "at", "cause": "an arc whose start and end are one point can't be built", "suggestion": "give two positions on the circle", "candidates": []}
```

A position at, beyond, or within 1e-7 mm of an end is refused, naming `at.N`. A point is refused as a curve that can't be split, naming `curve`.

#### `sketch_trim`

Trims a curve back to its neighbours: the piece holding the pick's projection is removed (pending Trevin, sketch-edit 2, 5, 6, and 8). FreeCAD finds three kinds of cut. In Silico, each is found in the core in closed form:

- crossings;
- tangent contacts and overlaps;
- other curves' ends on the curve.

A gap of at most 1e-7 mm counts as contact.

- **A new end at a cut** shares the cutter's point only when a constraint already holds the cutter's end on the trimmed curve. Otherwise it gets a new point, `on` the cutter.
- **A tangency with the cutter** becomes an end tangency at the new end, its `direction` as last solved.
- **A constraint no piece can take** refuses the trim, naming it (an arc's edge `tangent` that no piece touches, `symmetric` about the trimmed line).
- **A curve with no cut on either side** is removed whole.

```json
{"session": "s1", "revision": 12, "sketch": "s0000004", "curve": "nd000002", "pick": [12, 3], "ids": null}
```

```json
{"sketch": "s0000004", "added": ["pd000009", "kd00000f"], "removed": ["kd000004"], "changed": true, "commit": null}
```

Errors:

```json
{"code": "invalid_input", "message": "trimming line nd000002 there would leave constraint kd000006 on no piece of it", "feature": "s0000004", "elements": ["kd000006", "nd000002"], "elements_total": 2, "parameter": "pick", "cause": "the trim's pieces are separate, and the constraint names the part removed", "suggestion": "remove the constraint first, or trim the other side", "candidates": []}
```

#### `sketch_unjoin`

Pulls a shared point apart. One curve's use of the point moves to a new point at the same coordinates (pending Trevin, sketch-edit 9):

- The curves that stay keep the point, and every constraint on it.
- The detached curve gets the new point with none, and keeps every dimension it had.
- A `tangent_at` between the detached curve and another at the point is removed.

`check` then warns of the two points as `ends_not_joined` until something moves them.

```json
{"session": "s1", "revision": 12, "sketch": "s0000001", "point": "pa000004", "curve": "na000004", "ids": ["pa000008"]}
```

```json
{"sketch": "s0000001", "added": ["pa000008"], "removed": [], "changed": true, "commit": null}
```

Errors:

```json
{"code": "invalid_input", "message": "point pa000001 is used by no curve but line na000001, so there's nothing to unjoin", "feature": "s0000001", "elements": ["pa000001", "na000001"], "elements_total": 2, "parameter": "point", "cause": null, "suggestion": "name a point two or more curves share", "candidates": []}
```

A curve that doesn't use the point is refused, naming `curve`.

#### `sketch_merge`

Makes several points one (pending Trevin, sketch-edit 10). The first point named survives, at its own coordinates. The others' curves and constraints are re-pointed to it, and the others are removed. The edit's solve decides the rest, and a conflict refuses it. `silico fmt --merge-touching` is a thin client of it, with one merge for each `ends_not_joined` cluster, keeping the cluster's least ID (decision 17, A8's *Also*).

```json
{"session": "s1", "revision": 12, "sketch": "s0000001", "points": ["pa000004", "pa000008"]}
```

```json
{"sketch": "s0000001", "added": [], "removed": ["pa000008"], "changed": true, "commit": null}
```

Errors, each naming the points:

```json
{"code": "invalid_input", "message": "merging pa000004 and pa000005 would give line na000004 one point at both ends", "feature": "s0000001", "elements": ["pa000004", "pa000005", "na000004"], "elements_total": 3, "parameter": "points", "cause": null, "suggestion": "merge points of different curves", "candidates": []}
```

Also refused: points that are already one point; a constraint that would then name one point twice; and an edge `tangent` left between two curves that would then share an end, which must be `tangent_at` (sketch-edit 8).

Extending a curve (sketch-edit 11) isn't among #196's M5.10 edits (open item 8).

## 8. The layout (Fusion)

The app's layout follows Fusion's, as docs/ux/fusion.md describes it, built from `re_ui`'s styling and `egui_tiles` (per docs/study/toolkit.md, and pending Trevin, decision 11). Each line cites the note's section. M5.4 builds the shell, and M5.6 the viewport's controls.

- **Regions.** An application bar across the top, a toolbar under it, the browser at the top left of the canvas, the canvas, the ViewCube at its top right, the navigation bar at its bottom centre, and the timeline across the bottom of the window (fusion.md, *The window*). The Data Panel, the Assistant, and the Marking Menu's contents are out of M5 (fusion.md, *The window* and *Not covered*).
- **The application bar** holds, left to right, the File menu, Save, Undo and Redo, and the open documents' tabs (fusion.md, *The window*). Home, the Data Panel, extensions, jobs, notifications, and the profile are Autodesk's services, and are left out.
- **The toolbar** has the Design workspace only, with its SOLID tab (fusion.md, *The toolbar*). M5 fills these panels:
  - CREATE: the primitives, Create Sketch, pad, pocket, revolve, groove;
  - MODIFY: fillet, chamfer, the booleans;
  - INSPECT: Measure;

## 9. The tools' behavior (SolidWorks)

Each line is one behavior and its source in docs/ux/solidworks.md, so a test can be written from it, with the step that builds it. Where the help is silent, the line says so and the gap is in section 12.

### Rebuilds, errors, and suppression (M5.1, M5.4)

- Geometry is built when there are warnings, not when there are errors (§5, *Errors and warnings*). In Silico, a feature that failed doesn't build, and nor does what depends on it, which the core already does (M2.4).
- Marks: an error on a feature marks that feature and the document's node, and a warning beneath a node marks the node and its parent (§5, *Errors and warnings*). The app marks the timeline entry, the browser entry, and the document's tab. Errors are red and warnings the warning colour, and one combined mark shows both (§5).
- Selecting a marked item shows its errors and warnings with their suggestions, and links to edit the feature (§5, *Errors and warnings*). The app shows the core's message, elements by name, and suggestion (invariant 9). A click on the root lists every problem: the *What's Wrong* list, from `check`'s problems and warnings (§5).
- Ctrl+B rebuilds what changed, and Ctrl+Q rebuilds every feature (§5, *Rebuild*). In the app, these are `check` with `"model": "current"`, and with `"fresh": true` (M4.3: `fresh` is SolidWorks' forced rebuild).
- Esc interrupts a rebuild (§5, *Rebuild*). In the app, it's `cancel` (section 3).
- Suppressing a parent suppresses its children; unsuppressing the parent leaves them suppressed; unsuppressing a child unsuppresses its parent (§5, *Editing upstream*). This is `suppress_feature`.
- A child can't be moved before its parent (§5, *Editing upstream*). This is `move_feature`'s refusal.
- The help doesn't say what a feature after a failed one is built on (§5). Silico's is M2.4's: it's blocked.

### Saving, undo, and the file (M5.2, M5.4)

- An asterisk beside a document's name means it changed since it was saved (§6). This is `status.transaction.changed`.
- Ctrl+S saves (§6). Ctrl+W closes, asking whether to save a changed document (§6). Section 4 gives the commands.
- Ctrl+Z undoes and Ctrl+Y redoes (§6). These are `undo` and `redo`. The help doesn't list what's undoable (§6). In Silico, every edit inside the transaction is undoable, and a save ends the undo (pending Trevin, decision 2).
- *Reload* marks a reload that would lose unsaved changes (§6). This is section 4's choice when `disk` is `changed` and edits are held.
- A reminder after a set number of minutes unsaved, and auto-recover files (§6), are out of M5 (open item 21).

### Selection (M5.7)

- Select is the mode when no command is active, and a command returns to it when it ends (§1, *Hover*).
- The entity under the pointer is highlighted as the pointer moves over faces, edges, and vertices (§1, *Hover*). The app reads it from the viewport's ID buffer and resolves it to a name at once (M4.6), from the published model.
- A click selects the entity under the pointer, in the canvas or the browser, and Ctrl selects several (§1, *Click, Ctrl, Shift*). Whether a plain click replaces the selection, and whether a Ctrl-click deselects, the help doesn't say (§1). That's open item 12.
- An item selected in the browser highlights in the canvas. An item selected in the canvas expands and scrolls the browser to it (§1, *Click, Ctrl, Shift*).
- A drag from empty space draws a box. Left to right takes only what's wholly inside, and right to left also what it crosses (§1, *Box, cross, and lasso*). In a part, a box takes edges by default (§1). Shift with a box adds, and Ctrl with a box inverts inside it (§1).
- A drag that starts on geometry selects what's under the press and draws no box (§1, *Box, cross, and lasso*).
- Filters limit what can be selected to their types. E filters edges, X faces, and V vertices. F5 shows the filter toolbar, and F6 turns the chosen filters on or off (§1, *Selection filters*). Whether E, X, and V add to the filters or replace them, the help doesn't say (§1). That's open item 12.
- *Select Other* lists the entities under the pointer in the order they're met, and Tab or the wheel steps through them (§1, *Select Other*). The app reads them from the ID buffer at that pixel, then `elements` for each, in front-to-back order. That's #196's M5.7, after the viewport study (per docs/study/viewport.md).
- A selection is a list of names, each with its stability. An element whose name isn't stable can be selected. Anything that would store it (a fillet's edges) refuses it and says why, as references refuse it (#196's M5.7; M4.1 section 2, *Element entries*).
- What happens to a selection when a rebuild removes its entity, the help doesn't say (§ *Not covered*). #196's M5.7 recommends that a selection survives a rebuild that keeps its names, and is cleared, with a word, when a name is gone (pending Trevin with M5.7).

### Feature dialogs (M5.8)

- A feature's command opens its dialog. OK accepts and closes, and Cancel discards and closes (§5, *The PropertyManager*). Enter is OK and Esc is Cancel (§5).
- The active selection box is highlighted, and its items highlight in the canvas (§5, *The PropertyManager*).
- An extrude shows a shaded preview as soon as its dialog opens, and the view can be moved without losing it (§5, *The PropertyManager*). In the app, a dialog's edits are made in the transaction, and the preview is the published model as each rebuild lands.
- A slow preview of a fillet or a chamfer can be cancelled with Esc (§5, *The PropertyManager*). In the app, that's `cancel` of the rebuild, leaving the dialog open.
- What a dialog shows when its preview fails, the help doesn't say (§5). #196's M5.8 shows the core's error where the dialog is, with the rest of the model still drawn (pending Trevin with M5.8; open item 15).
- *Edit Feature* opens a feature's dialog, from the browser, the timeline, or the canvas, and OK applies the change (§5, *Editing upstream*).

### Sketching (M5.3, M5.9, M5.11)

- **Automatic relations.** As you sketch, the pointer shows the relations that can be created, and with *Automatic relations* on, they're added: horizontal, vertical, coincident, midpoint, perpendicular, tangent (§2, *Relations added while sketching*). A relation the pointer shows at the click that accepts an entity is added to it (§2). With shared points, a coincident relation is a shared point, never a constraint (D2).
- Holding Ctrl while sketching suppresses automatic relations (§2, *Relations added while sketching*).
- A relation to a line is to the infinite line, and one to an arc to its full circle (§2). This is D4's `on`.
- **Inference lines** are dotted lines from the pointer to existing entities, guiding it to cues such as midpoints (§2, *Inference lines and snaps*). Which of them add a relation, the help doesn't say (§2; open item 18).
- **Snaps** are all on by default but the grid: endpoints, centres, midpoints, quadrants, intersections, nearest, tangent, perpendicular, parallel, horizontal and vertical, and angle. Only the entity being sketched shows them (§2, *Inference lines and snaps*).
- **Definition states.** A sketch is under defined, fully defined, over defined, not solvable, or solved to geometry that can't be built (§2, *Definition states*), from M3.3's diagnosis. The status bar shows the pointer's coordinates and the state (§2). In the browser, a sketch's name is prefixed `(+)` over defined, `(–)` under defined, and `(?)` not solvable (§2).
- **Colours by state**: under defined blue, fully defined black, dangling olive, driven dimension gray (§2, *Definition states*). The help disagrees with itself on the colour of a conflict, red or yellow, and on which state is invalid and which unsolvable (§2). That's open item 17, for M5.11.
- **A dimension that over-defines** the sketch asks: make it driven, leave it driving and over defined, or cancel (§2, *Definition states*). In the app, a conflict that the edit's solve finds refuses the edit as data (M3.3), and the app offers to make the dimension driven (`"driving": false`). Whether to offer leaving it over defined is open item 17.
- **Dragging.** Under-defined endpoints and curves can be dragged (§3), with the drag commands. A line's endpoint dragged changes its length or angle (§3). Dimensions hold during a drag (§3). *Ghost image on drag* shows where the entity started (§3); the app draws the begin state faintly. What a release keeps beyond the position, the help doesn't say (§3): `drag_end` keeps the cursor's solve or the begin state (A5), and adds no relation (open item 13).
- **Line.** The first click decides the mode: a press and drag draws one line, ended by the release, and a press and release goes on clicking a chain of lines (§4, *Line*). A double-click or right-click > End chain ends the chain and keeps the tool. Esc ends it and leaves the tool. Choosing another tool ends it (§4). A chain's lines share their points (D2).
- **Corner rectangle.** A press at the first corner, a drag, and a release; or two clicks (§4, *Rectangle, circle, arc, point*). Shift held before the release makes a square (§4). It makes four lines sharing four points, with horizontal and vertical relations. That rectangle's relations come from an unofficial source (§2, *Relations added while sketching*), and #196's M5.11 takes them (pending Trevin with M5.11; open item 18).
- **Circle**: click the centre, then drag and click the radius. **Centrepoint arc**: the centre, the radius, the start, the end. **3-point arc**: the start, the end, then the radius. **Tangent arc**: a press on an endpoint, a drag, a release. **Point**: each click places one and the tool stays (§4, *Rectangle, circle, arc, point*).
- **Trim.** Power trim: a drag across entities trims each one crossed to its nearest intersecting entity (§4, *Trim, extend, split*). Trim to closest: a click removes the entity up to its closest intersection (§4). Each is `sketch_trim`. Power trim's extending (§4) needs extend (open item 8).
- **Split.** A click on an entity splits it there, and a closed curve needs two split points (§4, *Trim, extend, split*): `sketch_split`. Selecting a split point and pressing Delete joins the two again (§4). That would be a merge of the two pieces, which no edit in #196's M5.10 makes (open item 8).
- **Delete.** A relation is deleted by selecting it and pressing Delete (§4, *Delete, and relations*): `sketch_remove`. What deleting an entity does to its relations and shared endpoints, the help doesn't say (§4). Silico's is sketch-edit 7.
- **Edit Sketch** opens from the sketch, from a feature built on it, or from one of its entities. *Exit Sketch* keeps the changes, and Cancel discards them (§5, *Editing upstream*). In the app, a sketch's edits are counted as a dialog's are, so Cancel undoes them (`undo`, as M5.8's Cancel). Exiting rebuilds the part (§5).
- **Dimensioning**: Smart Dimension's type, chosen from the pick, and its Modify box. These weren't read for the study (§ *Not covered*), so M5.11 reads them from the help first (open item 17).

## 10. The viewport, the toolkit, and picking

How it embeds in egui, its outline and picking passes, and crisp edges, silhouettes, and hidden lines are per docs/study/viewport.md.

- **The toolkit** is `eframe` with its `wgpu` backend, `egui_tiles`, and `re_ui`'s styling, at the versions `re_ui` 0.38.1 pins, so one `wgpu` serves the viewport, the UI, and agents' renders (pending Trevin, decision 11). `re_ui` comes in as a dependency only if docs/study/toolkit.md finds its tree clean under `cargo-deny` and offline. Otherwise its style constants are copied, with attribution.
- **Warm start** (pending Trevin, decision 10). The app starts one kernel worker and one sketch worker when it launches, so a person's first rebuild doesn't wait for a process to start. The rest start on demand, as today. `silico serve` and the CLI are unchanged. ARCHITECTURE.md's pool paragraph says so in M5.3's PR.

## 11. Determinism

M4.1 section 10 holds for every new command, with A5:

- **Results.** These are functions of the files read, the commands run in order, and the model the envelope names:
  - every new command's result, a drag's edit, a mesh;
  - an undo's restored state, byte for byte the earlier state's;
  - a suppression's lists, in timeline order;
  - a sketch edit's added and removed members, sorted by ID within each list.
- **Diagnostics.** These are described so in their schemas, and nothing reaches a name, a file, or a result through them:
  - a drag's frames;
  - `status`'s `disk` and `drag`;
  - which published revision a published read answers from.
- **The app's own state** (the camera, the selection's order of clicks, the dialog's place) is the app's, not a command's, and reaches no document. A selection reaches a document only as names in an edit.

## 12. Open items

Neither #196 nor the port note decides these, or they're forced by the app. None is decided here. Each is for Trevin, with a recommendation where one is offered.

1. **An insert into a body's chain** (M5.1). A feature added before another that consumes the same solid is refused, since two features can't consume one solid. SolidWorks builds later features on the body as modified. Options:
   - (a) `before` places only, and an insert into a chain needs `replace_text`;
   - (b) an insert takes the place of the later feature's reference: that feature's `base` (or `tool`) moves to the new feature, listed in the result as `rewired`, and reached.

   Offered: (b), which is what the timeline's insert means to a SolidWorks user.
2. **Reordering within a chain** (M5.1). `move_feature` places only, and a move before a feature's base is refused. Swapping two pockets of one body means swapping their bases. Options: (a) as designed, the client changes bases; (b) a move within a chain rewires as open item 1's (b).
3. **Suppression in a chain** (M5.1). In Silico a base is a dependency, so suppressing a body's early pocket suppresses every later feature on that body. In SolidWorks, a later feature that doesn't reference the suppressed one's geometry builds on without it. Options:
   - (a) #196's dependents rule, as designed;
   - (b) a suppressed feature passes its base through, so a feature that names it only as its `base` builds on that base, while a feature naming its elements (a fillet's edges) is suppressed.

   (b) is closer to SolidWorks, but changes what a reference means.
4. **The suppression field** (M5.1, a schema change). A feature's `"suppressed": true`, written only when true, after `name` (as `note` is written only when present), and read as false when absent. Or always written. The schema snapshot changes only by that field (#196's M5.1).
5. **Undo's model** (M5.2). Rebuilt from the cache, as designed (memory bounded by the session's two kept models), or each edit's model kept (no rebuild, but up to the stack's depth in B-reps).
6. **Undo's bounds** (M5.2). 100 edits and 256 MiB of text, as designed. SolidWorks gives no number. Its help says only that Undo turns off past a set number of sketch entities (docs/ux/solidworks.md, §6).
7. **IDs of the members a sketch edit makes** (M5.10). Given in the request's `ids`, or made by the core when it's `null`, as designed, with a replay giving the recorded IDs (decision 20). Or always the client's, as a sketch's member IDs are in `add_feature` (M4.1 section 5).
8. **Extend, and joining a split** (M5.10). The port note's decision 11 (extend), SolidWorks' power trim extending, and Delete on a split point joining the pieces (docs/ux/solidworks.md, §4) aren't in #196's M5.10 list. Options: add `sketch_extend` (and a join) to M5.10, or leave them after M5.
9. **Saving elsewhere** (M5.4). Decision 3's (a) has a person keep their edits against a changed file and "save elsewhere". No step builds a Save As (a `commit` to another path, or `open` with `create` of a copy). Options: a command in M5.4, or "reload or lose the edits" only, in M5.
10. **The disk comparison** (M5.4). At most once a second, reading the whole file, as designed. Or comparing size and modification time first, reading bytes only when they differ. That's cheaper, but decision 2 compares bytes, since times can miss a change. Or file-system notifications (a `notify` dependency), with bytes compared on each.
11. **How MCP carries display meshes** (M5.5). As JSON numbers, as designed: exact, but about 25 bytes a coordinate. Or a binary file written to a `to` path, as `render`'s PNG can be. Or an MCP resource. The app takes the typed answer either way.
12. **What SolidWorks' help leaves open on selection** (M5.7): whether a plain click replaces the selection; whether a Ctrl-click deselects (Fusion's Ctrl removes, fusion.md, *Conflicts and gaps*); how a selection is cleared (a click on empty space, Esc); whether E, X, and V add a filter or replace it (docs/ux/solidworks.md, §1, *Not covered*).
13. **What a drag's release keeps** (M5.3, M5.11). Whether dropping an endpoint on another entity joins them (a merge) or relates them. The help is silent (docs/ux/solidworks.md, §3).
14. **Dragging curves and sizes** (M5.3, M5.11). SolidWorks drags a whole line, and a circle's edge to change its size (docs/ux/solidworks.md, §3). M3.7 ports one point's drag only (docs/ports/sketcher.md, *Dragging*). Options: points only in M5, or curves and radii ported in M5.3.
15. **A preview that fails** (M5.8). #196 shows the core's error in the dialog. SolidWorks' help is silent (docs/ux/solidworks.md, §5).
16. **Where a dialog opens** (M5.8). Fusion's sources disagree, right or left (fusion.md, *Conflicts and gaps*). Fusion's projection default, orthographic or perspective, isn't documented either (fusion.md, *ViewCube and Navigation Bar*).
17. **Sketch colours, over-definition, and dimensioning** (M5.11). The help disagrees on a conflict's colour and on which state is invalid and which unsolvable (docs/ux/solidworks.md, §2), and the study didn't read dimensioning (§ *Not covered*). M5.11 needs both read from the help first.
18. **Which relations tools and snaps add** (M5.11). The help doesn't say which inference lines and snaps leave a relation (docs/ux/solidworks.md, §2). The corner rectangle's relations come from an unofficial source.
19. **Visibility** (M5.4). The browser's eye hides a body or a sketch. As the app's view state only, or as a document field, so a part saved with a body hidden opens with it hidden (FreeCAD keeps visibility in the file's GUI part, SolidWorks in the part).
20. **A new document** (M5.4). `open` with `create` needs a path at once. SolidWorks asks for a name only at the first save (docs/ux/solidworks.md, §6). Options: ask for the path at New, or a session without a file until its first save (a change to sessions, M4.1 section 3).
21. **Auto-recover, backups, and the unsaved reminder** (docs/ux/solidworks.md, §6). Out of M5, or in M5.4.
22. **`drag_end` and the queue** (M5.3). `drag_end`'s edit runs ahead of queued commands, as designed (A1), so an edit queued against the begin's revision meets a `conflict`. Or it queues like an edit, which makes a release wait behind whatever the app queued during the drag.

## 13. Tests the design implies

For each step, with its PR. Expected values come from the design, from hand calculation, or from FreeCAD.

- **The examples, byte for byte**, as M4.1's: every JSON block in section 7 is read by Silico's reader and written back by the API's writer to the same bytes once its step exists, and each equals its file in `commands/examples/`.
- **M5.1:**
  - insert, move, and suppress each read and written back as their examples;
  - a move before a feature's base refused, naming both features;
  - suppressing a feature suppresses its dependents, each saved as suppressed;
  - unsuppressing it leaves them suppressed, and unsuppressing each in turn restores the model's fingerprints exactly;
  - unsuppressing a dependent unsuppresses what it depends on;
  - a document with an unsuppressed feature using a suppressed one refused by the gate, naming both;
  - a move or a suppression writes no fingerprint (it reaches nothing);
  - the schema snapshot changes only by the suppression field.
- **M5.2:**
  - a run of edits undone one by one restores each earlier state's text byte for byte, and its model's fingerprints, each at a new revision;
  - redo after undo restores the later one;
  - an edit after an undo drops the redo;
  - undo with nothing to undo, or outside a transaction, refused naming why;
  - past 100 edits, the oldest is dropped and `status.transaction.dropped` counts it;
  - a rollback after undos restores the transaction's start;
  - `status.transaction.changed` is false after undoing to `begin`'s state, and that state's commit writes nothing.
- **M5.3:**
  - a drag's moves all reach one worker while other sessions' rebuilds run;
  - a move sent while one is in flight replaces the waiting one, and the replaced move answers `dropped` (the fake sketch worker's call record);
  - the same begin, cursor path, and end give the same saved document byte for byte however many moves were dropped (moves held and released in different orders in the fake);
  - a final cursor that fails keeps the begin state (`"kept": "begin"`), never the last good frame;
  - a move after `drag_end`, after an edit, and after the worker's restart, each refused, and a new begin works;
  - `drag_end` is one undoable edit;
  - `drag_end` with `to` null changes nothing;
  - M3.7's drag benchmark through the client, within a 60 Hz frame on its sketches;
  - the app's first rebuild of a one-feature document starts no worker (the pool's launch log).
- **M5.4:**
  - the frame counter climbs while a rebuild is held, and the panels answer;
  - an edit marks the tab unsaved (`changed`), Save writes it, and Revert restores the file's text;
  - an agent's commit reloads the app's document when it holds no edits (`status.disk`, then `outline` with `"reloaded": true`), and with edits held it's offered, and the app's commit is a `conflict` until it reloads;
  - `status.disk` reads `changed` within two `DISK_CHECK_INTERVAL`s of a change that keeps the file's size and time;
  - `format` inside a transaction accepts drift into its state, undoably, and its commit saves it;
  - a cancelled render answers `cancelled`.
- **M5.5:**
  - a box's display mesh for the front view holds its six faces' triangles, each face named as the element map names it;
  - two views a power of two apart in pixel size share one mesh (the cache's call record);
  - a body meshed for `render` and for `meshes` at one view is meshed once;
  - a published read is counted against the eight;
  - a rebuild that publishes a new model is read without waiting on the current one.
- **M5.10:** every case in docs/ports/sketch-edit.md §9, FreeCAD's ported twice where the note says so, and Silico's own; each result's `added` and `removed` sorted; each refusal naming its members; `silico fmt --merge-touching` clears every `ends_not_joined` warning of a sketch, its points then shared.
- **The determinism sweep** extended to every new command's result, byte for byte, and the drag's edit across moves dropped.
