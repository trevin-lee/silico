## 1. Scope

The commands M5's steps need, beyond M4's, and the step that builds each:

| Command | Step | What it does |
|---|---|---|
| `add_feature`'s `before` | M5.1 | Adds a feature before another, rewiring the chain it joins |
| `move_feature` | M5.1 | Moves a feature to another place in the timeline, rewiring the chains it leaves and joins |
| `remove_feature`'s `rewired` | M5.1 | Removes a feature its chain passes through, its consumer taking its base (A9) |
| `suppress_feature` | M5.1 | Suppresses a feature and its dependents, or unsuppresses it and what it needs |
| `timeline` | M5.1 | The document's features, structured, each with its health: what the browser and timeline draw |
| `undo`, `redo` | M5.2 | Steps back or forward through a transaction's edits, one at a time or to a revision |
| `drag_begin`, `drag_move`, `drag_end` | M5.3 | Drags a sketch's point: its frames, then one edit |
| `meshes` | M5.5 | The display meshes of a model's bodies for a view, each face and edge named |
| `sketch` | M5.10 | A sketch as solved: its points and curves, its plane in 3D, each member's definition state, and its profile |
| `sketch_add`, `sketch_remove` | M5.10 | Adds a sketch's members, or removes them with what only they used |
| `sketch_split`, `sketch_trim` | M5.10 | Splits a curve; trims a curve back to its neighbours |
| `sketch_unjoin`, `sketch_merge` | M5.10 | Pulls a shared point apart; makes several points one |
| `status`'s `disk`, `drag`, and the transaction's counts | M5.2, M5.3, M5.4 | Whether the file changed on disk; the drag open; the undo and redo left |

Every new command is an MCP tool of the same name with the same shapes (M4.1 section 9), so an agent reaches everything the app does. `timeline` and `sketch` exist for that reason: what the app draws in the browser, the timeline, and sketch mode comes from commands, never from the core's model read in Rust (invariant 3).

M5.9 (sketches on faces, A4, in M5: pending Trevin, decision 5) adds no command. `add_feature` and `set_field` take the face plane, as M4.1 section 5 allows. A sketch corner's fillet and chamfer aren't in M5.10 (pending Trevin, decision 12). M5.4, M5.6, M5.7, M5.8, M5.11, and M5.12 are the app's own, and add no command.

## 2. The app's state

The app is one process, `silico-app`, which holds:

- one `command::Sessions`, whose sessions share its kernel pool, sketch solvers, render worker, and caches, as `silico serve`'s do (M4.1 section 3);
- one tab for each open document.

### What a tab holds

| Held | What |
|---|---|
| The session | Its `SessionId`, and the path it opened |
| The model it draws | `Sessions::published(&id)`'s model, read each frame, and its revision (decision 33) |
| Its meshes | The newest `meshes` answer, each body's mesh by its key and level, uploaded to the GPU once (M5.6) |
| Its status | The newest `status` answer: revision, transaction, rebuild, drag, and disk |
| The timeline | The newest `timeline` answer: the features, their health, the bodies (M5.4) |
| The sketch open | In sketch mode, the newest `sketch` answer (M5.11) |
| The selection | A list of element names, each with its `stable`, as an agent could write them (M5.7) |
| The commands under way | Each command's `Running` handle, and what it's for (section 3) |
| The dialog open | The feature dialog's inputs, and the revision it opened at (M5.8) |
| The drag | The drag open, if one is, and the newest frame drawn (M5.3) |
| The camera | The viewport's camera: the app's own, never a command's (decision 29) |

Each of these answers is of a revision, and the app draws each one as of its own revision, never waiting for them to agree. A frame can draw revision 8's published model under revision 9's timeline. The timeline marks a feature newer than the model as health `unknown` (section 7, `timeline`), and the rebuild indicator says a rebuild is running. This is what decision 33 allows: the app reads `published`, and never stalls.

### The unsaved state (pending Trevin, decision 1)

The app keeps its unsaved changes as a transaction, begun at a document's first edit, not when the document opens.

- **No edits held** (no transaction open): the session reloads what an agent commits, on its own thread, once a disk comparison finds the file changed (section 4; A3), as decision 2's reload, without waiting for a command.
- **Edits held** (a transaction open): the document is unsaved, and its tab carries an asterisk, as SolidWorks marks a changed document (docs/ux/solidworks.md, §6). Its file isn't reloaded (M4.1 section 4). `status.disk` says whether the file changed on disk (section 6), and the app offers what decision 3 says (section 4).
- **Save** is `commit`. **Revert** is `rollback`. **Close** asks if the tab holds edits, then rolls back and closes. Decision 22 refuses `close` inside a transaction.
- **A dialog's edits** are made inside the same transaction. The dialog's Cancel is `undo` back to the revision the dialog opened at (`"to"`, section 7), never `rollback`, which would drop the unsaved edits made before the dialog (M5.8). After OK, the app's Ctrl+Z undoes the dialog's edits as one step, as SolidWorks undoes a feature's edit: an `undo` to the revision the dialog opened at.

The tab is unsaved when `status.transaction.changed` is true (section 6). After undoing back to the state `begin` saw, it's false, and the asterisk goes.

## 3. The frame loop: polling, never waiting

The UI thread calls only what answers at once. M4.1 section 3 names these:

- `Sessions::published(&id)`;
- `status` and `read_logs`;
- the `Running` handle's `try_take`, `progress`, and `cancel`.

Every other command is started on the UI thread and runs off it. It returns a `Running` handle before its file read, gate, rebuild, save, or export. Each frame:

1. **Status.** For each tab, `status`, which reads only what the session holds, and `Sessions::published(&id)`.
2. **Results.** Every `Running` handle is polled with `try_take`. A finished command updates the tab's state, and a refusal shows its errors where SolidWorks shows them (section 9). A handle that isn't finished is left for the next frame. The app never calls `wait` or `wait_timeout` on the UI thread.
3. **Input.** Each user action starts its command and keeps the handle.

### Waking without input

The app draws a frame only when something changed. It doesn't redraw continuously while a long command runs.

- **The core wakes it.** `Sessions` takes a waker, `Sessions::on_change(Box<dyn Fn() + Send + Sync>)`. The core calls it when:
  - a `Running` answers;
  - a rebuild publishes a model;
  - a disk comparison ends;
  - a rebuild step settles, for the progress `status` reports;
  - the session reloads its file at a new revision (section 4).

  The app's waker asks the toolkit for a repaint (per docs/study/toolkit.md). The core calls it only once the answer can be taken (after the `Running`'s reply is sent), with no lock of the core's held, so the next frame's `try_take` finds it. It's called off the UI thread, and must only ask, never draw. A comparison's end wakes the app only if its finding changed.
- **Idle.** With nothing pending, the app asks for one frame each `DISK_CHECK_INTERVAL` (1 s). That frame's `status` starts the next disk comparison (section 4), so an agent's commit is found without the mouse moving.
- **During a rebuild,** the waker fires as each step settles. Progress (`status.rebuild.done`) redraws then, not at the display's rate.

### When the app reads

- **The model to draw** is the published one, read each frame.
- **The timeline** is read whenever the revision or the published revision changes (`timeline`, from the published model), including after the session reloads a file changed on disk (section 4). The browser, the timeline, and the error marks are drawn from it. The details of the problems are read with a published `check` when the person opens one (M5.4).
- **Meshes** are read when:
  - the published revision changes;
  - the view settles at a half pixel outside a body's `serves` (orthographic);
  - the camera settles after a move (perspective).

  Each read lists the meshes the tab already holds (`held`), so only new or changed bodies carry arrays. Until it lands, the viewport draws the meshes it has (M5.6). The tab keeps at most one `meshes` read in flight, and uploads each body's buffers once, by its key and level.
- **The sketch open** is read with each revision while sketch mode is open (`sketch`, `current`), so a dimension's edit redraws its sketch as solved.
- **Pre-selection and the Measure tool** read the published model (`elements`, `query`, `distance`, `angle`), as decision 33 intended. A picking read arrives a frame after the frame that asked for it (docs/study/viewport.md, §3), so hover lags the pointer by a frame.

### Bursts of edits

The session's queue is unbounded (an M4 low, #196's *What M4 leaves for M5*), so the app never queues edits one by one.

- A tab has at most one edit in flight.
- An edit made while one is in flight waits in the tab, and a newer edit of the same field replaces it (typing in a dialog's value box, say).
- When the edit in flight answers, the waiting one is sent, against the revision the answer gave (decision 12).
- A drag's moves are coalesced the same way, in the core (section 7, `drag_move`).

### Stop, and the rebuild indicator

- **The indicator** is `status.rebuild` (M4.1 section 9's table): `done` of `steps` while a rebuild runs, its state otherwise.
- **The stop button** is `cancel`, naming `status.running` or a published read in `status.reads` (decision 34). Esc does the same, as Esc interrupts a SolidWorks rebuild (docs/ux/solidworks.md, §5, *Rebuild*), but only when nothing nearer takes it. Esc goes to the first of these that's there: an open or queued drag (`drag_end` with `null`); a sketch tool's chain under way, which it ends, leaving the tool (§4); a dialog's preview rebuilding, which it stops with the dialog left open, as SolidWorks stops a slow preview (§5); an open dialog (its Cancel); the selection, which it clears (section 9); the stop. The stop and its button are off while `status.running` is `reload`, which `cancel` doesn't take.
- **A cancelled render** answers `internal` today (M4.6's open item). M5.4 makes it `cancelled`.

### How this is tested (pending Trevin, decision 7)

- **The frame counter.** It keeps climbing while the fake kernel holds a request, and the panels keep answering. Each of these is held in turn:
  - a rebuild (M5.4);
  - a `meshes` read (M5.6);
  - a `timeline` read (M5.4);
  - a drag's move in the fake sketch worker (M5.3, M5.11);
  - an export (M5.12);
  - a disk comparison, through a test hook that holds it while `status` keeps answering (M5.4).
- **Waits on the UI thread.** A frame counter can't see a short wait. A `wait_timeout(15 ms)` in a frame still lets frames climb. So in the app's tests the UI thread is marked, and `Running::wait` or `wait_timeout` called on it fails the test. That makes the rule structural, not timed.
- **Driving the app.** It's driven through `egui_kittest`'s accessibility tree, with no GPU (docs/study/toolkit.md, §4):
  - each `egui_tiles` pane has an accessible label;
  - frames are stepped with `step` and `run_steps` while a command is held, since `run` refuses a UI that keeps repainting;
  - a click in the viewport takes the `wgpu` feature and lavapipe on CI, and a test that doesn't need the pixel selects by name.
- **The viewport** is checked through its ID buffer against projections by hand, as M4.6's tests are. Screenshots are never compared with stored images.
- **The waker.** Its rules are checked from inside the callback: a test's waker calls `try_take` on the handle that answered, which must give the answer, and `status` on the same session under a timeout, which deadlocks if the core held a lock while calling. A test counts repaint requests: one when a held command answers (and its `try_take` in that frame takes it), none while nothing is pending, one idle frame per `DISK_CHECK_INTERVAL`, one more only when a comparison's finding changes, one as each step of a held rebuild settles, and one when the session reloads.

## 4. Files: open, save, revert, close, and a file changed on disk

| Action | Command | Notes |
|---|---|---|
| New | `open` with `"create": true` | Asks for the path first (open item 30) |
| Open | `open` | A document the gate refuses still opens, with its problems shown (decision 21) |
| Save (Ctrl+S) | `commit` | Writes only if the transaction's document differs from `begin`'s. Ctrl+S is SolidWorks' (docs/ux/solidworks.md, §6) |
| Save As | `commit` with a `path` | Open item 22 |
| Revert | `rollback` | Restores the file's text byte for byte (M4.1 section 4) |
| Close (Ctrl+W) | `rollback` if edits are held and the person agrees, then `close` | Closing a changed document asks whether to save it (docs/ux/solidworks.md, §6). Decision 22 refuses `close` inside a transaction |
| Quit | As Close, for each tab | Closing several changed documents lists them, to save all, some, or none (docs/ux/solidworks.md, §6) |
| Accept drift | `format`, naming the features | Allowed inside a transaction (pending Trevin, decision 8; A6) |

### A file changed on disk (pending Trevin, decisions 1 and 3)

Live co-editing follows decision 30's (a) for M5 (pending Trevin, decision 3). A person and an agent share a part through its file, not at once.

- **With no edits held,** the session reloads the file itself: a comparison that finds it changed queues the reload on the session's own thread (A3), so the session's state has one writer. The app sees the new revision in `status`, and reads `timeline` and the published model again, as for any revision. No published read reloads anything (M4.1 section 4).
- **With edits held,** `status.disk` says `changed` (or `gone`), and the app offers two choices:
  - **Reload**, dropping its edits: `rollback`, after which the next command reloads.
  - **Keep its edits**: its `commit` is refused as a `conflict` (decision 2) until it reloads, or saves elsewhere with Save As (open item 22).

  SolidWorks' *Reload* likewise marks a reload that would lose unsaved changes (docs/ux/solidworks.md, §6). Its help says nothing about another program changing a document open for writing (§6), so the choice offered is decision 3's.
- **The comparison runs off the UI thread.**
  - `status` answers from the session's last comparison, and starts the next if none is running and the last ended at least `DISK_CHECK_INTERVAL` ago.
  - It compares bytes, not times, as decision 2 does, reading the file whole, up to 16 MiB.
  - Each comparison records which of the session's reads and writes it compared against, by a counter the session advances at each one, never by the bytes (two of the session's own saves, A then B then A again, would match by bytes). A result whose counter is no longer the session's (its own commit landed meanwhile) is dropped, never reported. So the session's own Save never reads as a change on disk.

## 5. Amendments to M4.1

Each amendment replaces M4.1's text where it says, once M5.0 is approved. The step that builds it changes that text in the same PR, as M4.1's *as built* notes did.

**A1. Section 3, *One command at a time, per session*** (pending Trevin, decision 9; open item 18). The paragraph "Four kinds don't queue behind the session's other commands …" becomes:

> Five kinds don't queue behind the session's other commands.
> - `status`, `read_logs`, and `cancel` answer at once, because they only read what's held or stop what's running.
> - Reads of the published model, and `timeline`, run beside the queue: on the read lane where they need a worker (section 2), never waiting for a rebuild. None of them reads the file or changes what the session holds: only the session's own thread does.
> - `drag_move` runs on the session's drag, outside the queue. Only the newest move is solved: a move that arrives while one is solving waits, and a newer one replaces it.
>
> `drag_begin` and `drag_end` queue as commands, a cursor or none, so the order a client sends them in is the order they apply in: a release queued behind a commit lands after it, a begin after a queued release begins after that release's edit, and an Esc (`drag_end` with `null`) sent while its begin waits ends the drag that begin opens. A client sends moves only after its begin has answered; a move sent before then is refused as no drag being open, with the cause that a begin may still be queued. `drag_begin` waits only for the commands before it, never for a rebuild: it solves on the drag's own sketch worker (section 7). `status` lists the published reads running and the drag open, and `cancel` can stop the reads and a drag's move in flight. Commands of different sessions run at the same time.

*Recompute and the models* is unchanged. `status`'s line "Doesn't read the file" becomes "Doesn't read the file itself: it starts the disk comparison off the caller's thread (section 4)."

**A2. Section 3, *What a session holds*** (pending Trevin, decisions 1, 2, and 9). The table gains three rows:

> | The undo stack | Inside a transaction: each edit's text before it and what edits reached then, with the states undone since, for `redo`; bounded (section 6). A state is held as its header and its features' canonical texts in chunks of 64 features, each chunk an `Arc` the states share while none of its features changes, so a state costs its list of chunks (one pointer for each 64 features) and the chunks its edit changed (one, for a pad's length). An undo writes the text from them as canonical form writes it, byte for byte; a state before the transaction's first edit keeps its file bytes whole, once. The bound counts those bytes, and everything each later state adds: its list of chunks (24 bytes and 8 a chunk) and the chunks no earlier state shares (each its texts' bytes and 16), these overheads counting constants, not measured sizes; the transaction keeps one parsed header from `begin`, uncounted, which a state whose header is unchanged shares, and a changed one costs its canonical text's bytes, once, shared by later states while it doesn't change. The first state after `begin` shares no chunk with the begin's whole bytes, so it's charged in full. The begin's bytes are the transaction's, for `rollback`: counted, and never dropped, so the oldest state dropped is the first after `begin` (the text before the second edit), and undo can then reach neither it nor `begin`, leaving the first two edits out of its reach (`rollback` still reaches `begin`). `status.transaction.bytes` says the count. Checked forms aren't kept: an undo puts the text through the gate again, which gives the same `Checked` |
> | The drag | If one is open: its sketch and point, the begin state, the sketch worker it holds, and the newest cursor solved with its values |
> | The disk comparison | The last comparison's finding (`unchanged`, `changed`, `gone`, `unreadable`), the counter of the session's read or write it compared against, whether one is running, and whether a reload it found is queued |

*Per-client generations*, on sketch workers, gains:

> A drag takes a sketch worker of the `Sessions`' `SketchSolvers` from its begin to its end. While it does, that worker serves only the drag: rebuilds take another, and it isn't stopped for a superseded generation (ARCHITECTURE.md, *Sketches solve in the sketch worker*, which this builds). A move is a request like any other, under its own timeout (`DRAG_MOVE_TIMEOUT`, section 6) and the crash and hang handling. A move that hangs or crashes ends the drag. With drags, as many sketch workers can live as sessions were solving and dragging at once: 32 at most, one recompute's and one drag's for each of 16 sessions, never more. A sketch edit's solve (M5.10) runs on the session's recompute solver, before the edit is taken, so it adds none. A refused edit's solve is dropped, and starts no rebuild: the current revision's rebuild goes on as it was.

That last sentence replaces "never more than 16" in the same paragraph.

**A3. Section 4, *Transactions*** (pending Trevin, decisions 1, 2, and 8).

- "Inside a transaction, an edit is applied once the gate takes it …" gains: "It's pushed on the transaction's undo stack, and the stack's redo states are dropped."
- "After a commit there is no undo in the API (decision 9) …" becomes: "Inside a transaction, `undo` and `redo` step back and forth through its edits, each at a new revision whose state equals an earlier one (section 7). A commit or a rollback empties the stack. After a commit there's no undo in the API (decision 9, amended): the committed states are the file's history, which is git's."
- In *A file changed outside the session*, "inside a transaction, only `commit` reads it" becomes: "Inside a transaction, only `commit` reads it to decide anything. `status` compares it off the caller's thread, at most once each `DISK_CHECK_INTERVAL`, and reports what it found in `disk`, reloading nothing."
- The same section's *Outside a transaction* bullet gains: "A comparison that finds the file changed, with no transaction open, queues a reload on the session's own thread, as the next command would make it: a new revision, reached by nothing, in the queue's order. At most one reload is queued at once: a comparison that finds a change while one waits queues none. A reload that runs inside a transaction (a `begin` queued ahead of it), or finds the file as the session last read or wrote it, does nothing and makes no revision. If the session then holds the file as it is (a `begin` ahead of it reloaded it first, as every command outside a transaction does), `disk` becomes `unchanged`, the finding stale; otherwise it stays `changed`. It's named `reload` wherever a command's name is shown (`status.running`, `read_logs`' spans). `cancel`'s `command` stays `SessionCommand`, which hasn't `reload`, so a `cancel` naming it is refused as the reader refuses any value outside a field's kinds, naming `command`, and `reload` is never among `cancel`'s candidates. So `status.running` takes a type of its own, `SessionCommand` and `reload`, where M4.1 shares `SessionCommand` with `cancel`'s `command`: a change to the protected `status.json` contract and to `status`'s `outputSchema` in the protected `crates/silico-mcp/tests/contract/tools.json`, for Trevin with M5.4. So a client that only reads (the app with no edits held) sees an agent's commit without sending a command to find it." (Decision 2, amended; open item 20.)
- For `format` inside a transaction, see A6.

**A4. Section 6, *Limits*** (pending Trevin, decisions 2, 6, and 9). The table gains:

> | A transaction's undo stack | 256 MiB of what its states hold beyond what they share (open item 7), so 4 GiB at most across the 16 sessions a process holds | `undo`, `redo`, every edit inside a transaction | not refused: the oldest is dropped and counted (`status.transaction.dropped`) |
> | A disk comparison | one running a session, each at least 1 s (`DISK_CHECK_INTERVAL`) after the last ended | `status` | not refused: `disk` is the last comparison's |
> | Drags open in one session | 1 | `drag_begin` | `invalid_input`, naming `session` |
> | A drag's moves solving | 1, the newest waiting behind it, the rest dropped | `drag_move` | not refused: a move replaced before it's solved answers `dropped` |
> | A drag's move | 10 s (`DRAG_MOVE_TIMEOUT`) | `drag_move`, `drag_end`'s move | `worker_timeout`, a kernel fault; the drag ends |
> | A drag's part | 256 unknowns (`MAX_DRAG_UNKNOWNS`, M3.7) | `drag_begin` | `invalid_input`, naming `point` |
> | A display mesh read's size | 1 to 4,096 pixels a side, as `render`'s | `meshes` | `invalid_input`, naming `width` or `height` |
> | A display mesh read's answer | 128 MiB, the response's limit (M4.1) | `meshes` | `invalid_input`, naming `features` when the answer holds more than one body, `width` when one body alone passes it |
> | The new IDs a sketch edit is given | as many as it makes | the sketch edits' `ids` | `invalid_input`, naming `ids`, with the count it needs |

`version`'s `limits` gain `undo_bytes`, `disk_check_ms`, `drag_move_seconds`, and `drag_unknowns`, in that order, after `sketch_seconds`.

`DRAG_MOVE_TIMEOUT` is 10 s because `MAX_DRAG_UNKNOWNS` was sized so a move takes under a second: 0.76 s at 256 unknowns on a loaded machine (M3.7). A move past ten times that is hung, and a person's drag shouldn't wait out `SKETCH_TIMEOUT`'s 300 s. It bounds a move of the drag's part only. A whole-sketch solve, `drag_begin`'s when it needs one and `drag_end`'s closing solve, isn't bounded by the drag's limit, and runs under `SKETCH_TIMEOUT`, as any solve does.

**A5. Section 2, *Numbers*, and section 10, *Determinism*** (pending Trevin, decisions 6 and 9).

- **Numbers** gains:

  > **A mesh's coordinates** (`meshes`' `positions` and `edge_points`) are the kernel's `f64`, written as a `Coordinate` is (`-0` as `0`), never rounded to a `Length`: they're the mesh, not measures of it. **Its normals** are `f32`, as OCCT keeps them, written as the shortest decimal that reads back as the same `f32`, `-0` as `0`. **A mesh level** (`level`, `deflection`, `serves`) is a power of two, a body's floor, as `meshes.rs` holds it, or 0 (the lower end of a floor body's `serves`), written as a `Coordinate` is.

- **Orders** gains:

  > A mesh's faces and edges in the solid's own numbering (`Face1` first, `Edge1` first), as the ID buffer numbers them (M4.6); a mesh's bodies in timeline order. A sketch's members by kind, then by ID, as the document lists them. A sketch edit's `added` in the order it made them (section 7), which is the order its `ids` are taken in.

- **Not results** gains:

  > a drag's frames (`drag_begin`'s `moves` and `drag_move`'s answers: which moves are solved and which dropped depends on the worker's speed); `status`'s `disk` and `drag` (the file system's state, and the drag open).

- New bullet:

  > **A drag's edit.** `drag_end`'s edit is a function of the begin state and the final cursor alone: the sketch, from the begin state, dragged to the final cursor and then solved as a whole. If that fails, the begin state is kept, and the result says so. However many moves were dropped, the same begin, cursor, and end give the same document byte for byte. FreeCAD's App `moveGeometry` solves from the `initMove` state the same way, and `commitDragMove` aborts when the final move fails (`ViewProviderSketch.cpp`). FreeCAD's GUI, though, can re-base an absolute drag (`RecalculateInitialSolutionWhileDragging`, on by default): `Sketch::moveGeometries` begins again from the current frame once the cursor passes 20 times a step measured from `initToPoint`, which the GUI never sets, so it fires rarely and by the history of earlier drags (docs/ports/sketcher.md, *Dragging*). Its committed position can then depend on the path. Silico's begin-state rule is M3.7's deliberate departure from that (docs/ports/sketcher.md, *Dragging*).

- New bullet:

  > **Display meshes** are results: the kernel's tessellation at the level the ladder gives for the request's view and size. A body's `key` is the digest of its step as the recompute keys it, without the kernel's identity or the platform, which only the cache's key adds. So it's the same on every checked platform, as the mesh is.

**A6. Decision 31, and section 7's `format`** (pending Trevin, decision 8). "Refused inside a transaction (commit or roll back first); M5 revisits that …" becomes:

> Inside a transaction, it writes nothing to the file. It puts into the transaction's document every fingerprint and solve as rebuilt that it would write outside one: those `features` names (or all), drift accepted and named, and every `fingerprint_missing` it can store. If that changes the document, it's one edit (`changed: true`, undoable, at a new revision), and the transaction's commit saves it. Its result is the same shape: `changed` says whether the transaction's document changed; `written` is always `false`; `path` is the session's; `accepted` and `refingerprinted` are as outside. With `"write": false`, it changes nothing, makes no revision, and pushes no undo step, saying only whether it would change. Outside a transaction it's as before.

Decision 31's last sentence becomes: "*Amended (M5.0):* allowed inside a transaction, into the transaction's state (section 7)." In section 2's *Warnings*, the clause "(… `format` is refused inside a transaction)" goes, and `fingerprint_missing`'s suggestion holds inside a transaction too.

**A7. Decision 9** (pending Trevin, decision 2). "No undo stack in the API" becomes:

> No undo across commits. Inside a transaction, `undo` and `redo` step through its edits (M5.2), each a new revision equal to an earlier state, the stack bounded (section 6). Once committed, history is git's.

The reasons for decision 9 stand. So does invariant 3: an undo only in the app would let the app do what the API can't.

**A8. Decision 33, and section 2's *Reading the current or the published model*** (pending Trevin, decisions 6 and 9).

- The decision's text gains: "The app's viewport reads `meshes` of the published model (M5.5), its browser and timeline `timeline`, and its sketch mode `sketch`."

**A9. Section 5's `remove_feature`, and section 7's** (Fable, vetoable). "If others use it, the gate refuses the removal with each one's broken reference, naming it" becomes:

> A feature its chain passes through is removed with its consumer taking its base: the feature whose `base` (or `tool`) named it now names what it named. That consumer is listed in the result's `rewired` (section 7), and reached. The removal is refused, naming both features, where nothing can stand in: a chain's root under a feature that needs a base, a feature whose `sketch` it is, or a feature that stores names of its elements.

The result gains `rewired`, so insert and remove are inverses through typed commands. FreeCAD's `Body::removeObject` reroutes the same way (`src/Mod/PartDesign/App/Body.cpp`). It also removes a chain's root under a feature that needs a base, leaving that feature failing ("No base set", 1.1.3, for a through-all pocket). Silico refuses that removal instead, a deliberate departure: an edit that leaves a feature that can't build is refused before it's made. Under a pad or revolve, the removal goes ahead, and the consumer begins the body (`rewired`, `to` null), as in FreeCAD. Its way back is the root added again at its place (its recorded ID, `before` the feature that followed it), then a `set_field` of the consumer's `base`: an insert rewires only a consumer of an input the new feature takes, and a root takes none. FreeCAD's insert (`Body::setBaseProperty`) rewires the next solid feature to the inserted one every time, a base-less one too, which restores this in one step (4,075 mm³ in 1.1.3, the scripts of the port review). Silico doesn't, a deliberate departure: in a document with several bodies, a pad with no base begins a body of its own, and an insert before it mustn't silently join that body to another.

**A10. Section 5, *What an edit reaches*, and decision 28** (Fable, vetoable). "anything but `name`, `note`, and `fingerprint`" becomes "anything but `name`, `note`, `fingerprint`, and `suppressed`", and the bullet gains:

A suppressed feature carries no fingerprint: a save writes none for it, and drops the one it had, however it came to be suppressed (by command, by hand, by a merge), so what it holds is a function of the text alone. Unsuppressing a feature makes it reached, and its next save writes a fresh fingerprint. So an unsuppress never reads a change of base as drift, and a hand edit of `suppressed` and the command come to the same file.

## 6. `status`, amended

`status` gains `drag` and `disk`, and its `transaction` gains counts. The request is unchanged. The example's values are illustrative, not the bracket's.

```json
{
  "features": 9,
  "gated": true,
  "transaction": {"base": 4, "changed": true, "undo": 3, "redo": 0, "dropped": 0, "bytes": 61530},
  "running": null,
  "reads": ["meshes"],
  "rebuild": {"revision": 9, "state": "running", "done": 3, "steps": 9},
  "drag": {"sketch": "s0000001", "point": "pa000003"},
  "disk": "unchanged"
}
```

- `transaction` gains five fields:
  - `changed`: whether its document differs from the one `begin` saw. It's computed when each edit is applied and held, never in `status`. It's false after undoing to that state, and a commit then writes nothing.
  - `undo`: the edits it can undo.
  - `redo`: the edits it can redo.
  - `dropped`: how many of the transaction's edits undo can no longer reach, since the bound dropped their states (2 at the first drop: the edits before and after the state dropped).
  - `bytes`: what the stack holds, as its bound counts it (A2): a count the session holds, updated as each state is pushed, dropped, or discarded for redo, never worked out in `status`.
- `drag` is the drag open (its sketch and point), or `null`.
- `disk` is the last comparison's finding:
  - `unchanged`;
  - `changed`;
  - `gone`: no file at its path;
  - `unreadable`: not a regular file this user may read, or past what Silico reads of a document;
  - `null` before a first comparison has ended.

  It's a diagnostic (A5), and it reloads nothing.

### The chain (Fable, vetoable)

Every rule below follows from one: **the `base` links in the text are each body's chain, exactly as written.**

- Insert, move, and remove edit the chain in the text, and report every reference they rewire.
- Suppression never rewrites a reference: the rebuild skips the links it marks.
- Every rule is a function of the text: chains by `base` links, consumers by the gate's one-consumer rule, makers of a stored name by parsing it. No geometry decides any of them.

This is what FreeCAD's PartDesign does on its `BaseFeature` chain (`Body.cpp`'s `setBaseProperty` and `removeObject`; `Feature.cpp`, where a suppressed feature's shape is its base's), except where A9, `move_feature`, and `suppress_feature` state a departure, and it gives SolidWorks' behavior: later features build on the body as the earlier ones left it (docs/ux/solidworks.md, §5).

A **rewired** entry is `{"feature", "field", "from", "to"}`: a feature whose `base` or `tool` an edit changed, which the edit reaches (decision 28). `from` or `to` is `null` where the feature had no base or is left with none (a pad placed before its chain's root, or a pad root's consumer, a pad, after the root is removed). Each result lists them in timeline order, after the edit.

### `move_feature` (M5.1)

A move of `F` before `T` is a remove followed by an insert:

1. `F`'s consumer, if it has one, takes `F`'s `base`, as `remove_feature` rewires it (A9), whether the consumer named `F` as its `base` or its `tool`. If `F` is a chain's root and its consumer needs a base, the move is refused, naming both.
2. `F`'s `base` becomes the last member of its chain before the new place, or none for a pad or revolve placed before the chain's root. A primitive takes no base, so a move that would give one a base is refused, naming it.
3. The chain's next member after that place takes `F` as its `base`. A move never makes `F` another feature's `tool`.

Rules:

- A move that leaves `F` between its base and its consumer rewires nothing.
- A move that takes a feature off a tool's chain (one a boolean consumes as its `tool`) to a place past that boolean is refused, naming the boolean: the chain it would join has no member to give it as a base without a second consumer. Within the tool's chain, a move is as above.
- A child can't be moved before its parent (docs/ux/solidworks.md, §5, *Editing upstream*). FreeCAD's move (`CmdPartDesignMoveFeatureInTree`) is a remove then an insert too, and lets a chain's root move, leaving a feature that needs a base failing; Silico refuses that move, as A9 refuses the removal. So the gate still refuses a move that puts a feature:
  - before its sketch;
  - before a feature whose elements it names;
  - after a feature that names its elements or uses it as its sketch.

  Each refusal names both features.

Request: the feature, and the feature to move it before (`null` for the end).

```json
{"session": "s1", "revision": 12, "feature": "h0000001", "before": "f0000001"}
```

Result: where it was and where it is, from 0 (`to` counted after the move), what it rewired, whether the document changed, and the commit's result outside a transaction. Here the pockets swap in the chain: the timeline becomes `s0000001`, `p0000001`, `s0000002`, `s0000003`, `h0000002`, `h0000001`, `f0000001`, each pocket still after its sketch. The cuts commute, so the volume stays 20,739.435948.

### `suppress_feature` (M5.1; Fable, vetoable)

**What's suppressed.** Suppression behaves as SolidWorks' does (docs/ux/solidworks.md, §5, *Editing upstream*): suppressing a parent suppresses its children, and unsuppressing a child unsuppresses its parent. In Silico's terms:

- A suppressed feature isn't built.
- A feature whose `base` or `tool` names a suppressed feature builds on the nearest unsuppressed feature up that input's chain: its **effective base**.
- A body is the result of a built feature that nothing built consumes.

**Dependents.** A dependent of `X` is suppressed with it. Taken to a fixed point in timeline order, the dependents are:

- a feature whose `sketch` is `X`;
- a feature that stores an element name one of whose makers is `X` (a fillet's or chamfer's `edges`; A4's face): every feature ID in the parsed name, with modified names counted as their source;
- a feature one of whose inputs it needs has no unsuppressed feature up its chain. A pad's or revolve's base is optional (it can begin a body), so with its whole chain suppressed it builds on nothing, alone, as FreeCAD 1.1.3 builds it (`FeatureExtrude.cpp` takes the prism alone when the base is null) and as SolidWorks keeps a boss that isn't another's child (§5). A pocket's, groove's, fillet's, chamfer's, or boolean's inputs are needed.

The gate refuses a document in which a dependent of a suppressed feature is unsuppressed, naming both.

**Unsuppressing.** Unsuppressing `X` also unsuppresses, recursively, what `X` needs and lacks:

- its sketch;
- each suppressed maker of a name it stores;
- for an input it needs (not a pad's or revolve's base, which is optional) whose chain holds no unsuppressed feature, that chain's root.

What depends on `X` stays suppressed.

**Fingerprints (A10).** A suppressed feature carries no fingerprint: the save drops it, so the file's diff for a suppression is the `suppressed` line and the fingerprints it no longer holds. Suppression reaches every unsuppressed feature that uses `X`, refingerprinted as they build on another base, so a suppressed file still checks clean. Unsuppressing `X` reaches it, so its next save writes its fingerprint fresh, and a suppress then unsuppress, committed, gives the file byte for byte as it was.

**FreeCAD.** In 1.1.3, a suppressed feature's shape is its base's (`Feature.cpp`, `4d929d3301`), as here. A suppressed root stays suppressed with a null shape: a feature after it that can begin a body (a pad) builds alone, as here, and one that needs a base fails: a through-all pocket ("Base feature's TopoShape is invalid"); a pocket of a set depth builds its tool alone instead, which docs/ports/suppression.md, written with M5.1, records. `2a541c9536` removed the older branch, `86e75037d9`'s, in which a suppressed root unsuppressed itself. Silico suppresses the features that need the base instead, a deliberate departure: a feature that can't build is suppressed with its cause, not left failing.

**In the document,** a suppressed feature carries `"suppressed": true`, immediately after `name`, a schema change that goes to Trevin with M5.1 (open item 4). The file reader refuses `"suppressed": false`, naming the field, as M2.1's D6 writes optional fields omitted, never as their absent value. `false` is taken only by `suppress_feature` and `set_field`.

Request: the feature, and whether to suppress it.

```json
{"session": "s1", "revision": 12, "feature": "h0000001", "suppressed": true}
```

Result: the features this edit suppressed and unsuppressed, in timeline order and including the feature itself; whether the document changed; and the commit's result outside a transaction. `h0000001` alone is suppressed: `h0000002` builds on `p0000001`, and the volume is 20,977.019 mm³. A commit then writes `h0000002`'s and `f0000001`'s fingerprints, and drops `h0000001`'s (A10).

```json
{"feature": "h0000001", "suppressed": ["h0000001"], "unsuppressed": [], "changed": true, "commit": null}
```

Suppressing a sketch suppresses what's built on it. Unsuppressing that feature then unsuppresses its sketch:

```json
{"session": "s1", "revision": 12, "feature": "s0000002", "suppressed": true}
```

```json
{"feature": "s0000002", "suppressed": ["s0000002", "h0000001"], "unsuppressed": [], "changed": true, "commit": null}
```

```json
{"session": "s1", "revision": 13, "feature": "h0000001", "suppressed": false}
```

```json
{"feature": "h0000001", "suppressed": [], "unsuppressed": ["s0000002", "h0000001"], "changed": true, "commit": null}
```

Suppressing a feature already suppressed, or unsuppressing one that isn't, changes nothing: `"changed": false`, both lists empty, no new revision. Reading a suppressed feature's solid (`elements` with its ID) is refused, `invalid_input` naming `feature`, saying it's suppressed. Errors: a feature the document hasn't, and a stale revision.

### `undo` and `redo` (M5.2; pending Trevin, decision 2)

These work inside a transaction only.

- **`undo`** restores the state before the transaction's last edit not undone, or, with `to`, the state at that revision, undoing every edit after it.
- **`redo`** restores the state after the last edit undone, or, with `to`, redoes up to that revision.
- Each is at a new revision equal to that state, as `rollback` restores at a new revision.

**What's an edit.** Any command that changed the transaction's document (`"changed": true`), each one step:

- the typed edits and `replace_text`;
- `add_feature`, `move_feature`, `remove_feature`, and `suppress_feature`;
- `drag_end`;
- the sketch edits;
- `format` inside a transaction (A6).

Every edit is its own step, never merged with the one before: a client that wants a run of edits undone as one (a dialog's arrow dragged, its Cancel, its Ctrl+Z after OK) undoes `to` the revision the run began at. An edit after an undo drops the redo states. A commit or a rollback empties both stacks.

**What's restored.** The text, byte for byte, and what edits reached, exactly. The checked form is made again by the gate, which gives the same one. The model is rebuilt, its steps found in the cache, so its names and fingerprints equal the earlier state's (invariant 5; open item 6).

Request: the session, the revision the client last saw (decision 12), and `to`: `null` for one step, or for `undo` an earlier revision the stack holds, for `redo` a later one it holds. A `to` on the wrong side, or the session's own revision, is refused, naming `to`.

```json
{"session": "s1", "revision": 15, "to": null}
```

Result: the revision whose state is restored, and what's left to undo and redo. The envelope's revision is the new one. Here, `begin` came at revision 12 and three edits made revisions 13, 14, and 15, so one undo restores revision 14's state, as revision 16:

```json
{"restored": 14, "undo": 2, "redo": 1}
```

A dialog opened at revision 13 and cancelled at 16 undoes to it: `{"session": "s1", "revision": 16, "to": 13}`, restoring 13's state.

Errors:

```json
{"code": "invalid_input", "message": "no transaction is open in session s1", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": "undo steps through a transaction's edits: outside one, each edit was saved as it was made", "suggestion": "edit inside a transaction to undo; a saved file's history is git's", "candidates": []}
```

```json
{"code": "invalid_input", "message": "nothing to undo in session s1's transaction", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": null, "suggestion": "roll back to return to the state the transaction began from", "candidates": []}
```

```json
{"code": "invalid_input", "message": "revision 3 isn't a state of session s1's undo stack, which holds revisions 12 to 16", "feature": null, "elements": [], "elements_total": 0, "parameter": "to", "cause": "the stack dropped its oldest edits past its bound, or the revision is from before the transaction", "suggestion": "undo to a revision the stack holds, or roll back to the transaction's start", "candidates": []}
```

`redo` with nothing to redo is refused likewise, its cause "an edit after an undo drops what was undone". A stale revision is a `conflict`. Past the stack's bound, the oldest state is dropped and the edits it leaves out of undo's reach are counted in `status.transaction.dropped`. Undo then stops at the oldest state kept, and `rollback` still returns to `begin`'s.

### `drag_begin`, `drag_move`, `drag_end` (M5.3; pending Trevin, decision 9)

A drag of one of a sketch's points, through the sketch worker's drag session (M3.7). With shared points (D2), every point a drag takes is a point by its ID: a line's end, an arc's start, end, or centre, a circle's centre, a lone point.

- **What it pins.** The dragged point. For each arc whose start or end is that point, the drag also pins the arc's centre where it starts, a hundred times more weakly, so the end moves before the centre (FreeCAD `4d7a9435c1`, `Sketch.cpp`'s `initMove`, which pins the picked arc's centre). A point that ends two arcs pins both centres. M3.7's `DragBegin` pins an arc's centre only for `PointOf::Start` or `End`, so M5.3 gives it the pins from the core (open item 16).
- **What it doesn't drag.** Dragging a curve whole, or a circle's edge, isn't in M3.7's port (open item 17).
- **When it ends.** A drag's commands follow A1. A drag ends at `drag_end`, at any new revision of the session (an edit or a reload), when the session closes, or when its worker restarts. A move after the end is refused, and the client begins again.

#### `drag_begin`

Request: the sketch and the point. It carries no revision: it queues (A1), and drags the sketch as the session holds it when it runs, the revision the envelope names, which `drag_end`'s edit is made against.

```json
{"session": "s1", "sketch": "s0000001", "point": "pa000003"}
```

The begin state is the revision's solve of the sketch. If the session's current model already holds it (the revision's rebuild solved it), that's taken. Otherwise the drag's sketch worker solves the sketch from the revision's text, in FreeCAD's order (M3.3), under `SKETCH_TIMEOUT`, never waiting on the revision's rebuild. A sketch whose constraints conflict is refused. One whose solve fails otherwise begins from its stored coordinates, as FreeCAD's drag begins from its geometry (open item 15).

Result: the sketch's degrees of freedom left, and the points of the part the drag moves, by ID. Every other point stays where it began. `moves` is a diagnostic (A5).

The example is the L profile with the base leg's thickness, `ka00000a`, removed (`begin` at revision 12, the `sketch_remove` making revision 13, the drag beginning at 13). Its one freedom is that thickness:

```json
{"sketch": "s0000001", "point": "pa000003", "dofs": 1, "moves": ["pa000001", "pa000002", "pa000003", "pa000004", "pa000005", "pa000006"]}
```

A point no constraint leaves free still begins a drag, and its frames don't move it. SolidWorks' help doesn't say what dragging fully defined geometry does (docs/ux/solidworks.md, §3), and FreeCAD drags it so (`initDragging` has no such check).

Errors. The profile with a second length of `na000001` added (`ka00000d`, 61 mm):

```json
{"code": "over_constrained", "message": "the sketch's constraints conflict: these 2 can't all hold", "feature": "s0000001", "elements": ["ka000009", "ka00000d"], "elements_total": 2, "parameter": null, "cause": "a drag starts only from a sketch whose constraints agree, as FreeCAD refuses to drag one with conflicts", "suggestion": "remove or change one of the constraints named", "candidates": []}
```

```json
{"code": "invalid_input", "message": "the part of the sketch the drag moves has 300 unknowns, and a drag takes at most 256 there: each move of a larger part takes too long", "feature": "s0000001", "elements": [], "elements_total": 0, "parameter": "point", "cause": null, "suggestion": "drag a point of a smaller connected part, or set the value with a dimension", "candidates": []}
```

```json
{"code": "invalid_input", "message": "a drag is already open in session s1, of pa000003 in s0000001", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": null, "suggestion": "end it first: drag_end with to null leaves the sketch as it was", "candidates": []}
```

A point the sketch hasn't is `invalid_input`, naming `point`. A feature that isn't a sketch is `invalid_input`, naming `sketch`. A suppressed sketch is `invalid_input`, naming `sketch`.

#### `drag_move`

Request: the cursor, in the sketch's coordinates (two `Coordinate`s, M3.2's D3). A move carries no revision, since it's not an edit.

```json
{"session": "s1", "to": [62.5, 7]}
```

Result: the cursor solved for, and how the frame ended:

- `solved`: with the part's points and radii;
- `failed`: the solver didn't reach the cursor;
- `invalid`: it reached geometry that can't be built, M3.7's `SolvedInvalid`;
- `dropped`: a newer move replaced this one before it was solved.

Values come only with `solved`; otherwise the client keeps its last frame. `points` lists every point of the part, by ID. `radii` lists the part's circles and arcs whose radius is free, each `{"id", "radius"}`, by ID. A frame is a diagnostic (A5).

Here the cursor is off to the right of the leg's end: `pa000003` stays on its vertical line at x = 60, and the leg's top rises to y = 7, taking `pa000004` with it:

```json
{
  "to": [62.5, 7],
  "frame": "solved",
  "points": [
    {"id": "pa000001", "x": 0, "y": 0},
    {"id": "pa000002", "x": 60, "y": 0},
    {"id": "pa000003", "x": 60, "y": 7},
    {"id": "pa000004", "x": 5, "y": 7},
    {"id": "pa000005", "x": 5, "y": 50},
    {"id": "pa000006", "x": 0, "y": 50}
  ],
  "radii": []
}
```

```json
{"to": [70, 9], "frame": "dropped", "points": [], "radii": []}
```

Errors:

```json
{"code": "invalid_input", "message": "no drag is open in session s1", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": "a drag ends at drag_end, at a new revision of the session, or when its worker restarts", "suggestion": "begin the drag again", "candidates": []}
```

A cursor that isn't finite, or is out of reach, is refused by M3.7's `check_drag_target`, naming `to`. A move past `DRAG_MOVE_TIMEOUT` is `worker_timeout`, and ends the drag. `cancel` naming `drag_move` stops the move in flight by restarting its worker, which ends the drag.

#### `drag_end`

Request: the final cursor, or `null` to end the drag with no edit (Esc).

```json
{"session": "s1", "to": [62.5, 7]}
```

**How it solves.** With a cursor, it queues as an edit (A1). It's a function of the begin state and the final cursor alone (A5):

1. From the begin state, the sketch is moved to the final cursor. If the newest solved move had a cursor of the same bits, its values are taken and no move runs again.
2. The sketch is then solved as a whole, as M3.7's closing solve is, under `SKETCH_TIMEOUT` (A4).
3. Its points' coordinates, as solved, become the sketch's (M3.4).
4. The edit goes through the gate, at a new revision, and is one undoable edit.

If the final move fails, the begin state is kept, and the result says so. This is FreeCAD's `commitDragMove`, and it replaces M3.7's closing solve from the last good frame. docs/ports/sketcher.md's divergence note changes with M5.3. Dimensions hold during a drag, as SolidWorks' do (docs/ux/solidworks.md, §3), since the drag pins its point below every constraint. The release adds no relation (open item 19).

Result: the sketch, which state was kept (`cursor` or `begin`), whether the document changed, and the commit's result outside a transaction.

```json
{"sketch": "s0000001", "kept": "cursor", "changed": true, "commit": null}
```

```json
{"sketch": "s0000001", "kept": "begin", "changed": false, "commit": null}
```

With `"to": null`, it queues as the begin did (A1) and ends the drag with no edit: `kept` is `begin`, and nothing changes. A move still solving then is stopped by restarting the drag's worker, as `cancel` of `drag_move` stops it, so the session's queue never waits on a move; that move answers `cancelled`, which the app drops without a word. Queued behind a command that waits for a rebuild (a `commit`), it waits for that command, not for a rebuild of its own. Errors: no drag open, as for `drag_move` (a new revision between the begin and the release ends the drag); and the gate's errors for the dragged sketch, the drag then ended with no edit.

### `meshes` (M5.5; pending Trevin, decision 6)

The display meshes of a model's bodies for a view, on M4.6's ladder: each body at the largest power of two no coarser than half a pixel, from the same cache `render` meshes into. So the viewport and an agent's `render` of one view mesh a body once, and look the same (R1).

- **Culling.** `meshes` meshes every body asked for, never culling to the view, unlike `render`, which draws only what's in it. A pan never needs a read.
- **Levels.** An orthographic view gives every body one level. A perspective one gives each body its own, at its nearest point to the eye, as `render` does (`views::half_pixel_at` at the body's tight box's nearest depth).
- **Indexing.** The mesh is the kernel's as it made it: vertices shared within a face, triangles never split, each edge a B-rep polyline. So a renderer finds silhouettes from adjacency within each face, and across faces from the edges; duplicating a vertex across faces at upload is the client's.
- **Naming.** Each mesh face and edge is named by the element map, with its stability.
- **The mesh stays fixed.** The mesh is the kernel's, in the document's coordinates, with no camera and no light in it. The viewport moves the camera without remeshing (docs/study/viewport.md).

Request: as `render`'s without `highlight`, `to`, or `replace`, with two more fields:

- `features`: a list of IDs, or `null` for every body;
- `held`: the meshes the client already holds, each `{"key", "deflection"}`.

```json
{
  "session": "s1",
  "model": "published",
  "view": null,
  "camera": {"projection": "orthographic", "eye": [100, -50, 95], "target": [30, 20, 25], "up": [-0.40824829046386313, 0.40824829046386313, 0.8164965809277258], "view_height": 80, "field_of_view": null},
  "width": 1600,
  "height": 1000,
  "features": null,
  "held": []
}
```

Result: the camera, as `render` gives it, and each body in timeline order, with:

- `feature`;
- `body`: its number in the model, as the ID buffer writes it (M4.6), or `null` for a feature's solid that isn't a body;
- `key`: its step's digest, 64 hex digits (A5);
- `level`: the deflection asked;
- `deflection`: the one the kernel used, which a body's floor can raise (`meshes.rs`);
- `box`: the body's tight box, `[min, max]`, as `render` takes the nearest point from it;
- `serves`: the half pixels, `[at_least, below]`, that this level serves (`[0, 2 · mesh_level(floor)]` for a body meshed at its floor, which a perspective view reaching the eye's plane gives it, since every level at or under the floor gives the same mesh, so it isn't read again at every settle): in an orthographic view, the view's half pixel; in a perspective one, the half pixel at the body's nearest point. The app reads again only when that leaves the range, computing it with the core's own `silico_core::views::half_pixel_at(camera, height, depth)` at `views::depth_of_box(camera, box)`, the rule `render` uses (`command/render.rs`), so no rule is copied into the UI;
- `held`: true if the client holds this mesh (its `key` at its `deflection`), and then its geometry arrays (`positions`, `normals`, `triangles`, `edge_points`) are empty. `faces` and `edges`, with their names, are always given: a key covers the geometry, not the names, which two features of equal values, or a sketch's IDs swapped, can change without changing the geometry;
- `positions`, `normals`, `triangles`: the kernel's mesh (`silico_protocol::Mesh`);
- `faces`: each `{"name", "stable", "triangles"}`, its triangle count, in face order;
- `edge_points`, and `edges`: each `{"name", "stable", "points"}`, its polyline's point count, in edge order.

Numbers are A5's.

```json
{
  "camera": {"projection": "orthographic", "eye": [100, -50, 95], "target": [30, 20, 25], "up": [-0.40824829046386313, 0.40824829046386313, 0.8164965809277258], "view_height": 80, "field_of_view": null},
  "bodies": [
    {
      "feature": "f0000001",
      "body": 1,
      "key": "3f9a0c5e1d7b2a4c6e8f0a1b3c5d7e9f1a2b4c6d8e0f1a3b5c7d9e1f2a4b6c8d",
      "level": 0.03125,
      "deflection": 0.03125,
      "box": [[0, 0, 0], [60, 40, 50]],
      "serves": [0.03125, 0.0625],
      "held": false,
      "positions": [[0, 0, 0], [60, 0, 0], [60, 40, 0]],
      "normals": [[0, 0, -1], [0, 0, -1], [0, 0, -1]],
      "triangles": [[0, 2, 1]],
      "faces": [
        {"name": "p0000001.pad.Face(G s0000001.sketch.Edge.na000001)", "stable": true, "triangles": 1}
      ],
      "edge_points": [[0, 0, 0], [60, 0, 0]],
```

(The arrays are cut to one triangle and one edge, to show the shape. The view's half pixel is 80 / 1000 / 2 = 0.04, so its level is 0.03125.)

For the published model, a level the cache holds asks the kernel nothing (A8). A body of a feature that failed, or a kernel fault, is answered as `render` answers it: the failure once, the fault in `model.fault`. A suppressed feature in `features` is `invalid_input`, naming it.

Errors: `render`'s, for the view, the camera, and the size; a response past 128 MiB, `invalid_input` naming `features` (ask for fewer bodies) or `width` (a smaller view, so a coarser level). The Rust client takes `Arc<Mesh>` from the typed answer, as `render` already does, never cloned and never through JSON. How MCP carries meshes is open item 23.

### `sketch` (M5.10)

A sketch as the named model solved it, for sketch mode to draw and colour. An agent reads the same thing (invariant 3).

The result holds:

- **`plane`**: the sketch's frame in 3D, `origin`, `x`, `y`, and `normal`. For a face plane (A4), it's the face's frame as resolved.
- **`state`**: SolidWorks' five states (docs/ux/solidworks.md, §2, *Definition states*): `under_defined`, `fully_defined`, `over_defined`, `no_solution`, or `invalid`.
- **`dofs`**: the degrees of freedom left.
- **Each member, as solved, in its document form,** with its solved coordinates or radius in place of the stored ones, and a `state`. Points and curves have `under_defined`, `fully_defined`, or `over_defined`: SolidWorks gives each entity a state too (§2). Constraints have `satisfied`, `conflicting`, `redundant`, or `partially_redundant`. So a curve carries the points it joins and its `construction`, and a constraint its type, members, and value, and sketch mode draws from this alone. The core decides the states from M3.3's free unknowns and conflicts, so no client maps unknowns to members. A sketch whose constraints conflict has no solution, so its members are given as stored, their states from the conflict.
- **`regions`**: the profile's regions, as M3.5 finds them, each with its outer loop's curves and each hole's, by ID in loop order. If there's no profile, M3.5's reasons, as errors, go in `profile_problems`.

### The sketch edits (M5.10)

**Common rules.**

- Each edit names its sketch by ID, and its members by their IDs (M4.1 section 2).
- Each goes through the gate and then the sketch's solve. A conflict the solve finds refuses the edit as data (M3.3), and a bad edit is refused whole.
- Coordinates and projections are computed in the core, with the libm shim's math, so every platform gets the same bits (sketch-edit 6).
- `construction` is kept by every piece and every new point (`23ecf94ab6`).

**The rules are the port note's, and normative.** For split, they're §3's table in its Silico column. For trim, they're §4's items 8 and 9 with the decisions they cite. For removal, unjoining, and merging, they're §2, §5, and §6. Each is pending Trevin by the port note's decision number. This section gives each edit's shape and its key rules. Where the two differ, the port note's text governs, except where this section says otherwise and lists the difference in section 12.

**What a result lists.**

- `added`: the new members, in the order the edit made them. That's by kind (points, lines, circles, arcs, constraints), then in place along the curve from its start for points and pieces (a circle, which has no start, from `at.0`), then constraints in the order of the members they copy (by ID), then new joins.
- `modified`: members changed in place (a line's `to`, a constraint moved to a piece or retyped), by kind, then by ID.
- `removed`: members removed, by kind, then by ID.
- `references` (split and trim): the features that store a name made from the curve's ID or its points' IDs (`s0000001.sketch.Edge.na000001`, as a source anywhere in the name), in timeline order. Each such name now finds what the start-side piece makes, which is only part of what it found (open item 11), so the edit says which features to look at, as `rewired` does for the chain.

A constraint whose type changes (split's `length` becoming a `distance`, a merge's edge `tangent` becoming a `tangent_at`) keeps its ID and is listed in `modified`: it states the dimension or relation the person placed, in the pieces' terms (open item 10). So no edit makes an ID for a retype, and `silico fmt --merge-touching` writes the same file everywhere.

**New IDs.** These come from the request's `ids` if it gives a list, taken in `added`'s order, or from the core's generator if it gives `null` (decision 20). A list of the wrong length is refused, naming `ids`, with the count the edit needs. A replay that passes back the `added` IDs it recorded gives the recorded document byte for byte.

#### `sketch_add`

Adds members as the document writes them. A batch is checked whole before any is added (docs/ports/sketch-edit.md, §2). `side` and `direction` are given, never decided from geometry (D4). The request's members carry their own IDs, as `add_feature`'s sketch members do, so it has no `ids`.

```json
  "circles": [

  "arcs": [],
  "constraints": [
    {"id": "kb000007", "type": "equal", "a": "cb000001", "b": "cb000003"}
```

#### `sketch_remove`

Removes members by ID (sketch-edit 7):

- **A constraint.**
- **A curve,** with each of its points that no curve uses after the edit, and every constraint that names a member removed.
- **A point,** only if no curve uses it after the edit, with its constraints.

A set is judged as a whole: its curves are removed first, then its points judged, so a point and the curves that use it go together (`41c91574cf`). Duplicates are taken once. The sketch is solved once. A curve's points that another curve uses stay, with every constraint on them, so neighbours stay joined (§2). A `tangent_at` naming the removed curve is removed, never moved to a neighbour (`9ce5756011`'s intent).

```json
{"session": "s1", "revision": 12, "sketch": "s0000001", "members": ["na000003"]}
```

```json
{"sketch": "s0000001", "added": [], "modified": [], "removed": ["na000003", "ka000003"], "changed": true, "commit": null}
```

#### `sketch_split`

Splits a line or an arc at one position, or a circle at two (sketch-edit 1 to 4, and §3's table).

- **The new point** goes at the position's projection onto the curve. A position farther than 1e-7 mm from the curve is refused. FreeCAD projects any point, so this departs from it, by Silico's exactness rule. A position at an end, beyond it, or within 1e-7 mm of it is refused too (`82633fb5df`).
- **A point already on the curve.** If the sketch already has a point held `on` the curve at the position, that point is shared, and its `on` is removed.
- **A line's pieces** are held collinear by a `tangent_at` (`same`) at the split point, as FreeCAD main holds them (`6d06b61c7e`). Direction constraints stay on the start-side piece.
- **A circle** splits at two positions into two arcs, as SolidWorks' Split Entities needs two points on a closed curve (docs/ux/solidworks.md, §4).
- **Constraints on the curve** follow §3's table. In particular:
  - a `length` becomes a `distance` between the outer ends;
  - a `midpoint` becomes a `symmetric` of the outer ends;
  - an `equal` on a line is dropped (`857190a20a`, #25008);
  - a `tangent_on` at the split point becomes a `tangent_at`;
  - point constraints go to the piece whose span holds their point, else to the nearer end's piece.
- **IDs.** The start-side piece keeps the curve's ID, as FreeCAD's first piece keeps its index (`82610ca8fa`, `7d8a8b7cc8`). A circle's ID goes to the arc counter-clockwise from `at.0` to `at.1`. Names made from the curve's ID follow it (open item 11).

Splitting the base's bottom line at its middle:


#### `sketch_trim`

Trims a curve back to its neighbours. The piece holding the pick's projection is removed (sketch-edit 2, 5, 6, 8, and §4).

**Cuts** are found in the core in closed form:

- crossings;
- tangent contacts and overlaps;
- other curves' ends on the curve.

A gap of at most 1e-7 mm counts as contact.

**What cuts.** Every other curve, construction included (`715f98d1f3`). A sketch point doesn't cut, and neither do `x_axis` and `y_axis`. **A cut within 1e-7 mm of the curve's own end isn't a cut** (`226d24792d`), so a neighbour that shares the end never makes a piece of no length. FreeCAD's test is 1e-8 in the curve's parameter, strictly (`Precision::PApproximation`): r · 1e-8 mm on an arc. Silico's is 1e-7 mm on every curve, the gate's floor, a deliberate departure: on an arc of radius 1000, FreeCAD ignores a cut 5e-6 mm from the end, and Silico makes a piece of that length, which the gate takes.

**Whole-curve deletion.** The curve is removed whole when:

- there's no cut on either side;
- two cuts are within 1e-7 mm of each other;
- it's a circle with fewer than two distinct cuts (`testTrimCircleEnd`).

Trimming a point is refused (`5efb8e5e76`).

**The new ends.**

- A new end shares the cutter's point only when a constraint already holds the cutter's end on the trimmed curve. That `on` is then removed, and a `tangent_on` there becomes a `tangent_at`. Otherwise the new end gets a new point, `on` the cutter (sketch-edit 5).
- A tangency with the cutter becomes an end tangency at the new end, its `direction` as last solved, and a solve that flips it refuses the trim (sketch-edit 8).
- Trimming away an end a neighbour shares detaches the neighbour: the piece gets a new point, and the neighbour keeps the shared one (§4).

**Constraints** follow §4's items 8 and 9:

- an `on` on the removed part is dropped (`333ca836c0`);
- a `length` is dropped with one piece left, and becomes a `distance` with two (`2779f0b29f`);
- a constraint naming both ends survives only if both do (`f0d30cb570`);
- a line's `equal` is dropped (`857190a20a`);
- a `tangent_on` goes to the piece holding its `at`, and is dropped with it.

**Refusal.** Only decision 2's cases refuse the trim, naming the constraint: an arc's edge `tangent` that no piece touches, and a `symmetric` about the trimmed line.

**IDs.** The first piece keeps the curve's ID (`7d8a8b7cc8`).

#### `sketch_unjoin`

Pulls a shared point apart. One curve's use of the point moves to a new point at the same coordinates (sketch-edit 9):

- **The curves that stay** keep the point, and every constraint on it.
- **The detached curve** gets the new point with no constraints of the point's, but keeps every dimension of its own. FreeCAD keeps an end's own constraints with its curve. Silico's shared point carries them for every curve, so they stay with the curves that keep it.
- **A `tangent_at`** between the detached curve and another at the point is removed. FreeCAD's vertex Delete keeps every constraint but the coincidence there (`delConstraintOnPoint` with `onlyCoincident`), so an end-to-end `Tangent` keeps those ends joined. Silico removes it, a deliberate departure: an unjoin that left them joined wouldn't be an unjoin.
- **A `tangent_on` whose `a` is the detached curve** and whose `at` is the point is moved to the new point, so its `at` stays an end of `a` (open item 14).

Afterwards, `check` warns of the two points as `ends_not_joined` until something moves them.

A curve that doesn't use the point is refused, naming `curve`.

#### `sketch_merge`

Makes several points one (sketch-edit 10):

- **The first point named survives** at its own coordinates. A FreeCAD coincidence lands where its solve takes it. Silico's merge is a placement, so the edit's solve then decides the rest, and a conflict refuses it.
- **The others** have their curves and constraints re-pointed to it, and are removed.
- **An edge `tangent`** between two curves that would then share an end becomes a `tangent_at`, its `direction` as last solved, listed in `modified`. The conversion follows FreeCAD (`620188073e`: a coincidence where an edge tangency exists becomes an endpoint tangency) and sketch-edit 8, not decision 10's refusal (open item 13). FreeCAD deletes the tangency and appends a new one, so its index and name are lost. Keeping the ID is Silico's own choice (open item 10), so a merge makes no new member, and takes no `ids`.

`silico fmt --merge-touching` is a thin client of it, one merge for each `ends_not_joined` cluster, keeping the cluster's least ID (decision 17).

## 9. The tools' behavior (SolidWorks)

Each line is one behavior and its source in docs/ux/solidworks.md, so a test can be written from it, with the step that builds it. Where the help is silent, the line says so and section 12 recommends.

### Rebuilds, errors, and suppression (M5.1, M5.4)

- **When geometry is built.** Geometry is built when there are warnings, but not when there are errors (§5, *Errors and warnings*). A failed feature doesn't build, and what depends on it is blocked, as the core already does (M2.4). The help doesn't say what a feature after a failed one builds on (§5).
- **Error marks** (§5, *Errors and warnings*):
  - an error with a feature marks that feature's name;
  - an error with the model marks the document's name and the feature that contains the error;
  - a warning with a feature marks that feature;
  - a warning beneath a node marks the document's name and the parent feature.

  Items in error have red text, and items with a warning green. One combined mark shows both. The app marks the timeline entry, the browser entry, and, for the model's errors, the document's tab, from `timeline`'s health.
- **Showing a problem.** Selecting a marked item shows its errors and warnings with their suggestions, and links to edit the feature (§5). The app shows the core's message, elements by name, and suggestion (invariant 9), from a published `check`. A click on the root lists every problem, the *What's Wrong* list (§5).
- **Rebuilding.** Ctrl+B rebuilds what changed, and Ctrl+Q every feature (§5, *Rebuild*). In the app, these are `check` with `current`, and with `"fresh": true`, M4.3's forced rebuild.
- **Interrupting.** Esc interrupts a rebuild (§5, *Rebuild*). In the app, that's `cancel`.
- **Suppression.** Suppressing a parent suppresses its children, unsuppressing the parent leaves them suppressed, and unsuppressing a child unsuppresses its parent (§5, *Editing upstream*). In the app, that's `suppress_feature`, with children as Fable's rule defines them.
- **Moving.** A child can't be moved before its parent (§5, *Editing upstream*). In the app, that's `move_feature`'s refusal.

### Saving, undo, and the file (M5.2, M5.4)

- An asterisk beside a document's name means it changed since it was saved (§6). This is `status.transaction.changed`.
- Ctrl+S saves. Ctrl+W closes, asking whether to save a changed document (§6). Section 4 gives the commands.
- Ctrl+Z undoes and Ctrl+Y redoes (§6). These are `undo` and `redo`. The help doesn't list what's undoable (§6). Here, every edit inside the transaction is undoable, a dialog's edits are one step once it's OK'd, and a save ends the undo (pending Trevin, decision 2).
- *Reload* marks a reload that would lose unsaved changes (§6). In the app, that's section 4's choice.
- The unsaved reminder and auto-recover files (§6) are open item 31.

### Selection (M5.7)

- **The mode.** Select is the mode when no command is active, and a command returns to it when it ends (§1, *Hover*).
- **Hover.** The entity under the pointer highlights as the pointer moves over faces, edges, and vertices (§1, *Hover*). The app reads it from the viewport's ID buffer and resolves it to a name at once (M4.6), from the published model.
- **Click.** A click selects the entity under the pointer, in the canvas or the browser, and Ctrl selects several (§1, *Click, Ctrl, Shift*). A plain click replaces the selection, a Ctrl-click toggles one item, and a click on empty space or Esc clears it (open item 24).
- **Browser and canvas.** An item selected in the browser highlights in the canvas. One selected in the canvas expands and scrolls the browser to it (§1).
- **Box selection** (§1, *Box, cross, and lasso*):
  - a drag from empty space draws a box;
  - left to right takes only what's wholly inside, and right to left also what it crosses;
  - in a part, a box takes edges by default;
  - Shift with a box adds, and Ctrl with a box inverts inside it.
- **A drag on geometry** selects what's under the press, and draws no box (§1).
- **Filters** limit what can be selected to their types (§1, *Selection filters*). E filters edges, X faces, and V vertices. F5 shows the filter toolbar, and F6 turns the chosen filters on or off. E, X, and V each toggle their filter in the set (open item 24).
- **Select Other** lists the entities under the pointer in the order they're met, and Tab or the wheel steps through them (§1, *Select Other*). The ID-buffer depth this needs is per docs/study/viewport.md.
- **Stability.** A selection is a list of names with their stability. An element whose name isn't stable can be selected, but anything that would store it refuses it and says why (#196's M5.7; M4.1 section 2).
- **After a rebuild.** A selection survives a rebuild that keeps its names, and is cleared, with a word, when a name is gone (#196's M5.7). The help is silent here (§ *Not covered*).

### Feature dialogs (M5.8)

- A feature's command opens its dialog. OK accepts and closes, Cancel discards and closes, Enter is OK, and Esc is Cancel (§5, *The PropertyManager*).
- The active selection box is highlighted, and its items highlight in the canvas (§5).
- An extrude shows a shaded preview as soon as its dialog opens, and the view can be moved without losing it (§5). In the app, a dialog's edits are made in the transaction, and the preview is the published model as each rebuild lands.
- A slow preview of a fillet or a chamfer can be cancelled with Esc (§5). In the app, that's `cancel` of the rebuild, with the dialog left open.
- A failed preview shows the core's error in the dialog, and the rest of the model still draws. OK is still allowed, saving the feature with its error, as SolidWorks saves a part with rebuild errors (§5, *Errors and warnings*). The help is silent on the dialog itself (§5; open item 25).
- *Edit Feature* opens a feature's dialog, from the browser, the timeline, or the canvas, and OK applies the change (§5, *Editing upstream*).

### Sketching (M5.3, M5.9, M5.11)

- **Automatic relations** (§2, *Relations added while sketching*). As you sketch, the pointer shows the relations that can be created, and with *Automatic relations* on, they're added: horizontal, vertical, coincident, midpoint, perpendicular, tangent. A relation the pointer shows at the accepting click is added. With shared points, a coincident relation is a shared point, never a constraint (D2). Which relations each tool and snap leaves is open item 26.
- **Ctrl** held while sketching suppresses automatic relations (§2).
- **Lines and arcs.** A relation to a line is to the infinite line, and one to an arc to its full circle (§2). That's D4's `on`.
- **Inference lines** are dotted lines from the pointer to existing entities, guiding it to cues such as midpoints (§2, *Inference lines and snaps*).
- **Snaps** are all on by default but the grid, and only the entity being sketched shows them (§2).
- **Definition states.** A sketch and each entity are in one of SolidWorks' states (§2, *Definition states*), as `sketch` gives them. The status bar shows the pointer's coordinates and the state. In the browser, a sketch's name is prefixed `(+)` over defined, `(–)` under defined, and `(?)` not solvable.
- **Colours by state** (§2): under defined blue, fully defined black, dangling olive, a driven dimension gray. The colours of conflicts are open item 28.
- **A dimension that over-defines** the sketch asks whether to make it driven, leave it driving and over defined, or cancel (§2). In the app, a dimension's edit that conflicts is saved as the document holds it (M3.3 reports the conflict as a problem, which `sketch` shows as `over_defined`). The app offers the three: `set_field` of `driving` to false, keeping it, or `undo`.
- **Dragging** (§3):
  - under-defined endpoints and curves can be dragged, with the drag commands;
  - a line's endpoint dragged changes its length or angle;
  - dimensions hold during a drag;
  - *Ghost image on drag* shows where the entity started, and the app draws the begin state faintly.
- **Line** (§4, *Line*). The first click decides the mode: a press and drag draws one line, ended by the release; a press and release goes on clicking a chain of lines. A double-click or right-click > End chain ends the chain and keeps the tool. Esc ends it and leaves the tool. Choosing another tool ends it. A chain's lines share their points (D2).
- **Corner rectangle** (§4, *Rectangle, circle, arc, point*). A press at the first corner, a drag, and a release, or two clicks. Shift held before the release makes a square. It's four lines sharing four points, with horizontal and vertical relations (an unofficial source, §2; open item 26).
- **Circle, arcs, and points** (§4): a circle's centre, then its radius; a centrepoint arc's centre, radius, start, and end; a 3-point arc's start, end, then radius; a tangent arc pressed on an endpoint and dragged; a point at each click, the tool staying.
- **Trim** (§4, *Trim, extend, split*). Power trim trims each entity a drag crosses to its nearest intersecting entity, and Trim to closest removes the entity up to its closest intersection. Both are `sketch_trim`. Power trim's extending is open item 12.
- **Split** (§4). A click on an entity splits it there, and a closed curve needs two split points: `sketch_split`. Selecting a split point and pressing Delete joins the pieces again (§4; open item 12).
- **Delete** (§4, *Delete, and relations*). A relation is deleted by selecting it and pressing Delete: `sketch_remove`. What deleting an entity does to its relations and shared ends, the help doesn't say. Here, it's sketch-edit 7.
- **Editing a sketch** (§5, *Editing upstream*). *Edit Sketch* opens from the sketch, from a feature built on it, or from one of its entities. *Exit Sketch* keeps the changes, and Cancel discards them, which is an `undo` to the revision sketch mode opened at, as M5.8's Cancel is. Exiting rebuilds the part.
- **Dimensioning** wasn't read for the study (§ *Not covered*). M5.11 reads Smart Dimension from the help first (open item 28).

## 10. The viewport, the toolkit, and picking

From Worker 3's studies (#223), cited, not repeated. Each recommendation there goes to Trevin with this design.

- **The viewport** (docs/study/viewport.md). It draws `meshes` with `re_renderer` 0.38.1, from `silico-render`, as one renderer with agents' renders (R1).
  - **The renderer.** silico-render bakes M4.6's camera-fixed light, and the eye offset at `f64` precision, into each vertex for one view. So every orbit rebuilds every mesh: 3.1 ms on CTC 02, the corpus's largest part (664 faces), and 33 ms at 6,640 faces. The study recommends a renderer of Silico's own, through `re_renderer`'s public `Renderer` and `DrawData` traits, with no fork. In it, each face's number goes in the picking layer, the light is computed in the shader, and the eye offset is a per-body transform. Its probe gave per-face IDs at one mesh's cost, matching per-instance picking on every pixel. This is an amendment to M4.6, for Trevin, with the study's alternative beside it.
  - **What Silico draws itself.** Silhouettes and hidden or dashed lines aren't in `re_renderer` (viewport.md, §4).
  - **Picking latency.** Picking results arrive a frame late (viewport.md, §3).
- **Picking** (pending Trevin, decision 4). Per-instance picking passes cost 2.0 ms a frame on CTC 02, against 1.0 ms for one mesh, and 14.6 ms of CPU at 6,640 faces. With the renderer above, per-face IDs cost one mesh's, so decision 4's fallback becomes the plan. M5.7's benchmark measures the frame on the corpus's largest part either way.
- **The toolkit** (docs/study/toolkit.md; pending Trevin, decision 11). `eframe` with `wgpu_no_default_features`, `egui_tiles`, and `egui_kittest`, at `re_ui` 0.38.1's pins: egui 0.36.2, `egui_tiles` 0.17.1, `wgpu` 30. `re_ui`'s style constants are copied with attribution, not the crate: the study's judgement, though `re_ui`'s condition is nearly met. The study adds three `deny.toml` calls for Trevin, as #196's new decision 13:
  - the `wgpu` ban;
  - OFL-1.1, for Inter, plus Ubuntu-font-1.0 if egui's default fonts are kept;
  - RUSTSEC-2026-0370, 0371, and 0372, through eframe's Linux accessibility bridge.
- **Warm start** (pending Trevin, decision 10). The app starts one kernel worker and one sketch worker when it launches, on a thread of their own, never the UI thread. ## 11. Determinism

M4.1 section 10 holds for every new command, with A5.

- **Results** are functions of the files read, the commands run in order, and the model the envelope names:
  - every new command's result;
  - a drag's edit, and a mesh with its key;
  - an undo's restored state, byte for byte;
  - the chain's `rewired` lists, and a suppression's lists, in timeline order;
  - a sketch edit's members, in A5's orders.
- **Diagnostics** are described so in their schemas:
  - a drag's frames;
  - `status`'s `disk` and `drag`;
  - which published revision a published read answers from.
- **The app's own state** (the camera, the order of clicks, a dialog's place) reaches no document. A selection reaches one only as names in an edit.

## 12. Open items, each with a recommendation

Each is pending Trevin. Items 1 to 5 are Fable's (2026-10-27, `~/.cache/silico-review/m5.0-chain-fable.md`), Fable, vetoable. The rest follow the usual rule: SolidWorks' behavior, Fusion's layout, FreeCAD where they're silent, then the recommended option.

1. **Inserting into a chain** (M5.1). *Recommended (Fable, vetoable):* an insert takes its input's consumer's place, rewiring that consumer to it and listing the change in `rewired` (section 7). FreeCAD's `Body::setBaseProperty` does the same, and so does SolidWorks' insert, except that FreeCAD also rewires a base-less feature after the place, which Silico doesn't (A9). Placing only would leave a chain insert to `replace_text`, since no typed edit can do it one step at a time.
2. **Reordering within a chain** (M5.1). *Recommended (Fable, vetoable, with the format review's correction):* a move is a remove followed by an insert, rewiring both chains and listing every change. The parent and child refusals stay. Its first step rewires a `tool` as `remove_feature` does (A9), where Fable's text said a move never rewires one; that text contradicted remove-then-insert. A move never makes a feature another's `tool`, and a move off a tool's chain past its boolean is refused, naming the boolean.
3. **Suppression in a chain** (M5.1). *Recommended (Fable, vetoable):* a suppressed feature passes its base through. A feature that names it only as its `base` builds on the nearest unsuppressed feature up the chain. Only true children go with it: its sketch's users, the features naming its elements, and features left with no body. This is SolidWorks' behavior (§5), and FreeCAD's PartDesign, whose suppressed feature's shape is its base's (`Feature.cpp`, `4d929d3301`). Under #196's rule, suppressing a body's first hole would suppress the rest of the part. A pad or revolve whose whole chain is suppressed builds alone, as in FreeCAD 1.1.3 (the port review's correction to Fable's rule). Where FreeCAD 1.1.3 leaves a suppressed root's features that need a base failing, Silico suppresses them (section 7).
4. **The suppression field** (M5.1, a schema change). *Recommended (Fable, vetoable, with the format review's correction):* `"suppressed": true` on any feature type, immediately after `name`, written only when true and read as false when absent. The reader refuses `"suppressed": false`, so a document has one spelling, as M2.1's D6 writes optional fields omitted. The schema snapshot changes only by that field, and every saved file and the protected `tests/golden/` stay as they are. Always writing it would rewrite every feature line.
5. **`remove_feature` rewiring** (A9). *Recommended (Fable, vetoable):* as section 7. Insert and remove must be inverses through typed commands, and FreeCAD's `removeObject` reroutes alike. Removing a chain's root, which FreeCAD allows (leaving "No base set"), is refused, a stated departure.
6. **Undo's model** (M5.2). *Recommended:* rebuilt from the cache, not kept. Keeping each edit's model would hold up to the stack's depth in B-reps. A rebuild of a state the cache holds runs no kernel step, and gives the same names and fingerprints (invariant 5).
7. **Undo's bound** (M5.2). *Recommended:* 256 MiB of everything the stack's states add beyond what they share, with no count. Each state is its features in shared chunks of 64 (A2), so a step costs its chunk list and the chunks its edit changed. On a 16 MiB document of 50,000 features: the begin's 16 MiB, the first state's 16 MiB, then about 6.3 KB of list and a 21.5 KB chunk a step, so a thousand dragged-arrow values hold about 60 MB, all kept, and the bound holds about eight thousand such steps. An insert, move, or remove near the top of a large document shifts the chunks after it, so it costs nearly a whole copy: sixteen of those on a 16 MiB document fill the bound, and the oldest steps are dropped, counted, with `to` refusing loudly (chunk boundaries that follow features, not places, could lift that later). A bound on whole texts would hold 16 steps of a 16 MiB document, and a count of 100 would let a dialog's Cancel fail after a second of a dragged arrow, which sends an edit a round trip. FreeCAD's default is 20 steps (`MaxUndoSize`, `src/Gui/Document.cpp`), and SolidWorks gives no number (§6).
8. **Undo to a revision** (M5.2). *Recommended:* `to`, as designed. A dialog's Cancel and its one-step undo after OK are each an undo to the revision it opened at, refused loudly if the bound has dropped that state, never undoing less silently. An agent groups its own edits the same way.
9. **IDs a sketch edit makes** (M5.10). *Recommended:* the request's `ids`, or the core's when it's `null`, in `added`'s order, as designed. This follows decision 20 for features, the client's when given, and a replay passes back what it recorded.
10. **A retyped constraint's ID** (M5.10). *Recommended:* it keeps its ID, listed in `modified`. Split's `length` becoming a `distance`, and a merge's `tangent` becoming a `tangent_at`, state the dimension or relation the person placed, in the pieces' terms. Its `value` keeps its meaning. A path to a field the new type hasn't (`constraints.ka000009.line`) is refused loudly. A new ID would make a merge draw a random ID, and `silico fmt --merge-touching` would then write different files on different machines.
11. **Which piece keeps a split or trimmed curve's ID** (M5.10). *Recommended:* the start-side piece, as FreeCAD's first piece keeps its index for naming's sake (`82610ca8fa`, `7d8a8b7cc8`). A circle's ID goes to the arc counter-clockwise from `at.0` to `at.1`. Names made from the curve then follow its start-side piece: a chamfer on the pad's top edge over `na000001` chamfers the half that piece makes, as shortening the line would (N7). That's never silent: the edit's `references` lists every feature storing such a name, and the app shows them. Giving every piece a new ID instead would break every reference to the curve after any split, even where the piece is the part a person meant.
12. **Extend, and joining a split** (M5.10). *Recommended:* both in M5.10, since SolidWorks has them (§4: power trim extends; Delete on a split point joins the pieces). Extend is `sketch_extend`, as sketch-edit 11 has it. Joining is `sketch_join`, of two pieces held collinear (a line's) or sharing a circle (an arc's), with a section added to docs/ports/sketch-edit.md first from FreeCAD's `SketchObject::join`.
13. **A merge that leaves an edge tangency at a shared end** (M5.10). *Recommended:* convert it to a `tangent_at`, its `direction` as last solved, as FreeCAD converts one (`620188073e`) and as sketch-edit 8 has it, rather than refusing it (sketch-edit 10). The port note contradicts itself here, and FreeCAD settles it. Keeping the constraint's ID through the conversion is Silico's own choice (open item 10), where FreeCAD appends a new constraint. Section 13's port of §9's "a merge that would leave an edge `tangent` … is refused" changes to the conversion.
14. **Unjoining at a `tangent_on`'s point** (M5.10). *Recommended:* move its `at` to the new point when its `a` is the detached curve, as FreeCAD keeps an end's constraints with its curve (`delConstraintOnPoint`). Otherwise the gate refuses the result, since `at` would no longer end `a`.
15. **Dragging a sketch that doesn't solve** (M5.3). *Recommended:* refuse only conflicts. Any other failed solve begins from the stored coordinates, as FreeCAD's drag begins from its geometry (`SketchObjectOperations.cpp`, refusing only conflicts and negative freedoms).
16. **The arc centre pin at a shared point** (M5.3). *Recommended:* pin the centre of every arc that starts or ends at the dragged point, weakly (0.01), with the pins given to the worker by the core, and tested against FreeCAD's `moveGeometry`. FreeCAD pins the picked arc's centre. A shared point has no "picked" arc, so all of them are pinned.
17. **Dragging curves and sizes** (M5.3). *Recommended:* in M5.3, since SolidWorks drags a whole line and a circle's edge (§3). Before it's built, a section of docs/ports/sketcher.md is ported from FreeCAD's `moveGeometries` for edges and its relative mode (not yet ported, M3.7).
18. **The drag's commands and the queue** (M5.3). *Recommended:* `drag_begin` and `drag_end` with a cursor queue like any command, as A1 now says. `drag_move` alone runs beside the queue. Running a release ahead of queued commands could save a drag outside the transaction a queued `begin` would open (the architecture review's case). Running a begin ahead of them would let a queued commit end the drag mid-gesture, and lose its release. Queued, both keep section 3's arrival order. Auto-constraints on release are on FreeCAD's main only (`ec298e9e9a`, 2026), not in 1.1, and SolidWorks' help is silent (§3). A join is an explicit `sketch_merge`.
20. **The disk comparison** (M5.4). *Recommended:* bytes, once a second at most, each against a counter of the session's own reads and writes, with a change found outside a transaction reloaded on the session's own thread (A3). Decision 2 compares bytes because times miss changes. Reloading on the session's thread keeps the session's state to one writer, where a read that reloaded would race a queued edit's save and could lose an agent's commit. 21. **A timeline read** (M5.1). *Recommended:* `timeline`, as designed, so the browser and timeline come from a command (invariant 3), not from `outline`'s display text or the model in Rust.
22. **Save As** (M5.4). *Recommended:* `commit` gains `path` (`null` for its own) and `replace`, under decision 35's rules for files a command writes. The session then holds the new path and claims it. SolidWorks has Save As, and decision 3's (a) needs a way to keep edits against a changed file.
23. **Meshes over MCP** (M5.5). *Recommended:* JSON numbers, as designed, with `held`, so a re-read carries only what changed. Agents perceive through `render` and `elements`, and a binary file or an MCP resource would be a second shape for one result.
24. **What SolidWorks' help leaves open on selection** (M5.7). *Recommended:* a plain click replaces the selection; a Ctrl-click toggles one item, as Fusion's Ctrl removes one (fusion.md, *Conflicts and gaps*); a click on empty space or Esc clears it, as in FreeCAD; E, X, and V each toggle their filter in the set, as SolidWorks' filter toolbar is a set of toggles (§1).

26. **Which relations tools and snaps add** (M5.11). *Recommended:* the relations SolidWorks' help lists as added while sketching (§2): horizontal and vertical when a line is within the angle snap of an axis, coincident when a click lands on a point (a shared point), `on` when it lands on a curve, midpoint at a midpoint, tangent for a tangent arc, perpendicular where the pointer shows it. Snaps that only guide add nothing. FreeCAD's autoconstraints add the same set where SolidWorks is silent. The rectangle's four horizontal and vertical relations are as #196's M5.11 has them.

The over-defining dimension's three choices are section 9's. M5.11 reads Smart Dimension from the help before it's built.
29. **Visibility** (M5.4). *Recommended:* the app's view state, not a document field, kept by the app for each file outside the repository. SolidWorks and Fusion keep it in the part, but here a click on an eye would then dirty the document and its diff (principle: git-native), for what doesn't change the part.
30. **A new document** (M5.4). *Recommended:* ask for the path at New, so a session always has a file (M4.1 section 3). SolidWorks asks only at the first save (§6). A session without a file would be a new state for every command, which nothing else needs.
31. **Auto-recover, backups, and the unsaved reminder** (§6). *Recommended:* after M5. A transaction's edits live only in the session until Save, so a crash loses them. That risk is stated in M5.4's walkthrough, and auto-recover is a step of its own after the slice.
32. **A sketch read** (M5.10). *Recommended:* `sketch`, as designed, so sketch mode draws from a command. Without it, the app would read the solves in Rust, and an agent couldn't see what's drawn.
33. **The app's waker** (M5.4). *Recommended:* `Sessions::on_change`, as section 3 has it, plus one idle frame each `DISK_CHECK_INTERVAL`. Redrawing at the display's rate while a long command runs would cost a core for nothing.

  - **Coalescing.** Ten keystrokes in a dialog's value, the first edit held by the fake, make exactly two edits: the one in flight and the newest, and the text then holds the last value.
  - **Cancel.** A dialog's Cancel, after earlier unsaved edits, leaves the text byte for byte as it was before the dialog, the earlier edits kept, and `rollback` isn't called (the call record).
  - **Saving.** An edit marks the tab unsaved, Save writes it, and Revert restores the file's text.
  - **The disk comparison** runs with an injected clock and interval:
    - `disk` is `unchanged` after the session's own commit, including one that lands during a comparison;
    - `unchanged` after a reload;
    - `changed` for a change that keeps the file's size and time;
    - `gone` and `unreadable`;
    - `null` before the first comparison;
    - one comparison at a time, and none started by a `status` within `DISK_CHECK_INTERVAL` of the last's end: the comparison held by its hook while the injected clock moves 0.8 s, then a `status` at its end plus 0.5 s starts none, and one at its end plus 1 s starts one.
  - **Reloading.** An agent's commit reloads the app's document when it holds no edits: the session's own reload, a new revision, with no command from the app, named `reload` in `status.running` while it runs. Comparisons that find the change while that reload waits behind a held command queue no second one. Exactly one new revision results, so the app's next edit, against the revision it read, meets no spurious `conflict`. A second agent commit after the first reload has run is reloaded too, so the queued-reload flag clears. A `set_field` queued while that reload is found (the comparison held by its hook until the edit is queued) applies after the reload, and meets a `conflict` against the reloaded revision. The agent's commit is never written over. With edits held, the reload is offered, and the app's commit is a `conflict` until the app reloads.
  - **The disk read's bound.** A file of 16 MiB is compared; one byte more is `unreadable`.
  - **`format` inside a transaction** accepts drift into its state and writes nothing to the file before the commit (bytes unchanged). With `"write": false`, it makes no revision and no undo step. One that accepts nothing makes no undo step.
  - **Cancelling a render** answers `cancelled`.
  - **Esc's order.** With a dialog open and its preview's rebuild held in the fake, Esc stops the rebuild and leaves the dialog open; a second Esc is the dialog's Cancel; with a drag open, Esc ends the drag first. With a line chain under way and a rebuild held, Esc ends the chain, not the rebuild. With a selection held and a rebuild held, Esc clears the selection; a second Esc stops the rebuild. With edges selected in an open fillet dialog, Esc is the dialog's Cancel, and the selection stays. With only a `reload` running, Esc and the stop do nothing.
  - **The reload's own rules.** A reload queued behind a `begin`, which reloaded the file itself, runs inside the transaction and makes no revision, and `disk` becomes `unchanged`. A file changed again after that `begin` leaves `disk` `changed`. A reload that finds the file as the session last wrote it makes none either, and `disk` becomes `unchanged`. `cancel` naming `reload` is refused, naming `command`, and `reload` is never in `cancel`'s candidates.
- **M5.5:**
  - **The front view.** A box's front-view mesh holds its six faces' triangles, each face named by the element map.
  - **The ladder** (`meshes.rs`'s `mesh_level`):
    - two views within one octave share a mesh;
    - two views an octave apart don't;
    - a half pixel exactly a power of two, and one an ulp under it, take their levels by hand;
    - a floor-raised `deflection` differs from `level`.
  - **One mesh.** A body meshed for `render` and for `meshes` at one view is meshed once.
  - **`held`.** A re-read with `held` carries no arrays for the bodies held.
  - **Published reads.** Eight held published reads, a cached-level `meshes` among them, make a ninth refused, and a slot frees when one finishes.
  - **Without waiting.** A rebuild that publishes a new model is read without waiting on the current one.
  - **Keys.** Every key is equal across the two checked platforms. When the pad's length goes from 40 to 41, body `f0000001`'s key changes, though `f0000001`'s own fields don't, and after an undo it equals the earlier state's key. Each key equals the recompute's key of its body's last step.
  - **`serves`.** At a half pixel of 0.04, `serves` is [0.03125, 0.0625]. In a perspective view of the bracket from eye (100, −100, 100) towards its box's centre (30, 20, 25), at a 30° field of view, 1,024 pixels high: the nearest corner's depth is 117.497 mm and its half pixel 0.030745 (by hand), so `level` is 0.015625 and `serves` exactly [0.015625, 0.03125]. The box's centre would give 0.041311, at level 0.03125, so a build that takes the centre's depth fails. At 1,012 pixels high, the nearest corner's depth gives 0.031110, level 0.015625, where its distance from the eye (118.743 mm) would give 0.031440, level 0.03125, so a build that takes the distance for the depth fails. A body at its floor (a view reaching the eye's plane): the bracket's floor is its box's diagonal × 1e-4, about 0.00878 from OCCT's enlarged box (`mesh_floor`; the tight box gives 0.0087750), whose level is 0.0078125, so `serves` is exactly [0, 0.015625], and a half pixel of 0.016 is served by level 0.015625, its own mesh, not the floor's.
  - **`held`, both ways.** With one body held and one not, only the one not held carries arrays. The same key at another deflection carries arrays. Every held body still carries `faces` and `edges` with their names, and two equal boxes of different IDs carry their own names.
  - **Limits.** `width` 0 and 4,097 are refused. A response past 128 MiB is refused, naming `features` when it holds more than one body, and `width` when one body alone passes it.
