# M5.0 design: the app

**Status: approved.** Its decisions were taken on 2026-10-29 under the maintainer's standing brief (Fable, `~/.cache/silico-review/m5-decisions-fable.md`), each standing unless Trevin vetoes it. Its sources are marked as follows:

- *decision N*: the answers taken to the open decisions of the M5 plan (docs/roadmap/m5-app.md on branch `m5-plan`, #196), by #196's numbers.
- *sketch-edit N*: the sketch edits' rules, which are the recommendations of docs/ports/sketch-edit.md (#208), by that note's numbers, each taken as recommended.
- *Fable*: what this design asked Fable to decide (insert, move, remove, and suppress in a body's chain, 2026-10-27).
- Section 12: what #196 and the port note left open, and what this design found the app forces, each with what was taken.

Like M4.1, this design comes before anything else in M5 is built. It gives:

- the app's state;
- how the app polls its commands without waiting;
- each new command's request, result, and errors as JSON;
- each amendment to an approved M4.1 decision, written as text and marked as an amendment;
- the layout, as docs/ux/fusion.md gives it;
- each tool's behavior, as docs/ux/solidworks.md gives it.

It describes shapes, and changes none: no schema or contract file changes with it. Each step changes its own snapshots and examples with Trevin's approval, as M4.1 section 8 requires. Suppression's field and a sketch's face plane are schema changes, and they go to Trevin with M5.1 and M5.9.

The viewport and the toolkit are Worker 3's studies (#223), cited, not repeated:

- docs/study/viewport.md: `re_renderer`, picking, and what Silico draws itself.
- docs/study/toolkit.md: `eframe`, `egui_tiles`, `re_ui`, `egui_kittest`.

## 1. Scope

The commands M5's steps need, beyond M4's, and the step that builds each:

| Command | Step | What it does |
|---|---|---|
| `add_feature`'s `before` | M5.1 | Adds a feature before another, rewiring the chain it joins |
| `move_feature` | M5.1 | Moves a feature to another place in the timeline, rewiring the chains it leaves and joins |
| `remove_feature`'s `rewired` | M5.1 | Removes a feature its chain passes through, its consumer taking its base (A9) |
| `suppress_feature` | M5.1 | Suppresses a feature and its dependents, or unsuppresses it and what it needs |
| `timeline` | M5.1 | The document's features, structured, each with its health: what the browser and timeline draw |
| `undo`, `redo` | M5.2 | Steps back or forward through a transaction's edits, one at a time or to a revision |
| `drag_begin`, `drag_move`, `drag_end` | M5.3 | Drags a sketch's point or a curve's edge: its frames, then one edit |
| `meshes` | M5.5 | The display meshes of a model's bodies for a view, each face and edge named |
| `sketch` | M5.10 | A sketch as solved: its points and curves, its plane in 3D, each member's definition state, and its profile |
| `sketch_add`, `sketch_remove` | M5.10 | Adds a sketch's members, or removes them with what only they used |
| `sketch_split`, `sketch_trim` | M5.10 | Splits a curve; trims a curve back to its neighbours |
| `sketch_unjoin`, `sketch_merge` | M5.10 | Pulls a shared point apart; makes several points one |
| `sketch_extend`, `sketch_join` | M5.10 | Extends a line's or arc's end, by an increment or to the next curve it meets; joins two pieces on one carrier, split's inverse (open items 12, 12b, 12c) |
| `status`'s `disk`, `drag`, and the transaction's counts | M5.2, M5.3, M5.4 | Whether the file changed on disk; the drag open; the undo and redo left |

Every new command is an MCP tool of the same name with the same shapes (M4.1 section 9), so an agent reaches everything the app does. `timeline` and `sketch` exist for that reason: what the app draws in the browser, the timeline, and sketch mode comes from commands, never from the core's model read in Rust (invariant 3).

M5.9 (sketches on faces, A4, in M5: decision 5) adds no command. `add_feature` and `set_field` take the face plane, as M4.1 section 5 allows. A sketch corner's fillet and chamfer aren't in M5.10 (decision 12). M5.4, M5.6, M5.7, M5.8, M5.11, and M5.12 are the app's own, and add no command. M5.11's sketch tools are headless logic in silico-core (`sketch_tools`: each tool a state machine from the pointer's events to the `sketch_add` its gesture makes), beside the drag client and the selection, with no command of their own: the viewport feeds them points and draws their preview, and sends what they make as a `sketch_add`.

## 2. The app's state

The app is one process, `silico-app`, which holds:

- one `command::Sessions`, whose sessions share its kernel pool, sketch solvers, render worker, and caches, as `silico serve`'s do (M4.1 section 3);
- one tab for each open document.

### What a tab holds

| Held | What |
|---|---|
| The session | Its `SessionId`, and the path it opened, or none for an untitled part (open item 30, overturned): its name "Untitled", then "Untitled 2", and so on, until its first save gives it the file's |
| The model it draws | `Sessions::published(&id)`'s model, read each frame, and its revision (decision 33) |
| Its meshes | The newest `meshes` answer, each body's mesh by its key and level, uploaded to the GPU once (M5.6) |
| Its status | The newest `status` answer: revision, transaction, rebuild, drag, and disk |
| The timeline | The newest `timeline` answer: the features, their health, the bodies (M5.4) |
| The sketch open | In sketch mode, the newest `sketch` answer (M5.11) |
| The selection | A list of element names, each with its `stable`, as an agent could write them (M5.7) |
| The commands under way | Each command's `Running` handle, and what it's for (section 3) |
| The dialog open | The feature dialog's inputs, and the revision it opened at (M5.8) |
| The drag | The drag open, if one is, and the newest frame drawn (M5.3) |
| The camera | The viewport's camera: the app's own, never a command's (decision 29) |

Each of these answers is of a revision, and the app draws each one as of its own revision, never waiting for them to agree. A frame can draw revision 8's published model under revision 9's timeline. The timeline marks a feature newer than the model as health `unknown` (section 7, `timeline`), and the rebuild indicator says a rebuild is running. This is what decision 33 allows: the app reads `published`, and never stalls.

### The unsaved state (decision 1)

The app keeps its unsaved changes as a transaction, begun at a document's first edit, not when the document opens.

- **No edits held** (no transaction open): the session reloads what an agent commits, on its own thread, once a disk comparison finds the file changed (section 4; A3), as decision 2's reload, without waiting for a command.
- **Edits held** (a transaction open): the document is unsaved, and its tab carries an asterisk, as SolidWorks marks a changed document (docs/ux/solidworks.md, §6). Its file isn't reloaded (M4.1 section 4). `status.disk` says whether the file changed on disk (section 6), and the app offers what decision 3 says (section 4).
- **Save** is `commit`. **Revert** is `rollback`. **Close** asks if the tab holds edits, then rolls back and closes. Decision 22 refuses `close` inside a transaction.
- **A dialog's edits** are made inside the same transaction. The dialog's Cancel is `undo` back to the revision the dialog opened at (`"to"`, section 7), never `rollback`, which would drop the unsaved edits made before the dialog (M5.8). Cancel waits for the dialog's queued edits to answer first, so the revision it sends is the newest, not one decision 12 refuses as a `conflict` (#273). After OK, the app's Ctrl+Z undoes the dialog's edits as one step, as SolidWorks undoes a feature's edit: an `undo` to the revision the dialog opened at.

The tab is unsaved when `status.transaction.changed` is true (section 6). After undoing back to the state `begin` saw, it's false, and the asterisk goes.

## 3. The frame loop: polling, never waiting

The UI thread calls only what answers at once. M4.1 section 3 names these:

- `Sessions::published(&id)`;
- `status` and `read_logs`;
- the `Running` handle's `try_take`, `progress`, and `cancel`.

Every other command is started on the UI thread and runs off it. It returns a `Running` handle before its file read, gate, rebuild, save, or export. Each frame:

1. **Status.** For each tab, `status`, which reads only what the session holds, and `Sessions::published(&id)`.
2. **Results.** Every `Running` handle is polled with `try_take`. A finished command updates the tab's state, and a refusal shows its errors where SolidWorks shows them (section 9). A handle that isn't finished is left for the next frame. The app never calls `wait` or `wait_timeout` on the UI thread.
3. **Input.** Each user action starts its command and keeps the handle.

### Waking without input

The app draws a frame only when something changed. It doesn't redraw continuously while a long command runs.

- **The core wakes it.** `Sessions` takes a waker, `Sessions::on_change(Box<dyn Fn() + Send + Sync>)`. The core calls it when:
  - a `Running` answers;
  - a rebuild publishes a model;
  - a disk comparison ends;
  - a rebuild step settles, for the progress `status` reports;
  - the session reloads its file at a new revision (section 4).

  The app's waker asks the toolkit for a repaint (per docs/study/toolkit.md). The core calls it only once the answer can be taken (after the `Running`'s reply is sent), with no lock of the core's held, so the next frame's `try_take` finds it. It's called off the UI thread, and must only ask, never draw. A comparison's end wakes the app only if its finding changed.
- **Idle.** With nothing pending, the app asks for one frame each `DISK_CHECK_INTERVAL` (1 s). That frame's `status` starts the next disk comparison (section 4), so an agent's commit is found without the mouse moving.
- **During a rebuild,** the waker fires as each step settles. Progress (`status.rebuild.done`) redraws then, not at the display's rate.

### When the app reads

- **The model to draw** is the published one, read each frame.
- **The timeline** is read whenever the revision or the published revision changes (`timeline`, from the published model), including after the session reloads a file changed on disk (section 4). The browser, the timeline, and the error marks are drawn from it. The details of the problems are read with a published `check` when the person opens one (M5.4).
- **Meshes** are read when:
  - the published revision changes;
  - the view settles at a half pixel outside a body's `serves` (orthographic);
  - the camera settles after a move (perspective).

  Each read lists the meshes the tab already holds (`held`), so only new or changed bodies carry arrays. Until it lands, the viewport draws the meshes it has (M5.6). The tab keeps at most one `meshes` read in flight, and uploads each body's buffers once, by its key and level.

  *As built (M5.6):* `serves` is the rule in both projections: a perspective view, once settled, reads again only when a body's half pixel at its meshing depth leaves its `serves`, which covers "after a move" without a read that would answer the same meshes. The half pixel is computed on the camera the core levels with (`AnsweredCamera::of`, rounded to the nanometre), and the read last answered is never asked again, so a view at a level's edge can't read for ever. The first read asks for Home's view, fitted by the core, and the tab takes its camera; with no box to fit (no body, or one unmeasured) the tab keeps Home of a 100 mm cube about the origin. A refusal of what was asked (its view, camera, size, or features, an eye inside a solid) isn't asked again until something differs; one of the moment (`worker_crashed`, `worker_timeout`, `internal`, too many published reads) is asked again after 0.25 s, doubling to 8 s, woken by a frame asked for then; while it waits, the backoff holds back every read of its revision, the view moving or settled (a wheel's every notch settles it), and at its time the view as it is then is read; a new revision is read at once. The delay grows with each refusal of the revision in a row, and a retry that falls due with the view at rest and no read wanted ends the run, so the next refusal waits the shortest delay again; one falling due mid-move leaves it growing. Each refusal is said once a revision. A view's least is by the bodies drawn, a body with no box by its mesh's extent, as the renderer measures the reach; a body shown again raises the view to the least it then allows. An orthographic view is never under the least its bodies' reach from its target allows (`views::least_view_height`): a zoom stops there, and a view under it when new bodies come is raised to it. A read past 4,096 pixels on its longer side is scaled by one factor, keeping the view's shape. One renderer serves the app: a tab switch forgets every body and uploads the shown tab's. A body's first upload, and each mesh that replaces it (every preview's), is made whole on the UI thread; M5.7's benchmark times it at 10 × CTC 02.
- **The sketch open** is read with each revision while sketch mode is open (`sketch`, `current`), so a dimension's edit redraws its sketch as solved.
- **Pre-selection and the Measure tool** read the published model (`elements`, `query`, `distance`, `angle`), as decision 33 intended. A picking read arrives a frame after the frame that asked for it (docs/study/viewport.md, §3), so hover lags the pointer by a frame.

### Bursts of edits

The session's queue is unbounded (an M4 low, #196's *What M4 leaves for M5*), so the app never queues edits one by one.

- A tab has at most one edit in flight.
- An edit made while one is in flight waits in the tab, and a newer edit of the same field replaces it (typing in a dialog's value box, say).
- When the edit in flight answers, the waiting one is sent, against the revision the answer gave (decision 12).
- A drag's moves are coalesced the same way, in the core (section 7, `drag_move`).

### Stop, and the rebuild indicator

- **The indicator** is `status.rebuild` (M4.1 section 9's table): `done` of `steps` while a rebuild runs, its state otherwise.
- **The stop button** is `cancel` naming `rebuild`, on while `status.rebuild.state` is `running` (decision 34, as amended 2026-10-31): one rule, whatever `status.running` is. The command waiting on the rebuild, if one is, stops with it and answers `cancelled`; a published read running goes on. A dialog preview's stop is the same call (its `timeline` read of the current model is the waiter, and answers `cancelled`). A command running with no rebuild (an export meshing) is its own dialog's to stop (M5.12), not the status bar's. Esc does the same, as Esc interrupts a SolidWorks rebuild (docs/ux/solidworks.md, §5, *Rebuild*), but only when nothing nearer takes it. Esc goes to the first of these that's there: an open or queued drag (`drag_end` with `null`); a sketch tool's chain under way, which it ends, leaving the tool (§4); a dialog's preview rebuilding, which it stops with the dialog left open, as SolidWorks stops a slow preview (§5); an open dialog (its Cancel); the purple banner of a reload with nothing held, which it dismisses, its marks staying (section 4; DESIGN.md, 6c, the prototype's `escChain`); the selection, which it clears (section 9); the stop. The stop and its button are off while no rebuild runs, a `reload` among what runs then, which `cancel` doesn't take. **Rebuild** (Ctrl+B, and a button beside the stop) starts a stopped rebuild again, as SolidWorks' Rebuild follows an interrupt (docs/ux/solidworks.md, §5, *Rebuild*): a read of the current model, whose rebuild takes what was built before the stop from the cache. It's on only while the tab's revision's rebuild is stopped; meanwhile nothing reads that revision's current model (which would undo the stop), and a pane with no timeline yet says "Rebuild stopped" where it would say it's building. An edit, which makes a new revision, rebuilds too.
- **The rebuild's time** (*amended*, #421; Fable's decision of 2026-11-09): the status bar's "Rebuilt · revision N · 84 ms" and an up-to-date preview's "Preview up to date · revision N · 84 ms" are the core's `elapsed_ms` for the revision's last rebuild done whole (every step settled, no feature left queued or running), never another rebuild's. A save's revision (its model rebound) and a rollback's (its model kept) say no time: `status` gives none for them, and its null says nothing was rebuilt; another rebuild's time would misreport that. The prototype's bar keeps its last rebuild's time, since its save makes no revision and its Cancel rebuilds.
- **A cancelled render** answers `internal` today (M4.6's open item). M5.4 makes it `cancelled`.
- **A feature dialog's preview, as built (M5.8).** While a dialog is open on its feature, the tab reads `timeline` of the current model, not the published one, so the browser and the timeline show the preview's health. That read waits for the revision's rebuild, which the per-frame `published` read starts. Esc stops the rebuild with the stop's own call, `cancel` naming `rebuild`, and the read, its waiter, answers `cancelled`. The stop cancels the tab's reads of the model (its `timeline` read, and a `check` of the current model) through their handles first: one still queued behind another command isn't the rebuild's waiter yet, and, run after the stop, would start the rebuild again, as the next command that needs the model does (decision 34). The one sent later is cancelled first: the session runs its queued commands in the order sent (a read of the published model runs on a thread of its own and waits on no rebuild), and the earlier read, the rebuild's waiter, cancelled, stops the rebuild and answers at once, its session going straight on to the next in its queue, which, not yet cancelled, would start the rebuild again. A stop that finds the rebuild ended (it published since `status` said it ran) stops nothing, and the Esc goes on to the dialog's Cancel; so does an Esc after an edit in the same frame, whose cancel of the read already stops that rebuild. The tab then reads no current model of that revision while `status` says its rebuild is stopped, so the stop holds until the next edit. Anything the tab sends that changes the document (an edit, an add, an undo or redo, Cancel's undo or rollback, Revert) first cancels its reads still in flight, the `timeline` read and a `check`, the one sent later first, so the change doesn't wait for a rebuild of a revision it makes old: a check left queued behind the read would start that rebuild again once the read stopped it. While the read waits, `status.running` is `timeline`.
- **A dialog's Cancel, as built (M5.8).** Cancel is `undo` with `to` set to the revision the dialog opened at, so edits made before the dialog stay. When the dialog's own edits began the transaction, nothing came before them, so Cancel is `rollback` instead. That leaves no empty transaction open, so the session reloads a change made outside it (section 4). Section 9's "never rollback" is about keeping earlier edits, and in this case there are none.

### How this is tested (decision 7)

- **The frame counter.** It keeps climbing while the fake kernel holds a request, and the panels keep answering. Each of these is held in turn:
  - a rebuild (M5.4);
  - a `meshes` read (M5.6);
  - a `timeline` read (M5.4);
  - a drag's move in the fake sketch worker (M5.3, M5.11);
  - an export (M5.12);
  - a disk comparison, through a test hook that holds it while `status` keeps answering (M5.4).
- **Waits on the UI thread.** A frame counter can't see a short wait. A `wait_timeout(15 ms)` in a frame still lets frames climb. So in the app's tests the UI thread is marked, and `Running::wait` or `wait_timeout` called on it fails the test. That makes the rule structural, not timed.
- **Driving the app.** It's driven through `egui_kittest`'s accessibility tree, with no GPU (docs/study/toolkit.md, §4):
  - each `egui_tiles` pane has an accessible label;
  - frames are stepped with `step` and `run_steps` while a command is held, since `run` refuses a UI that keeps repainting;
  - a click in the viewport takes the `wgpu` feature and lavapipe on CI, and a test that doesn't need the pixel selects by name.
- **The viewport** is checked through its ID buffer against projections by hand, as M4.6's tests are. Screenshots are never compared with stored images.
- **The waker.** Its rules are checked from inside the callback: a test's waker calls `try_take` on the handle that answered, which must give the answer, and `status` on the same session under a timeout, which deadlocks if the core held a lock while calling. A test counts repaint requests: one when a held command answers (and its `try_take` in that frame takes it), none while nothing is pending, one idle frame per `DISK_CHECK_INTERVAL`, one more only when a comparison's finding changes, one as each step of a held rebuild settles, and one when the session reloads.

*Paths, as built:* Open (Command+O, File > Open…, and the start page's Open…) goes straight to the platform's own open panel, and Save As (Command+Shift+S, File > Save As…, and an untitled part's Save) to its save panel, with no question of the app's first: NSOpenPanel and NSSavePanel, sheets on the app's window on macOS (that window given to rfd as the parent, since without one rfd takes `NSApp`'s main window, none while the app isn't active, or else the first in its list, which isn't the one drawn), brought to the front with the app made active when the window isn't focused; the XDG desktop portal on Linux. Open's pick opens, as a typed path does; Save As's is saved as, with `replace: true` (the panel asked about replacing). A cancel does nothing, but a cancelled Save panel that was to close its document refuses the close (a quit stops). The question of a typed path, with a Browse… of its own, is the fallback: for a client without native dialogs, a panel that won't open (on macOS, a window with no handle), or an Open or Save As asked while another native dialog is open. Export's path field has a Browse… beside it too. Each is filtered to `.silico` (Export's to `.3mf`, and `.step` and `.stp`, the format chosen first) and starts in the document's folder, or else the folder last picked in. The frame polls the dialog's future, never waiting on it (invariant 4), and its answer wakes egui for the frame that takes it. Browse…'s pick fills its field (the typed Open's opens the file), and the dialog's own Save or Export (and Replace) goes on as for a typed path; Export's format follows a picked path's extension. Nothing changes for an answer whose question has closed meanwhile, nor Export's while its export runs or asks whether to replace, nor a Save panel's whose document has closed or is closing. The typed path stays, for a client without dialogs. A field in a modal is drawn as the prototype's Modify box draws its value (`.modify-box input`: Gray.150 in a Gray.350 border), not as its `.field` (Gray.200 with no border at rest), which on a modal's Gray.200 shows nothing at rest, a clash in the prototype itself; fields on the panels are its `.field`.

### A file changed on disk (decisions 1 and 3)

Live co-editing follows decision 30's (a) for M5 (decision 3). A person and an agent share a part through its file, not at once.

- **With no edits held,** the session reloads the file itself: a comparison that finds it changed queues the reload on the session's own thread (A3), so the session's state has one writer. The app sees the new revision in `status`, and reads `timeline` and the published model again, as for any revision. No published read reloads anything (M4.1 section 4).
- **With edits held,** `status.disk` says `changed` (or `gone`), and the app offers two choices:
  - **Reload**, dropping its edits: `rollback`, after which the next command reloads.
  - **Keep its edits**: its `commit` is refused as a `conflict` (decision 2) until it reloads, or saves elsewhere with Save As (open item 22).

  *Show changes* (DESIGN.md's 6d; Fable's decision of 2026-11-04, *6d's other half*) lists both halves before the person chooses, each from its own `diff`, each answered or refused on its own: "Their change (on disk)", `diff` from the transaction's `base` to `"disk"` (the file as the core reads it then, inside the transaction, reloading nothing and touching no edit), and "Your unsaved edits", `diff` from `base` to the session's revision now. Neither moves the session's revision, pushes an undo state, or changes `status.disk`. A `"disk"` side that doesn't read as a document says the reader's message in its section; a file `gone` offers no Show changes. 6c's banner, with no edits held, asks `diff` with both numbers it saw (`from` the revision replaced, `to` the one reloaded), which reads nothing of the file, so a write landing after the reload never refuses it.

  SolidWorks' *Reload* likewise marks a reload that would lose unsaved changes (docs/ux/solidworks.md, §6). Its help says nothing about another program changing a document open for writing (§6), so the choice offered is decision 3's.
- **The comparison runs off the UI thread.**
  - `status` answers from the session's last comparison, and starts the next if none is running and the last ended at least `DISK_CHECK_INTERVAL` ago.
  - It compares bytes, not times, as decision 2 does, reading the file whole as the session reads a document (at most `MAX_INPUT_LEN`, 64 MiB), so a file the session opened is never `unreadable` for its size. The read isn't chunked (#267). A read that stalls is logged, and `disk` keeps its last finding (open item 20).
  - Each comparison records which of the session's reads and writes it compared against, by a counter the session advances at each one, never by the bytes (two of the session's own saves, A then B then A again, would match by bytes). A result whose counter is no longer the session's (its own commit landed meanwhile) is dropped, never reported. So the session's own Save never reads as a change on disk.

### The chain (Fable)

Every rule below follows from one: **the `base` links in the text are each body's chain, exactly as written.**

- Insert, move, and remove edit the chain in the text, and report every reference they rewire.
- Suppression never rewrites a reference: the rebuild skips the links it marks.
- Every rule is a function of the text: chains by `base` links, consumers by the gate's one-consumer rule, makers of a stored name by parsing it. No geometry decides any of them.

This is what FreeCAD's PartDesign does on its `BaseFeature` chain (`Body.cpp`'s `setBaseProperty` and `removeObject`; `Feature.cpp`, where a suppressed feature's shape is its base's), except where A9, `move_feature`, and `suppress_feature` state a departure, and it gives SolidWorks' behavior: later features build on the body as the earlier ones left it (docs/ux/solidworks.md, §5).

A **rewired** entry is `{"feature", "field", "from", "to"}`: a feature whose `base` or `tool` an edit changed, which the edit reaches (decision 28). `from` or `to` is `null` where the feature had no base or is left with none (a pad placed before its chain's root, or a pad root's consumer, a pad, after the root is removed). Each result lists them in timeline order, after the edit.

### `move_feature` (M5.1)

A move of `F` before `T` is a remove followed by an insert:

1. `F`'s consumer, if it has one, takes `F`'s `base`, as `remove_feature` rewires it (A9), whether the consumer named `F` as its `base` or its `tool`. If `F` is a chain's root and its consumer needs a base, the move is refused, naming both.
2. `F`'s `base` becomes the last member of its chain before the new place, or none for a pad or revolve placed before the chain's root. A primitive takes no base, so a move that would give one a base is refused, naming it.
3. The chain's next member after that place takes `F` as its `base`. A move never makes `F` another feature's `tool`.

Rules:

- A move that leaves `F` between its base and its consumer rewires nothing.
- A move that takes a feature off a tool's chain (one a boolean consumes as its `tool`) to a place past that boolean is refused, naming the boolean: the chain it would join has no member to give it as a base without a second consumer. Within the tool's chain, a move is as above.
- A child can't be moved before its parent (docs/ux/solidworks.md, §5, *Editing upstream*). FreeCAD's move (`CmdPartDesignMoveFeatureInTree`) is a remove then an insert too, and lets a chain's root move, leaving a feature that needs a base failing; Silico refuses that move, as A9 refuses the removal. So the gate still refuses a move that puts a feature:
  - before its sketch;
  - before a feature whose elements it names;
  - after a feature that names its elements or uses it as its sketch.

  Each refusal names both features. The two refusals for named elements are cases of the lineage rule below (`lineage_broken` in `document::chain`), so they may go, their tests kept, the message becoming the lineage one (open item 2b).
- After a move, every maker of a feature's stored names must still be in what its base is built from: its base, and that one's inputs and sketches, transitively. A move that breaks this is refused, naming the feature and the maker (open item 2b). Move and remove check it from text alone; a document that reaches the state another way fails the feature at rebuild with `reference_broken`.

Request: the feature, and the feature to move it before (`null` for the end).


Result: where it was and where it is, from 0 (`to` counted after the move), what it rewired, whether the document changed, and the commit's result outside a transaction. ### `suppress_feature` (M5.1; Fable)

**What's suppressed.** Suppression behaves as SolidWorks' does (docs/ux/solidworks.md, §5, *Editing upstream*): suppressing a parent suppresses its children, and unsuppressing a child unsuppresses its parent. In Silico's terms:

- A suppressed feature isn't built.
- A feature whose `base` or `tool` names a suppressed feature builds on the nearest unsuppressed feature up that input's chain: its **effective base**.
- A body is the result of a built feature that nothing built consumes.

**Dependents.** A dependent of `X` is suppressed with it. Taken to a fixed point in timeline order, the dependents are:

- a feature whose `sketch` is `X`;
- a feature that stores an element name one of whose makers is `X` (a fillet's or chamfer's `edges`; A4's face): every feature ID in the parsed name, with modified names counted as their source;
- a feature one of whose inputs it needs has no unsuppressed feature up its chain. A pad's or revolve's base is optional (it can begin a body), so with its whole chain suppressed it builds on nothing, alone, as FreeCAD 1.1.3 builds it (`FeatureExtrude.cpp` takes the prism alone when the base is null) and as SolidWorks keeps a boss that isn't another's child (§5). A pocket's, groove's, fillet's, chamfer's, or boolean's inputs are needed.

The gate refuses a document in which a dependent of a suppressed feature is unsuppressed, naming both.

**Unsuppressing.** Unsuppressing `X` also unsuppresses, recursively, what `X` needs and lacks:

- its sketch;
- each suppressed maker of a name it stores;
- for an input it needs (not a pad's or revolve's base, which is optional) whose chain holds no unsuppressed feature, that chain's root.

What depends on `X` stays suppressed.

**Fingerprints (A10, as amended).** A suppressed feature's stored fingerprint is carried as stored, never checked or rewritten, so the file's diff for a suppression is the `suppressed` line and the fingerprints of what builds on another base now. Suppression reaches every unsuppressed feature that uses `X`, refingerprinted as they build on another base, so a suppressed file still checks clean. Unsuppressing `X` reaches it, so its next save writes its fingerprint fresh, and a suppress then unsuppress, committed, gives the file byte for byte as it was.

**FreeCAD.** In 1.1.3, a suppressed feature's shape is its base's (`Feature.cpp`, `4d929d3301`), as here. A suppressed root stays suppressed with a null shape: a feature after it that can begin a body (a pad) builds alone, as here, and one that needs a base fails: a through-all pocket ("Base feature's TopoShape is invalid"); a pocket of a set depth builds its tool alone instead, which docs/ports/suppression.md, written with M5.1, records. `2a541c9536` removed the older branch, `86e75037d9`'s, in which a suppressed root unsuppressed itself. Silico suppresses the features that need the base instead, a deliberate departure: a feature that can't build is suppressed with its cause, not left failing.

**In the document,** a suppressed feature carries `"suppressed": true`, immediately after `name`, a schema change in Trevin's batch of protected changes (open item 4). The file reader refuses `"suppressed": false`, naming the field, as M2.1's D6 writes optional fields omitted, never as their absent value. `false` is taken only by `suppress_feature` and `set_field`.

Request: the feature, and whether to suppress it.

```json
{"session": "s1", "revision": 12, "feature": "h0000001", "suppressed": true}
```

Result: the features this edit suppressed and unsuppressed, in timeline order and including the feature itself; whether the document changed; and the commit's result outside a transaction. `h0000001` alone is suppressed: `h0000002` builds on `p0000001`, and the volume is 20,977.019 mm³. A commit then writes `h0000002`'s and `f0000001`'s fingerprints, and carries `h0000001`'s as stored (A10, as amended).

```json
{"feature": "h0000001", "suppressed": ["h0000001"], "unsuppressed": [], "changed": true, "commit": null}
```

Suppressing a sketch suppresses what's built on it. Unsuppressing that feature then unsuppresses its sketch:

```json
{"session": "s1", "revision": 12, "feature": "s0000002", "suppressed": true}
```

```json
{"feature": "s0000002", "suppressed": ["s0000002", "h0000001"], "unsuppressed": [], "changed": true, "commit": null}
```

```json
{"session": "s1", "revision": 13, "feature": "h0000001", "suppressed": false}
```

```json
{"feature": "h0000001", "suppressed": [], "unsuppressed": ["s0000002", "h0000001"], "changed": true, "commit": null}
```

Suppressing a feature already suppressed, or unsuppressing one that isn't, changes nothing: `"changed": false`, both lists empty, no new revision. Reading a suppressed feature's solid (`elements` with its ID) is refused, `invalid_input` naming `feature`, saying it's suppressed. Errors: a feature the document hasn't, and a stale revision.

### `timeline` (M5.1)

The document's features as the browser and the timeline draw them, structured, so no client parses `outline`'s text (decision 33, A8).

- **The features** come from the session's document at its revision.
- **Each feature's health** is the one the named model gave it, in Fusion's health states (docs/ux/fusion.md, *The timeline*): `healthy`, `warning`, `error`, `suppressed`, or `unknown`. A feature the model's revision doesn't have, or one the model hasn't built yet, is `unknown`.
- **A refused document:** with the gate's refusal, `features` is the document as read, every health is `unknown`, and the result's `problems` is the gate's count (0 for a document the gate took). Under an older published model, it answers that model's revision and bodies, so the browser's bodies match what the canvas still draws; with nothing published, `model_revision` is `null` and there are no bodies. A refused document whose ID is used twice lists both entries, so a client mustn't key entries by ID while the gate refuses it. If the text doesn't read as a document, `features` is `null`, and `problems` is the reader's count.
- **Before the first rebuild publishes,** a published timeline of a valid document is refused, naming `model`, so the app's bar shows that it's building rather than an empty browser.

### `undo` and `redo` (M5.2; decision 2)

These work inside a transaction only.

- **`undo`** restores the state before the transaction's last edit not undone, or, with `to`, the state at that revision, undoing every edit after it.
- **`redo`** restores the state after the last edit undone, or, with `to`, redoes up to that revision.
- Each is at a new revision equal to that state, as `rollback` restores at a new revision.

**What's an edit.** Any command that changed the transaction's document (`"changed": true`), each one step:

- the typed edits and `replace_text`;
- `add_feature`, `move_feature`, `remove_feature`, and `suppress_feature`;
- `drag_end`;
- the sketch edits;
- `format` inside a transaction (A6).

Every edit is its own step, never merged with the one before: a client that wants a run of edits undone as one (a dialog's arrow dragged, its Cancel, its Ctrl+Z after OK) undoes `to` the revision the run began at. An edit after an undo drops the redo states. A commit or a rollback empties both stacks.

**What's restored.** The text, byte for byte. What the edits had reached is worked out again from it and what the transaction holds fixed, so it's exactly what it was; the checked form is made again by the gate, which gives the same one. The model is rebuilt, its steps found in the cache, so its names and fingerprints equal the earlier state's (invariant 5; open item 6).

Request: the session, the revision the client last saw (decision 12), and `to`: `null` for one step, or for `undo` an earlier revision the stack holds, for `redo` a later one it holds. A `to` on the wrong side, or the session's own revision, is refused, naming `to`.

```json
{"session": "s1", "revision": 15, "to": null}
```

Result: the revision whose state is restored, what's left to undo and redo, and `dropped`: how many more of the transaction's edits this step left out of undo's reach, the bound (section 6) having dropped the oldest states after `begin`'s, never the session's current state. It counts as `status.transaction.dropped` does, 2 at the first drop (`begin`'s edit and the dropped state's) and 1 for each state after, so a step that drops one state when none was dropped before says 2. An undo can hold more than the edit it undoes (a state that shares nothing, after an insert near the top), so it can drop states as an edit does. The envelope's revision is the new one. Here, `begin` came at revision 12 and three edits made revisions 13, 14, and 15, so one undo restores revision 14's state, as revision 16:

```json
{"restored": 14, "undo": 2, "redo": 1, "dropped": 0}
```

A dialog opened at revision 13 and cancelled at 16 undoes to it: `{"session": "s1", "revision": 16, "to": 13}`, restoring 13's state.


Its candidates are the revisions of the states the same command can restore, each a `to` it takes: for `undo`, those before the session's state that undo reaches (here 12's and 13's: 14's is the session's, as revision 16, and 15's is after it); for `redo`, those after it. ### `drag_begin`, `drag_move`, `drag_end` (M5.3; decision 9)

A drag of one of a sketch's points, through the sketch worker's drag session (M3.7). With shared points (D2), every point a drag takes is a point by its ID: a line's end, an arc's start, end, or centre, a circle's centre, a lone point.

- **What it pins.** The dragged point. For each arc whose start or end is that point, the drag also pins the arc's centre where it starts, a hundred times more weakly, so the end moves before the centre (FreeCAD `4d7a9435c1`, `Sketch.cpp`'s `initMove`, which pins the picked arc's centre). A point that ends two arcs pins both centres. M3.7's `DragBegin` pins an arc's centre only for `PointOf::Start` or `End`, so M5.3 gives it the pins from the core (open item 16).
- **Dragging an edge** (open item 17; docs/ports/sketcher.md, *Dragging an edge*). A press on a curve rather than a point drags the curve. A line moves whole: both of its points pinned at full weight, each moved by the cursor's offset from the press, as FreeCAD's relative drag moves it, so a neighbour sharing an end follows. A circle's or an arc's edge sizes it through the cursor: a target held on its circle at full weight, moved to the cursor, and its centre pinned where it starts at 0.01. A release at the press is a click: the begin state is kept, with no edit, as for a point released where it began. Every frame and the end are functions of the begin state, the press, and the cursor alone.
- **When it ends.** A drag's commands follow A1. A drag ends at `drag_end`, at any new revision of the session (an edit or a reload), when the session closes, or when its worker restarts. A move after the end is refused, and the client begins again.

#### `drag_begin`

Request: the sketch and the point, or the sketch, a curve, and `press`, where the press on its edge landed, in the sketch's coordinates (two `Coordinate`s, M3.2's D3). It carries no revision: it queues (A1), and drags the sketch as the session holds it when it runs, the revision the envelope names, which `drag_end`'s edit is made against.

```json
{"session": "s1", "sketch": "s0000001", "point": "pa000003", "curve": null, "press": null}
```

```json
{"session": "s1", "sketch": "s0000001", "point": null, "curve": "na000001", "press": [30, 0]}
```

*As built (M5.3):* every field is given, `null` where it doesn't apply, as M4.1's *Requests are strict* has it: `point`, or `curve` and `press`. Not two shapes: an MCP tool's input schema is one object, and agents' clients refuse a choice at its root (`anyOf` or `oneOf`). The result and `status.drag` give the same three fields.

The begin state is the revision's solve of the sketch. If the session's current model already holds it (the revision's rebuild solved it), that's taken. Otherwise the drag's sketch worker solves the sketch from the revision's text, in FreeCAD's order (M3.3), under `SKETCH_TIMEOUT`, never waiting on the revision's rebuild. A sketch whose constraints conflict is refused. One whose solve fails otherwise begins from its stored coordinates, as FreeCAD's drag begins from its geometry (open item 15).

Result: the sketch's degrees of freedom left, and the points of the part the drag moves, by ID. Every other point stays where it began. `moves` is a diagnostic (A5).

The app projects its pick onto the exact curve before it sends it, since a pick lies on the curve's tessellation, not on the curve. A feature that isn't a sketch is `invalid_input`, naming `sketch`. A suppressed sketch is `invalid_input`, naming `sketch`.

#### `drag_end`

Request: the final cursor, or `null` to end the drag with no edit (Esc).

```json
{"session": "s1", "to": [62.5, 7]}
```

**How it solves.** With a cursor, it queues as an edit (A1). It's a function of the begin state and the final cursor alone (A5):

1. From the begin state, the sketch is moved to the final cursor. If the newest solved move had a cursor of the same bits, its values are taken and no move runs again.
2. The sketch is then solved as a whole, as M3.7's closing solve is, under `SKETCH_TIMEOUT` (A4).
3. Its points' coordinates, as solved, become the sketch's (M3.4).
4. The edit goes through the gate, at a new revision, and is one undoable edit. As every edit that writes geometry is (*The sketch edits*), the sketch's solve as the edit writes it then judges it: one whose solve is worse than the sketch's before the drag is refused, "after the drag, ...", the document as it was; a problem the sketch had already isn't the drag's. For a drag, worse is a redundancy its solve flags that the solve before didn't: the drag's own solve (step 2) already keeps the begin state for a conflict, a failure, or a result the file can't hold, and the file it writes solves as that solve did (M3.4).

If the final move fails, the begin state is kept, and the result says so. This is FreeCAD's `commitDragMove`, and it replaces M3.7's closing solve from the last good frame. docs/ports/sketcher.md's divergence note changes with M5.3. Dimensions hold during a drag, as SolidWorks' do (docs/ux/solidworks.md, §3), since the drag pins its point below every constraint. The release adds no relation (open item 19).

Result: the sketch, which state was kept (`cursor` or `begin`), whether the document changed, and the commit's result outside a transaction.

```json
{"sketch": "s0000001", "kept": "cursor", "changed": true, "commit": null}
```

```json
{"sketch": "s0000001", "kept": "begin", "changed": false, "commit": null}
```

With `"to": null`, it queues as the begin did (A1) and ends the drag with no edit: `kept` is `begin`, and nothing changes. A move still solving then is stopped by restarting the drag's worker, as `cancel` of `drag_move` stops it, so the session's queue never waits on a move; that move answers `cancelled`, which the app drops without a word. Queued behind a command that waits for a rebuild (a `commit`), it waits for that command, not for a rebuild of its own. Errors: no drag open, as for `drag_move` (a new revision between the begin and the release ends the drag); the gate's errors for the dragged sketch; and a solve worse than the one before the drag (step 4); the drag then ended with no edit.

### `meshes` (M5.5; decision 6)

The display meshes of a model's bodies for a view, on M4.6's ladder: each body at the largest power of two no coarser than half a pixel, from the same cache `render` meshes into. So the viewport and an agent's `render` of one view mesh a body once, and look the same (R1).

- **Culling.** `meshes` meshes every body asked for, never culling to the view, unlike `render`, which draws only what's in it. A pan never needs a read.
- **Levels.** An orthographic view gives every body one level. A perspective one gives each body its own, at its nearest point to the eye, as `render` does (`views::half_pixel_at` at the body's tight box's nearest depth). A body wholly behind the eye's plane, which `render` culls and `meshes` doesn't, takes as its depth the distance from the eye to its box's nearest point (`views::meshing_depth`). So one just behind the camera has about the level it needs when a turn brings it into view, and one far behind a coarse one, where the depth along the view (0) would give every such body the finest mesh there is. Decided (Main, 2026-10-27): a reversible performance choice.
- **Indexing.** The mesh is the kernel's as it made it: vertices shared within a face, triangles never split, each edge a B-rep polyline. So a renderer finds silhouettes from adjacency within each face, and across faces from the edges; duplicating a vertex across faces at upload is the client's.
- **Naming.** Each mesh face and edge is named by the element map, with its stability.
- **The mesh stays fixed.** The mesh is the kernel's, in the document's coordinates, with no camera and no light in it. The viewport moves the bodies under a fixed camera, through each body's transform, without remeshing (section 10).

Request: as `render`'s without `highlight`, `to`, or `replace`, with two more fields:

- `features`: a list of IDs, or `null` for every body;
- `held`: the meshes the client already holds, each `{"key", "deflection"}`.

### `sketch` (M5.10)

A sketch as the named model solved it, for sketch mode to draw and colour. An agent reads the same thing (invariant 3).

The result holds:

- **`plane`**: the sketch's frame in 3D, `origin`, `x`, `y`, and `normal`. For a face plane (A4), it's the face's frame as resolved; `null` when the rebuild couldn't resolve it, `plane_problem` saying why. Nothing guesses a placement: the document stores no last frame, so `null` is the exact answer.
- **`state`**: SolidWorks' five states (docs/ux/solidworks.md, §2, *Definition states*): `under_defined`, `fully_defined`, `over_defined`, `no_solution`, or `invalid`. It follows `solve_problem`'s code, then the flagged constraints, then `dofs`, in that order: `over_constrained` is `over_defined`, `solve_failed` is `no_solution`, and `invalid_result` is `invalid`; a solved sketch with any `redundant` or `partially_redundant` constraint is `over_defined`, one with `dofs` above 0 `under_defined`, and any other `fully_defined`. An empty sketch is `fully_defined`, `dofs` 0 (open item 32).
- **`dofs`**: the degrees of freedom left, PlaneGCS's number as given: its unknowns less the rank of its equations, so 0 or more while something is free, a conflict or not (two driving lengths on one free line leave 3). Where nothing is free and a linear dependency among the equations holds no constraint PlaneGCS found redundant (a conflict, or an arc's own rules repeating each other), PlaneGCS counts the equations left in place of their rank, and the number is negative: a 40 by 20 rectangle given a second width of 50 reads −1.
- **`solve_problem`**: why the sketch wasn't solved, as the error contract's object (the same shape as an `errors[]` entry), for every refused solve, `over_constrained` included; `null` when it solved.
- **`plane_problem`**: why `plane` is `null`, as the error contract's object: the rebuild's one error for the plane. For a face plane whose face isn't found, or isn't planar, or whose `x` lies along its normal, it's `reference_broken` on `plane.face` or `plane.x`, with candidates, as `check` reports the sketch; for one whose face's frame can't place the sketch, or places its profile or axis past the reach, `invalid_input` on `plane`; for one whose face's feature didn't build, the error a read of the sketch's own solid gives (the root it's blocked on, or the kernel fault, kept); and for a bug, `internal`. `null` when the plane was resolved. The rest of the read is whole all the same (the rebuild solves a sketch in 2D before it places it): `state`, `dofs`, each member and its state, `regions`, and `profile_problems`, with `solve_problem` `null` unless the solve itself was refused. The sketch's dependents are as `check` and `timeline` report them: its sweeps are blocked on it. The repair is SolidWorks' *Edit Sketch Plane*: `set_field` of `plane` to a candidate, or an origin plane, or of `plane.face` alone (M5.9's part 3).
- **Each member, as solved, in its document form,** with its solved coordinates or radius in place of the stored ones, and a `state`. Points and curves have `under_defined`, `fully_defined`, or `over_defined`: SolidWorks gives each entity a state too (§2). A point is `over_defined` when a flagged constraint reads its x or y, else `under_defined` when either is free; a curve is `over_defined` when a flagged constraint names it, else `under_defined` when any of its or its points' values is free; a curve doesn't take its points' over-definition. Constraints have `satisfied`, `conflicting`, `redundant`, `partially_redundant`, or `unsolved`: on a sketch that wasn't solved, every constraint not flagged is `unsolved`, so `satisfied` always means independent and met on the coordinates the read shows. Which constraint of a dependent group is flagged is PlaneGCS's choice, as it lists it. So a curve carries the points it joins and its `construction`, and a constraint its type, members, and value, and sketch mode draws from this alone. The core decides the states from M3.3's free unknowns and conflicts, so no client maps unknowns to members. A sketch whose constraints conflict isn't solved: its state is `over_defined`, its members are given as stored, their states from the diagnosis.
- **What the states measure**: the first-order diagnosis at the solution, as `dofs`, the free values, and redundancy are (Fable's Addendum 5). Two circles touching at a point held `on` both read `over_defined`, though not every small change of a radius conflicts; `tangent` is the way to draw that, and makes no dependency.
- **`regions`**: the profile's regions, as M3.5 finds them, each with its outer loop's curves and each hole's, by ID in loop order. If there's no profile, M3.5's reasons, as errors, go in `profile_problems`: the first 100 (`PROBLEMS_LISTED`), in the order M3.5 checks them, and `profile_problems_total` counts them all, the count `check` gives a feature that sweeps the sketch.
- **Totals**: each list the read caps gives its total in a sibling `_total` field, listed or not, as an error's `elements` gives `elements_total` (invariant 9).

The dependent groups, `dependencies` and `dependencies_total` (Fable's Addendum 4: each linear dependency among the rows, by constraint ID), join the result with #282, which has PlaneGCS give them; until then the read has neither field.

### The sketch edits (M5.10)

**Common rules.**

- Each edit names its sketch by ID, and its members by their IDs (M4.1 section 2).
- Each goes through the gate, and a bad edit is refused whole.
- **An edit that writes geometry** (split, trim, merge, unjoin, extend, join, and a drag's release, `drag_end`) writes positions, directions, or structure of its own, so the sketch's solve then checks it, against the sketch's solve before it (refines SD7: pre-existing conflicts). The edit is refused as data (M3.3) where its solve is worse than before, by FreeCAD main's ranking (`getCoincidentSolveStatusSeverity`, with the DoF count read first): solved, then solved with redundant constraints, in conflict, over-constrained (in conflict with no freedom left, DoF below 0), no solution, and a result the file can't hold, which always refuses. At the same rank, it's refused where it flags a constraint redundant or in conflict that the solve before didn't, naming them (`shouldRejectCoincidentSolve`, `cb2780e2fa`). A conflict the sketch had already isn't the edit's. One rule for every such edit, the merge's, the extend's, and the join's included; `drag_end` follows it when it's wired. And one rule for where a drag can start: a line's extend and a drag begin only from a sketch whose constraints agree (open item 15, FreeCAD's drag), so in a sketch that conflicts, already or not, they're refused `over_constrained`, naming the conflict.
- **`sketch_add` and `sketch_remove`** write nothing of their own: they add or remove what the person wrote. Once the gate takes them, they're applied, with no solve-refusal, and the solve's verdict is the sketch's state (`sketch`'s `state`, open item 32). A sketch they leave over defined or unsolvable reads so, and its features fail loudly, as `add_feature` adds a fillet too large and it fails (open item 25), and as `set_field` of a constraint's value already behaves (SD7). FreeCAD keeps a conflicting constraint and reports it (docs/ports/sketch-edit.md, §2), so this follows it.
- **A suppressed sketch** can be edited, as `set_field` edits any suppressed feature, and its edits are judged as any sketch's, since a geometry edit's solves run on the edit's own worker, never reading the model, which doesn't solve a suppressed sketch.
- Coordinates and projections are computed in the core, with the libm shim's math, so every platform gets the same bits (sketch-edit 6).
- `construction` is kept by every piece and every new point (`23ecf94ab6`).

**The rules are the port note's, and normative.** For split, they're §3's table in its Silico column. For trim, they're §4's items 8 and 9 with the decisions they cite. For removal, unjoining, and merging, they're §2, §5, and §6. Each was taken as the port note recommends, by its decision number. This section gives each edit's shape and its key rules. Where the two differ, the port note's text governs, except where this section says otherwise and lists the difference in section 12.

**What a result lists.**

- `added`: the new members, in the order the edit made them. That's by kind (points, lines, circles, arcs, constraints), then in place along the curve from its start for points and pieces (a circle, which has no start, from `at.0`), then constraints in the order of the members they copy (by ID), then new joins. A member added with an ID a removal freed is the same member to every stored name (`sketch_add`).
- `modified`: members changed in place (a line's `to`, a constraint moved to a piece or retyped), by kind, then by ID.
- `removed`: members removed, by kind, then by ID.
- `references` (split, trim, and join): the features that store a name made from the curve's ID or its points' IDs (for a join, either piece's) (`s0000001.sketch.Edge.na000001`, as a source anywhere in the name), in timeline order. After a split or a trim, each such name finds what the start-side piece makes, which is only part of what it found (open item 11), so the edit says which features to look at, as `rewired` does for the chain. After a join, what each finds is as `sketch_join`'s `references` says.

A constraint whose type changes (split's `length` becoming a `distance`, a merge's edge `tangent` becoming a `tangent_at`) keeps its ID and is listed in `modified`: it states the dimension or relation the person placed, in the pieces' terms (open item 10). So no edit makes an ID for a retype, and `silico fmt --merge-touching` writes the same file everywhere.

**New IDs.** These come from the request's `ids` if it gives a list, taken in `added`'s order, or from the core's generator if it gives `null` (decision 20). A list of the wrong length is refused, naming `ids`, with the count the edit needs. A replay that passes back the `added` IDs it recorded gives the recorded document byte for byte.

Adds members as the document writes them. A batch is checked whole before any is added (docs/ports/sketch-edit.md, §2). `side` and `direction` are given, never decided from geometry (D4). The request's members carry their own IDs, as `add_feature`'s sketch members do, so it has no `ids`.

```json
{
  "session": "s1",
  "revision": 12,
```

#### `sketch_trim`

Trims a curve back to its neighbours. The piece holding the pick's projection is removed (sketch-edit 2, 5, 6, 8, and §4).

**Cuts** are found in the core in closed form:

- crossings;
- tangent contacts and overlaps;
- other curves' ends on the curve.

A gap of at most 1e-7 mm counts as contact.

**What cuts.** Every other curve, construction included (`715f98d1f3`). A sketch point doesn't cut, and neither do `x_axis` and `y_axis`. **A cut within 1e-7 mm of the curve's own end isn't a cut** (`226d24792d`), so a neighbour that shares the end never makes a piece of no length. FreeCAD's test is 1e-8 in the curve's parameter, strictly (`Precision::PApproximation`): r · 1e-8 mm on an arc. Silico's is 1e-7 mm on every curve, the gate's floor, a deliberate departure: on an arc of radius 1000, FreeCAD ignores a cut 5e-6 mm from the end, and Silico makes a piece of that length, which the gate takes.

**Whole-curve deletion.** The curve is removed whole when:

- there's no cut on either side;
- two cuts are within 1e-7 mm of each other;
- it's a circle with fewer than two distinct cuts (`testTrimCircleEnd`).

Trimming a point is refused (`5efb8e5e76`).

**The new ends.**

- A new end shares the cutter's point only when a constraint already holds the cutter's end on the trimmed curve. That `on` is then removed, and a `tangent_on` there becomes a `tangent_at`. Otherwise the new end gets a new point, `on` the cutter (sketch-edit 5).
- A tangency with the cutter becomes an end tangency at the new end, its `direction` as last solved, and a solve that flips it refuses the trim (sketch-edit 8).
- Trimming away an end a neighbour shares detaches the neighbour: the piece gets a new point, and the neighbour keeps the shared one (§4).

**Constraints** follow §4's items 8 and 9:

- an `on` on the removed part is dropped (`333ca836c0`);
- a `length` is dropped with one piece left, and becomes a `distance` with two (`2779f0b29f`);
- a constraint naming both ends survives only if both do (`f0d30cb570`);
- a line's `equal` is dropped (`857190a20a`);
- a `tangent_on` goes to the piece holding its `at`, and is dropped with it.

**Refusal.** Only decision 2's cases refuse the trim, naming the constraint: an arc's edge `tangent` that no piece touches, and a `symmetric` about the trimmed line.

**IDs.** The first piece keeps the curve's ID (`7d8a8b7cc8`).

#### `sketch_unjoin`

Pulls a shared point apart. One curve's use of the point moves to a new point at the same coordinates (sketch-edit 9):

#### `sketch_merge`

Makes several points one (sketch-edit 10):

- **The first point named survives** at its own coordinates. A FreeCAD coincidence lands where its solve takes it. Silico's merge is a placement, so the edit's solve then decides the rest. #### `sketch_join`

Joins the two pieces a split leaves at a point into one curve again: split's exact inverse (open item 12b). The request names the point they share, as Delete on a split point joins the pieces (section 9, *Split*).

- **What joins.** Two lines that share the point, one ending there and the other starting there, held on one line by a `tangent_at` (`same`) at it, as a split holds its pieces; two arcs about one centre point, one ending at the point and the other starting there; or a split circle's two arcs, which share both their ends. Arcs need no `equal`: sharing their centre and the point already makes their radii equal, which is how 12b's pair is "held equal". Two arcs join only where the joined arc's own sweep, as the document measures it (the angles of its kept start and its far end about the centre, by `libm::atan2`), exceeds each piece's sweep: pieces sweeping a turn or more between them would make the sliver left over, or no arc, so they're refused.
- **The start-side piece,** the one that ends at the point, keeps its ID and takes the other's far end, a point the sketch already holds, so nothing moves. The joined curve is that piece's ID, listed in `modified` (the one curve there), and the other piece is in `removed`. A split circle's two arcs become one circle, the arc that ends at the point keeping its ID, of its radius (from its centre to its start). So the circle a split made two arcs of has its ID back when it's joined at the split's second point, `at.1`'s. Its radius is the kept arc's, never invented: once the circle is split, the document holds only the points the split projected onto it, not the radius. Where those points are exact in binary, the circle comes back byte for byte; elsewhere its radius is the kept arc's, its centre's distance to its start as the document holds that point, which can differ from the original in its last digits, more so for a circle far from the origin (the split rounds each coordinate to the coordinate's own size, not the radius's).
- **Removed:** the other piece, the point (and a circle's other shared point), and every constraint naming a point removed, the joining `tangent_at` among them.
- **Re-pointed:** every constraint naming the other piece names the kept one, listed in `modified`. One that then repeats another (a `horizontal` on each piece, a `parallel` either way round), or names the joined curve twice (an `equal` of the two pieces), is dropped and listed in `removed`. So is an `on` that then holds the joined curve's own end, as implied (open item 13b).
- **Nothing is retyped.** A split's `distance` of the outer ends stays a `distance`, exact on one line: a line with a `length`, split and joined, holds the distance where the length was.
- **It makes no member,** so it takes no `ids`. It writes structure, so the sketch's solve judges it by the common rules, as split's does.
- **`references`:** the features that store a name made from either piece's ID or its points' IDs, in timeline order. A name made from the kept piece then finds the whole joined curve; one made from the other piece, or from the point, finds nothing, and its feature fails loudly (`reference_broken`, M2.8).
- **FreeCAD's join** (`SketchObject::join`, `SketchObjectOperations.cpp:1285`, from `c5aceb0182`; C1 continuity `da7d5391af`) always makes a B-spline, which Silico has no type for. That's a departure, recorded in docs/ports/sketch-edit.md. Its refusals are kept where they apply: a curve's own two ends, and construction joined to non-construction.

Also refused, naming the point and the pieces: a member that isn't a point; a point more than two curves use, or one that's a curve's centre; a line and an arc; construction joined to non-construction (FreeCAD's "Cannot join construction and non-construction geometries"); pieces that don't run on through the point (both starting there, or both ending); arcs with no centre in common, which no constraint holds on one circle; lines whose join would start and end at one point, a curve's own two ends (FreeCAD's "Connecting the end points of the same curve"); arcs that sweep a turn or more between them, by the sweep rule above; a split circle's two arcs whose other shared point another curve uses, which the circle would drop; a constraint the join would make hold the joined curve's own point on it, other than an `on`, which goes as implied (a `point_line_distance` of the kept piece's start from the other piece), naming the constraint; and a joined sketch the gate refuses. A piece's `length`, its `midpoint`, or a line's `equal` with another line is refused too, naming the constraint: on the joined line it would measure the whole, which the person never placed, so remove it first, or dimension the outer ends instead (a split makes them the outer ends' `distance` and `symmetric`, which the join keeps).

## 9. The tools' behavior (SolidWorks)

Each line is one behavior and its source in docs/ux/solidworks.md, so a test can be written from it, with the step that builds it. Where the help is silent, the line says so and section 12 recommends.

### Rebuilds, errors, and suppression (M5.1, M5.4)

- **When geometry is built.** Geometry is built when there are warnings, but not when there are errors (§5, *Errors and warnings*). A failed feature doesn't build, and what depends on it is blocked, as the core already does (M2.4). The help doesn't say what a feature after a failed one builds on (§5).
- **Error marks** (§5, *Errors and warnings*):
  - an error with a feature marks that feature's name;
  - an error with the model marks the document's name and the feature that contains the error;
  - a warning with a feature marks that feature;
  - a warning beneath a node marks the document's name and the parent feature.

  Items in error have red text, and items with a warning green. One combined mark shows both. The app marks the timeline entry, the browser entry, and, for the model's errors, the document's tab, from `timeline`'s health.
- **Showing a problem.** Selecting a marked item shows its errors and warnings with their suggestions, and links to edit the feature (§5). The app shows the core's message, elements by name, and suggestion (invariant 9), from a published `check`. A click on the root lists every problem, the *What's Wrong* list (§5).
- **Rebuilding.** Ctrl+B rebuilds what changed, and Ctrl+Q every feature (§5, *Rebuild*). In the app, these are `check` with `current`, and with `"fresh": true`, M4.3's forced rebuild.
- **Interrupting.** Esc interrupts a rebuild (§5, *Rebuild*). In the app, that's `cancel`.
- **Suppression.** Suppressing a parent suppresses its children, unsuppressing the parent leaves them suppressed, and unsuppressing a child unsuppresses its parent (§5, *Editing upstream*). In the app, that's `suppress_feature`, with children as Fable's rule defines them.
- **Moving.** A child can't be moved before its parent (§5, *Editing upstream*). In the app, that's `move_feature`'s refusal.

### Saving, undo, and the file (M5.2, M5.4)

- An asterisk beside a document's name means it changed since it was saved (§6). This is `status.transaction.changed`.
- Ctrl+S saves. Ctrl+W closes, asking whether to save a changed document (§6). Section 4 gives the commands.
- Ctrl+Z undoes and Ctrl+Y redoes (§6). These are `undo` and `redo`. The help doesn't list what's undoable (§6). Here, every edit inside the transaction is undoable, a dialog's edits are one step once it's OK'd, and a save ends the undo (decision 2).
  - *As built (docs/design/m5-ui/js/app.js: the Undo and Redo buttons' `data-tip`, and `renderStatus`):* Undo's and Redo's tooltips name the step each would take, as the prototype's do (`Undo: Edit Pad`, `Redo: Rename Pin`), and the status bar counts the unsaved edits (`Unsaved · 2 edits`). The names and the count are the app's own record of the steps it made, not the core's: a step is the client's (section 7's `undo` and `redo`: every edit its own step, a run grouped by the client undoing `to` where it began), so a dialog's OK'd edits, and sketch mode's once finished, are one step named by the dialog or the sketch, which only the client knows; a session is one client's, and inside a transaction the file is never reloaded, so no state comes that the client didn't make but another client's in the same session (then it names and counts none). The core's API is unchanged: `status.transaction` still gives the counts, and an agent names its own steps as it makes them.
- *Reload* marks a reload that would lose unsaved changes (§6). In the app, that's section 4's choice.
- The unsaved reminder and auto-recover files (§6) are open item 31.

### Selection (M5.7)

- **The mode.** Select is the mode when no command is active, and a command returns to it when it ends (§1, *Hover*).
- **Hover.** The entity under the pointer highlights as the pointer moves over faces, edges, and vertices (§1, *Hover*). The app reads it from the viewport's ID buffer and resolves it to a name at once (M4.6), from the published model.
- **Click.** A click selects the entity under the pointer, in the canvas or the browser, and Ctrl selects several (§1, *Click, Ctrl, Shift*). A plain click replaces the selection, a Ctrl-click toggles one item, and a click on empty space or Esc clears it (open item 24).
- **Browser and canvas.** An item selected in the browser highlights in the canvas. One selected in the canvas expands and scrolls the browser to it (§1).
- **Box selection** (§1, *Box, cross, and lasso*):
  - a drag from empty space draws a box;
  - left to right takes only what's wholly inside, and right to left also what it crosses;
  - in a part, a box takes edges by default;
  - Shift with a box adds, and Ctrl with a box inverts inside it.
- **A drag on geometry** selects what's under the press, and draws no box (§1).
- **Filters** limit what can be selected to their types (§1, *Selection filters*). E filters edges, X faces, and V vertices. F5 shows the filter toolbar, and F6 turns the chosen filters on or off. E, X, and V each toggle their filter in the set (open item 24).
- *As built (M5.7's part 2):* a box decides what's inside, or crossing it, against the displayed mesh, what the person sees, not the exact B-rep: each body drawn, its edges' polylines cut where a perspective drawing cuts them (nearer the eye than `MIN_EYE_DISTANCE`, #353) and projected by the renderer's own projection, tested in f64 (an edge is inside when every point of what's drawn of it is, and crosses when a drawn segment meets the box). A curved edge's chord can lie inside a box its true arc bulges out of, and it's taken. The box is clamped to the canvas, and takes what's behind other faces too. "Edges by default" follows the approved prototype's `onBox` (Trevin's approval of docs/design/m5-ui): a box in a part takes edges, whatever the face and vertex filters; with the edge filter off it takes nothing and a toast says "The edge filter is off, and a box selects edges in a part."; else a toast counts them ("Window selection: 4 edges"). A drag whose press the hover hasn't answered yet waits for it, asking it again each frame, and a release meanwhile keeps the box's corners and is decided when the answer comes; the camera, the bodies, the model, or the filter changing first lets it go, and a toast says why. F5 shows a toast saying the filters are in the toolbar, under SELECT, as the prototype does (DESIGN.md, open question 2), not a command of the registry nor on the sheet, as the prototype's isn't; the toolbar shows SOLID whenever no sketch is open. X, E, and V aren't taken while a sketch is open, where X is Construction (`crate::app::filter_keys`), nor while a field is typed in.
- *As built (M5.7's part 3a, vertices):* a vertex is picked through the ID buffer, with no WGSL: a frame that picks, with V on, draws a disc 7 points across (the prototype's `d < 7`) about each vertex that lands near the picking square, into the picking layer alone (invisible, colour and alpha 0, writing no depth to the image), its picking ID the body's and `1 << 32 | n`, so `EDGE_BIT` and the worker's u32 ID buffer are untouched. Its points are `meshes`' `vertex_points` (section 7), placed in f64 about the camera's point as edges are, at a depth offset past the edges'. A vertex at the pointer's pixel comes before an edge in the band, and that before the face. *Departure from the part 3 design note:* the disc is drawn toward the eye by 1.2% of the view's height at it, the prototype's own tolerance (`pickAll`'s `eps`, a vertex `visible` where `t <= tFace + eps`): drawn at the vertex itself, a disc facing the eye is hidden by every face it bounds that turns toward the eye (a box's corner seen from outside loses half its disc to the face rising to the nearest corner), so the design's corner case missed at a pixel's centre half a row below the corner. A vertex hidden behind a face by more than that isn't picked. *Its limit, accepted for M5 (N5, decided 2026-11-08):* the reach is depth alone, so a vertex behind a wall thinner than about 1.2% of the view's height (1.2 mm in a view 100 mm high) can be picked through it, and Select Other lists it unhidden. The reach can't be less, or the disc loses its rim (it must win 7 points from the vertex against the faces it bounds rising toward the eye); the pick shows on hover before a click, it can be undone, and the case is rare. The better rule, by adjacency, is a follow-up after M5 (docs/roadmap/m5-app.md). A perspective vertex nearer the eye than `MIN_EYE_DISTANCE` has no disc and no dot. Its pick's point is the vertex's own. The dot is painted over the bodies by the pane, for the hovered and the selected vertices only (the hover's first), at `render::project` of the point: 4.5 points, a 1-point black ring, white hovered and `#4676ff` selected. A box still takes edges alone.
- **Select Other** lists the entities under the pointer in the order they're met, and Tab or the wheel steps through them (§1, *Select Other*). The ID-buffer depth this needs is per docs/study/viewport.md.
- *As built (M5.7's part 3b, Select Other):* no ID-buffer depth: a cast on the CPU in f64 (`silico_render::render::hits`, beside `ray` and `project`, the part 3 design's option (c)), at the right click's pixel centre with that frame's camera and size, on the bodies the frame drew and the meshes the renderer was given, each body's boxes made once a mesh (`Pickable`: each edge's box, and the body's triangles in a tree of boxes, chunks of eight of a face's triangles under a tree split at its chunks' median, so a line meets them in about the log of their number; a triangle no line can meet, its first corner repeated, left out). They're made off the UI thread, on a thread of the tab's own, as the view takes each new mesh (`crate::boxes`, as the recent documents are kept): about 17 ms for ten copies of CTC 02 (the picking bench's `boxes_ms`, run 42536385366) and about 70 ms at a million triangles, where the cast itself takes 0.1 to 0.5 ms there. They're kept by the mesh's `Arc` while the view holds it, through the tab hidden and the body hidden in the browser, and let go the frame it doesn't. A right click before a drawn body's boxes are made waits for them, and its menu opens once they are, a frame or more later, as it would have at the click (the part 3 design's section 2: past the budget, the cast moves off thread and the menu opens a frame later); it never casts without a body that's drawn, and while it waits a press, Esc, or anything that closes an open menu lets it go. It takes each face whose triangles the ray meets, each edge whose drawn polyline passes within 6 points of the pointer in the image (at its point nearest it; seen end on, at its end nearest the eye), and each vertex within 7, every kind whatever the filters (decision 2); in perspective nothing nearer the eye than `MIN_EYE_DISTANCE` (each edge cut there in 3D first), orthographic the whole line. A face is hidden where another is met strictly nearer on the pointer's ray. *Departure from the design note* (which ordered by depth with no tolerance and hid what a face is met strictly nearer than): a vertex is taken toward the eye by part 3a's disc reach (`VERTEX_REACH`, 1.2% of the view's height there, the prototype's `pickAll` `eps`; orthographic, at most halfway to the near plane the renderer sets past the bodies, and in perspective at most a quarter of the depth: one function for the disc and the cast, `vertex_reach`), and an edge, since N5, by its picking strip's (`edge_reach`, below), each listed by its depth less its reach and hidden only where a face is met nearer than that on the ray through its own point. By the note's rule, in any oblique view an edge 2 pixels from the pointer on the face under it was listed after that face and marked hidden (the face, receding, is nearer at the pointer than at the edge), and so was a corner whose face rises toward the eye. A triangle's edges are its own to a part in 2^40 (`WATERTIGHT`), so a line along an edge two triangles share meets both. The same tie order: vertex, edge, face, then body and number. Only the nearest 256 are cast on again for whether a face hides them, each such cast walking the trees past every box no nearer than its element and stopping at the first triangle met nearer; they're chosen from the rest in time linear in their number. Each edge is cut where the drawing cuts it by the drawing's own rule (`render::cut_by`, about the eye), as box selection's segments now are (`render::project_segment`; cut in the document's coordinates, a cut a nanometre from an eye far from the origin landed pixels off). *The hover and the cast:* the hover and the click take an edge by the cast's threshold, the prototype's 6 points (its `pick` takes `pickAll`'s `d < 6`, as it takes its `d < 7` for a vertex: one constant each, `HIT_EDGE_POINTS` and `HIT_VERTEX_POINTS`, from which the selection's band and vertex disc are made). They part in two ways. Within 6 points, in depth: the cast lists an edge at its depth less one reach, so an edge more than one reach behind the face under the pointer comes after that face in the list, where the hover takes the edge over the face; in hits_tests' view from above the front at 45 degrees (40 mm high on 400 pixels, an edge's reach 0.2 mm, the top receding 0.1 mm a pixel down the image), its back edge comes after the top once the pointer is more than 2 pixels below it. Near a vertex whose edge runs toward the eye, the edge, nearer, comes first in the list while the hover takes the vertex, as the prototype's `pickAll` orders them. In a sketch, the canvas's menu is sketch mode's (G7), drawn as every menu is too: End chain (Esc, off with no gesture under way, saying so), Smart Dimension (D, choosing its tool as D does; it's never open with the tool on, where a right click is the tool's lock), a separator, Finish Sketch (Ctrl+↵, ⌘↵ on macOS), and Cancel sketch, each cap the registry's.
- *As built (N5, concave edges):* an edge's stroke is drawn square to the view at its line's depth, so at a concave edge, whose faces both rise toward the eye away from its line, they hid every pixel of it from the picking layer (by 0.153 mm a pixel off its line in a view 100 mm high on 800 rows, against the edges' depth offset of about 3e-6 mm), and a hover or a click on it took a face. A frame that picks now draws each edge near its picking square again, into the picking layer alone, as the vertex discs are: invisible (colour and alpha 0, writing no depth to the image and no outline mask), at the edges' width and depth offset, with the drawn strip's picking ID (`EDGE_BIT`), placed in f64 about the camera's point as the drawn edges are (in perspective, cut where they're cut first), and moved toward the eye by `edge_reach`: 2 pixels of the view's depth there, with `vertex_reach`'s caps (orthographic, at most halfway to the near plane; in perspective, along its line to the eye, at most a quarter of the depth), and never more than `vertex_reach` (the two are equal under 167 rows). So an edge wins the pixel nearest its line against a face rising toward the eye by up to 4 pixels of depth a pixel across it (turned up to 76° from face-on), at any pixels a point, and its whole stroke, a point either side of its line, against one rising by up to 2 over the stroke's pixels a point: up to 2 (63°) at one pixel a point, up to 1 (45°) at two; a concave edge as a convex one; and a wall more than 2 pixels of depth thick in front of an edge (0.25 mm in a view 100 mm high on 800 rows) still hides it, where `vertex_reach` (1.2 mm there) would have let an edge 1 mm behind such a wall through. Only frames that pick edges draw them (`Frame::edges`, the selection's edge filter: with it off, as in a dialog's box taking faces, an edge's drawn stroke alone is picked, a concave edge's as a convex one's, and a click past it takes the face), after every edge drawn, and only for edges whose box lands within a stroke of the square (each box tested by one corner a side of the square, through the projection's own matrix). The image was as it was until N5's image (section 10) moved the drawn edges toward the eye too, by no more than `edge_reach`; since then the worker's ID buffer has each edge where its image draws it. An edge pick's point is its strip's taken back from the eye by the reach, the drawn line's point there. Select Other's cast takes an edge by the same `edge_reach`, so the hover, the click, and the list agree on it, but where a face within 14° of edge-on rises more than the reach in the half pixel between a pixel's centre and the edge's line: there the cast lists the edge unhidden after the face, and the hover can't take it. Box selection is unchanged: it never asked what hides an edge. *As built (a stroke takes the face under it):* with edges filtered out and faces not, a hover or a click whose centre pixel holds an edge's stroke takes the face under the pointer, the one the ray through that pixel's centre meets first (`render::face_hit`, Select Other's cast on faces alone, on the bodies the frame drew and their boxes, so no crowd of edges or vertices nearer the eye can leave it out), as SolidWorks' face filter selects only faces (docs/ux/solidworks.md §1, *Selection filters*); none past a silhouette, where no face is under the stroke. While a body drawn has its boxes still to come (made off the UI thread as the view takes its mesh, about 70 ms at a million triangles), a click on a stroke waits for them, as Select Other's right click waits for its boxes: its pick's answer kept, nothing more asked and no frame counted, the selection untouched, and decided the frame they're made, cast with that frame's view (the camera moving lets it go; new bodies ask its pick again; another model published leaves it waiting for that model's meshes). A hover there takes nothing, asked again each frame till then. So what a click does never depends on whether a build behind it has finished. The picking layer still holds the edge there: the cast is the selection's, on the UI thread, only for a pick on a stroke. frame_tests pins the study's scenes by hand: the L's concave corner at its pixel and 1 to 2 pixels either side, an edge hidden behind the body, an edge behind a plate's top at 1, 0.3, and 0.2 mm, orthographic and in perspective, and another body's edge under a 1 mm plate.
- **Stability.** A selection is a list of names with their stability. An element whose name isn't stable can be selected, but anything that would store it refuses it and says why (#196's M5.7; M4.1 section 2).
- **After a rebuild.** A selection survives a rebuild that keeps its names. A name that's gone is dropped, and the rest stay selected, as SolidWorks' selection box keeps its valid items; the status bar says how many of that kind went ("2 of 12 selected edges are gone after the rebuild"), with the core's reason when one name went (#196's M5.7; decided at #385's review). The help is silent here (§ *Not covered*).

### Feature dialogs (M5.8)

- A feature's command opens its dialog. OK accepts and closes, Cancel discards and closes, Enter is OK, and Esc is Cancel (§5, *The PropertyManager*).
- The active selection box is highlighted, and its items highlight in the canvas (§5).
- An extrude shows a shaded preview as soon as its dialog opens, and the view can be moved without losing it (§5). In the app, a dialog's edits are made in the transaction, and the preview is the published model as each rebuild lands.
- A slow preview of a fillet or a chamfer can be cancelled with Esc (§5). In the app, that's `cancel` of the rebuild, with the dialog left open.
- A failed preview shows the core's error in the dialog, and the rest of the model still draws. OK is still allowed, saving the feature with its error, as SolidWorks saves a part with rebuild errors (§5, *Errors and warnings*). The help is silent on the dialog itself (§5; open item 25).
- *Edit Feature* opens a feature's dialog, from the browser, the timeline, or the canvas, and OK applies the change (§5, *Editing upstream*).

### Sketching (M5.3, M5.9, M5.11)

- **Automatic relations** (§2, *Relations added while sketching*). As you sketch, the pointer shows the relations that can be created, and with *Automatic relations* on, they're added: horizontal, vertical, coincident, midpoint, perpendicular, tangent. A relation the pointer shows at the accepting click is added, every one, and the pointer shows none the sketch already fixes: a tool leaves out an inferred relation asserting two coordinates equal that the sketch already makes equal, or one reading only values it already holds fixed, and never shows it; what it can't see is added, and the `sketch` read marks it redundant, drawn with a glyph of its own, for the person to delete (#278's G as amended, Fable, 2026-11-08, docs/ports/sketch-tools.md; open item 28). Points get `horizontal_points` or `vertical_points` only when the pointer shows the relation, never from a dotted line alone (#278's E). A point clicked at the origin gets `horizontal_points` and `vertical_points` with `origin` (#278's A). A point clicked on a lone point adds nothing, and the tool says so (#278's D). With shared points, a coincident relation is a shared point, never a constraint (D2). Which relations each tool and snap leaves is #278's A to G (open item 26).
- **Points lined up** (#278's E; the coordinator's decision, 2026-10-31, for #335's review). A point placed on nothing lines up only with a point the pointer has woken, as SolidWorks wakes a point by hovering it: one the pointer has passed within the pick tolerance of while the tool is in use, or one the tool has added; the last 8, the newest first, forgotten on Esc and when the tool is left. So a point far off at the same x lines up only once hovered. Lining up is a relation (`horizontal_points`, `vertical_points`) only for a lone point (the point tool's, and a circle's, an arc's, or a centre rectangle's centre); a line's or an arc's end, or a rectangle's corner, follows a dotted guide only.
- **Not built in M5.11:** a tangency along an edge (`tangent`, or `tangent_on`: a line ended tangent on a circle, a circle drawn tangent to a curve), and `perpendicular` or `parallel` to a line the pointer only hovered (a new line shows them only to a line ending at its start). A line leaving an arc's end along its tangent gets `tangent_at` (`same`); where it is also near an axis, the tangent wins (the coordinator's rule, #335 round 2): the line is written along the arc's tangent, and gets `horizontal` or `vertical` too only where the arc leaves along that axis exactly (to a picometre, an obround's join), so every relation added holds where it's written. FreeCAD 1.1.3's `seekAutoConstraint` adds both whatever, and its main since `d77c9647c3` skips the alignment wherever there's a tangency; this sits between them.
- **Ctrl, and *Automatic relations* off** (§2; #278's F). Ctrl held while sketching, or the setting off, suppresses only the relations the pointer infers: `horizontal`, `vertical`, `on`, `midpoint`, `tangent`, `perpendicular`, `parallel`, and the points' `horizontal_points` and `vertical_points`. A click on an existing point always shares it, as a chain's joins, a rectangle's corners, and a tangent arc's start do: that's structure (D2), not a relation, so profiles stay buildable. An unwanted join is undone with `sketch_unjoin`. FreeCAD 1.1.3 infers nothing then, leaving a new end at the same place unjoined, which M3.5 refuses in a profile; Silico doesn't follow it there.
- **Lines and arcs.** A relation to a line is to the infinite line, and one to an arc to its full circle (§2). That's D4's `on`.
- **Inference lines** are dotted lines from the pointer to existing entities, guiding it to cues such as midpoints (§2, *Inference lines and snaps*).
- **Snaps** are all on by default but the grid, and only the entity being sketched shows them (§2).
- **Definition states.** A sketch and each entity are in one of SolidWorks' states (§2, *Definition states*), as `sketch` gives them. The status bar shows the pointer's coordinates and the state. In the browser, a sketch's name is prefixed `(+)` over defined, `(–)` under defined, and `(?)` not solvable.
- **Colours by state** (§2): under defined blue, fully defined black, dangling olive, a driven dimension gray; over defined red, invalid yellow, and unsolvable red. A redundant relation is drawn with a glyph of its own, its entities untouched (open item 28).
- **A dimension that over-defines** the sketch asks whether to make it driven, leave it driving and over defined, or cancel (§2). In the app, a dimension placed (`sketch_add`) or edited (`set_field`) that conflicts, or is redundant, is applied as the document holds it, never refused (SD7; section 7, *The sketch edits*). M3.3 reports the conflict as a problem, which `sketch` shows as `over_defined`. The app offers the three: driven, a `set_field` of `driving` to false; leave it, which does nothing; or Cancel, an `undo`. The offer is judged by the dimension's own row: an add by the freedoms it left (dependent) or its own flag, an edit by any constraint it newly set in conflict, either by a solve newly refused (`sketch_tools::offer`, c3 as amended 2026-11-09).
- **Dragging** (§3):
  - under-defined endpoints and curves can be dragged, with the drag commands;
  - a line's endpoint dragged changes its length or angle;
  - dimensions hold during a drag;
  - *Ghost image on drag* shows where the entity started, and the app draws the begin state faintly.
- **Line** (§4, *Line*). The first click decides the mode: a press and drag draws one line, ended by the release; a press and release goes on clicking a chain of lines. A double-click or right-click > End chain ends the chain and keeps the tool. Esc ends it and leaves the tool. Choosing another tool ends it. A chain's lines share their points (D2).
- **Corner rectangle** (§4, *Rectangle, circle, arc, point*). A press at the first corner, a drag, and a release, or two clicks. Shift held before the release makes a square. It's four lines sharing four points, with horizontal and vertical relations (an unofficial source, §2; open item 26).
- **Centre rectangle,** if M5.11 builds it (#278's C). One construction point at the centre, with a `symmetric` of two opposite corners about it, as FreeCAD's; no diagonals, which the construction-line tool draws.
- **Circle, arcs, and points** (§4): a circle's centre, then its radius; a centrepoint arc's centre, radius, start, and end; a 3-point arc's start, end, then radius; a tangent arc pressed on an endpoint and dragged; a point at each click, the tool staying. The tangent arc draws tangent arcs only, with no normal zones, in M5 (#278's B).
- **Trim** (§4, *Trim, extend, split*). Power trim trims each entity a drag crosses to its nearest intersecting entity, and Trim to closest removes the entity up to its closest intersection. Both are `sketch_trim`. Power trim's extending is `sketch_extend` (open item 12).
- **Split** (§4). A click on an entity splits it there, and a closed curve needs two split points: `sketch_split`. Selecting a split point and pressing Delete joins the pieces again (§4): `sketch_join`, split's exact inverse, giving one line or one arc (open item 12b).
- **Delete** (§4, *Delete, and relations*). A relation is deleted by selecting it and pressing Delete: `sketch_remove`. What deleting an entity does to its relations and shared ends, the help doesn't say. Here, it's sketch-edit 7.
- **Editing a sketch** (§5, *Editing upstream*). *Edit Sketch* opens from the sketch, from a feature built on it, or from one of its entities. *Exit Sketch* keeps the changes, and Cancel discards them, which is an `undo` to the revision sketch mode opened at, as M5.8's Cancel is. Exiting rebuilds the part.
- **Smart Dimension** (docs/study/smart-dimension.md; SD1 to SD9, open item 28). Each placement is a `sketch_add`, applied as the over-defining dimension above is (SD7).
  - **What it places** (SD1), for the forms the document has: `length`; `diameter` on a circle and `radius` on an arc; `distance`, `distance_x`, or `distance_y` by the pointer, ordered so the value starts positive; `point_line_distance`, its `side` read from the drawn geometry; to a centre by default; `angle` as `{a, b}` or `{b, a}`; and a centreline's near side as a `point_line_distance`. Esc undoes the last pick, and a right-click locks the kind.
  - **Driving** (SD2). A placement writes `driving: true` with the value typed. A skipped box writes the measured value, rounded by the core to the nanometre.
  - **Two parallel lines** (SD4) get a `point_line_distance` from the second line's `from` to the first line, as FreeCAD's tool writes it. What holds them parallel is the person's relation.
  - **The Modify box** (SD9) takes plain numbers only, read as the document reads a value: no arithmetic, units, or equations.
  - **Not in M5:** arc length, the Min and Max gaps, and a doubled distance, each a new form, so their picks aren't offered (SD3); and a toggle between radius and diameter (SD8).
  - **The 135° supplement** is in: `angle` has `reversed`, `b`'s direction taken from its `to` to its `from`, so every angle the pointer picks is stored as typed (Fable's chain-corner decision, 2026-10-31, superseding SD5, which assumed both lines leave the corner); the tool's choice of quadrant is #345.
  - **Not ported:** SolidWorks' first-dimension scaling, since the help gives neither its anchor nor whether it can be turned off (SD6; docs/ux/solidworks.md, §2).

## 10. The viewport, the toolkit, and picking

From Worker 3's studies (#223), cited, not repeated, with what was taken from each (decisions 4, 11, and 13).

- **The viewport** (docs/study/viewport.md; decision 4). It draws `meshes` with `re_renderer` 0.38.1's own mesh and line renderers, from `silico-render`, as one renderer with agents' renders (R1). No renderer of Silico's own, no WGSL Silico owns, and no fork in M5.
  - **Why the camera moved meshes.** silico-render bakes M4.6's camera-fixed light, and the eye offset at `f64` precision, into each vertex for one view. So every orbit rebuilds every mesh: 3.1 ms on CTC 02, the corpus's largest part (664 faces), and 33 ms at 6,640 faces. The study recommended a renderer of Silico's own; it isn't taken.
  - **The bodies move instead.** The camera stays fixed in the world. Each face's positions are stored about its own box centre once, at upload (each face is already its own mesh and instance), and each frame its `world_from_mesh` is the view rotation and the face's box centre minus the eye, computed in `f64` and cast to `f32`. A face that f32 about its centre would draw more than an eighth of a pixel off in that view (its box's half diagonal over 2²², times the image corner's sec² in perspective, against the pixel at the face's nearest point; a huge face seen very close, or one whose box holds the eye) is uploaded for that view, alone, about the camera's point: the eye in perspective, and in an orthographic view the point on the view's line through the target at the face's own depth (anchored at the target itself, or at the nearer of target and centre, a kilometre rod with the target 6e5 mm along the ray had its end drawn 3.5 pixels off, where M4.6 drew it right; on the line at the face's depth, what the view sees of the face is near the anchor wherever along the ray the target is). The body's other faces stay put. No hysteresis: a render depends only on its scene and its view (Fable's decision on #332, 2026-10-31). The light is `re_renderer`'s `simple_lighting` (an ambient of 0.2 and two lights), world-fixed and so camera-fixed here, per pixel rather than per vertex. That replaces M4.6's shading formula. Pixels aren't results (R5) and no test compares them, so nothing protected changes; the look's change is a veto line for Trevin.
  - **One path for the worker and the app.** The render worker draws the same way, so `silico-render` loses its per-view baking (the vertex light, the `f64` eye offset per view, normals zeroed). Its drawing is separated from its device: `Renderer::new` is split, so the worker makes its device and the app takes eframe's (M5.6).
    *As built (M5.6):* the app makes `silico_render::Renderer` on eframe's adapter, device, queue, and target format (`renderer::on_eframe`), installed in egui_wgpu's callback resources; with no wgpu, or a device it can't draw on, the app runs with no viewport drawn, said in the log. A test draws the viewport through it on lavapipe (egui_kittest's `wgpu` feature) and picks a box's front face by its name, `Face3`, a frame or two later.
  - **Edges** are `re_renderer` line batches, placed in the view in `f64` on the CPU each frame: each point's offset from the camera's point and its rotation into the view, so the GPU's transform for them (`world_from_obj`) is the identity. The offset alone wasn't enough: an oblique orthographic view with its target a kilometre along the ray drew 131 of 353 edge pixels off their projection, the f32 rotation mixing the depth's rounding across the view. Their draw data is uploaded each frame anyway, as Rerun does, so a camera move rebuilds the strips, never the meshes. Edges stay blended as M4.6 draws them, one path on lavapipe and GPUs.
    *As built (N5's image, the drawing's depth offsets):* an edge's stroke is drawn square to the view at its line's depth, half its width either side of its line, and was offset toward the eye by `EDGE_DEPTH_OFFSET` alone (about 3e-6 mm in an orthographic view). So a face beside it rising toward the eye across its stroke hid the stroke on that side: at a concave edge both faces, the whole stroke (the L's, its faces rising 1.22 pixels of depth a pixel across it at the home view, 0.153 mm in a view 100 mm high on 800 rows); at a fillet's tangent edge the flat face, half of it, as the bracket's two show (on its dark upright, the half left is a rim a point wide, 10 of 255 darker than the face, which Metal showed as no edge); inside a silhouette the face it bounds, its inner half; and in perspective, where `re_renderer` spans a stroke square to its own ray, off the view's axis even a face square to the axis rose across it (by tan of the ray's angle off the axis, 0.2 pixels of depth a pixel 11° off). On a convex edge, whose faces recede from its line, only a rare sample within f32's step of the line was lost. The fillet's chords weren't the cause there: its mesh passes through the tangent line, and its first chord, 9° from the flat face, recedes from the eye as the face it leaves rises. Each drawn edge's strip is now moved toward the eye too, in f64 on the CPU as its picking strip is (along the view, or in perspective along its line to the eye, so it keeps its pixel), by its own reach, `drawn_edge_fraction`: the least that draws its whole stroke, h pixels either side of its line (a point), over a face rising toward the eye by up to √2 pixels of depth a pixel (turned 54.7° from face-on, as each face of a part square to its axes is from a corner, the home view), and over a curved face's mesh, whose chords lie up to half a pixel (the deflection `meshes` meshes a view at) nearer the eye than the surface its line is on: √2 h + 1/2 pixels of depth, 1.91 at a pixel a point. It takes `edge_reach`'s caps and is never more than it, so a pick's strip stays nearest and the pick's point right: from 1.06 pixels a point it is `edge_reach`, 2 pixels, and at 2 pixels a point a stroke is drawn whole over a flat face rising up to 1 (45°), and over the L's to 1.63 of its 2 pixels either side. Its costs are an edge pick's: a wall thinner than the reach in front of an edge doesn't hide it (0.239 mm in a view 100 mm high on 800 rows; at 1 mm it's hidden), and an edge going behind a face shows a stub where it's within the reach of it (under a pixel at a box's hidden corner from the home view). A silhouette keeps its pixels, drawn whole now over the face it bounds. The picking layer has the drawn strips too: with edges not picked, an edge is picked where it's drawn, a concave edge's stroke as a convex one's, and the selection takes the face cast under it (section 9, *Selection*); the worker's ID buffer has each edge where its image draws it; and an edge pick's point is taken back from the eye by the reach of the strips its frame picks from, `edge_reach` with edges picked and the drawn strip's with them not, so it's the line's either way (found by /break-it: taken back by `edge_reach` alone, a frame not picking edges left it behind the line by what the drawn reach falls short of `edge_reach`, 0.09 pixels of depth at a pixel a point and 0.44 at 3/4). A highlighted edge in a render (4 pixels wide, `Highlight::Tint`; a frame's highlights are outlined at the plain width) is moved by the plain stroke's reach, so at a concave edge its outer part is hidden where the faces rise past it: the L's to 1.56 of its 2 pixels either side. A reach of its own, 2√2 + 1/2 = 3.33 pixels, would draw it whole, but it's more than `edge_reach`, and a highlighted edge would show through a wall up to 0.42 mm thick in a view 100 mm high on 800 rows. frame_tests pins it on lavapipe, each line projected by hand and its stroke's pixels counted along it: the L's concave edge and a filleted L's two tangent edges drawn whole (at 2 pixels a point, to 1.63 pixels and no farther), the convex edge whole (as it was, but for 1 of its 116 pixels), the silhouettes' strokes whole and their pixels over nothing and past them as they were (orthographic and in perspective), the edges behind the L and a cube's hidden corner not drawn, an edge behind a plate drawn at 0.2 and 0.23 mm behind its top and hidden at 0.245, 0.3, and 1 mm, orthographic and in perspective, and at half a pixel a point drawn at 0.13 mm and hidden at 0.17, at two drawn at 0.245 and hidden at 0.26; an edge pick's point on its line with edges picked and not, at 3/4, 1, and 2 pixels a point; and a highlighted concave edge in a render drawn to 1.2 pixels of its line and its face's 1.9 to 2.2 off.
  - **What Silico draws itself:** nothing in M5. Silhouettes and hidden or dashed lines aren't in `re_renderer` (viewport.md, §4), each would be a pass of Silico's own, and Fusion's default style shows visible edges only, so both are out of M5.
  - **Picking latency.** Picking results arrive a frame late (viewport.md, §3), which is accepted, with Rerun's larger picking rectangle.
- **Picking** (decision 4). Per-instance picking, as today: object a body, instance a face, with outlines by instance. Its passes cost 2.0 ms a frame on CTC 02, against 1.0 ms for one mesh, which is inside a frame, decision 4's own test. **The check** is M5.7's benchmark on CTC 02 with its 1,647 edges drawn, which the study didn't measure. If it misses a frame, the study's renderer is the fallback, with its probe as its design (per-face IDs in the picking layer at one mesh's cost). It also watches the CPU's placement of each view (each face's anchor and transform, its instance, and the edges' strips, `Renderer::placed`): 0.3–0.4 ms on CTC 02 and 3.1–3.9 ms at 10 × CTC 02 on CI's lavapipe, at #332. It times, too, the first frame (every face uploaded) and a mesh replaced (a body's faces uploaded again) at 10 × CTC 02: if either misses a frame, the frame gains an upload budget, so a frame uploads at most so many faces and draws the rest at their next frames. *As built (N5):* the picking layer's depth isn't the image's for an edge: on a frame that picks, each edge near the picking square is drawn again into the picking layer alone, toward the eye by `edge_reach` (2 pixels of the view's depth, never more than a vertex disc's `vertex_reach`), so a concave edge is picked as a convex one is (section 9, *Selection*).
- **The toolkit** (docs/study/toolkit.md; decision 11). `eframe` with `wgpu_no_default_features`, `egui_tiles`, and `egui_kittest`, at `re_ui` 0.38.1's pins: egui 0.36.2, `egui_tiles` 0.17.1, `wgpu` 30. Not `re_ui` itself.
  - **The look.** Only the values the app sets are taken from `re_ui`: the palette, panel margins, bar heights, list item height, and corner radii, as Rust constants in one module (`silico-app/src/theme.rs`) with Rerun's MIT and Apache notice, applied to `egui::Style` in one function Silico writes. Not the three RON files, a loader, or a port of `DesignTokens::apply`: the layout follows Fusion, not Rerun, so the rest of Rerun's tokens would be code to own for nothing.
  - **The font.** `eframe`'s `default_fonts` is off. Inter (OFL-1.1) is the text's family, and JetBrains Mono (OFL-1.1) the one for names, IDs, and values, as the approved prototype (docs/design/m5-ui) sets them, each notice beside its font.
- **`deny.toml`** (#196's decision 13, from the toolkit study):
  - **13a, the `wgpu` ban,** stays. Its wrappers gain `silico-app` and `egui-wgpu` for `wgpu`, and `silico-app` for `re_renderer`. Its reason reads "only the crates that draw: the render worker and the app". It still keeps a GPU driver out of the core, MCP, and the CLI.
  - **13b, the font's licence.** OFL-1.1 enters as an `exceptions` entry for the font crate alone, so no other crate brings a font licence in unseen. Ubuntu-font-1.0 never enters, since egui's default fonts are off. This is a veto line for Trevin, not a question.
  - **13c, the advisories.** Linux screen readers stay. RUSTSEC-2026-0370, 0371, and 0372, reached only through eframe's Linux accessibility bridge, are ignored by name, with the reason ("unmaintained, reached only through eframe's Linux screen-reader bridge; not a vulnerability"). A daily `cargo deny check advisories` job on a control runner checks main and fails visibly. The gate stays `bans licenses sources`, with no conditional advisories step: a PR that brings a new advisory merges, and is flagged the next morning.
- **Warm start** (decision 10). The app starts one kernel worker and one sketch worker when it launches, on a thread of their own, never the UI thread. M5.3 adds the pool's call for it, `KernelPool::warm(n)`, which starts workers the pool then holds as idle, and the same for the sketch solvers; a first rebuild that comes while they're starting waits for them rather than starting more. The rest start on demand. `silico serve` and the CLI are unchanged. ARCHITECTURE.md's pool paragraph says so in M5.3's PR, with the first rebuild's time measured there with and without warm start.

## 11. Determinism

M4.1 section 10 holds for every new command, with A5.

- **Results** are functions of the files read, the commands run in order, and the model the envelope names:
  - every new command's result;
  - a drag's edit, and a mesh with its key;
  - an undo's restored state, byte for byte;
  - the chain's `rewired` lists, and a suppression's lists, in timeline order;
  - a sketch edit's members, in A5's orders.
- **Diagnostics** are described so in their schemas:
  - a drag's frames;
  - `status`'s `disk` and `drag`;
  - which published revision a published read answers from.
- **The app's own state** (the camera, the order of clicks, a dialog's place) reaches no document. A selection reaches one only as names in an edit.

1. **Inserting into a chain** (M5.1). *Taken as recommended (Fable; built, #241):* an insert takes its input's consumer's place, rewiring that consumer to it and listing the change in `rewired` (section 7). FreeCAD's `Body::setBaseProperty` does the same, and so does SolidWorks' insert, except that FreeCAD also rewires a base-less feature after the place, which Silico doesn't (A9). Placing only would leave a chain insert to `replace_text`, since no typed edit can do it one step at a time.
2. **Reordering within a chain** (M5.1). *Taken as recommended (Fable, with the format review's correction; built):* a move is a remove followed by an insert, rewiring both chains and listing every change. The parent and child refusals stay. Its first step rewires a `tool` as `remove_feature` does (A9), where Fable's text said a move never rewires one; that text contradicted remove-then-insert. A move never makes a feature another's `tool`, and a move off a tool's chain past its boolean is refused, naming the boolean.
2b. **A stored name's maker stays upstream** (M5.1; found by /break-it on M5.1's timeline core). *Taken as recommended (built):* after a move or a removal, every maker of a feature's stored names must still be in what its base is built from: its base, and that one's inputs and sketches, transitively. An edit that breaks this is refused, naming the feature and the maker. It's judged per stored name: a name whose makers were all in what the feature's base was built from before the edit must keep them all after it. A name with any maker outside that lineage before the edit is already broken, and the rebuild reports it, whatever the edit does to its other makers. So a move that repairs a lineage goes ahead, and its move back is refused. Move and remove check it from text alone; a document that reaches the state another way fails the feature at rebuild with `reference_broken`.
   - **Why not the gate.** A gate refusal stops the whole document opening and rebuilding. A broken reference reached by `set_field`, `replace_text`, or a hand edit fails only its own feature, loudly, with candidates, while the rest rebuilds, as a SolidWorks part opens with its errors marked. It also keeps today's valid documents valid, with no format change. The edit commands refuse up front, where refusing is cheap and names the fix.
   - **The case.** `b0000001` and `t0000001` are boxes, `j0000001` fuses them, and `r0000001` is a fillet on `j0000001` naming `t0000001.box.Edge1`. Moving `j0000001` after `r0000001`, or removing it, passes the rule above ("names its elements"), since `r0000001`'s name mentions only `t0000001`, not `j0000001`. `r0000001` then builds on `b0000001` alone and fails with `reference_broken`.
   - **Why refuse.** For a move, SolidWorks refuses a reorder that puts a child before what its references come from (docs/ux/solidworks.md, §5, *Editing upstream*), and `r0000001`'s edge comes from `j0000001`'s result. For a removal, M4's `remove_feature` refused an edit that left broken references, naming them, and A9 keeps that spirit. Refusing names the fix for an agent (remove `r0000001` first), where a failed rebuild doesn't.
   - **A note for the worker.** `move_feature`'s checks "before a feature whose elements it names" and "after a feature that names its elements" (`Child::Names`) are cases of the lineage rule (`lineage_broken`). They can go, their tests kept, the message becoming the lineage one. The removal's direct check of a feature whose elements another names stays, since a removed maker can't be parsed.
3. **Suppression in a chain** (M5.1). *Taken as recommended (Fable):* a suppressed feature passes its base through. A feature that names it only as its `base` builds on the nearest unsuppressed feature up the chain. Only true children go with it: its sketch's users, the features naming its elements, and features left with no body. This is SolidWorks' behavior (§5), and FreeCAD's PartDesign, whose suppressed feature's shape is its base's (`Feature.cpp`, `4d929d3301`). Under #196's rule, suppressing a body's first hole would suppress the rest of the part. A pad or revolve whose whole chain is suppressed builds alone, as in FreeCAD 1.1.3 (the port review's correction to Fable's rule). Where FreeCAD 1.1.3 leaves a suppressed root's features that need a base failing, Silico suppresses them (section 7).
4. **The suppression field** (M5.1, a schema change). *Taken as recommended (Fable, with the format review's correction; a protected schema change, in Trevin's batch):* `"suppressed": true` on any feature type, immediately after `name`, written only when true and read as false when absent. The reader refuses `"suppressed": false`, so a document has one spelling, as M2.1's D6 writes optional fields omitted. The schema snapshot changes only by that field, and every saved file and the protected `tests/golden/` stay as they are. Always writing it would rewrite every feature line.
5. **`remove_feature` rewiring** (A9). *Taken as recommended (Fable):* as section 7. Insert and remove must be inverses through typed commands, and FreeCAD's `removeObject` reroutes alike. Removing a chain's root, which FreeCAD allows (leaving "No base set"), is refused, a stated departure.
6. **Undo's model** (M5.2). *Taken as recommended (built):* rebuilt from the cache, not kept. Keeping each edit's model would hold up to the stack's depth in B-reps. A rebuild of a state the cache holds runs no kernel step, and gives the same names and fingerprints (invariant 5).
7. **Undo's bound** (M5.2). *Taken as recommended (built, #260):* 256 MiB of everything the stack's states add beyond what they share, with no count. Each state is its features in shared chunks of 64 (A2), so a step costs its chunk list and the chunks its edit changed. On a 16 MiB document of 50,000 features: the begin's 16 MiB, the first state's 16 MiB, then about 6.3 KB of list and a 21.5 KB chunk a step, so a thousand dragged-arrow values hold about 60 MB, all kept, and the bound holds about eight thousand such steps. An insert, move, or remove near the top of a large document shifts the chunks after it, so it costs nearly a whole copy: sixteen of those on a 16 MiB document fill the bound, and the oldest steps are dropped, counted, with `to` refusing loudly (chunk boundaries that follow features, not places, could lift that later). A bound on whole texts would hold 16 steps of a 16 MiB document, and a count of 100 would let a dialog's Cancel fail after a second of a dragged arrow, which sends an edit a round trip. FreeCAD's default is 20 steps (`MaxUndoSize`, `src/Gui/Document.cpp`), and SolidWorks gives no number (§6).
8. **Undo to a revision** (M5.2). *Taken as recommended (built):* `to`, as designed. A dialog's Cancel and its one-step undo after OK are each an undo to the revision it opened at, refused loudly if the bound has dropped that state, never undoing less silently. An agent groups its own edits the same way.
9. **IDs a sketch edit makes** (M5.10). *Taken as recommended (built):* the request's `ids`, or the core's when it's `null`, in `added`'s order, as designed. This follows decision 20 for features, the client's when given, and a replay passes back what it recorded.
10. **A retyped constraint's ID** (M5.10). *Taken as recommended (built):* it keeps its ID, listed in `modified`. Split's `length` becoming a `distance`, and a merge's `tangent` becoming a `tangent_at`, state the dimension or relation the person placed, in the pieces' terms. Its `value` keeps its meaning. A path to a field the new type hasn't (`constraints.ka000009.line`) is refused loudly. A new ID would make a merge draw a random ID, and `silico fmt --merge-touching` would then write different files on different machines.
11. **Which piece keeps a split or trimmed curve's ID** (M5.10). *Taken as recommended (built):* the start-side piece, as FreeCAD's first piece keeps its index for naming's sake (`82610ca8fa`, `7d8a8b7cc8`). A circle's ID goes to the arc counter-clockwise from `at.0` to `at.1`. Names made from the curve then follow its start-side piece: a chamfer on the pad's top edge over `na000001` chamfers the half that piece makes, as shortening the line would (N7). That's never silent: the edit's `references` lists every feature storing such a name, and the app shows them. Giving every piece a new ID instead would break every reference to the curve after any split, even where the piece is the part a person meant.
12. **Extend, and joining a split** (M5.10). *Taken as recommended:* both in M5.10, extend first (built, #259 and #270), join after it, since SolidWorks has them (§4: power trim extends; Delete on a split point joins the pieces). Extend is `sketch_extend`, as sketch-edit 11 has it. Joining is `sketch_join`, split's exact inverse, on the basis 12b takes.

   **12b. Join's basis** (M5.10; decided: split's exact inverse). FreeCAD's `SketchObject::join` (`SketchObjectOperations.cpp:1285`, from `c5aceb0182`, 2022; C1 continuity `da7d5391af`, 2023) always makes a **B-spline**: both curves go to NURBS and are concatenated, so two lines join as a degree-1 B-spline. Silico has no B-spline type, so FreeCAD's join can't be ported as it behaves. *Recommended:* SolidWorks' behaviour. Delete on a split point gives one line, for pieces held collinear, or one arc, for pieces on one circle. FreeCAD's B-spline is recorded in docs/ports/sketch-edit.md as a departure, and its refusals are kept where they apply: a curve's own two ends, periodic curves, and construction joined to non-construction.

   *Taken (SolidWorks' basis, made exact as split's inverse):* one line or one arc, from two pieces that share a point and are held on one carrier by constraint: a line pair by the split's `tangent_at` (`same`); an arc pair sharing `center` and held `equal`, or a split circle's two arcs. The start-side piece keeps its ID and takes the far end. The other piece, the shared point, and the joining constraint are removed. Constraints naming the dropped piece are re-pointed to the one kept, and duplicates are dropped and listed. Nothing is retyped: a `distance` of the outer ends is exact on one line. Refused: a curve's own two ends, construction joined to non-construction, and pieces not held on one carrier. FreeCAD's B-spline is recorded as a departure. Silico has no B-spline, and the inverse of split needs no new rule. Join is built after extend.

   **12c. Extend's command** (M5.10; from #259's architecture review). `silico_core::extend` is built as a core function. Its command needs three things:
   - **The sketch it starts from:** the revision's sketch as solved and written back, as `drag_begin`'s `prepare` gives it, so the result matches the preview whatever the file's drift.
   - **Its stopper:** a line's one move runs under a solve's time, up to 1,024 unknowns, so the command takes the solver's stopper itself (`cancel` naming it), rather than `extend` dropping it.
   - **Extend to the next curve:** SolidWorks' Extend Entities, so an agent needn't compute it as the app's Gui would. FreeCAD has none: its Extend tool takes the cursor through its snap manager and sends the increment printed to six places (`DrawSketchHandlerExtend.h:293`). An increment can't carry it: `By::Length` is whole nanometres, so an end extended by the nearest one misses an arbitrary crossing by up to 0.5 nm, past the 1e-7 mm the gate and trim count as touching. *Recommended:* a core query giving the nearest crossing past the end (the curve it meets, and the point, as trim finds its cuts), and `By::To(point)` for `extend`, which places the end there exactly: a line's one move to it, an arc's end at it, refused if it isn't on the curve's carrier past the end. *Taken as recommended (the core built, #270):* all three, in M5.10. *As built (#309):* a point on the carrier on the end's side of the other end is taken, short of the end too, which shortens the curve, as a negative increment does (§7's `sketch_extend`); one off the carrier, or past the other end, is refused.
13. **A merge that leaves an edge tangency at a shared end** (M5.10). *Taken as recommended (built, #272):* convert it to a `tangent_at`, its `direction` as last solved, as FreeCAD converts one (`620188073e`) and as sketch-edit 8 has it, rather than refusing it (sketch-edit 10). The port note contradicts itself here, and FreeCAD settles it. Keeping the constraint's ID through the conversion is Silico's own choice (open item 10), where FreeCAD appends a new constraint. Section 13's port of §9's "a merge that would leave an edge `tangent` … is refused" changes to the conversion. A split meets the same case: an edge `tangent` with a curve whose end the split point is (held there by an `on` or a `tangent_on`) leaves two curves sharing an end, edge tangent. #240 now refuses it, naming it, as the merge does (found by the split property at the mutants seed). The conversion recommended here would cover the split too.

   **13b. An `on` a merge makes implied** (M5.10; from `/break-it` on #239). A point held `on` a line or an arc, merged with that curve's end: a T drawn at a line's end, which is exactly what `silico fmt --merge-touching` meets. After the merge the point *is* the end, so the `on` holds by construction. The gate refuses a curve's own point held on it, so keeping it, as FreeCAD does, isn't open to Silico. Options:
   - **(a) Refuse the merge, naming the `on`,** as #239 does today under decision 10 ("no automatic fix-up").
   - **(b) Drop the `on` as implied,** listed in `removed`, as trim drops one at a shared cut (sketch-edit 5).

   FreeCAD keeps it and flags it. Its coincident command adds the `Coincident` and leaves the `PointOnObject`. (The sketch-edit oracle, `merge_holds_own_point_on_line` and the sweep's `edit_32_490`, adding the coincidences one at a time as the command does: FreeCAD's solve finds the `on` redundant, as the probe above does, and main's rollback, emulated, refuses the merge. 1.1.3's command, which has no rollback, makes it with the `on` redundant. Silico refuses it up front, by the gate's own-curve rule. An earlier reading that FreeCAD solves it cleanly came from the harness adding the coincidences in one batch, and was wrong.) 1.1.3, probed: a `PointOnObject` of a point on a line, then a `Coincident` of the line's end with the point; the solve returns −2, with the `PointOnObject` listed in `RedundantConstraints`. `substituteConstraintCombinationsCoincident` (`Gui/CommandConstraints.cpp`) substitutes only an edge `Tangent`, and `removeRedundantPointOnObject` removes a `PointOnObject` only on a B-spline. Validate's fix (`makeMissingPointOnPointCoincident`) adds coincidences and removes nothing either.

   *Recommended, and taken: (b),* scoped as below. I read dropping it as consistent with the exactness rule. The rule forbids moving or snapping a value to make a sketch fit. Here no value changes and no geometry moves: the constraint says what the shared point already makes true, exactly, with no tolerance. It follows trim's decision 5, which the port note already takes for the same case.

   The drop covers only an `on` whose point becomes an end of its own curve (a line's or an arc's end). Any other constraint the merge puts on its own curve stays refused, because each would conflict, not merely repeat:
   - an `on` of a circle's or arc's centre;
   - a `midpoint`;
   - a `point_line_distance`;
   - a mirrored `symmetric`.

   These stay refused, as #239 refuses them: one rule, an implied constraint is dropped, a contradictory one is refused.
