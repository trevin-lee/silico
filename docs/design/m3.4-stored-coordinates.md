# M3.4: stored coordinates

M3.4 (docs/roadmap/m3-sketcher.md) makes a sketch's file hold its last solve. A sketch is solved every time its document is rebuilt, starting from the coordinates the file stores. `silico check` reports a sketch whose solve no longer matches its file. `silico fmt`, and every save, writes the solve back. Decision 4 (M3.2's D3) already stores coordinates in full, as `f64`s, so writing a solve back loses nothing.

## What FreeCAD does

`SketchObject::execute()` (1.1.3, `SketchObject.cpp:318`) solves the sketch on every recompute, from the geometry the document holds, with `solve(true)`. That writes the solved geometry back into the document's properties, so a saved file holds the last solve. On restore (`onSketchRestore`, `:1408`), FreeCAD doesn't solve again unless the sketch has no shape yet. The next recompute that touches the sketch does. A redundant sketch fails `execute` in FreeCAD; Silico keeps redundant constraints that agree (M3.3, decision 5).

Silico does the same with two differences. Every rebuild solves every sketch, because a rebuild is how a document is read. And the drift from a hand edit is reported as data, not left in the file until someone recomputes.

## The fixed point this rests on

A sketch solved on every load from its last solve must come back exactly as it was. Otherwise an unchanged sketch shows drift on every load, for good. This was measured on 2026-10-18 and is kept as two tests in the regular suite, which runs on both platforms:

- **Worker level, the stress corpus** (silico-sketch's `tests/stress.rs`, `every_generated_sketch_that_solves_comes_back_unchanged_from_a_load`). Each case is solved by its own algorithm and by the core's whole fallback order, then solved again from that solution with the whole order, as a load does. All 347 solved runs come back bit for bit, including 29 that BFGS solved.
- **Document level, the oracle's 15 sketches** (`tests/fixed_point.rs`). Each is used as stored and from twenty starts with its points moved up to 2% of the sketch's size. Each is solved, written through the canonical writer and reader, and solved again. All 252 that solve come back with the same bits and the same text.

BFGS alone isn't a fixed point. Started at its own solution, it steps again, by up to 6e-12 relative; 28 of 29 BFGS solutions moved, most of them still moving at a third solve. DogLeg and Levenberg–Marquardt never moved (0 of 178). A load never runs BFGS first: the order starts with DogLeg, which returned every BFGS solution untouched (0 ulps).

Redundancy and arcs aren't fixed points by themselves either. PlaneGCS drops the redundant constraints it picks where it diagnoses, and counts degrees of freedom there; a kept constraint that fixes a value only loosely leaves a dropped one off by more than the solver's convergence (a 2.395781 × 1,984.774709 rectangle kept its perpendicular, a sine below 1e-10, and dropped the vertical, leaving a corner 45 nm off, which its load moved); and a load works an arc's radius and angles out from its stored points, not the solver's values, so an arc held at 45° moved by ulps on load. So every solve that reaches a solution is checked by loads, written as its file would hold it and solved as a load solves it, until a load leaves it where it is, and only such an answer is kept (`Translation::solve`, docs/design/m3.3-solving.md, *Checked by loads*). silico-sketch's `adversarial_document.rs`, `adversarial_redundant_resolve.rs`, and `adversarial_load_path.rs` check rectangles, slots, triangles, circles, and arcs whole: the save's answer against its load's, Ok or refused, bits, and the redundant constraints named.

What's left is a sketch whose DogLeg and Levenberg–Marquardt both fail even from BFGS's solution. It would show drift on every load: a loud failure, not a silent one. No case reached it in 347 runs, and FreeCAD, which solves on every recompute, shares it. No guard is added for it (Main, 2026-10-18).

## Solving in a rebuild

- **Every run solves every sketch** (`recompute::Recompute`), from the coordinates its document stores, through `sketch::solve`.
  - A sketch that solves becomes `FeatureOutcome::Sketch(Arc<SketchSolution>)`.
  - One that doesn't becomes `FeatureOutcome::Failed`, with the solve's error: `over_constrained`, `solve_failed`, or `invalid_result`, naming the sketch and its constraints or geometry.
  - A sketch that failed is a failure of the document, which `silico check` reports, as a feature the kernel refused is. Features using a sketch (M3.6) are blocked by it.
- **A solve is keyed like a step:** by its feature's ID (a solve's errors name it) and the sketch as the file writes it, plane and elements, stored coordinates included. An unchanged sketch in a later recompute takes its last solution without the worker.
  - Only in memory, kept as step results are (`PUBLISHED_KEPT`). One engine has one solver for its life, and a sketch worker is started again only from the build it started from, so the solver's identity needn't be in the key. It would have to be if solves were kept on disk.
  - Not in the rebuild cache on disk: a solve takes milliseconds, and a cached solve would have to carry everything the core reads from the worker's reply.
- **The solver is the recompute's**, beside its kernel: `Recompute::new(kernel)` starts the sketch worker at its first sketch, found as the kernel worker is (`SILICO_SKETCH_WORKER`, or beside the running executable); `Recompute::with_sketches(solver)` gives another `SketchSolver`, and `Recompute::with_sketch_starter(start)` another way to start one. A solver that can't be started (a missing or misnamed worker, one that can't be run, or another build) is the solver's failure, not the sketch's: `worker_unavailable` (the M3 review's start-code decision), passed on as finding or starting the worker said it with the sketch's feature named, and not kept as the sketch's result, so `check` and `fmt` exit 2, write nothing, and the next recompute tries again. That's `SketchWorker` for the clients, and a fake for the core's tests (`fake::FakeSketches`, behind the `fake` feature: it answers a sketch with the values it was sent, met or not, unless told otherwise; it records each request and can hold a solve until it's released or stopped).
  - Sketches solve one at a time on it, in timeline order. They come before any feature that uses them, and today no feature does.
- **Superseding** (M3.3's open low: the solver had no generation). A recompute superseded while its sketch is solving has that solve stopped, as ARCHITECTURE.md's rule for superseded work has it: once it has run longer than replacing its worker takes (`SKETCH_STOP_AFTER`, 10 ms; a sketch worker restarts and solves in 6 to 8 ms, while a kernel worker takes about 30 ms to replace), unless it finishes first. A `cancel` stops it the same way; a dropped engine stops it at once, since nothing is left to stop it later. A stopped solve stays stopped: its later requests (a re-diagnosis from its solution) are refused. A solve that has begun starts no worker, since one would be out of its stopper's reach: a worker that dies during it fails it as `worker_crashed` (or `worker_unavailable`, if it died before its first frame), and the next solve's start replaces the worker. So a newer recompute waits at most that grace behind an older one's solve, which can take up to `SKETCH_TIMEOUT`, and a superseded recompute waiting for the solver stops waiting.

- **A solve must be savable.** A solve is met only to rounding, and where a value sits at its limit, the file's own measure of it can land past the limit. Break-it's case: an arc of radius exactly 1 km solved to points 1 km and one ulp apart, and the gate measures an arc's radius from its points. So each solve runs the gate's sketch rules on the sketch as it would be saved (`sketch::savable`). A solve the gate would refuse is an `invalid_result` naming what the gate names, never a file that can't be opened again.

## Drift

`Model::drift` reports each sketch whose solve differs from its file, with the `drift` code, so no new error code joins the protected list. Compared:

- **Points' `x` and `y`, and circles' `radius`:** exactly, bit for bit. Both are full `f64`s, and the fixed point makes exactness the right test (`exactness-over-heuristics`).
- **Reference dimensions' `value`:** the measure, rounded as the file writes a value of its kind (a length to the nanometre, an angle to the nanodegree, each by the same rounding the reader applies), against the stored value.

The error names the sketch (its feature) and, as elements, every point, circle, and reference dimension that moved, with their total. Its message gives the first few with old and new values, for example "sketch k7f2qx3m solves to other coordinates than its file holds: p0000003 x 4 → 4.5, …". Its suggestion is the fingerprint's, for a sketch: "if this sketch was edited by hand or in a merge since it was saved, run `silico fmt` (or save) to write its solved coordinates; if not, this is a determinism bug or a change in the solver".

A sketch that failed isn't drift: its failure says why.

## Writing back

`Model::fingerprinted` becomes `Model::saved`: the document as a save writes it. Each built feature gets its fingerprint (as now). Each solved sketch gets its points' coordinates, its circles' radii, and its reference dimensions' values, rounded as above. A sketch that didn't solve keeps what its file holds, as an unbuilt feature keeps its fingerprint. `command::Formatted` gains `resolved`: the sketches whose stored values the solve changed, in timeline order, so `silico fmt` can say what it rewrote, as it does for fingerprints.

## Tests

- The roadmap's two:
  - a hand edit to a dimension makes `silico check` report drift naming the sketch and its moved points, and `silico fmt` writes the corrected coordinates;
  - an unchanged sketch re-solved leaves the file's bytes unchanged, through the CLI, on both platforms.
- The fixed-point tests above.
- Recompute: a sketch solved once per distinct sketch (the fake's requests counted); a failed sketch is a failed feature; a superseded solve stops its worker (a slow fake, or the real worker on the impossible chain).
- Drift:
  - each kind that can move (a point, a circle's radius, a reference length, a reference angle);
  - a reference measure that rounds to its stored value isn't drift, and one a nanometre off is;
  - a failed sketch isn't drift.
- `/break-it`: hand edits that make the sketch unsolvable, a reference whose measure can't be written (too large), a sketch at the size limit, and a recompute superseded mid-solve.
