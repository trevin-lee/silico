# M2.5: the rebuild cache's bound

M2.5 (docs/roadmap/m2-document-naming.md) keeps each kernel step's result in `.silico-cache/`, beside a document. As built, it grows without limit: every version of every step stays, and a write killed partway leaves its `.partial-*` file behind for good. This note bounds it.

## What FreeCAD does

FreeCAD has no rebuild cache. Its nearest equivalent is the shapes it saves in the document itself: `PropertyPartShape::SaveDocFile` (`src/Mod/Part/App/PropertyTopoShape.cpp:731`) writes each feature's B-rep into the `.FCStd` archive on save, and a document opens from them without a recompute. That store is one shape per feature, for the version saved, replaced on every save, so it is as large as the document and no larger. It needs no bound and has no eviction.

Silico keeps B-rep out of the document (ARCHITECTURE.md, invariant 6). Its cache is keyed by each step's inputs, so it keeps every version of every step any session has built, and it keeps growing. FreeCAD has nothing to port here; what follows is Silico's own.

## The bound

- **Each cache directory has a bound on the bytes it holds:** its entries and partial files, by their length. The cache belongs to a directory (`.silico-cache/` beside the documents in it), so the documents of one directory share it.
- **The default is 2 GiB** (`cache::DEFAULT_BOUND`). That is twice the largest entry (`MAX_ENTRY`, 1 GiB), so even the largest is kept. It is set per cache (`Cache::with_bound`). No client can set it yet: M4's cache control is to set, clear and inspect it through the command API.
- **An entry larger than the bound isn't written.** Nothing is evicted for it, and it's logged at debug.
- **Nor is an entry no eviction can make room for:** what can't be evicted, plus the entry, would pass the bound. What can't be evicted is the entries the session is writing at once (not in place yet), other processes' partial files not yet stale, and files the cache couldn't remove. It's a miss later. A refusal for the session's own writes is logged at debug. One for files it can't evict is a warning, once a session, naming that cause.

A bound can't avoid every thrash. A document whose steps together take more than its directory's bound misses on its oldest steps at every rebuild, as any LRU cache does with a working set larger than itself. 2 GiB holds about a hundred 20 MB B-reps. A larger part needs a larger bound, which clients can set once M4's cache control exists.

## Eviction

- **What goes:** the least recently used entries, until what's left plus the new entry is at most three quarters of the bound. The slack means the cache doesn't scan again at the very next put.
- **Last use** is an entry's modification time. A write sets it as it renames the entry into place, and every hit sets it again. Both use the system clock at nanosecond precision, set explicitly, because Linux's own file times move only once a tick.
- **Ties** go by the entry's path, so the order is the same whatever order the directory lists in.
- **What is never evicted:** the entry being written, files the cache doesn't recognize, and anything behind a link.
- **Results never depend on eviction.** An evicted entry is a miss, and a miss is a rebuild, which recompute makes byte-for-byte the same.
- **The clock matters only to what's evicted, never to results.** A clock set back makes new entries look old, so they go sooner, which only costs misses.
- **A hit or write that can't set its time still counts** (a read-only cache, or a file system that won't take a time, such as vfat or some network shares). Its entry ages by the time the file system gave it.
- **Use means use from the disk.** A step a session reuses from its own memory renews nothing on disk, so another session may evict it. The next session to open the document misses it once.

## When it runs

- **On put, never on get.** A cache's first put in a session scans the directory, to learn its total; the clones of a cache share what that scan learned.
- **After that,** the cache counts what it writes. It scans again when a put would take the count over the bound, and when it has written an eighth of the bound since its last scan, so other sessions' writes are seen.
- **A scan holds no lock while it reads and removes files.** Other puts that fit by what's known go on meanwhile. A put that would pass the bound waits for the scan in progress, since that scan may be making its room. Every put waits for the session's first scan, before which nothing is known. When the scan ends, what it found counts, plus everything being written when it began and since, whether or not it saw them.
- **The bound is exact for one session,** however many of its puts run at once. With several sessions on a directory, the total stays within the bound plus, for each other session, an eighth of the bound or the entries it's writing at once, whichever is more: each session sees the others' writes at its next scan, but not entries another starts writing before it sees them. Sessions keep no shared index or lock, so they can't block each other, and a crash never leaves one stale.
- **A scan counts exactly:** files' lengths, which sparse files can make sum past what 64 bits hold, are added in 128.
- **A scan reads metadata only:** one `lstat` for each file in the 256 subdirectories. It runs in the job's thread, as the put does now: after the job's dependents are woken, so it never delays them, but before the job counts as done, so the recompute ends after it.
- **What it costs:** about 8 µs an entry on APFS with metadata cached, measured in review. That's milliseconds for thousands of entries, 1.5 to 1.8 s for 200,000 (a full 2 GiB of 10 KB entries), and 4.8 s more to evict 50,000 of them. A fresh session's first put, and each eviction, pays it, and the recompute ends that much later. A background thread for this is M5's, with the app, where a session lives long enough to warm it.

## Partial files

- **A scan removes a `.partial-*` file whose last write was an hour or more ago** (`STALE_PARTIAL`), in the cache's root or a subdirectory. A writer's partial is written as it's made and renamed within moments of its last byte, so a partial an hour old is a write that was killed.
- **A partial dated an hour or more in the future is stale too.** It comes from a write killed while the clock was wrong, or from a server whose clock runs ahead. Otherwise it would count toward the bound until the clock caught up, and one the size of the bound would keep every result out.
- **A writer stalled for an hour** (a hung network filesystem) loses its partial. Its rename then fails, which it warns of, and the entry isn't kept: a miss later, never a wrong result.
- **Why not "older than this process"?** That rule would never clear partials from writes killed after a long session started. And a process's start says nothing about a writer that started before it and is still writing; its partial's time does.
- **Partials not yet stale are counted toward the bound** and left alone, except this process's own, which its puts already count as being written.

## What it logs

- **Each eviction scan is a `cache.evict` span** (debug), with what it found and removed: entries, bytes, and stale partials.
- **A removal that fails** for any reason but the file already being gone (another session evicted it first) is a warning, once per scan.
- **A put refused for files the cache can't evict** is a warning, once a session (see *The bound*).

## What stays the same

- **The entry format** (`silico cache 4`) and the layout. Caches written before this are bounded and cleaned the same way at their first put.
- **Every guarantee the cache already makes.** An entry is used only by the same kernel, platform and secret, and anything that can't be read is a miss.

## Tests

`crates/silico-core/tests/cache_bound.rs`. Expected values are written by hand from the entries' sizes on disk.

- **Under the bound:** puts past the bound leave the cache's total within it after every rebuild, and the newest document's entries all survive.
- **A hit renews an entry:** a step used by every rebuild survives entries written after it and never used again.
- **Identical rebuilds:** a document whose entries were evicted rebuilds through the kernel to the same shapes as its first build.
- **Too large to keep:** an entry larger than the bound isn't written, and nothing is evicted for it.
- **Partials:** a fresh partial (a concurrent writer's) survives a scan; one an hour old is removed, in the root and in a subdirectory; a stale partial that's a link is removed as a link, and what it points at stays; files the cache doesn't know are kept and not counted.
- **Partials count:** a writer's partial counts toward the bound. One nearly the bound's size makes the next put evict every entry.
- **Between scans:** one session building sixty documents stays within its bound after each. It keeps the newest document's own steps, and evicts its block, which it reused only from memory.
- **Future partials:** a partial dated more than an hour ahead is removed; one half an hour ahead is kept.
- **Eviction order:** of eight planted entries with hand-set times, the three oldest go, and the cut falls between two used at once, so the tie by path decides.
- **Two sessions:** two caches on one directory keep it within the bound plus an eighth for each.
- **Hostile directories** (`adversarial_cache_bound.rs`, from break-it): one session's puts at once stay within the bound; eight sessions at once stay within the promise above; sparse files whose lengths sum past 64 bits are counted and evicted; partials at the edge of stale, before the epoch, and of other kinds; names one character off an entry's; links, FIFOs, hard links and read-only subdirectories; bounds of 0, 1, an entry exactly, and `u64::MAX`.
- **Read-only:** a read-only cache's hits are still hits.
