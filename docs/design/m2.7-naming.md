# M2.7–M2.8 design: element names and references

> The names as built are in docs/ports/naming.md, which supersedes the syntax shown here: a primitive's element says its type (`k7f2qx3m.box.Face3`), and an element from above is named by every named element it bounds, with a place `n/m` only where needed (Trevin's decisions, 2026-10-17).

**Status: accepted.** The maintainer took every recommendation below (2026-10-16). The study behind them is `docs/ports/naming.md`. M2.7 builds the names (`silico-core`'s `naming` module); M2.8 the references.

M2.7 builds the element map: every face, edge, and vertex of every step's result gets a name derived from the kernel's history, as FreeCAD's `makeShapeWithElementMap` derives it. M2.8 lets a document refer to elements by those names (fillet and chamfer edges) and resolves the references after an upstream edit, or fails loudly.

## Already decided (ARCHITECTURE.md)

- The kernel returns history; the core builds the element map from it, as a port of FreeCAD's `ElementMap` and `TopoShapeExpansion`.
- Names stored in files are human-readable. No opaque hashes.
- After an upstream edit, a reference resolves to the geometrically equivalent element or fails loudly with a structured error listing candidates. It never silently resolves to another element.
- A placement or move keeps every element's name, as FreeCAD's `makeElementTransform` does (M2 roadmap).

## What FreeCAD's names hold (from the study)

A FreeCAD name records the element's whole derivation: which source elements it came from (modified, generated, or derived from a neighbour), the position in OCCT's list where it came from, the operation, and which object owned the source. For example, the circle edge where a cylinder cuts a box's top face is

```
Face6;:G2(Face1;K-2;:Ha91,F);CUT;:Hk7f,E
```

"generated, second in OCCT's list, from the box's Face6 and from the cylinder's Face1 (also generated, second), by a cut". FreeCAD's own documents can't show even that much: they replace nested names with numbers from a string table (`#3:1;:U;XTR;:H12d7:7,E`), use session object IDs as tags (random per new document), and add a random suffix to duplicate names in release builds. Silico keeps the information and the algorithm, and drops those three.

Internally, Silico's names are a structured type (an enum of origin, derived, upper, lower, duplicate), not strings, so the syntax below is only how they're written and read.

## Decisions for the maintainer

### N1. The syntax of a name in a file

The open question in ARCHITECTURE.md.

- **Recommended: Silico's own compact form.** A name is the ID of the feature that made the element, its kind, and how it came about:

  | Name | Meaning |
  |---|---|
  | `k7f2qx3m.Face3` | Face3 of the primitive `k7f2qx3m`, as the kernel made it |
  | `m3tq8v0z.Face(M a91cw0de.Face1)` | a face the cut `m3tq8v0z` modified from the pin's Face1 (the hole's wall) |
  | `m3tq8v0z.Edge(G k7f2qx3m.Face6, G a91cw0de.Face1)` | an edge the cut generated from the block's top face and the pin's side, the hole's rim |
  | `f00ffxyz.Face(G m3tq8v0z.Edge(...))` | the face a fillet generated from that edge |
  | `f00ffxyz.Edge(U2 f00ffxyz.Face(G ...))` | the second unnamed edge of that fillet face |
  | `x.Face(L a, b, c)` | a face named from the edges bounding it |

  The letters are FreeCAD's (`M` modified, `G` generated, `U` from the element above, `L` from the elements below), with, where two elements would otherwise be named alike, the element's rank among them in that source's OCCT list and how many there are (`G1/2`, N7). Every source is written out in full, so a name says exactly what the element is without a table, and an agent can read it. A name is a JSON string: no quotes, backslashes, or control characters, so it's never escaped.
- Alternative: FreeCAD's grammar with readable tags (`Face6;:G2(Face1;K-2;:Ha91cw0de,F);CUT;:Hk7f2qx3m,E`). The strings would compare directly with FreeCAD's in oracle tests, but the `;:` markers, op codes, and inside-out order are harder to read. A test-only renderer gives the FreeCAD form from the structured name anyway, so the oracle comparison doesn't need it in the file.

### N2. Names don't grow when an element is kept

FreeCAD appends a level (`;:H<tag>`) every time an element passes unchanged through a feature, so a box face kept through twenty features carries twenty levels.

- **Recommended:** a kept element keeps its name exactly. `k7f2qx3m.Face6` stays `k7f2qx3m.Face6` through every feature that doesn't change it, so a reference to it never changes and names grow only with real derivation. This is safe because a solid is consumed once (D2): an element's lineage is a tree, so one origin can't reach a shape twice. (Patterns and mirrors, which copy, add a copy marker: N10, scheme 6.) Silico's names then differ from FreeCAD's strings by those levels, and agree in every relation.
- Alternative: FreeCAD's levels, written out.

### N3. Two elements whose derivations are the same

Rarely, two result elements come about identically. FreeCAD appends `;D` with a random number in release builds, so a reference to either breaks on the next rebuild.

- **Recommended:** number them deterministically, in the result's element order (`...~1`, `...~2`), so every element still has a name, and **refuse a reference to such a name** with a structured error saying it's ambiguous and listing the candidates: an upstream edit can reorder them, and the reference would silently move. In the cases studied (Silico's primitives, booleans, fillets, chamfers), OCCT's list positions keep names apart, and no duplicate arises.
- Alternative: resolve `~n` like any other name and accept that an edit may move it.

### N4. A new error code for a broken reference (M2.8)

The error contract (`tests/contract/`, protected) has no code for "this name no longer names anything".

- **Recommended:** `reference_broken`, appended to the codes. The error names the feature, the parameter (`edges.2`), the reference as written, and, as `candidates`, the likeliest elements: what the history says it became (when an element split into several, each piece), then elements of the last good build that are geometrically identical. Candidates are never applied by themselves. Every broken reference of a feature is reported at once.
- Alternative: report it as `invalid_input`. It isn't an invalid input, though: the document was valid when written, and an agent needs to tell "fix your edit" from "this reference lost its element".

### N5. Fillet and chamfer in the document (M2.8)

D1 (M2.1) deferred them until names exist. They change the document schema, a protected contract.

- **Recommended:**
  ```json
  {"id": "f00ffxyz", "type": "fillet", "v": 1, "name": "round the rim", "base": "m3tq8v0z",
   "edges": ["m3tq8v0z.Edge(G k7f2qx3m.Face6, G a91cw0de.Face1)"], "radius": 1}
  {"id": "c4mf3rqa", "type": "chamfer", "v": 1, "base": "f00ffxyz",
   "edges": ["k7f2qx3m.Edge1"], "size": {"distance": 1}}
  ```
  The feature consumes `base`, as a boolean does (D2). Each edge is stored by name only (no edge number beside it, which would go stale the way FreeCAD's index names do, and no `?` marker for a lost one): a rebuild never rewrites a reference. The chamfer's `size` takes the kernel's three forms (`distance`; `distance` and `other`; `distance` and `angle`); the two uneven ones measure `distance` along a reference face, which the document then names per edge too (the details are settled with the chamfer in M2.8).
- Alternative: store the edge number beside the name as a hint for resolution. FreeCAD does, and it's what lets FreeCAD fall back to "whatever element is now at that index", the silent re-pointing ARCHITECTURE.md forbids.

### N6. A fillet with one broken edge among several (M2.8)

- **Recommended:** the whole feature fails, with `reference_broken` for every broken edge, and its users are blocked (M2.4's failures). Nothing is built from a partial reading of the user's intent.
- Alternative: build the fillet on the edges that still resolve, and report the broken ones. SolidWorks may do this (to confirm); it shows the model sooner, but the part is then silently different from what was asked.

### N7. An element modified one from one, over and over (decided in review)

The review measured names growing a level for each feature that modifies an element: a plate's top face, modified by each of 150 holes, nested 150 deep, its rims 2.6 KB each, 805 KB for one solid's names, and inserting an earlier hole renamed every later rim. A depth bound then made such a face unreferenceable for good.

- **First decided (the maintainer, 2026-10-16):** a run of single-source, first-position modifications written as the origin element and `*` (`pppppppp.Face6*`). Building it showed a second source of renaming: with no earlier hole the rims were `G2 ... Face5` and `G ... Face6`, with one they were the other way round, as OCCT's lists ordered them differently.
- **Decided (the maintainer, 2026-10-16, on a Fable analysis), superseding the star:**
  - An element an operation modified from one element, as that operation's sole result of it (nothing else modified or generated from it of its kind), is its source's own name exactly, with no marker: `pppppppp.Face6` after any number of holes. The operation is held with the name as data that isn't part of its identity, for FreeCAD's form and FreeCAD's orders. Unique, since such a step makes one element of one; a face kept and also modified (a broken history) gives two names alike, numbered `~1` and refused (N3).
  - A source's position in OCCT's list is written only where it's needed: names are built without positions, grouped by kind and name, and in a group of m ≥ 2, each source is written `n/m`, the element's rank among the group in that source's list (`c.Edge(G1/2 ball.Face1, G1/2 pin.Face1)`; a split face's pieces `s.Face(M1/2 p.Face6)`, `s.Face(M2/2 p.Face6)`). The raw positions are held as data, not identity. `~n` only where members still coincide. An `n/m` name is stable: it can be referenced.
  - The spelling `1/2` is part of the name grammar; the maintainer can change it before M2.8 parses references.
  - A hole's rims are `c0000149.Edge(G pppppppp.Face6, G y0000149.Face1)` and `...Face5...` with no hole before it or any number. FreeCAD writes a level per feature and hashes it, and writes every position.
  - The analysis's census: collisions occur only where elements split and where curved faces meet curved faces in loops (a ball with a through hole, a torus with a pin, a tube's wall); in each, positions are the only thing that tells them apart. The residual case, OCCT reordering look-alikes the same way in every list, so ranks swap silently, is FreeCAD's too and wasn't reproduced; it's recorded, not guarded.

### N8. The operation in a name, and pieces (decided in the milestone review)

The milestone review (MF1, critical, proven on the real kernel) found two silent re-pointings. A derived name's text didn't say its operation: the parser took it from the feature as it is now, so a cut made a common took a reference to its rim for the common's rim, a different edge. And N7 held under any operation: a box's Edge9, modified one from one, kept its bare name under a cut, a common, and a cut with base and tool swapped, three different edges, and a fillet of it took each in turn (removing 0.429, removing 0.107, adding 0.107).

- **Decided (Fable, 2026-10-18, on Trevin's behalf; the protected changes approved by Trevin):**
  - Every name writes its feature's type after the ID, an operation's as a primitive's: `cccccccc.cut.Edge(G aaaaaaaa.box.Face6, G bbbbbbbb.cylinder.Face1)`, `ffffffff.fillet.Face(G aaaaaaaa.box.Edge7)`, the last resort `cccccccc.cut.Face7`. The parser reads it from the text and never from the feature: a word another than the feature's now reads, and the lookup breaks the reference, with candidates.
  - N7 holds for *bites* only: where the operation keeps what of the element lies outside its other operand (a cut's base, a fuse's operands, a fillet's or chamfer's input), as for the holes, bosses, and blends it was made for. Where it keeps what lies inside (a cut's tool, a common's operands) the element is a *piece*, the feature's own one-`M` derived name, as FreeCAD names it: `c0000001.cut.Face(M y0000001.cylinder.Face1)`, the hole's wall; `cccccccc.common.Edge(M aaaaaaaa.box.Edge9)`. In the builder, `OpCode::bites(input)`: a cut, its base only; a common, never; a fuse, a fillet, a chamfer, always. A cut's base and tool swapped flips the side too, so the same rule catches it.
  - The naming scheme is 3.
- **Not taken:** a set of the operations an element passed through, written on sole-modified names. Fable showed it isn't stable: the first hole renames `Face6` to `Face6{cut}` and with it every rim derived from it, which N7 exists to stop, and a common inserted before the cuts changes the set again. Nor writing the operation on derived names alone, which leaves a flipped piece silent, nor FreeCAD's level per feature, which undoes N7.
- **Residuals, recorded:** a cut made a fuse keeps a base's element bitten alike: silent, and the kernel gives the same element, so nothing re-points. A fuse's or a common's operands swapped make the same solid, and its bites and pieces are named alike; its generated elements list their sources base first (Silico orders sources by role, FreeCAD by object), so a reference to a rim breaks, loudly, the reordered rim its first candidate (found writing N8's tests, which Fable's decision had expected alike). Commons in a row grow a level each, and inserting, deleting, or reordering one renames, loudly. A tool's element kept whole, then trimmed by an edit, becomes a piece: the bare reference breaks, with the piece as its candidate.

### N9. The side of every source (decided in the milestone review's second round)

Round 2 found N8 still let two edits move a fillet silently. A cut's base and tool swapped re-pointed a reference to a piece of an edge split on both sides, both written `cccccccc.cut.Edge(M1/2 aaaaaaaa.box.Edge9)` (R2F1, the format review, on a fork-shaped tool: a fillet took 0.034336 from the outside piece, then added 0.008584 to the inside one). A tool's element kept whole kept its bare name under a cut and a common, so a void's concave rim and the pin's convex rim were one name (R2B1, break-it: +0.05153 then −0.05153).

- **Decided (Fable, 2026-10-18, on Trevin's behalf; no protected change):**
  - A third source letter, `I`: what an operation keeps of an input inside its other operand (`OpCode::bites` false: a cut's tool, a common's operands), kept whole, trimmed, or split, is the feature's own, its source `I`: `cccccccc.cut.Edge(I bbbbbbbb.cylinder.Edge3)`, `cccccccc.cut.Edge(I1/2 aaaaaaaa.box.Edge9)`. N8's one-`M` piece is withdrawn; `M` is only a biting input's source.
  - Kept whole is no separate fate: the kept step asks `bites` as the derived step does. A kept `I` has no OCCT position (held outside the identity), and FreeCAD's form writes it as its source.
  - `bites` is read in two places, both to pick the letter. The N7 collapse is "a sole `M` at OCCT's first position"; an `I` never collapses.
  - Grammar: `source = ( "M" | "G" | "I" ) [ place ] " " name`. The naming scheme is 4.
- **What it changes beyond the findings:** N8's loud boundary (a tool's element kept whole, then trimmed by an edit, became a piece and its bare reference broke) is gone: a piece keeps one name whole or trimmed. The void's elements, a blind hole's floor, and a common's untouched faces are the feature's own.
- **Not taken:** roles written on every source (a fuse's or a common's swap would rename everything, loudly and needlessly); `I` only on modified sources (leaves R2B1, a kept element having no letter to differ by); accepting either as a residual (ARCHITECTURE forbids silent re-points).
- **Residuals, recorded:** a vertex generated from an edge of one input and a face of the other keeps its text under a cut's swap (sources by kind before input): the same point, no vertex references in M2, and FreeCAD alike. The others are N8's.
- **For M3.6:** a name must fix the side of every source it names that's another feature's: by the type word where the word fixes it, by `I` where it doesn't. A sweep's own boolean step bites its sweep (the word fixes the side), so no `I` ever appears in a sweep feature's names; a sweep's profile, which the step keeps neither side of, is written `M`, uncollapsed, as M3.6's review planned. M3.6 takes scheme 5.

### N10. Copies: the copy marker (scheme 6, for patterns and mirror)

N2 left a copy marker for features that copy. A linear pattern, a polar pattern, and a mirror place copies of an original's tool (or of a whole solid) and fuse them into, or cut them from, a solid that already holds the original. Without a marker, each copy of a pad's side face would be `p0000001.pad.Face(G s0000001.sketch.Edge.6t7v8w9x)`, the original's name, and N2's tree would have one origin reaching the solid several times.

- **Decided (Fable, 2026-10-29, the maintainer may veto; docs/ports/patterns.md §3, decisions 7 and 10; the design is docs/design/m6.0-patterns.md, section 3):** one form and three type words are added, and nothing else changes:

  ```text
  base     = …                                                     scheme 5's forms, unchanged
           | feature "." type "." kind "(" ( "C" | "S" ) instance " " name ")"
                                      a copy of `name`, placed at `instance`. `C`: a copy of `name`,
                                      an element of a feature's tool; `S`: a copy of `name`, an
                                      element of the base's solid
  instance = offset ( "," offset )*   one offset per direction of the feature, in the document's
                                      order (direction 1 first), trailing zeros left off: the
                                      last offset written is 1 or more
  offset   = "0" | digit19 digit*     steps from the original, at most 2^32 − 1, no leading zero
  digit19  = "1" | "2" | "3" | "4" | "5" | "6" | "7" | "8" | "9"
  digit    = "0" | digit19
  type     = … | "linear_pattern" | "polar_pattern" | "mirror"
  ```

  | Name | Meaning |
  |---|---|
  | `t0000001.linear_pattern.Face(C2 q0000002.pocket.Face(G s0000003.sketch.Edge.cc000001))` | the wall of copy 2 of pocket `q0000002`: two steps along the pattern's one direction |
  | `t0000001.linear_pattern.Face(C0,1 q0000002.pocket.Face(G s0000003.sketch.Edge.cc000001))` | the same wall in a grid, no steps along direction 1 and one along direction 2 |
  | `t0000001.linear_pattern.Face(C2,1 q0000002.pocket.Face(G s0000003.sketch.Edge.cc000001))` | the grid's copy two steps along direction 1 and one along direction 2 |
  | `m0000001.mirror.Face(C1 q0000001.pocket.Face(G s0000002.sketch.Edge.nb000001))` | a mirror's one copy of a pocket's wall |
  | `m0000002.mirror.Face(S1 p0000001.pad.Face(G s0000001.sketch.Edge.na000001))` | a whole-solid mirror's copy of a face of its base |
  | `m0000002.mirror.Face(S1 t0000001.linear_pattern.Face(C2,1 q0000002.pocket.Face(G s0000003.sketch.Edge.cc000001)))` | the whole-solid mirror's copy of the grid's copy (2, 1): nested, the copy applied last outermost |
  | `t0000001.linear_pattern.Edge(G p0000001.pad.Face(G s0000001.sketch.Face1), G t0000001.linear_pattern.Face(C2,1 q0000002.pocket.Face(G s0000003.sketch.Edge.cc000001)))` | the edge where copy (2, 1)'s wall meets the plate's top: a section with the base |
  | `t0000001.linear_pattern.Face(M1/2 t0000001.linear_pattern.Face(C2 q0000002.pocket.Face(G s0000003.sketch.Edge.cc000001)))` | the first piece of copy 2's wall where the base splits it |

  - **The original is unmarked.** Its elements are the base's and keep their names exactly (N2, N7): a fillet on the original's edge is untouched by adding a pattern after it. The original's instance has every offset 0, which trailing zeros leave empty, and `C` or `S` alone is refused, so no name marks it.
  - **One spelling an instance.** The parser refuses `C`, `C0`, `C2,0`, `C0,0`, `C02`, `C2,`, a sign, a space, and an offset past 2^32 − 1, and the same after `S` (`S`, `S0`, `S2,0`, …), each naming its place in the name, as it refuses any name it can't read. Instance (2) and instance (2, 0) are one instance, written `C2`, so adding a second direction renames no copy.
  - **A grid writes direction 1's offset first,** never FreeCAD's flat `i·n₂ + j`, which renames every copy past the first row when direction 2's count changes (patterns.md §3, rule 5).
  - **An instance counts steps along `directions` by place, as written** (Fable, 2026-11-10). A direction's fields, `along` included, and the directions' order are the pattern's values: an edit to them moves instances and renames none. So two directions swapped keep their names by index: `C2,1` is two steps along the new direction 1 and one along the new direction 2. With direction 1 removed and direction 2 kept, `C1` is one step along the one direction left, and `C0,1`, two offsets in a pattern of one direction, finds nothing: `reference_broken`, with candidates.
  - **A mirror's copy is index 1: `C1` of a tool, `S1` of the solid.** A mirror is a pattern of two instances.
  - **A copy's elements are the tool's, wrapped once.** Copy k's elements are numbered as the tool's, so the core names them from the tool's map (`ElementMap::copy`) without asking the kernel or reading OCCT's lists. In the structured type it's one variant, `Name::Copy { feature, operation, kind, copied, instance, of }`, `copied` saying which was copied (`Copied::Tool` for `C`, `Copied::Solid` for `S`), whose parts are its inner name's: a copy of an unstable name is unstable, and the depth bound counts a level for each copy.
  - **Past the depth bound,** a copy's element is named by its number in the step's result, assigned after the step, as any element past the bounds is (*How M2.7 is built*), never by the tool's element number, which every copy of that element shares.
  - **The pattern's steps bite every input** (`OpCode::{LinearPattern, PolarPattern, Mirror}`, each input `Outside` at every stage), base and copies, as a sweep feature's boolean bites its own sweep (N9, M3.6's S4). So a copy's element kept whole, or modified one from one, keeps its `C` or `S` name; one the base or another copy splits is ranked as any split is; and no `I` appears. The letter fixes the side: an `S` copy is always fused; a `C` copy's side is its inner type word's (a pad's or a revolve's fused, a pocket's or a groove's cut).
  - **The parser judges by the type word in the text** (N8), whatever the feature is now, as it refuses a primitive's word before a derived form (`box.Face(…)`). It refuses, `invalid_input` at the column where the form goes wrong: a `(C…)` or `(S…)` form under a word that doesn't copy (`pad`, `cut`, `fillet`, any but the three); more than one offset under `polar_pattern` or `mirror`; more than two under `linear_pattern`, after either letter; and a `C` whose inner name's type word isn't a sweep's (`pad`, `pocket`, `revolve`, `groove`), since a tool is always a sweep step: `(C2 k7f2qx3m.box.Face6)` is refused. An `S`'s inner name may be of any word the base can hold. An instance the feature doesn't make (`C3` of a count of 3, `C2` of a mirror) reads, finds nothing, and the reference breaks with candidates.
  - **FreeCAD's form** writes the original's form and FreeCAD's postfix (`Data::indexSuffix`, `src/App/ElementNamingUtils.cpp:116-124`): nothing for the first copy, `_k` from the second, as FreeCAD 1.1 numbers the copies of one direction (`FeatureTransformed.cpp:347` at the 1.1 branch point, `af2d42a4aa`; FT:357-371 in docs/ports/patterns.md §3). A grid's copy writes Silico's offsets (`;_2,1`), not FreeCAD's flat place `i·n₂ + j` (`FeatureLinearPattern.cpp:250-256` at `af2d42a4aa`): the form orders a name's sources and the elements above and below it (`freecad::compare`), so it decides saved names' text, and a flat place would rename them when direction 2's count changed, which the table below forbids, and needs a count no name holds. So a grid's copies neither compare with FreeCAD's nor order as FreeCAD orders them; should M6.4's oracle need FreeCAD's exact text of a grid, it takes a renderer of its own given the counts, apart from the ordering form (decided by Main, 2026-11-16, a consistency fix of the approved design; the maintainer may veto).
  - **Open, for M6.3, before any step builds a copy:**
    - **FreeCAD's op code in a pattern step's names.** FreeCAD 1.1 fuses an additive tool's copies and cuts a subtractive one's (`FeatureTransformed.cpp:392`, `:399` at `af2d42a4aa`), so its form of a cut step's elements writes `CUT`. An `OpCode` carries no boolean, so M6.1 gives the three types' `code()` `FUS`, with a doc line saying a cut step's form differs; nothing names a copy before M6.3, so no saved name and no candidate order meets it. M6.3 settles a cut step's form (the step's boolean in FreeCAD's form, or `FUS` kept and the difference recorded, as S4 keeps `XTR` for a sweep's boolean) and pins the cut case's form with a test (Main, 2026-11-16).
    - **A copy's element past the bounds.** `ElementMap::copy` leaves out a copied name past `MOST_DEPTH` or `MOST_WEIGHT`, never numbering it by the tool's number. The step's builder, given an input element its map doesn't name, numbers it by that input's number today (`kept`, `source_name`), which for a copy map would be the tool's number again; M6.3 numbers such an element by its place in the step's result, as the bullet above has it, and pins it with a test that runs a step over a copy map past the bound.
  - **What stays and what breaks** is patterns.md §3's table: a count raised, an instance brought back from `skip`, a distribution, `reversed`, a direction's `along`, an axis, or a plane changed, the directions swapped, and a second direction added rename no copy, the instances moving under their names; a count lowered, an instance skipped, and an original taken out of `copies.features` remove the names they remove, and a reference to one breaks, loudly, with candidates; `copies` switched between `features` and `solid` breaks every copy's name (`C` to `S` or back), loudly, with candidates.
- **The scheme is 6, a strict superset of 5** (patterns.md, decision 10). Every scheme-5 name is a scheme-6 name, written byte for byte alike, naming the same element, so a document of either scheme is read as it is: no migration and no refusal. A document's `naming` reads as 5 or 6, and a missing one as 5 (`UNRECORDED_NAMING_SCHEME` stays 5); every save writes 6; any other scheme is refused, naming the field. An older Silico refuses a scheme-6 document, naming it, which is right: it can't read a `C` or `S` name.
- **Not taken:** FreeCAD's flat index; one offset for every direction always (one rule fewer, but adding direction 2 renames every copy); indices from 1 (the index is the multiplier in a position's arithmetic, as main's `SuppressedIndices` counts, `cdb4624675`); negative offsets now, for symmetric patterns (docs/roadmap/m6-features.md, open decision 6: a scheme 7 adds them later, reading 6 as 6 reads 5).

## How M2.7 is built (no decision needed)

- **Adjacency from the kernel.** FreeCAD names elements that have no history (a fillet face's new edges and vertices) from their neighbours, which needs the result's topology: each face's edges, each edge's vertices, in OCCT's order, and each face's outer-wire edges. The worker reports them as raw facts with each history (invariant 2: workers stay dumb), and the core checks them like the rest of a history.
- **Names in the core.** `naming::Name` (the structured name), `naming::ElementMap` (each element's names, the first canonical, and each name's element: two-way, every name unique), and the naming algorithm from history, inputs' maps, and adjacency, in FreeCAD's order: kept by identity, modified and generated with positions, names from above, names from below, and, where FreeCAD leaves an element unnamed, its number (unstable). FreeCAD's second round, for a whole solid an extrusion's profile generates, waits for extrusions (M3). A primitive's map is its elements' own names; a move keeps its input's map. Every name is bounded in depth and size; past the bounds an element is named by its number.
- **Named when asked for**: a model names a feature's elements the first time its map is asked for, from the maps the engine keeps by naming key (a feature's step, ID, and inputs' naming keys), so a feature named alike isn't named again and an edit names only what it changes. Maps aren't written to the cache; the histories they're built from are.
- **Compared with FreeCAD**, through a renderer of FreeCAD's form without its tags: the ported `TopoShapeExpansion` tests (booleans, fillet, chamfer, transforms) name for name, `TopoShapeTest.py`'s map sizes, and `TestTopologicalNamingProblem.py`'s element-map tests. FreeCAD's known defects (the stale text in names from below, random duplicate suffixes) are expected as their intended relations, and each is noted where it differs.
