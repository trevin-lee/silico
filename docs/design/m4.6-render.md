# M4.6: render, a PNG of the model

`render` draws the model to a PNG without a window, from a named view or a camera, with elements highlighted, and returns the camera it used. Its request, result, and errors are M4.1's (docs/design/m4.1-command-api.md, `render`, and section 6's limits and *Files a command writes*). This note settles:
- the process it runs in, and the new crate;
- the protocol between the core and that process;
- what the core does before it asks: the meshes, the camera, highlights, and checks;
- what a render looks like;
- the ID buffer the tests read;
- the build steps.

It changes no contract until the command lands: the protocol's messages aren't one, and the command's JSON shape is M4.1's.

## Where it runs (decision 29)

A render worker process, `silico-render-worker`, from a new crate, `silico-render`. It's one more worker on `silico-worker`'s loop, beside the kernel and sketch workers: the inherited socket, the request loop, logging, and the same framing.
- **A timeout that stops the work.** The core kills a worker that's past its 30 seconds, and starts a new one for the next render. A GPU or driver hang inside the core's process couldn't be stopped, only stopped waiting for.
- **A crash is `worker_crashed`, and a missing GPU is `worker_unavailable`** (#89's code; `worker_crashed` until #89 merges). No new error code.
- **`silico-core` doesn't depend on `silico-render`, `wgpu`, or any GPU crate.** It speaks to the worker through `silico-protocol`, as it speaks to OCCT. The core needs no unsafe for this, and `silico-render` has none of its own (`wgpu` and its backends are its dependencies' unsafe, as `cxx` is the kernel's).
- **No C++ in the app process.** The render worker links none, so it's Rust only. Mesa is a shared library `wgpu` loads in the worker process, and only there.

### The renderer: `re_renderer`, pinned to the Rerun SDK's version

`silico-render` draws with `re_renderer` 0.38.1, Rerun's `wgpu` renderer (it uses `wgpu` 30), pinned `=0.38.1` beside the workspace's `rerun` SDK. #50's M4.6 plans `silico-render` as the crate M5's viewport grows from, on `re_renderer`. So the render an agent sees is drawn by the same code that will draw a person's viewport: one renderer, one look, one set of bugs.
- **It has the ID buffer already.** Its picking layer (`draw_phases/picking_layer.rs`) renders each object's and instance's ID into a 32-bit-per-channel target and reads it back. Each B-rep face is an instance of its own (below), so the ID buffer gives each pixel's face, or edge, exactly.
  - Its picking ID is per instance (`mesh_renderer.rs:157`), so each face is a mesh and a draw of its own. That's nothing for one render on lavapipe. It's a cost M5's viewport inherits on large models (thousands of draws a frame), to be met there by per-triangle IDs: a fork, as ARCHITECTURE.md allows one, or the fallback's per-triangle `R32Uint` target.
- **It has the highlight already.** Its outline pass, Rerun's selection look, outlines what's highlighted. Its additive tint colours a highlighted face.
- **It runs headless.** Its own tests build a `RenderContext` from any adapter with no surface (`context_test.rs`), and render on lavapipe on Linux.
- **The cost:**
  - a set of `re_*` crates, `re_video` among them, with its default features, which `re_renderer` turns on and Silico can't turn off: AV1 through `re_rav1d` (a Rust port of dav1d: no C to build), and `ffmpeg-sidecar`, which runs an `ffmpeg` program only when a video is decoded, which a render never does;
  - the default features' importers (`dae`, `gltf`, `obj`, `stl`), which `default-features = false` leaves out;
  - `cargo-deny` has to pass on all of it, a check for the build's first step.
- **The fallback** if the first step's probe finds `re_renderer` can't be used headless on lavapipe, or doesn't pass `cargo-deny`: plain `wgpu` 30, with two pipelines and their WGSL. One draws shaded triangles, writing each pixel's face ID into a second, `R32Uint`, colour target; the other draws edges. That's about the same code as the probe, but M5 would then draw differently. Decision R1 below.

### The rasterizer: Mesa's lavapipe, pinned in pixi (decision 5)

Measured on the maintainer's Mac:
- conda-forge's `mesa-lavapipe` 26.2.5, with `libvulkan-loader` (both on `osx-arm64`, `linux-64`, and the other platforms Silico builds), gives `wgpu` 30 a Vulkan adapter: `llvmpipe (LLVM 23.1.3, 128 bits)`, `device_type: Cpu`, `Mesa 26.2.5`.
- That needs `wgpu`'s `vulkan-portability` feature on macOS, `VK_ICD_FILENAMES` pointing at the environment's `lvp_icd.*.json`, and the environment's `lib` on the library path. The probe: `/tmp/w3/lvp`.
- `mesa-lavapipe` needs `[system-requirements] macos = "15.0"`.

**Recommended (decision R2): the worker renders on lavapipe whenever it has it, and on the machine's GPU only when it doesn't.**
- With lavapipe everywhere, a render is drawn by one rasterizer of one version on every machine Silico's pixi environment runs on, the maintainer's Mac and CI's Linux runner alike. An agent sees what a test saw: the same rasterizer and shaders, so the same elements at every pixel but those on an element's boundary, and shading that may differ in the last bits.
- The worker never meets a GPU driver's hang or crash in the pinned setup.
- At M4's sizes (up to 4,096 pixels a side, the meshes of one part) a CPU rasterizer takes a fraction of a second. The render limit is 30 seconds.
- The app (M5) draws its viewport on the GPU, in its own process; that isn't this command.

**How the worker gets its rasterizer.** Never from ambient environment. `Worker::spawn_checked` clears a worker's environment, and an MCP host starts `silico serve` without pixi's activation, so nothing set in a shell can be relied on.
- **Where lavapipe is,** compiled into the worker. `silico-render-worker`'s build script records lavapipe's ICD (`share/vulkan/icd.d/lvp_icd.*.json`) and the Vulkan loader's directory from the pixi environment it's built in, as `cargo:rustc-env` values (`rerun-if-env-changed` on the environment's prefix, and `rerun-if-changed` on its `conda-meta`, so installing or removing lavapipe later is seen). There's no file beside the binary, so a moved target directory, cargo's `build-dir`, or a worker found through a variable can't lose it.
- **The worker sets its own environment.** At startup, before it touches `wgpu`, it re-executes itself (`std::os::unix::process::CommandExt::exec`, no `unsafe`), with these added, but only when the compiled-in ICD exists (under `Any`, a missing lavapipe then leaves the machine's own Vulkan drivers visible; under `Software`, it goes on to refuse cleanly):
  - `VK_ICD_FILENAMES`, to lavapipe's ICD;
  - the loader's directory on `DYLD_FALLBACK_LIBRARY_PATH` (macOS) or `LD_LIBRARY_PATH` (Linux);
  - `LP_NUM_THREADS` (below).

  The inherited socket survives the exec, and once they're set, the second start runs. The restart is marked (`SILICO_RENDER_RESTARTED`), so a restart that lost a variable on the way fails, naming it, instead of restarting forever. A signed macOS app with the hardened runtime would need the `allow-jit` entitlement (llvmpipe compiles its shaders) and `allow-dyld-environment-variables` (the loader's path) for this to work; none is signed yet. Nothing in pixi's activation changes, so no other program's library resolution does, and the core knows nothing of Vulkan or Mesa.
- **The adapter policy** is the core's one say: a setting given when the render client is made (`RenderAdapter::Software`, the default, or `RenderAdapter::Any`), passed to the worker as an argument, not an environment variable.
  - `Software` takes only a CPU adapter, and is `worker_unavailable` without one, its cause saying lavapipe wasn't found (the paths compiled in gone, or no ICD there).
  - `Any` prefers a CPU adapter, then a discrete GPU, then any, as `re_renderer`'s own test adapter choice does.
  - A machine with neither is `worker_unavailable`, with a cause naming the backends tried.
- **llvmpipe's threads.** llvmpipe runs a thread per core by default. The worker sets `LP_NUM_THREADS=2`: renders are small, and the machine's other work (rebuilds, CI's gates) needs the cores. The build's probe measures a 4,096² render at two threads (below).

Pixels still aren't results (M4.1 section 10). LLVM generates different code on ARM and x86, and nothing reaches a name, a file the core checks, or another result from them. Tests read the ID buffer against the projection by hand, never stored images (decision 5).

### Measured: the probe (2026-10-25, the maintainer's Mac, M4 Pro)

A standalone probe (`/tmp/w3/lvp/rrp`, not in the repository) used `re_renderer` 0.38.1 with `default-features = false` and `wgpu` 30. It drew a 40 × 20 × 10 box headless on lavapipe, each face an instance of its own, from `front`, with `LP_NUM_THREADS=2`, `VK_ICD_FILENAMES`, and the loader on `DYLD_FALLBACK_LIBRARY_PATH`. It read the picking layer back, in release:
- **At 400 × 400:** the context took 0.4 s to make, and the render and readback 0.06 s. Every pixel more than one pixel inside the hand-projected rectangle of the front face (`Face3`) was `Face3`'s ID, and every pixel more than one pixel outside it was the background. The pixels off: 0. Peak memory 142 MiB.
- **At 4,096 × 4,096:** the render and readback took 0.41 s. The pixels off the hand projection: 0. Peak memory 1.6 GiB, from the 4× multisampled colour and depth targets and the picking layer with its readback. lavapipe's `max_buffer_size` is 2 GiB.
- **One trap:** macOS strips `DYLD_*` variables from a child of a protected system binary (`/usr/bin/time`), which made lavapipe disappear. The worker's re-exec of itself isn't one.

**Step 1's probe, in the repository** (`silico-render-probe`, `tests/probe.rs`, and the `render` bench on CI, run 40179967390), with lavapipe's paths compiled in and the probe's environment cleared. The Mac's memory is `/usr/bin/time -l`'s maximum resident size (run with the paths set by hand, as SIP strips them through it) and `ps -o rss`; the VM's is the probe's own `VmHWM` and `VmRSS`:

|---|---|---|---|---|

- The ID buffer's counts are the same on both machines, pixel for pixel, though llvmpipe vectorizes 128 bits wide on the Mac and 256 on the VM (which has FMA and AVX-512).
- On Linux, the memory is given back once the context is dropped. On macOS it isn't, so a worker that drew a large render keeps it, and stopping the worker after a large render (above) is what gives it back on both. Remaking the context in the worker wouldn't on macOS.

So a full-size render is far inside the 30-second limit on both machines. Its memory is large, and a real part's is larger than the box's: a CTC-scale part with highlights at 4,096² peaked at 3.9 GiB (step 2's review), and each face drawn holds about 75 KiB. So the render tests at the limit run one at a time, each with every test thread (a nextest test group, as the document reader's memory-heavy tests do), and stay out of mutant runs; and the core's "large render" for stopping the worker (below) is to count faces as well as pixels.

### ARCHITECTURE.md's worker rules (decision R5, decided)

**Decided** (Fable for the maintainer, 2026-10-25, `~/.cache/silico-review/m4.6-render-fable.md`; his veto open): ARCHITECTURE.md's *Deterministic kernel* rules are scoped to the workers whose output is a result: a shape and its history, a solve, a measure, a mesh (the kernel, sketch, and assembly workers). The render worker's outputs, a PNG and the ID buffer, are not results (M4.1 section 10 and decision 5), so none of the rules binds it:
- Mesa's lavapipe and its LLVM come from conda-forge, pinned by version and hash in `pixi.lock`;
- llvmpipe runs two threads (it rasterizes tile by tile, so its pixels don't depend on the thread count);
- there's no trap check (below).

**In exchange, one rule: nothing the render worker returns reaches a result, a name, a document, the cache, or a stored expected value.**
- The core computes the camera, decides which bodies are in view and at what mesh level, resolves every highlight name, and decides every refusal but a worker fault before the scene is sent. The worker's only refusal of a scene is of one that fails `RenderScene::check`, which the core never sends; beyond that it fails only as a worker does, a fault of the machine and not the scene: no adapter it may draw on (`Refusal::NoAdapter`, which the core words as `worker_unavailable`); the GPU (lavapipe's: the machine's memory) out of memory (`Refusal::OutOfMemory`, `resource_exhausted`); any other GPU or renderer error, as an internal one; a crash; a timeout. After a failed render it keeps no render context.
- No command returns the ID buffer.
- Tests read it only against a projection computed by hand: exact inside a face, within one pixel of an element's boundary (a rasterizer's quantization, which the vertex transform's `f32` math can move by a subpixel between platforms). Never against a stored image or buffer, and a PNG's bytes and `png_bytes` are never compared.
- The viewport's picking (M5) reads it as a selection, resolved to a name at once.

### Floating-point traps

`silico-worker`'s `Platform` checks the traps at startup and after every request, through functions the worker's C++ supplies. The render worker has no C++, and reading the floating-point control register from Rust takes inline assembly, which is `unsafe` outside an FFI crate. Nothing it loads enables traps, and the FP environment is reset to its default at `execve`, which its re-exec repeats. So the check is skipped, and skipped as data, not stubbed:
- `Platform`'s trap functions become `Traps::Checked { mask, disable }` or `Traps::Unchecked`;
- `run` switches traps off and checks them only for `Checked`, and logs `traps = "unchecked"` once at startup otherwise;
- `serve` checks after each request only for `Checked`.

The kernel and sketch workers pass `Checked`, with what they pass today. The render worker passes `Unchecked`, its `built_from` naming `re_renderer` and `wgpu`; the adapter it got is logged when it makes its render context. A `fp_trap_mask` returning 0 would say "every trap is off" when it means "not looked".

## The protocol

Two messages in `silico-protocol`, appended to `Op` and `Reply` as #123's and M4.4's were, so no index moves:

```rust
Op::Render(Box<RenderScene>)
Reply::Rendered { png: Vec<u8>, ids: Option<Vec<[u32; 2]>> }

pub struct RenderScene {
    pub bodies: Vec<RenderBody>,   // one per solid drawn, in the model's order
    pub camera: Camera,            // the core's, checked (below)
    pub width: u32,                // 1 to 4,096
    pub height: u32,
    pub ids: bool,                 // whether to read the ID buffer back (tests, and the app's picking later)
}
pub struct RenderBody {
    pub body: u32,                     // the model's body number, from 1 (its place among the model's bodies), which the ID buffer writes
    pub mesh: Mesh,                    // the kernel's display mesh, as `KernelRequest::tessellate` gives it
    pub highlight_faces: Vec<u32>,     // faces by index from 0, ascending, each once
    pub highlight_edges: Vec<u32>,     // edges by index from 0, ascending, each once
}
pub struct Camera {
    pub projection: Projection,        // Orthographic { view_height } or Perspective { field_of_view }
    pub eye: [f64; 3],
    pub target: [f64; 3],
    pub up: [f64; 3],
}
```

- **The ID buffer:** one `[u32; 2]` per pixel, row by row from the top left. The first is the body's number from 1, its `RenderBody::body` (the model's, not its place in the scene, so a body left out of the view never renumbers the others), or 0 for the background. The second is its face's number from 1, or its edge's number from 1 with the top bit set (`0x8000_0000 | edge`). These are the numbers `Face1` and `Edge1` name, so a test reads names straight off it.
- **Each face drawn about its own centre, and moved into view; edges about the camera** (docs/design/m5.0-app.md, section 10, which replaced M4.6's positions drawn about the target, or the eye, for one view). `re_renderer`, like most GPU renderers, works in 32-bit floats. A part 5·10⁴ mm from the origin would round there to 4e-3 mm, more than a pixel at a close view. So each face's mesh (each face is its own mesh and instance) is uploaded once, its positions about the centre of its own box (its triangles' positions'), subtracted in f64 before converting to f32. The camera stays fixed in the world, at the origin looking along −z, and each view moves the faces: a face's instance transform (`world_from_mesh`) is the view's rotation and the face's centre about the camera, `R (centre − eye)`, computed in f64 and then f32, where for an orthographic view the eye is the target and the camera sits past the scene behind it (below). A new view of the same bodies uploads nothing: the renderer keeps the last scene's bodies uploaded, finds a body again by its number and its mesh, and rebuilds only the instances and the edges' line strips. What's f32 about a face's centre is the face's size, not the view's, so a face whose rounding there (its box's half diagonal over 2²², times the image corner's sec², 1 + tan²(fov/2)(1 + aspect²), in perspective) would pass an eighth of a pixel at its nearest point to the eye (a kilometre face seen at a few millimetres, or a face whose box holds the eye: a tube's walls seen from its bore) is drawn about the camera's point instead, as M4.6 drew every view, uploaded again for that view, alone (found by `/break-it`; Fable's decision on #332): the eye in perspective, where a position's rounding grows with its distance from it as the pixel does; in an orthographic view, the point on the view's line through the target at the face's own depth, where what the view sees of the face is (anchored at the target itself, or at the nearer of target and centre, a kilometre rod with the target 6e5 mm along the ray had its end drawn 3.5 pixels off, where M4.6 drew it right). Edges are placed in the view in f64 on the CPU each frame, each point's offset from the camera's point and its rotation into the view, so the GPU's transform for them is the identity and they're precise across the view at every distance: with the offset alone, an oblique orthographic view with its target a kilometre along the ray drew 131 of 353 edge pixels off their projection. Their draw data is uploaded each frame anyway. Before a new scene uploads anything, the bodies it doesn't draw again with the same mesh are dropped, and of those it does, each face's mesh about another point or in the colour it isn't drawn in (plain or highlighted), so the GPU holds about one scene's meshes; a render that fails keeps none. The view's frame (its direction, its up made perpendicular, its right) is computed once in f64, by `Camera::frame`, which the check uses too. The core sends positions as the kernel gives them.
- **The app's frames, on the same path** (docs/design/m5.0-app.md, section 10). The viewport draws through `Renderer` too, a frame at a time, never waiting for the GPU. Each body's mesh is given once, by its number (`upload`, which checks it as `RenderScene::check` checks a body's mesh, `check_render_mesh`, and `forget`; the same mesh again changes nothing, another replaces it), and its faces go to the GPU the first time a frame draws them. Each frame (`prepare`, called from egui_wgpu's `prepare`) names the camera, the size in pixels, the pixels per point, the bodies to draw, the highlights (a body's face or edge by number), and a picking rectangle, if any; the renderer moves each face into the view and places the edges itself, as a render does, and returns the command buffer for egui to submit. A frame's highlights are `re_renderer`'s per-instance outlines alone, in the highlight's blue, as Rerun's viewer draws hover and selection (m5.0-app.md section 10, "outlines by instance"): each face and edge keeps its mesh, colour, and width as uploaded, so a hover that moves every frame uploads nothing and changes no pixel of the picking layer. A render keeps its tinted faces and wider blue edges, the agents' PNG look. `composite` draws the frame into egui's pass (from its `paint`), and `take_picking` gives the newest picking the GPU has answered, a frame or two late (re_renderer maps a frame's readback when the next begins): of the frame's own pixels in the rectangle, the one with a body nearest its centre, its body, face or edge, pixel, and the point seen at the pixel's centre in the document's coordinates (the centre unprojected at the picking layer's depth there, in f64), and the serial of the frame that asked (`Renderer::frame`), so a click is matched to its frame. A body forgotten or given another mesh since that frame is passed over as background (each mesh uploaded takes a generation the request records), so a late answer never names a face of a mesh the frame didn't draw; the answer still comes, so a hover clears. A frame has no cap on its faces or triangles (a render's caps are the worker's), and the pane keeps repainting while an answer is due. A frame that fails its checks (a size of 0 or past the device's largest texture, pixels per point not above 0 or past 32, bodies not ascending or not uploaded, a highlight of an element the body hasn't, a picking rectangle of 0 or more than 256 pixels on a side) is refused naming its parameter, before anything is drawn. The worker's `render` builds its view by the same function, then submits it and waits for its readbacks, so there is one drawing path. The egui callback that calls `prepare` and `composite` is the app's: `deny.toml` keeps egui-wgpu to eframe and egui_kittest, and so out of `silico-render`.
- **Nothing behind an orthographic eye is cut off.** An orthographic view uses only the eye's direction: the worker sets the camera past the whole scene, as FreeCAD fits its clipping planes to the scene. A perspective view's near plane is a millionth of the farthest point's distance from the eye.
- **The scene's checks are one function,** `RenderScene::check` in silico-protocol, as `Primitive::check` is. Both sides call it:
  - the core, before sending;
  - the worker, on what it's sent, so a hand-built request can't make it index out of range.

  It checks only structure: the bodies' numbers, at least 1 and strictly ascending (the model's order); the sizes; at most 20,000 faces, 200,000 edges, and 2,000,000 triangles across the bodies (`MAX_RENDER_FACES`, `MAX_RENDER_EDGES`, `MAX_RENDER_TRIANGLES`; 4 million triangles took 34 s in a debug build; each face is a mesh of its own, about 75 KiB of the worker's memory, so 100,000 held 7.5 GiB, where a real part has hundreds to thousands); the camera's numbers, finite and not degenerate; the meshes' indices in range and positions finite; the highlights ascending, once each, and in range. A scene that fails it in the worker is a `Failure` of kind `InvalidInput`. The core never sends one: it counts the bodies' B-rep faces and edges (their element counts) once it has left out the bodies the view can't see, and before it meshes any, and refuses past those caps as `invalid_input` naming `camera`, with the suggestion of a camera on part of the model; and it counts the triangles once the bodies are meshed (their number depends on the mesh level, so on `height`), refusing past that cap as `invalid_input` naming `height`, with the suggestion of a smaller `height`, as the frame limit's rule does. What needs the model (a name, the eye inside a body) is the core's alone.
- **The kernel and sketch workers refuse `Op::Render`** with `OtherWorkersOp`, as they refuse each other's ops. The render worker refuses every other op the same way.
- **One frame each way.** A scene's meshes for a 4,096-pixel view of one part are a few megabytes (below), and a 4,096² ID buffer is at most about 167 MB of postcard; the frame limit is 512 MiB. A scene whose encoding passes the frame limit is refused in the core, before it's sent, as `invalid_input`. It names the field that would fix it, with a suggestion an agent can follow:
  - for a camera, `height`, with the suggestion of a smaller `height`: the level is `view_height / height / 2`, so it makes coarser meshes, past the floor where it binds, and never brings a body into view. Only where the core left no body out of the view does the suggestion add a wider view (a larger `camera.view_height`, or for a perspective camera a larger `camera.field_of_view` or an eye further away): where it left some out, a wider view brings them in, and the scene can grow;
  - for a named view, whichever of `width` and `height` bound its fit, since its pixel's size is 1.1 × the larger of the extent along `up` over `height` and along `right` over `width`. Fewer pixels there make coarser meshes.

## In the core

`command::render` checks the request in M4.1's order, then:
1. **The model.** It reads the `current` or `published` model (decision 33). A published render runs on the session's read lane.
2. **The bodies.** It takes every solid the model shows: each built feature's result that no later feature consumes, in the document's order (the bodies M4.1's `outline` and `elements` name). A model with none renders the background, from a camera; a named view of it is refused (below).
3. **The camera.** A named view's is computed from the bodies (below). A given camera is checked.
4. **The meshes.** Each body's mesh comes from `KernelRequest::tessellate`, at about half a pixel:
   - **On a ladder.** Half a pixel is `view_height / height / 2` for an orthographic camera, and for a perspective one the same at the body's nearest point to the eye (its tight box's), where its pixels are finest: so a target far past the part never meshes it coarser than its pixels (found by `/break-it`; the target's distance did). The deflection asked is the largest power of two no coarser than that, taken exactly from its bits, so views of nearly one size share meshes and a mesh is never coarser than half a pixel.
   - **Never finer than the floor.** The display mesh's floor (docs/ports/tessellation.md: `max(1e-4 × the diagonal, 1e-7)`) is the worker's to apply. Its diagonal is of OCCT's enlarged box, which the core doesn't have. Today a deflection under the floor is refused (`DeflectionTooFine`), so the render asks with a new flag on `Op::Tessellate`, `at_least_the_floor`. With it, the worker meshes at the larger of the deflection and its floor, and says which it used. Without it, nothing changes for today's callers.

   So a mesh is as fine as the image can show and no finer, down to the floor. A 4,096-pixel view of a 100 mm part asks for 2⁻⁷ = 0.0078 mm and meshes at its floor, 0.0173 mm. A zoomed view of a fillet does the same.
   - **Only what the view can see.** A body whose tight box lies wholly outside the view's volume isn't meshed or sent. A body with no box (its measure failed) is always kept, meshed at the floor in a perspective view, and the eye's check asks of it. A highlight on a body left out has no pixels, and is dropped. So a camera on part of the model meshes only that part, and a zoomed view doesn't mesh every off-screen body at its floor.
   - **Kept in memory, beside the kernel.** The meshes are kept in an in-memory cache held by `Sessions`, beside its kernel, as its disk caches are held. It's shared by that kernel's sessions, bounded at 256 MiB, and drops the least recently used first. Two `Sessions` on different kernels (a fake's and OCCT's, in one test binary) never share one, since a step key alone doesn't fix the shape (the disk cache keys on the kernel's identity too).
     - **Keyed by what was made.** An entry is keyed by the body's step key (content-addressed, so sessions sharing a step share its mesh) and the deflection the worker actually used, which its reply says.
     - **The floor remembered.** The first reply that met a body's floor records it by step key. A later level below it is mapped to the floor's entry before any request is sent, so zooming in past the floor meshes once, not once a level.
     - **Floors kept apart from meshes** (M5.5, #244). The floors are kept in their own list, one number per step key, up to 65,536 of them (`MESH_FLOORS_KEPT`, about 5.5 MiB of data), the least recently used dropped first. A floor isn't dropped when its step's last mesh is, and is recorded even for a mesh too large to keep; it goes only when the mesh that reported it is refused and forgotten. So `meshes` knows a body held at its floor is held without meshing it again. A floor dropped from that list is learnt again by meshing once more, to the same answer, so what the cache has seen changes only how long a read takes, never what it says. This replaces the first rule, under which a step's floor went with its last mesh.
     - **Not on disk.** The rebuild cache on disk keeps only built steps, and a mesh's level changes with zooming, so it isn't put there.
   - **In parallel.** The bodies are meshed at once, across the kernel pool, through the session's lane.
5. **The highlight.** Each name in `highlight` resolves through its body's element map (M2.7) to a face or an edge. A name that finds nothing is `reference_broken`, naming `highlight.N`, with candidates (M2.8). An unstable name is taken, as read-only commands take one (M4.1 section 2). A vertex or a solid is refused as `invalid_input`, naming `highlight.N`: it has no pixels of its own to colour. A name of an element of a feature that didn't build is answered with that feature's failure, once, as `elements` and the measures answer it. Names are found through the lookup every command that reads elements by name shares (`command::lookup`); a body that built is drawn and its faces lit whether or not its description could be had, since a highlight needs only the element map.
6. **The render.** It sends the `RenderScene` to the render worker, and takes the PNG.
   - **One worker, renders in turn.** One render worker per `Sessions`, held beside its kernel and its mesh cache and given when `Sessions` is made (as its kernel is, so the core's tests give a fake one; step 4), started on first use, renders one scene at a time, in the order they come, across that `Sessions`' sessions. The client checks each scene before it's queued, so a scene that fails is Silico's bug, answered at once and never sent, and a worker that refuses one the core checked is at fault, and stopped.
   - **Stopped after a large render, and when idle.** A worker that drew a 4,096² render keeps about 1.6 GB after it, which freeing its textures doesn't give back (the round-4 review's measurement: 1,615 MB footprint at idle, all dirty "Malloc Large"), so a long-running `silico serve` must not keep it. A 400² render peaks at 142 MiB. So:
     - the core stops the worker as soon as a render of more than 1,048,576 pixels (1,024²), or of more than 10,000 faces (each about 75 KiB of the worker's memory, so about as much as those pixels) or 200,000 triangles (each about 0.5 KiB), has answered, and after any render that failed (macOS doesn't give the memory back, and nothing vouches for the context after a failure);
     - it keeps one after smaller renders warm until it has been idle 2 minutes, so an agent's next render, after a turn of its own, doesn't pay a new start (about 0.4 s against a 0.06 s render).

     Both are settings of the render client, given with its adapter policy, so the tests use milliseconds. At M4's sizes a render takes well under a second on lavapipe, and an agent's session renders one view at a time, so a queue beats a pool's cost: a lavapipe context in each worker, two threads each.
   - **Out of memory.** A render the worker ran out of memory for (`Refusal::OutOfMemory`) is `resource_exhausted`, its suggestion a smaller `height` or a camera on part of the model, not the kernel's "make the part simpler"; the worker is stopped after it, as after any failed render.
   - **The timeout** of 30 seconds starts when the scene is sent, so one session's render never times out for another's. Waiting in the queue counts against nothing but the command's own time, which a client can cancel.
   - **Cancelling,** and a session closing. A render still queued is dropped, and answers `cancelled`. One that's running is stopped by killing the worker, which the next render replaces, and answers `cancelled` (decision 34). The render worker has no generations to supersede, so killing it is how its work stops, as the kernel pool's own superseded path ends with a killed worker. A session that closes does the same to its renders, as M4.1 section 2 ends its reads: its queued ones dropped, its running one's worker killed.
7. **The file.** With `to`, it writes the PNG through decision 35's rules, shared with `export`. It refuses:
   - a path that doesn't end in `.png`;
   - a `.silico` path, a document a session holds, or anything in `.silico-cache/`;
   - a path outside the workspace or through a link out of it;
   - an existing file, unless `replace`.

   It writes a new file beside the target and renames it into place. One function for both commands, in `file`.

The result is M4.1's: `png_bytes`, `path`, `width`, `height`, and `camera`. Over MCP, the PNG is the reply's image block.

### Named views

The document is Z-up (FreeCAD's axes, M4.1). Each named view looks along a fixed direction (`dir`, from the target to the eye) with a fixed `up`:

| View | `dir` | `up` |
|---|---|---|
| `front` | (0, −1, 0) | (0, 0, 1) |
| `back` | (0, 1, 0) | (0, 0, 1) |
| `left` | (−1, 0, 0) | (0, 0, 1) |
| `right` | (1, 0, 0) | (0, 0, 1) |
| `top` | (0, 0, 1) | (0, 1, 0) |
| `bottom` | (0, 0, −1) | (0, 1, 0) |
| `top_front_right` and the other seven corners | (±1, ±1, ±1)/√3: `right` is +x, `back` is +y, `top` is +z | +z made perpendicular to `dir`: (z − (z·dir) dir), normalized |

- **The corner names** are `{top,bottom}_{front,back}_{left,right}`, eight of them, as Fusion's ViewCube corners are. `top` and `bottom` keep +y up, so `top` shows the front at the bottom of the image, as Fusion's and FreeCAD's do.
- **Fitting the view.** Every named view is orthographic. Its target is the centre of the bodies' tight box (`tight_box`, M4.5, FreeCAD's `optimalBoundingBox`). Its `view_height` is 1.1 times the larger of:
  - the box's eight corners' extent along `up`;
  - their extent along `right` (`dir × up`, reversed, so the image isn't mirrored) times `height / width`.

  So the bodies fill the image with a twentieth of it to spare on each side of the tighter direction. It's never under 1.01 × `MIN_VIEW_HEIGHT_OF_REACH` of half the box's diagonal, so a body far deeper along the view than across it (a rod seen end on) is drawn, not refused for its reach.
- **A named view of a body that couldn't be measured** is refused as `invalid_input`, naming `view` and the body: it has no box to fit. A camera draws it.
- **The eye** is at `target + dir × 2r`, where r is half the box's diagonal, so it's outside every body and the near plane cuts nothing.
- **Computed in f64,** in the order written here, with no trigonometry (the corners' 1/√3 is `1.0 / 3.0f64.sqrt()`), so the camera is the same on every platform. It's a result.
- **For M4.1's example** (the 40 × 20 × 10 block's box, `top_front_right` at 800 × 600), this gives:
  - a target of (20, 10, 5);
  - an up of (−0.40824829046386313, 0.40824829046386313, 0.8164965809277258);
  - a view height of 1.1 × max(32.660, 42.426 × 0.75) = 35.925849560819955;
  - an eye 45.83 from the target.

  M4.1's example is this camera as a result writes it: the eye (46.457513, −16.457513, 31.457513), rounded to the nanometre, and the view height 35.92585; the render draws with that camera, so it passes back unchanged.
- **A named view of a model with no bodies** is refused as `invalid_input`, naming `view`: there's nothing to fit. A camera works, and renders the background.

### A given camera

Checked in this order, each refusal `invalid_input` naming the field:
- `camera.projection`: `orthographic` or `perspective`.
- `camera.eye`, `camera.target`: finite and within 1e12 mm of the origin (`MAX_RENDER_COORDINATE`). `camera.up`: finite.
- `camera.eye`: at least a nanometre (1e-6 mm, `MIN_EYE_DISTANCE`) from the target: nearer, a perspective view's near plane is 0 in f32. `camera.up`: not parallel to the view, with its component perpendicular to the view at least 1e-9 of its length; its length is otherwise free (lengths are found scaled, so none overflows).
- `camera.view_height` (orthographic): from 1e-6 to 1e12 mm, and at least 1e-5 of how far the bodies in view reach from the target. `camera.field_of_view` (perspective, vertical, in degrees as the document's angles are): from 0.001 to 179.999. The field that doesn't belong to the projection must be `null`.
- These bounds are what a renderer drawing in f32 draws exactly (the break-it run of step 2): past them a view lost pixels, turned upside down, or drew nothing. A closer look than a perspective view's 0.001° is an orthographic view's.
- **`camera.eye` inside a body** (M4.1's example error), for a perspective view only: an orthographic view uses only the eye's direction, so where the eye is doesn't matter to it, as Fusion's doesn't clip an orthographic view at the eye. The core asks the kernel whether the eye is inside each body's solid, by a new kernel request, `Op::Classify { shape, point }`, with `BRepClass3d_SolidClassifier` at the shape's tolerance. A point on the surface counts as inside. A point past 1e12 mm from the origin is refused, naming `point`: there OCCT's classifier answers wrongly (a box holds (1e18, 0, 0), as FreeCAD's `isInside` says too) or throws. It's asked only for bodies whose tight box holds the eye, so an eye outside the part's box costs no request. The display mesh can't decide this exactly within its deflection, and OCCT's classifier is what FreeCAD's `isInside` uses.

The camera returned is the camera used: the given one, or the named view's, with `up` made perpendicular to the view and normalized, so the next request can pass it back unchanged.

## What a render looks like (visuals follow Fusion 360)

- **Background:** a flat light grey, sRGB (230, 233, 237). Fusion's default environment is a light grey gradient; flat keeps the ID buffer's background a single value, and the PNG small.
- **Bodies:** Fusion's default appearance (steel, satin): sRGB (170, 175, 182), lit as Fusion lights a model, by lights fixed to the camera: a key light above and to the left of it, a soft fill below and to the right, and an ambient, so a box's faces seen at a corner each read in a shade of their own (decided for the maintainer by Main, 2026-10-25: visuals follow Fusion). Lambertian shading from the mesh's own normals (the kernel's, per vertex, made unit length in f64 at upload), so curved faces shade smoothly and planar faces evenly. Since docs/design/m5.0-app.md section 10 it is `re_renderer`'s own light, per pixel: in linear light, the albedo times 0.2 + max(0, n · l₁) + 0.5 × max(0, n · l₂), at most 1, with l₁ = (1, 2, 3) and l₂ = (−1, −3, −5) of unit length, fixed in the world (its `simple_lighting`), which the fixed camera makes fixed to the camera, in its frame (right, up, back). A face square to the view takes 1; from `top_front_right` a box's top takes 1, its right 0.634, and its front 0.256. A normal of zero is drawn unlit, at the body's own colour (re_renderer's rule). That replaced M4.6's own light (the albedo times 0.30 + 0.65 × max(0, n · key) + 0.20 × max(0, n · fill), the key above and to the left of the camera, the fill below and to the right), which was computed per vertex for one view, so every orbit rebuilt every mesh; the look's change is a veto line for Trevin.
- **Edges:** every B-rep edge, as the display mesh's polylines, 2 pixels wide, dark and solid, sRGB (40, 40, 40), drawn over the faces with a depth offset so an edge on a face isn't hidden by it, antialiased by blending (re_renderer's alpha-to-coverage gave a 1.5-pixel line about half its coverage on lavapipe). Hidden edges aren't drawn. Fusion shows visible edges only by default.
- **Highlight:** Fusion's selection blue, sRGB (6, 150, 215).
  - A highlighted face is tinted with it at half strength (in linear light, half the body's colour and half the blue, then shaded) and outlined, 1.5 pixels. Its tinted mesh is uploaded when it's first drawn highlighted, in place of its plain one, and the plain one again when the highlight ends.
  - A highlighted edge is drawn in it, 4 pixels wide, twice a plain one.
  - The ID buffer marks neither: it says which element each pixel is, and the scene says which are highlighted.
- **No antialiasing** in the ID buffer. The PNG's colour target is 4× multisampled; the picking layer isn't, so each ID pixel is one element.
- **The PNG:** 8-bit sRGB RGB, no alpha (the background is opaque), encoded by the `png` crate with its default compression, no metadata chunks: no time, no software name.

## Tests

From #50's key tests and M4.1's decisions. The rendering tests run in silico-render's tests on lavapipe, with the `Software` policy, on the Mac and on CI's Linux runner; the command's tests run in the core with a fake render worker.
- **A box from the front:**
  - Every pixel inside the rectangle the front face projects to, computed by hand from the camera, is that face's ID (`Face1` of the body, by number), with pixels within one of the rectangle's boundary allowed to be an edge's.
  - Every pixel more than one outside it is the background.
  - Its four edges are on the boundary rows and columns, by their numbers.
- **A box from `top_front_right`:** exactly the three faces the view sees (top, front, right) appear in the ID buffer, each over the hexagon's third its projection covers by hand. The others never appear.
- **Highlight:**
  - With a face highlighted, the scene's highlight reaches the worker as that face's index.
  - The PNG's pixels over that face, away from its edges, are bluer than the same render's without the highlight (the blue channel up and the others down), and every other pixel is unchanged, compared within the render, not with a stored image.
  - A highlighted edge's pixels likewise.
- **Cameras:**
  - Each named view's camera is checked against the table and the fitting rule by hand, for the 40 × 20 × 10 box, to the bit.
  - A camera passed back from a result gives the same render's ID buffer.
  - Orthographic and perspective views of a box put its front face's centre at the image's centre.
- **Refusals,** each naming the field:
  - a width or height of 0, of 4,097, or that isn't a whole number;
  - a camera with a NaN, an eye at the target, an up along the view, a view height of 0, or a field of view of 0 or 180;
  - a camera inside the box (the kernel's classifier), and one on its face;
  - more than 1,000 highlights, a highlighted name that finds nothing (`reference_broken`, `highlight.0`), and a vertex highlighted;
  - a named view of an empty model.
- **The worker:**
  - A render worker made to hang (`test_ops`, as the kernel worker's are) is killed at 30 s as `worker_timeout`, and the next render works.
  - One made to crash is `worker_crashed`.
  - With the `Software` policy and lavapipe's compiled-in paths gone, the result is `worker_unavailable` with a cause that says so.
  - The render worker, re-executed, holds the three variables above and nothing of the parent's but what `spawn_checked` passes, and the core's own environment is unchanged.
  - A session closed with a render queued and one running: the queued one is never sent, and the running one's worker is killed.
  - A queued render cancelled answers `cancelled` and is never sent. A running one cancelled kills the worker, answers `cancelled`, and the next render works.
  - Two sessions' renders queued: each one's 30 s counts from its own send.
  - A render worker idle past its idle period (milliseconds, in the test) is stopped, its process gone, and the next render starts another; one after a render over the pixel threshold is stopped at once.
  - Three bodies, a camera on the third only: the scene holds the third alone, and its pixels carry body 3.
- **The meshes:**
  - The ladder's level for half a pixel, from its bits, at powers of two and an ulp either side.
  - A 4,096-pixel view of a 100 mm cube meshes at its floor, not refused.
  - A second render at one level meshes nothing (the fake kernel's record).
  - Two zooms past the floor mesh once.
  - Two sessions rendering one step share its mesh.
  - The cache drops its least recently used mesh at its bound.
  - A step's floor outlives its meshes. The floors are bounded by count, the least recently used dropped first. A floor dropped is learnt again by a mesh, to the same answer (M5.5).
- **The result** never holds the PNG's bytes, only their count. With `to`, the file is a PNG of the size asked, decoded by the `png` crate, and the write follows decision 35's tests, which `export` shares.
- **Hostile scenes,** `/break-it` on the worker: meshes with indices out of range, NaN positions, a zero-area triangle, a million highlights, a 4,096 × 4,096 render of a CTC part. They're refused or drawn; nothing panics or hangs past the limit.
- **Determinism:** the camera of every named view is in the determinism sweep, byte for byte, and `render`'s result is compared with `png_bytes` masked. A PNG and the ID buffer never are.
- **The boundary rule, enforced** (R5):
  - A contract test that `render`'s result has exactly M4.1's five members, so the ID buffer can't drift into it. The result's schema marks `png_bytes` as machine-dependent.
  - The fake render worker records what it's sent. Every refusal test asserts it was sent nothing: sizes, camera numbers, the eye inside and on the box, a highlight not found, a vertex highlighted, more than 1,000 highlights, an empty model with a named view, and `to` refused.
  - No test fixture is an image or a buffer.
- **Traps:** an `Unchecked` platform serves a request that leaves a trap on without an `FpTrapsOn` refusal; the `Checked` tests are unchanged.

## Decisions taken here (recommended, for Trevin)

- **R1. The renderer.** `re_renderer` 0.38.1, so M5's viewport and agents' renders are one renderer, with plain `wgpu` as the fallback if the first step's probe fails. The alternative, plain `wgpu` from the start, is less code to depend on, but a second renderer M5 would replace or keep beside the first.
- **R2. The rasterizer.** Lavapipe whenever the worker has it (pinned in pixi, so every development machine and CI draw alike), the GPU only without it. The alternative, the GPU first, is faster for large renders, but it brings each machine's driver into every render, hangs included.
- **R3. Perspective.** Taken from M4.6, as M4.1's camera has a `field_of_view`; named views are orthographic, as FreeCAD's are and as measuring by eye needs. The alternative is orthographic only until M5.
- **R4. The eye inside a body.** OCCT's classifier, through a new kernel request (`Op::Classify`), asked only when the eye is inside a body's box. The alternative is the display mesh's winding number in the core: no request, but not exact within the mesh's deflection.
- **R5. The render worker outside ARCHITECTURE.md's worker rules. Decided** (Fable for the maintainer, 2026-10-25; his veto open): *Deterministic kernel*'s rules are scoped to workers whose output is a result, so they don't bind the render worker. In exchange, one rule: nothing it returns reaches a result, a name, a document, the cache, or a stored expected value. Its traps are unchecked, as data (`Traps::Unchecked`). ARCHITECTURE.md's edits E1 to E6 are the decision's.

## Build steps

0. **ARCHITECTURE.md**, the decision's edits E1 to E6, citing R5; and `silico-worker`'s `Traps` (`Checked` or `Unchecked`), with its tests.
1. **Probe** (no contract, no core change). `silico-render` with `re_renderer` (`default-features = false`): a box rendered headless on lavapipe, its picking layer read back, on the Mac and on CI.
   - `cargo-deny` on the new dependencies.
   - pixi's `mesa-lavapipe` and `libvulkan-loader` pinned, with `macos = "15.0"`, the paths compiled into the worker, its re-exec, and no loader variables in pixi's activation.
   - Measured at the limit: a 4,096² render of a CTC part with a highlight, at two threads, its time and peak memory against the 30 s limit. If the time fails, the size limit comes down, with a word to Trevin. The picking readback (about 320 MiB at 4,096²) is only for `ids`, which agents never ask for, so a shortfall there limits only `ids` renders (or reads the picking rectangle in tiles), never `render_side`.
   - If the probe fails, the fallback (R1) and a word to Trevin.
2. **The worker.** The protocol's messages, `silico-render-worker` on `silico-worker`, the scene's checks, the ID buffer, and the visuals. Tests in silico-render. The worker absorbs the probe: its render and readback become the worker's (`render::Renderer`), its test reads the worker's ID buffer, and `silico-render-probe` goes. CI's `render` bench draws the same box through the worker's renderer (`silico-render-bench`).
3. **The core's client.**
   - `worker::WorkerKind::Render`, and the render worker's client, `render::RenderClient` (started on first use; stopped after a large render or 2 minutes idle; replaced after a crash, a timeout, a cancel, or a failed render; its scenes checked, then drawn in turn; a ticket for each, waited on, polled, or cancelled from any thread), with the adapter policy above (`RenderAdapter`, in silico-protocol, written as the worker's arguments and read back by it).
   - `Op::Classify` (where a point is: inside, on the boundary, or outside, the core counting on as inside), and `Op::Tessellate`'s `at_least_the_floor`, in the kernel, and both in the fake kernel too: a symbolic mesh with the kernel's floor rule (`mesh_floor`, `at_least_the_floor` honoured, the deflection used reported), and a classification of its symbolic solids by their boxes.
   - The mesh cache, `meshes::MeshCache`.
   - Holding the client and the cache in `Sessions`, given when it's made, is step 4's, built with the command that uses them and clear of the session work then under way; so are the mesh-cache tests that read the fake kernel's record (a second render at one level meshes nothing; two zooms past the floor mesh once; two sessions share a mesh).
4. **The command.** Built as `Sessions::render` on `command::render::render`, its renderer given by `Sessions::rendering` and its meshes held by `Sessions`; a read's cancel cancels its render through the read's stop, and it settles before writing its file. `command::render`: the camera, the meshes, the highlight, and the file, sharing decision 35's writer with `export`; and `Sessions` holding the render client (behind a small trait, so the core's tests give it a fake render worker that records what it's sent) and the mesh cache. Its tests, with a fake render worker for the core's, and the worker for the rest. A body's mesh reaches the scene shared from the cache, not copied, if `RenderBody` holds it as an `Arc`.
5. **`/break-it`** on each, and the council before merging.
