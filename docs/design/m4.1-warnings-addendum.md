# M4.1 warnings: addendum

Additions to docs/design/m4.1-command-api.md, section 2, *Warnings*, recording what's built where the approved text doesn't say it. The approved text is unchanged; where the two seem to differ, this note says how the code reads it.

## `fingerprint_missing` in a published check of an older model

Closes #189's architecture review, open low L3 (carried forward by the M4 milestone review).

**The gap.** A save that writes a sketch's solve doesn't publish its own model, since the saved document's rebuild solves from what it wrote (`Session::write`). Until that revision's model is published, the newest published model is the older one, and its document stores no fingerprint for the features the save just fingerprinted. Round 4's A4-1 fixed this for a transaction's commit: an older model whose own revision was a transaction's spares what that transaction's edits reached. The same window stayed open after `format`, and after an edit's commit outside a transaction. In both, a published check warned of a feature whose file already stored its fingerprint, for one rebuild.

**What the design says.** Its rule is that a warning is "a feature that built whose file stores no fingerprint, where a save would store one". Its message is "f0000003 built, but its file stores no fingerprint, so a change in what it builds isn't caught as drift". `check` "lists the warnings of the model it reads, the current or the published", and a published read "answers from the newest model the session has published, which may be of an older revision", with "the envelope's `model.revision`" saying "which revision the answer is of".

**Decided.** Whether the file stores a fingerprint is judged by the session's document as it is now, not by the older model's (option (b) of the gap's two). The rule and the message speak of the file. A fingerprint the file stores isn't missing, whichever model is read. The other option, (a), would have had the published model take the saved fingerprints when the save was made. That would put a later revision's records into a model its `model.revision` names as an older one's, so it wasn't taken. Everything else about the warning stays the model's: that the feature built, and that it can be fingerprinted.

**As built (`Checking::spared`, `silico_core::command::session`).** A check of a model older than the session's revision spares two kinds of feature:

- what a commit writes, as before (`Reached::committing`);
- every feature the session's document stores a fingerprint for now, if that document reads (one the gate refused still reads).

This only ever spares a warning; it never adds one. The case it leaves alone runs the other way: a fingerprint the model's document stores, and the session's no longer does (one removed by hand and reloaded). That is warned of once the session's revision's model is published, as everything else of that revision is. A model of the session's revision has the session's document, so nothing changes for it.

**Tests** (`crates/silico-core/tests/check_warnings.rs`):

- `a_feature_format_fingerprinted_isnt_warned_of_in_a_published_check_after_a_format_that_doesnt_publish`: `format` writes a box's fingerprint and a sketch's solve. The published check of the opened revision then warns of nothing, and its problems are the model's, as before.
- `a_carried_feature_an_edits_commit_fingerprinted_isnt_warned_of_in_a_published_check_but_one_still_missing_is`: an edit's commit outside a transaction writes a carried feature's fingerprint and a sketch's solve. The published check spares that feature, and still warns of the box that no edit reached, whose file stores no fingerprint.
