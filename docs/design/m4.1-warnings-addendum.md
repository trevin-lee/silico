# M4.1 warnings: addendum

Additions to docs/design/m4.1-command-api.md, section 2, *Warnings*, recording what's built where the approved text doesn't say it. The approved text is unchanged; where the two seem to differ, this note says how the code reads it.

## `fingerprint_missing` in a published check of an older model

Closes #189's architecture review, open low L3 (carried forward by the M4 milestone review).

**The gap.** A save that writes a sketch's solve doesn't publish its own model, since the saved document's rebuild solves from what it wrote (`Session::write`). Until that revision's model is published, the newest published model is the older one, and its document stores no fingerprint for the features the save just fingerprinted. Round 4's A4-1 fixed this for a transaction's commit: an older model whose own revision was a transaction's spares what that transaction's edits reached. The same window stayed open after `format`, and after an edit's commit outside a transaction. In both, a published check warned of a feature whose file already stored its fingerprint, for one rebuild.

**What the design says.** Its rule is that a warning is "a feature that built whose file stores no fingerprint, where a save would store one". Its message is "f0000003 built, but its file stores no fingerprint, so a change in what it builds isn't caught as drift". `check` "lists the warnings of the model it reads, the current or the published", and a published read "answers from the newest model the session has published, which may be of an older revision", with "the envelope's `model.revision`" saying "which revision the answer is of".

**Decided.** Whether the file stores a fingerprint is judged by the session's document as it is now (the file, outside a transaction; inside one, the document as its edits left it, as a check of the current model reads it), not by the older model's (option (b) of the gap's two). The rule and the message speak of the file. A fingerprint the file stores isn't missing, whichever model is read. The other option, (a), would have had the published model take the saved fingerprints when the save was made. That would put a later revision's records into a model its `model.revision` names as an older one's, so it wasn't taken. Everything else about the warning stays the model's: that the feature built, and that it can be fingerprinted. So does everything else in the answer: its problems, a sketch's drift among them, are the model's revision's, as `model.revision` says. After a save that wrote a sketch's solve and didn't publish, a published check still says that sketch's drift, until the saved revision's model is published: the answer is of the older revision, and only the warning's one claim about the file is judged by the file.

**As built (`Checking::spared`, `silico_core::command::session`).** A check of a model older than the session's revision spares two kinds of feature:

- what an open transaction's commit will write (what its edits reached);
- every feature the session's document stores a fingerprint for now.

That holds when the session's document reads (one the gate refused still reads). When it doesn't, the rule is A4-1's, as before (`Reached::committing`): an older model whose own revision was a transaction's spares what that transaction reached. With the document read, that rule isn't asked: what the file stores decides. So after a transaction's commit that wrote nothing, and a reload, a feature carried with no fingerprint is warned of, as its file stores none.

This only ever spares a warning; it never adds one. The case it leaves alone runs the other way: a fingerprint the model's document stores, and the session's no longer does (one removed by hand and reloaded). That is warned of once the session's revision's model is published, as everything else of that revision is. A model of the session's revision has the session's document, so nothing changes for it.

**Tests** (`crates/silico-core/tests/check_warnings.rs`):

- `a_feature_format_fingerprinted_isnt_warned_of_in_a_published_check_after_a_format_that_doesnt_publish`: `format` writes a box's fingerprint and a sketch's solve. The published check of the opened revision then warns of nothing, and its problems are the model's, as before.
- `a_carried_feature_an_edits_commit_fingerprinted_isnt_warned_of_in_a_published_check_but_one_still_missing_is`: an edit's commit outside a transaction writes a carried feature's fingerprint and a sketch's solve. The published check spares that feature, and still warns of the box that no edit reached, whose file stores no fingerprint.
- `a_refused_document_that_stores_a_fingerprint_still_spares_it_in_a_published_check`: the file comes to store a box's fingerprint beside a box of no length the gate refuses; the published check of the older model spares it.
- `after_a_commit_that_wrote_nothing_and_a_reload_a_carried_feature_is_warned_of_in_a_published_check`: a transaction's commit that wrote nothing, then a reload; the published check of the transaction's model warns of the carried feature with no fingerprint.

## `ends_not_joined` for a cluster of three or more points

Closes a gap the M4 milestone review carried forward. The design's example, in section 2, *Warnings*, shows only the two-point form, whose cause is "the points are 4e-8 mm apart, closer than FreeCAD's joining distance of 1e-7 mm". The approved text says the cause of a cluster is "the largest distance between two of its points", but gives no wording for a cluster of three or more points.

**As built (`silico_core::warnings`).** Only the cause has a form of its own for a cluster of three or more points. Every other field is worded as for two:

- The message counts the cluster's points: "3 points that end curves are at one place but aren't one point, so the profile is open there".
- The cause is "the points are at most D mm apart, each closer than FreeCAD's joining distance of 1e-7 mm to another of them".
  - D is the largest distance between two of the cluster's points, measured as FreeCAD measures it (`gp_Pnt::Distance`) and written as Silico writes numbers.
  - "Each closer … to another of them" holds because a cluster joins through its members. Each point is within 1e-7 mm of at least one other point, but not necessarily of every other, so D can be 1e-7 mm or more.
- The two-point cause is unchanged.

**The text, pinned** by `a_tiny_arc_short_of_a_half_turn_with_both_ends_in_a_cluster_is_to_be_lengthened` (`crates/silico-core/tests/check_warnings.rs`). That test's sketch is an arc whose ends are 1.5e-7 mm apart, each 7.5e-8 mm from a line's end. Its whole warning, as the wire writes it, is:

```json
{"code": "ends_not_joined", "message": "3 points that end curves are at one place but aren't one point, so the profile is open there", "feature": "s0000001", "elements": ["pa000001", "pa000002", "pa000003"], "elements_total": 3, "parameter": null, "cause": "the points are at most 1.5e-7 mm apart, each closer than FreeCAD's joining distance of 1e-7 mm to another of them", "suggestion": "lengthen arc na000001; then share one point: make the curves that end at the points named end at one of them", "candidates": []}
```

Its elements are the cluster's three points alone, 3 counted, as a two-point cluster's are its two (approved at M4's close, 2026-10-29). D here is 1.5e-7, the distance between the arc's two ends. That is more than 1e-7, though each end is 7.5e-8 from the line's end. The same cause, with other distances, is in `ends_joined_through_each_other_are_one_cluster_its_cause_their_farthest` and the file's other cluster tests, through its `at_most` helper.
