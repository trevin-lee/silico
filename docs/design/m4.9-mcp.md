# M4.9 design: the MCP server

**Status: approved by the architecture reviewer (round 2, 2026-10-26), before the crate is built; the bound on calls in flight settled by the maintainer (a transport limit, 2026-10-26).** It builds M4.9's row of the M4 plan (#50) on docs/design/m4.1-command-api.md: section 6 (long work, limits), section 8 (`tools.json`), section 9 (transport, exact JSON, a tool's answer), and decisions 7 (stdio), 10 (MCP's cancellation), 23 (exact JSON both ways), 24 (the contract files), and 26 (the workspace in the core). Where this note and M4.1 disagree, M4.1 is right, and this note is the bug.

## What's added

| Where | What |
|---|---|
| `silico-core`, `command::call` | One entry for every command by name, for every client, built only on the public typed methods, so the typed API stays a superset: `Sessions::call(name, arguments) -> Call`. `arguments` is a request's text, read by Silico's own reader. The names are one enum, `Command`, matched whole (as #180's `FromCentre` is), and `COMMANDS` (the snapshots) is generated from it, so a command can't be in `tools/list` and not dispatch: a test checks every `COMMANDS` name dispatches. `version` and `schema` go through it too. |
| `silico-core`, the workspace (decision 26) | `Sessions::in_workspace(root) -> Result<Sessions, Error>`, a builder as `rendering` is: the root canonicalized once, fixed for the `Sessions`' life. `open`'s path, and `render`'s and `export`'s, are relative to it; a path outside it, or one that reaches out of it through a link, is refused as `invalid_input` naming the field, with M4.1's message (section 7's `open` example), the path quoted as every message quotes one, whether or not anything is there: the path is walked a name at a time through its links, never looking a name up in a directory outside the workspace (only in the root, below it, or the root's ancestors, going on from an ancestor only by the next name on the way down to the root, by any spelling the file system takes for it, or by a link), so `../secret/../work/x` is outside whether `secret` exists or not, and no lookup outside can wait on a slow mount. The check is made where a path is resolved, not only when it's given: at `open`, at every re-read and save of a session's file (`found_at`: a link swapped in after `open` would otherwise lead out), and where its `.silico-cache/` is opened (which can be a link out too), and again by the cache itself as each of its reads, writes, evictions, and clears begins (`Cache::within`: a link put on its way later, in a transaction that reads nothing again, has nothing done through it). A re-read or save that finds its path now leads out is `invalid_input` naming `path`, as `open` is, never `io_failed`. One implementation, in `file`, which `file::Output` already calls with its workspace. The CLI gives none, so it reads paths as it does today. |
| `silico-mcp` (new) | The server, as a library: `Server::new(sessions)`, `serve(input: impl BufRead, output: impl Write)`, and a `Stop` handle whose `stop()` ends `serve` from another thread (a signal, the reader blocked on stdin) as stdin's end does. JSON-RPC 2.0 over lines, MCP's methods, the tool list, cancellation, progress, and the end of a client. It depends on `silico-core` and serde_json (with `raw_value`) only: no MCP SDK (below). No `unsafe`, no C++, no network. |
| `silico-cli`, `silico serve [--workspace DIR]` | Starts the pools (kernel, sketch, render) as `silico check` does, `Sessions::in_workspace`, and runs `silico_mcp::serve` on stdin and stdout. The workspace is `DIR`, or the current directory; `/` (or a drive's root) is refused, since some MCP clients start servers there, which would make the whole disk the workspace. Logs go to stderr (MCP's stdio rule: nothing but messages on stdout; workers' stdout is already `Stdio::null()`). docs/cli.md says so. |

### `Call`

```rust
pub enum Call {
    /// No command has this name (a JSON-RPC error, not an envelope: M4.1 section 9).
    Unknown,
    Running(Calling),
}

/// A command running, of any type: what a transport needs of it.
impl Calling {
    pub fn progress(&self) -> Option<Progress>;     // Running::progress
    pub fn stopper(&self) -> Stopper;               // Running::stopper
    pub fn wait_timeout(self, d: Duration) -> Result<Answered, Calling>;
}

pub struct Answered {
    pub ok: bool,
    pub text: String,          // the envelope, Layout::OneLine, response_text's
    pub png: Option<Vec<u8>>,  // render's, beside the envelope, never in it
}
```

`Sessions::call` never blocks on a session: every command it starts is queued and runs off the caller's thread (M4.2), so it returns a `Calling` at once.

## The protocol

- **Revision 2025-06-18,** pinned: the first with `structuredContent` and `outputSchema`. It has cancellation and progress, and drops JSON-RPC batches. `initialize` answers with it whatever the client asks; a client that can't speak it disconnects, as the spec says. A later revision is a change to this pin, with its own tests.
- **Methods:** `initialize`, `notifications/initialized`, `ping`, `tools/list`, `tools/call`, and `notifications/cancelled`. `initialize`'s capabilities are `tools` with `listChanged: false`; `serverInfo` is `silico` and the build's version; `instructions` names the workspace (what relative paths resolve against) and section 9's three things an agent most needs. Every other request is JSON-RPC's `-32601`; every other notification is ignored, as JSON-RPC asks. A `tools/call` before `initialize` is refused (`-32600`, saying `initialize` comes first); a second `initialize` is answered as the first was. `initialize` isn't cancellable.
- **`tools/call`'s params:** `name`; `arguments`, optional in 2025-06-18, read as `{}` when absent; `_meta`; any other key ignored. A request ID already in flight is refused (`-32600`), so a cancellation can't reach the wrong call.
- **No SDK** (decision 23 allows one for the handshake's types at most): the handshake is a few small messages, written with serde_json, and an SDK would bring an async runtime and a second JSON path. About 500 lines; conformance is tested against the spec's examples and live with a TS-SDK client (Claude Code), below.

## Exact JSON both ways (decision 23)

- **In:** each line is parsed by serde_json into a frame (`jsonrpc`, `id`, `method`, and `params` as a `RawValue`). A `tools/call`'s `arguments` stays a `RawValue`, and its text goes to `Sessions::call`, so Silico's reader sees the bytes the client sent: a key given twice, a number with too many digits, a nesting past 64, all refused as the core refuses them. Tested as section 9 asks: `0.1` reaches the core as exactly 100,000 nm, and `0.10000000000000000001` is refused for its decimals, not rounded.
- **Out:** the server writes each reply line itself. `structuredContent` is the envelope's text spliced in raw, and `content`'s one text block is that same text as a JSON string, its escaping streamed to the writer rather than built as a second copy. `isError` is `!ok`. `render`'s PNG is an image block of its own (base64), never in `structuredContent` or the text. A JSON-RPC error's `data` is a refused envelope, spliced the same way.
- **Lines:** a line is read up to the core's 64 MiB (`MAX_INPUT_LEN`) plus the frame's room. A longer line is skipped to its end without being held, and answered with `-32600` if its ID can be found in what was read, so a huge argument can't exhaust memory.

## Tools

- **One tool per command,** in `COMMANDS`'s order, with the same name, a title, and the command's description, written for agents (edit inside a transaction, read `current` after an edit, names come from `elements` and `query`). MCP's annotations: `readOnlyHint` for the reads; `destructiveHint` for `commit`, `format`, and the edits (an edit outside a transaction saves); `openWorldHint: false` for all.
- **`inputSchema`** is the command's `request` snapshot as it is (each has `type: object` at its root).
- **`outputSchema`** (M4.4's open point, recommended to the maintainer): MCP checks `structuredContent`, the whole envelope, against it, and wants `type: object` at its root. So it's built as:
  - the root `{"$schema": 2020-12, "type": "object", "anyOf": [answered, refused], "$defs": ...}`, with the envelope's two branches, `answered`'s `result` set to the command's `result` snapshot;
  - that snapshot inlined without its `$schema` and `title` (2020-12 allows `$schema` only at a resource's root), its `$defs` lifted to the root, where its `#/$defs/...` references resolve;
  - the envelope's and the snapshot's `$defs` merged, a name in both that differs being a build-time error, not a silent pick (today the only shared name is `Error`, identical in every snapshot).
  The dialect is JSON Schema 2020-12, as the snapshots are; the snapshots use `unevaluatedProperties` and schemars' `uint32`, `uint64`, and `double` formats, which a draft-07 validator may not compile, so the live check below is what tells.
- **Tested:** every example envelope in `crates/silico-core/tests/contract/commands/examples/` and every reply in the bracket's replay validates against its tool's `outputSchema` (the `jsonschema` dev-dependency); and live, a TS-SDK client (Claude Code) loads `tools/list` and validates a refused call's reply.
- **Size:** `tools/list`'s input schemas are about 49 KB (about 12,000 tokens in every agent's context; `add_feature`'s 22 KB of it), its output schemas about 215 KB. Recorded here so a change that grows them is seen; trimming them is a change to the snapshots, the maintainer's.
- **`crates/silico-mcp/tests/contract/tools.json`** (protected; decision 24) is the `tools/list` reply, written canonically. A test checks it equal to what the server sends, and each tool's schemas equal to what the core's snapshots build, so the server and the core can't drift. Worker 2's `cache_clear` and `read_logs` and Worker 3's `export` change this file in their PRs as they land, which decision 24 covers when it matches the core's snapshots.

## Running a call

- **The reader dispatches in line order.** It reads a line, and for a `tools/call` calls `Sessions::call` itself, which queues the command and returns at once, so commands reach a session in the order the client sent them, and `open`s take session IDs in that order: nothing in a result depends on thread scheduling. A session is opening from its `open`'s call: a command naming it, sent before the open answers, waits behind the open (queued commands first in the session's queue, published reads started as it opens), and if the open doesn't open it, is refused "no session sN is open", exactly as one sent after the refusal is, so which reached the core first changes nothing. The `Calling` goes to a waiter thread, which waits, sends progress, and writes the answer. `status`, `cancel`, `version`, and `schema` take no place in a session's queue and answer on their own waiters. `status` and `cancel` answer from the session's state when they're asked, which is timing by their nature (what's rebuilding now, what's running to cancel): one naming a session still opening is answered "no session sN is open".
- **Calls in flight are bounded:** 64 in the process. A call holds its slot until its waiter ends (answered, or cancelled and the core's answer come back), not until its cancel arrives, so call-then-cancel against a hung kernel request can't grow threads without bound. Past it, a call is answered at once with a refused envelope that names the limit: `invalid_input`, no parameter, "64 calls are already running in this server, the most it runs at once", suggesting the client wait for one to answer (or cancel one) and call again. It's a transport limit, the server's, not the core's (the maintainer's choice, 2026-10-26): this note records it, and `version` doesn't report it, so `version.json` is unchanged.
- **Progress:** if the call's `_meta.progressToken` is given, its waiter waits in steps of 100 ms (`wait_timeout`) and reads `progress()` between. `progress()` is the session's newest rebuild, which may be another than the call's own, so its `done` can fall (a `check` queued behind an edit reads the edit's 9 of 9, then its own 0 of 12). MCP requires each notification's `progress` to increase, so the server keeps a count per call that grows by each step seen done and never falls, sends it with no `total` (a rebuild's steps aren't the call's), and the step running as `message`; nothing is sent until the count grows. Notifications are timing; results never are.
- **The writer** is one lock on the blocking output: a client that stops reading stops the waiters (backpressure), never an unbounded queue. A call's progress notifications are dropped, not queued, while the writer is busy. Whether a call is answered or cancelled is decided under a small lock of the call's own, never the writer's: a waiter marks its call answered, then writes; a cancel that finds it answered is ignored, as the spec allows. So the reader doesn't wait on a call's answer being written: it keeps reading pings and cancels while a slow client holds the writer, up to 64 of its own replies (pings, errors, `status` and the like) waiting to be written; past those, it waits for the client to read, which is the backpressure, so a client that never reads holds nothing but those 64.
- **Cancellation (decision 10):** `notifications/cancelled` with a call's `requestId` cancels it through its `Stopper`, the pool's superseded path, and the call gets no reply. One already answered is left as it is, as the spec allows. A commit cancelled midway is safe: the cancel is settled before the file is written (M4.2). `cancel` the tool is the other way in.
- **A client that goes away:** stdin's end, a write that fails (the client closed its end), or SIGTERM (MCP's next step after closing stdin; `silico serve` registers it with `signal-hook`'s safe `flag::register` and calls `Stop::stop`), cancels every call in flight, drops every session, and ends `serve` cleanly. Dropping `Sessions` rolls back each open transaction (`close` refuses one) and stops its work, so no session is left holding a transaction for no one and no worker is left running. A `save_over` temporary is removed if the drop finishes within the client's grace period; a SIGKILL after it can leave one (`.NAME.part-PID`), which the next save of that file replaces. Uncommitted edits are lost, as they are when a session is dropped.
- **Faults:** the workspace's lints keep `unwrap`, `expect`, and `panic!` off every input path; a thread that ends without an answer anyway is answered by the core's `Running` (its `lost` error) as a refused envelope, so every call gets an answer or, cancelled, none.

## Errors on the wire

| What came | Answer |
|---|---|
| A line that isn't JSON | `-32700`, `id: null`, `data` a refused envelope (`invalid_input`, the parse error's place) |
| JSON that isn't a request or a notification (a batch, a wrong `jsonrpc`, an ID that's neither a string nor a number, an ID in flight) | `-32600` |
| An unknown method | `-32601` |
| `tools/call` with an unknown tool, or `arguments` that aren't an object | `-32602`, `data` naming the field (`name`, with the tools as candidates; or `arguments`) |
| A known tool whose arguments the core refuses | a result: `isError: true`, the core's refused envelope, as for any refusal |

## The bracket (the milestone's done test)

- **A scripted client** (`crates/silico-mcp/tests/bracket.rs`) starts `silico serve` in a temporary workspace and replays `tests/bracket/session.jsonl`, a recorded agent session, sending each request only after the reply to the one before. It designs an L-bracket from a written spec (`tests/bracket/spec.md`): two legs, two M5 clearance holes in each (5.5 mm), the inside corner filleted. It rolls back one wrong edit, renders it, and measures it.
- **Compared byte for byte:** every reply's `structuredContent` (the replay makes no refusal that quotes the temporary workspace's absolute path), but not what's never compared: a PNG's bytes, `render`'s `png_bytes` (ARCHITECTURE.md), progress notifications (timing), and `serverInfo`'s version (the build's).
- **Hand-checked:** the volume, by hand: the legs (60 × 40 × 5 and 5 × 40 × 45 above it: 21,000 mm³), less four holes' cylinders (π · 2.75² · 5 each), plus the fillet's (1 − π/4) · r² · width (r = 5, width 40): 22,000 − 401.25π ≈ 20,739.44 mm³, against `mass_properties` to the measure's bound; the area and centre of mass, by hand; each hole's `distance` to its leg's edges; the render's size.
- **Export:** once Worker 3's `export` lands, the replay exports a 3MF that passes M4.8's checks, whose mesh's volume is the hand calculation's within the tolerance's bound, and which FreeCAD reads back as a solid (the oracle). PrusaSlicer slicing it, and the maintainer's run of the same spec with a fresh agent that has only the MCP server, are recorded in `docs/walkthrough/m4.md`.
- **`/break-it`'s catalog:** malformed JSON-RPC, unknown tools, wrong types, huge arguments, calls during a rebuild, cancellation races, an ID reused in flight, and a client that disconnects mid-call, each with a structured answer and no crash or hang.

## Not in M4.9

A network transport; MCP resources, prompts, sampling, and elicitation; `listChanged` (the tool list is fixed for a build); and MCP's logging notifications (`read_logs` is a tool, section 9).
