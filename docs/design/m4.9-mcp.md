# M4.9 design: the MCP server

**Status: a draft for the architecture reviewer, before the crate is built.** It builds M4.9's row of the M4 plan (#50) on docs/design/m4.1-command-api.md: section 8 (`tools.json`), section 9 (transport, exact JSON, a tool's answer), and decisions 7 (stdio), 10 (MCP's cancellation), 23 (exact JSON both ways), 24 (the contract files), and 26 (the workspace in the core). Where this note and M4.1 disagree, M4.1 is right, and this note is the bug.

## What's added

| Where | What |
|---|---|
| `silico-core`, `command::call` | One entry for every command by name, for every client: `Sessions::call(name, arguments) -> Call`, where `arguments` is a request's text, read by Silico's own reader. It answers with the envelope's text, one line (`Layout::OneLine`), and, for `render`, the PNG beside it. An unknown name is `Call::Unknown`, which isn't an envelope (section 9: a JSON-RPC error). `version` and `schema` go through it too. `COMMANDS`'s order is its order. |
| `silico-core`, the workspace (decision 26) | `Sessions::in_workspace(root)`: `open`'s path, and `render`'s and `export`'s, are relative to `root`. A path outside it, or one that reaches out of it through a link, is refused as `invalid_input` naming the field, with M4.1's message (section 7's `open` example). `file::Output` already takes the workspace; `open` gains the same check, with one implementation of it in `file`. The CLI gives none, so it reads paths as it does today. |
| `silico-mcp` (new) | The server, as a library: `serve(sessions, input: impl BufRead, output: impl Write)`. JSON-RPC 2.0 over lines, MCP's methods, the tool list, cancellation, progress, and the end of a client. It depends on `silico-core` and serde_json (with `raw_value`) only: no MCP SDK (below). No `unsafe`, no C++, no network. |
| `silico-cli`, `silico serve` | Starts the pools (kernel, sketch, render) as `silico check` does, `Sessions::in_workspace(current directory)`, and runs `silico_mcp::serve` on stdin and stdout. Logs go to stderr (MCP's stdio rule: nothing but messages on stdout). |

## The protocol

- **Revision 2025-06-18,** pinned: the first with `structuredContent` and `outputSchema`. It has cancellation and progress, and drops JSON-RPC batches. `initialize` answers with it whatever the client asks; a client that can't speak it disconnects, as the spec says. A later revision is a change to this pin, with its own tests.
- **Methods:** `initialize` (capabilities: `tools` with `listChanged: false`; `serverInfo`: `silico` and the build's version; `instructions`: the three things an agent most needs, section 9's), `notifications/initialized`, `ping`, `tools/list`, `tools/call`, and `notifications/cancelled`. Every other request is JSON-RPC's `-32601`; every other notification is ignored, as JSON-RPC asks. A `tools/call` before `initialize` is refused (`-32600`, saying `initialize` comes first).
- **No SDK** (decision 23 allows one for the handshake's types at most): the handshake is four small messages, written with serde_json, and an SDK would bring an async runtime and a second JSON path for 200 lines' worth of types. Each message's shape is tested against the spec's examples.

## Exact JSON both ways (decision 23)

- **In:** each line is parsed by serde_json into a frame (`jsonrpc`, `id`, `method`, and `params` as a `RawValue`). A `tools/call`'s `params.arguments` stays a `RawValue`, and its text goes to `Sessions::call`, so Silico's reader sees the bytes the client sent: a key given twice, a number with too many digits, a nesting past 64, all refused as the core refuses them.
- **Out:** the server writes each reply line itself. `structuredContent` is the envelope's text spliced in raw, and `content`'s one text block is that same text as a JSON string. `isError` is `!ok`. A JSON-RPC error's `data` is a refused envelope, spliced the same way.
- **Lines:** a line is read up to the core's 64 MiB (`MAX_INPUT_LEN`) plus the frame's room. A longer line is skipped to its end without being held, and answered with `-32600` if its ID can be found in what was read, so a huge argument can't exhaust memory.

## Tools

- **One tool per command,** in `COMMANDS`'s order, with the same name. The description is the command's, written for agents (edit inside a transaction, read `current` after an edit, names come from `elements` and `query`).
- **`inputSchema`** is the command's `request` snapshot as it is.
- **`outputSchema`** (M4.4's open point, recommended to the maintainer): MCP checks `structuredContent`, the whole envelope, against it, and wants an object at its root. So it's the envelope's schema with `result` set to the command's `result` snapshot, under `"type": "object"`, the envelope's `anyOf` (answered or refused) kept beneath it, and the two schemas' `$defs` merged (a name in both that differs is a build-time error, not a silent pick).
- **`crates/silico-mcp/tests/contract/tools.json`** (protected; decision 24) is the `tools/list` reply, written canonically. A test checks it equal to what the server sends, and each tool's schemas equal to what the core's snapshots build, so the server and the core can't drift. Adding Worker 2's `cache_clear` and `read_logs` and Worker 3's `export` as they land changes this file in their PRs, which decision 24 covers when it matches the core's snapshots.

## Running a call

- **Each `tools/call` runs on its own thread,** so a slow `check` doesn't hold up a `status` or a `cancel`. Sessions already run one command at a time per session, in order, so ordering within a session is the core's. Replies go through one writer, a line at a time, and may come back in another order than their requests, as JSON-RPC allows. Calls in flight are bounded (64): past it, a call is refused with a refused envelope, not queued without end.
- **Progress:** if the call's `_meta.progressToken` is given, the thread waits on the command in steps of 100 ms (`Running::wait_timeout`) and sends `notifications/progress` when `status`'s progress changes (`progress`: steps done, `total`: steps, `message`: the step running). Notifications are timing; results never are.
- **Cancellation (decision 10):** `notifications/cancelled` with a call's `requestId` cancels it through its `Stopper`, the pool's superseded path, and the call gets no reply. One whose answer was already written is left as it is, as the spec allows. `cancel` the tool is the other way in.
- **A client that goes away:** stdin's end, or a write that fails (the client closed its end), cancels every call in flight, closes every session, and ends `serve` cleanly: no session is left holding a transaction for no one, and no worker is left running. Uncommitted edits are dropped, as `close` drops them.
- **Faults:** the workspace's lints keep `unwrap`, `expect`, and `panic!` off every input path; a thread that ends without an answer anyway is answered by the core's `Running` (its `lost` error) as a refused envelope, so every call gets an answer or, cancelled, none.

## Errors on the wire

| What came | Answer |
|---|---|
| A line that isn't JSON | `-32700`, `id: null`, `data` a refused envelope (`invalid_input`, the parse error's place) |
| JSON that isn't a request or a notification (a batch, a wrong `jsonrpc`, an ID that's neither a string nor a number) | `-32600` |
| An unknown method | `-32601` |
| `tools/call` with an unknown tool, or `arguments` that aren't an object | `-32602`, `data` naming the field (`name`, with the tools as candidates; or `arguments`) |
| A known tool whose arguments the core refuses | a result: `isError: true`, the core's refused envelope, as for any refusal |

## The bracket (the milestone's done test)

- **A scripted client** (`crates/silico-mcp/tests/bracket.rs`) starts `silico serve` in a temporary workspace and replays `tests/bracket/session.jsonl`, a recorded agent session (its requests, and the answers' bytes it expects). It designs an L-bracket from a written spec (`tests/bracket/spec.md`): two legs, two M5 clearance holes in each (5.5 mm), the inside corner filleted. It rolls back one wrong edit, renders it, and measures it.
- **Hand-checked:** its volume (the legs' boxes, less the holes' cylinders, plus the fillet's (1 − π/4)·r² · width), area and centre of mass, against `mass_properties`, to the measure's bound; each hole's `distance` to its leg's edges; the render's size.
- **Export:** once Worker 3's `export` lands, the replay exports a 3MF that passes M4.8's checks, and FreeCAD reads it back as a solid of the same volume (the oracle). PrusaSlicer slicing it is the maintainer's live run, recorded in `docs/walkthrough/m4.md`.
- **`/break-it`'s catalog:** malformed JSON-RPC, unknown tools, wrong types, huge arguments, calls during a rebuild, cancellation races, and a client that disconnects mid-call, each with a structured answer and no crash or hang.

## Not in M4.9

A network transport; MCP resources, prompts, sampling, and elicitation; `listChanged` (the tool list is fixed for a build); and MCP's logging notifications (`read_logs` is a tool, section 9).
