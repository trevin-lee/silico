# M4.1 design: the command API

**Status: approved by the maintainer, 2026-10-24: all recommended (decisions 1–7 and 9–35, and the protected changes as stated).** Added since, accepted by Main (not reopening a decision): a torus's `major_radius` and `minor_radius` (M4.4's design); a cone's `half_angle` and `apex`, an edge's `start` and `end` in its curve's own order, and a degenerated edge's type (M4.4's review). Revised after round 1 of review and its verification (the architecture and format reviewers, 2026-10-24); M4.2 builds from it. M4.1 (docs/roadmap/m4-mcp.md, #50, with the amendments in `m4-plan-amendments.md`) designs every command the agent interface needs: each command's request, its result, and its errors as JSON; sessions; transactions; edits as commands and as text; a file changed outside the session; undo; cancellation; faults reported once; one table of limits; and how the shapes are versioned. The command API's shapes are the MCP tools' shapes, one to one, so the CLI and the app read the same ones. Each decision is in section 11, with its options and the recommendation taken, marked **Decided (recommended, approved 2026-10-24):**. The body of this document is written to those decisions.

Step numbers are #50's. If amendment A4 (sketches on faces) is taken, a step is added after M4.4, and #50's M4.5 to M4.9 become M4.6 to M4.10. This document uses #50's numbers throughout and calls the added step A4's.

## 1. Scope

The commands M4.2 to M4.9 need, and nothing more. Each names the step that builds it.

| `open` | M4.2 | Opens a document's file as a session, or creates a new, empty document |
| `close` | M4.2 | Closes a session |
| `status` | M4.2 | A session's path, revision, transaction, and rebuild |
| `cancel` | M4.2 | Stops the command a session is running, for clients that don't send MCP's cancellation (decision 34) |
| `begin` | M4.2 | Begins a transaction |
| `commit` | M4.2 | Ends it, saving what its edits changed through `file::save` |

| `format` | M4.2 | Saves the document in canonical form with every fingerprint and solve as rebuilt, accepting drift by name: what `silico fmt` runs (decision 31) |

## 2. Shapes every command shares

### The response

Every command answers with one of two shapes. A command that ran:

```json
{
  "ok": true,
  "session": {"id": "s1", "path": "bracket.silico", "revision": 4, "transaction": false, "reloaded": false},
  "model": null,
  "result": {"base": 4}
}
```

A command that read a model says which:

```json
{
  "ok": true,
  "session": {"id": "s1", "path": "bracket.silico", "revision": 7, "transaction": true, "reloaded": false},
  "model": {"revision": 6, "of": "published", "fault": null},
  "result": {"problems": [], "problems_total": 0, "warnings": [], "warnings_total": 0}
}
```

A command that was refused or couldn't run:

```json
{
  "ok": false,
  "session": {"id": "s1", "path": "bracket.silico", "revision": 4, "transaction": true, "reloaded": false},
  "model": null,
  "errors": [
    {"code": "invalid_input", "message": "a transaction is already open in this session", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": null, "suggestion": "commit or roll back the open transaction, then begin again", "candidates": []}
  ],
  "total": 1
}
```

- `session` is the session's state after the command: its ID, its path as opened, its revision (section 3), whether a transaction is open, and whether the session reloaded its file from disk before running the command (decision 2). It's `null` for a command that takes no session (`version`, `schema`, an `open` that failed).
- `model` is the model the command read, if it read one: its revision, whether it was the session's `current` revision's or the newest `published` (decision 33), and the kernel fault its rebuild met, if any, once (section 6). `null` for a command that read none.
- `errors` holds every reason the command was refused, in the order found, each in the error contract's shape, the first `PROBLEMS_LISTED` (100) of them; `total` is how many there are, listed or not. One shape for one error and for a gate's hundred.
- A document's problems are not a refusal. `check` that finds a failed fillet ran: its problems are in its `result`. `ok: false` means the command didn't do what it was asked: a bad request, an edit the gate refused, or a kernel fault that kept it from answering at all. That is the CLI's exit 1 against exit 2 (docs/cli.md), kept.

In the command reference below, each example is the `result` member, or one member of `errors`, as its envelope carries it.

### Layout and key order

- Every request and result is JSON in M2.1's canonical layout (D7): an object or array on one line when it holds no object at any depth, otherwise one member per line, indented two spaces; `, ` and `: ` between members on one line; LF, and no trailing newline (a response is a value, not a file).
- Keys are in schema order: the order each shape below gives them. Never sorted, never in a map's order. JSON Schema can't record the order (and the generated snapshots sort `properties`), so the order's record is the example files (section 8), which the writer is tested against byte for byte.
- On a transport that needs one message a line (MCP's stdio), the same value is written on one line. That's the only difference: the same members, in the same order, with the same numbers. Section 9 says how MCP keeps them so.

### Numbers

As the document writes them (ARCHITECTURE.md, *Numbers in the file*), read exactly from their digits by Silico's own reader, never through a float:

- **Lengths** (a distance, a radius, a point's coordinates) are `Length`: millimetres, plain decimals, at most 6 places (`2.5`, `0.000001`). Computed lengths are rounded to the nanometre once, at the end (`Length::rounded`, as Fable's measurement decision does).
- **Angles** are `Angle`: degrees, at most 9 places.
- **Areas and volumes** are a fingerprint's `Measure`: mm² and mm³, 6 places (`780.365046`), held as whole millionths in an `i128`, so their digits can pass what an `f64` holds.
- **A sketch's coordinates** (a point's `x` and `y`) are a `Coordinate`, as the document holds them (M3.2's D3): an `f64`, written as Rust writes it, the shortest decimal that reads back as the same `f64`; `-0` reads and writes as itself.
- **Directions** (a normal, an axis) are unit vectors of `f64`, written as a `Coordinate` is, `-0` written as `0`.
- **Counts, revisions, byte sizes** are whole numbers.

A request's `Length` with a seventh decimal, an `Angle` with a tenth, or either written `-0`, is refused as the document refuses them: `invalid_input`, naming the field.

### Names and IDs

- A feature is named by its ID (`k7f2qx3m`), never its display name, which needn't be unique.
- An element is named by its stable name in scheme 5's form (`m3tq8v0z.cut.Edge(G k7f2qx3m.box.Face6, G a91cw0de.cylinder.Face1)`), never by OCCT's index. A name that finds nothing is `reference_broken`, with candidates (M2.8), never a guess.
- **Paths to a field** are dotted, as the error contract's `parameter` is, and requests and errors use one rule (decision 15): a list of objects that have an `id` (a sketch's points, lines, circles, arcs, constraints) is indexed by the member's ID (`constraints.g4h5j6k7.value`); any other array by place, from 0, with no leading zeros (`position.2`, `edges.0`). A member with no usable ID (its `id` missing, not an ID, or held by a member before it in the sketch) is named by place too (`constraints.3.id`, the later holder of a repeated ID), so no two members share a path, and in a sketch's lists a segment of eight characters is an ID and any shorter one a place (docs/design/m3.2-sketch-format.md, *The gate's rules for sketches*).
  - **A request names a sketch's members by ID only.** A place there is refused, with the member's ID path as the candidate when it has one (`constraints.3.value` → `constraints.g4h5j6k7.value`; M4.2's `set_field` builds the refusal). The place is counted in the list as the session's whole-document `text` shows it (the file's bytes until an edit, then the canonical form), so the candidate is the member the agent counted to. A place path appears only in errors about a document the reader or the gate refuses, which only `replace_text` mends (a refused document refuses every other edit, below).
  - **An edit that repeats an ID** is refused at the field the request named (`circles`, or `circles.g4h5j6k7.id`), with the member already holding the ID in `elements` and the message (M4.2's `set_field`), not at the untouched member the gate would name by place. The gate's rule stays the rule for checking a file or a text.

### Requests are strict

A request is read as a document is: unknown keys refused, a key given twice refused, every field the shape gives required, `null` where the shape allows it and the client has nothing to give. A request a newer client sends to an older server fails loudly, naming the field the server doesn't know, rather than being half-understood.

### Reading the current or the published model

Every command that reads a model (`check`, `elements`, `query`, `mass_properties`, `distance`, `angle`, `render`) takes `"model": "current"` or `"published"` (decision 33):

- `current` waits for the session's current revision's rebuild, and answers from its model, never an older one's.
- `published` answers from the newest model the session has published, which may be of an older revision, and starts the current revision's rebuild if none is running. It doesn't wait for a rebuild, and it doesn't queue behind the session's other commands (section 3). If nothing has been published yet, it's refused, naming `model`. At a revision the gate refused, it answers from the newest model published (an older revision's, as `model.revision` says) and starts nothing; with nothing published then, it's refused with the gate's (or the reader's) problems.
- **What a published read costs.** `elements`, `query`, `check`, and `mass_properties` need no kernel on a published model: every solid a read can name is described as part of the rebuild that made it, before the model is published (below). `distance`, `angle`, and `render` do need a worker (`BRepExtrema`, the meshes to draw). They run on the session's read lane: a second handle the session's `KernelPool::client` gives, whose generation the session's rebuilds never advance, so a rebuild that starts never drops or stops a published read. A read on the lane ends when it's done, when it's cancelled, or when its session closes; it's under each worker request's timeout like any other. So a published read doesn't wait for a rebuild, but one that needs the kernel takes as long as its own kernel work, and an app's hover after an edit measures the published model rather than failing or flickering.

Either way, the envelope's `model.revision` says which revision the answer is of. The app reads `published` for pre-selection, the viewport, and its Measure tool, so none of them stalls during a rebuild; an agent reads `current`, to answer about what it just did. `export` and `commit` read only the current model.

### Element entries

`elements` and `query` return elements in one shape, every field always present, `null` where it doesn't apply. The fields M4.5's measures need are Fable's (`m4-measure-fable.md`, *Build*, 1); M4.4's design settles the rest within this shape. A box's top face, after the hole M2.1's example cuts in it:

```json
{"name": "k7f2qx3m.box.Face6", "aliases": [], "stable": true, "feature": "m3tq8v0z", "kind": "face", "type": "plane", "area": 780.365046, "length": null, "position": null, "normal": [0, 0, 1], "centroid": [20, 10, 10], "start": null, "end": null, "midpoint": null, "straight": null, "axis": null, "radius": null, "diameter": null, "major_radius": null, "minor_radius": null, "half_angle": null, "apex": null, "default_x": "+x"}
```

- `name` is the element's own name, the first of its names in the element map; `aliases` are its other names, other derivations that reach it, in the map's order (`ElementMap`'s, naming/mod.rs), each `{"name": ..., "stable": ...}` with its own stability. Entries are ordered by `name`.
- `stable` is whether `name` is stable: `false` for a name that came about for more than one element, a `~n` duplicate, an operation's element by its number, or one made from such a name (`ElementMap::is_unstable`). A reference stored in the document (a fillet's edge, A4's face) refuses an unstable name, as references do today (references.rs); a command that only reads (`distance`, `angle`, `render`'s `highlight`) takes one, since it's answered once and stored nowhere. `query`'s `"stable": true` keeps an element if any of its names is stable (its `name` or an alias), so an element with an unstable own name and a stable alias isn't filtered out; a reference then uses the stable alias.
- `feature` is the feature whose solid the element is of; `kind` is `face`, `edge`, or `vertex`; `type` is the geometry's, as OCCT names it: for faces `plane`, `cylinder`, `cone`, `sphere`, `torus`, `bezier`, `bspline`, `revolution`, `extrusion`, `offset`, `other`; for edges `line`, `circle`, `ellipse`, `hyperbola`, `parabola`, `bezier`, `bspline`, `offset`, `other`; for vertices `point`. A degenerated edge (a sphere's pole, a cone's apex) is `other`, with `length` 0, `start` and `end` its vertex's point, and `straight` false: FreeCAD gives a sphere's pole no curve and a cone's apex a circle of radius 0, and an entry's radii are never 0.
- `area` (a face's), `length` (an edge's), `position` (a vertex's) are M1's precise measures (a relative 1e-9).
- `normal` is a planar face's outward unit normal; `centroid` a face's centre of area.
- `start`, `end` are an edge's end points, in its curve's own order, as FreeCAD's `Edge.firstVertex()` and `lastVertex()` give them (not the orientation a face gives the edge, which an upstream edit reordering faces could flip); `midpoint` a straight edge's; `straight` whether an edge is straight (a line, or a degree-1 B-spline of two poles).
- `axis` is `{"point": [...], "direction": [...]}` for a cylinder, cone, sphere, torus, circle, or arc. A cylinder's and a cone's direction keeps its surface's own sign, never turned to point "up": a cylinder primitive's side (a reversed face, as `Part::Cylinder` makes it) and a pad's cylinder both have −z, as FreeCAD 1.1.3 gives them (only `Part.makeCylinder`, which no feature uses, gives +z). `radius` is a cylinder's, sphere's, circle's, or arc's; `diameter` twice the radius, for a circle or arc edge and a cylinder face; `major_radius` and `minor_radius` a torus's (FreeCAD's Toroid MajorRadius and MinorRadius), `null` for every other type, one field per number as decision 14 has it (from M4.4's design, docs/design/m4.4-describe.md, accepted by Main as adding to the approved shape). `half_angle` and `apex` are a cone's: its half-angle (an `Angle`, in degrees, keeping its sign, as OCCT's `gp_Cone` and FreeCAD's `Part.Cone.SemiAngle` give it) and its apex (`[Length; 3]`: `axis.point` − `axis.direction` · r / tan(half-angle), where r is the cone's radius at `axis.point`, OCCT's reference radius and not an entry field; `Part.makeCone(4, 0, 6)` has its apex at (0, 0, 6) and a half-angle of −33.690067526 degrees, as FreeCAD gives), `null` for every other type. A cone that's nearly a cylinder has its apex beyond what a `Length` holds (`Part.makeCone(1e6, 1e6 − 1e-6, 1e5)`, valid from lengths a primitive takes, has it at about 1e17 mm): its `apex` is then `null`, the cone otherwise described as any other, and its `half_angle`, rounded to 9 places once at the end, may read `0`, losing its sign; countersinks and chamfered holes need `half_angle` and `apex`, and no M4.5 measure covers a cone (from M4.4's review, likewise accepted).
- `default_x` is A4's: for a planar face, the axis token a sketch on it would take by default (F1); `null` otherwise. It goes if A4 isn't taken.

An entry holds an object only in `axis`, so a face of a cylinder is written one member per line:

```json
{
  "name": "m3tq8v0z.cut.Face(I a91cw0de.cylinder.Face1)",
  "aliases": [],
  "stable": true,
  "feature": "m3tq8v0z",
  "kind": "face",
  "type": "cylinder",
  "area": 157.079633,
  "length": null,
  "position": null,
  "normal": null,
  "centroid": [20, 10, 5],
  "start": null,
  "end": null,
  "midpoint": null,
  "straight": null,
  "axis": {"point": [20, 10, -1], "direction": [0, 0, -1]},
  "radius": 2.5,
  "diameter": 5,
  "major_radius": null,
  "minor_radius": null,
  "half_angle": null,
  "apex": null,
  "default_x": null
}
```

**Where the entries come from** (M4.4's protocol, stated here because it decides its shape). The worker's `describe` request runs as part of each rebuild, once for every solid a read can name (each body, and each built feature's solid, which `feature` can ask for), before the model is published, never per call: its raw measures are kept on the `Model` beside the element map, and in `.silico-cache/` in the step's own entry, beside its summary (a description is the shape's alone, and the names come from the element map, so no naming key is needed: docs/design/m4.4-describe.md, *Described as part of the rebuild*), so `elements` and `query` on any published model ask the kernel nothing, and a rebuild that hits the cache asks it nothing either. A solid's faces, edges, and vertices are described in batches of at most 1,000 elements a request, so no single request nears the kernel's timeout on a large solid.

### Warnings

`check` reports warnings beside problems (ROADMAP.md's M4, which M3 deferred to here: M3.2's D2 warning for two curve ends at one place that aren't one point, and M3.3's agreeing redundant constraints). A warning is in the error contract's shape, so an agent reads one shape, with its code from a list of its own (decision 17): it never fails anything.

```json
{"code": "ends_not_joined", "message": "two curve ends are at one place but aren't one point, so the profile is open there", "feature": "s0000002", "elements": ["pb000003", "pb000007"], "elements_total": 2, "parameter": null, "cause": "the ends are 4e-8 mm apart, within FreeCAD's joining distance of 1e-7 mm", "suggestion": "share the point: make one curve end at the other's point", "candidates": []}
```

## 3. Sessions

A session is one open document, held between commands (M4.2's `command::Sessions`, each session addressed by its `SessionId`). Every client holds documents this way: MCP's tools, the app's windows, and the CLI, whose commands open a session, run one command, and close it in one process. A session belongs to the client that opened it; clients in different processes share a document through its file (decision 30).

### Opening, holding, closing

- **`open`** reads the file (`file::read`: a regular file, no more than a document may be) and puts it through the gate. The session opens even if the gate refuses the document (decision 21): it then holds the bytes and the gate's problems, `open`'s result lists them, and the commands that need a checked document refuse until `replace_text` gives it one (SolidWorks opens a part whose rebuild fails; an agent must be able to open a broken file to mend it). With `"create": true`, `open` writes a new, empty document to the path (`{"silico": 1, "units": ..., "naming": 5, "features": []}`, in canonical form) and refuses if the file exists.
- **A file open once a process.** Opening a file a session of this process already holds is refused, naming that session (decision 22). A session claims its file by two keys, refusing an open that matches either: its path as its links resolve, which a save by rename (an editor's, git's) leaves in place, and the file it is, its device and inode, held open while claimed so the inode isn't reused, which catches a hard link and macOS's second name for a file on the data volume. Two sessions saving one file would each see the other's saves as changes outside the session.
- **Paths** are relative to the workspace when the process has one (decision 26): `silico serve` is started in a directory and refuses any path outside it or through a link out of it (M4.9). The CLI has none, so `silico check ../part.silico` works as it does today.
- **`close`** ends the session. It's refused while a transaction is open (commit or roll back first), so nothing is dropped without the client saying so. A client that goes away (MCP's stdin closed, the app quit) rolls back every open transaction and closes its sessions: only a commit or a `format` ever writes the document.
- **Session IDs** are `s1`, `s2`, ... in the order the process opened them, never reused within the process: a counter, not randomness.

### What a session holds

| Held | What |
|---|---|
| The path | As given, and as its links resolve |
| The file's bytes | As last read from the file or written to it: what decision 2 compares the file with |
| The document's text | The bytes the session's document is: the file's, until an edit; after one, the edited document in canonical form |
| The checked form | The gate's `Checked` for that text, or the gate's problems if it refused it |
| The revision | A whole number, 1 at `open`, one more for each change of the session's document: an accepted edit, a reload from the file, a rollback, a commit or `format` that writes. It never goes back and is never reused, so a result and an edit can say which state they're of |
| The models | The current revision's `Model` or its rebuild, and the newest model published |
| What edits reached | The features the session's edits changed since the last save, and every feature that uses them (section 5): what a commit may write new fingerprints for |
| The transaction | If one is open: the state `begin` saw (text, checked form, model, revision, what edits reached) |
| A kernel handle | The session's own handle on the shared pool, with its own generations (MA2, below) |
| Its logs | M4.7's bounded buffer of the session's `tracing` events |

### Rebuilds and the models

A new revision's rebuild starts when a command first needs its model: a read of the current model, a read of the published model (which starts it without waiting), a commit, `format`, an edit outside a transaction (which commits), or `export`. An edit inside a transaction starts none, so a run of edits doesn't start and stop a rebuild each (the pool kills a superseded request after 50 ms, `STOP_AFTER`). A rebuild that starts supersedes the session's older one, if it's still running. The app reads the published model each frame, which keeps the current revision rebuilding in the background without ever waiting for it.

### Per-client generations (MA2), and what sessions share

Today the pool's generations are global: `Kernel::advance` supersedes every older generation, whoever started it, so one document's new rebuild could drop another's work (the M2 review's MA2). M4.2 gives each session its own handle on the shared pool (`KernelPool::client`), with its own generations: a session's new revision supersedes only its own older work, never another session's. Generations are internal: no result carries one. The revision is what a client sees.

- **Kernel workers are shared,** up to one a core (ARCHITECTURE.md's pool), and the pool serves its clients' queues in turn, so one session's long rebuild doesn't starve another's.
- **Sketch workers are not.** Each `Recompute` starts its own sketch worker when it first solves (recompute.rs, `start_solver`), and keeps the B-reps of its last two published models (`PUBLISHED_KEPT`). So 16 sessions can mean 16 sketch workers and 16 sets of kept B-reps, with no bound on their memory but the session limit (section 6). Sharing sketch workers between sessions waits until it's measured as needed.
- **One cache a directory.** Sessions on documents in one directory share one `Cache` (M2.5: a process keeps one cache per directory), so two documents' common steps are built once.

### One command at a time, per session

Every command's whole body runs off the caller's thread: the file read before it (up to 16 MiB), the gate, the rebuild, the save, an export. In Rust each command returns a `Running` handle (section 6). The Rust API's only calls that answer on the caller's thread are `Sessions::published(&id)` (the model, for the app to draw), `status`, and `read_logs`, which read only what the session already holds. Reads of the published model run off it too: they only don't queue.

A session runs its commands one at a time, in the order they arrive, so a result never depends on how two of a client's requests interleave; an edit that arrives while a read of the current model waits queues behind it. Four kinds don't queue behind the session's other commands: `status`, `read_logs`, and `cancel` answer at once, because they only read what's held or stop what's running; reads of the published model run beside the queue, on the read lane where they need a worker (section 2), and never wait for a rebuild. `status` lists the published reads running, and `cancel` can stop them. Commands of different sessions run at the same time.

## 4. Transactions

As plan decision 1 recommends, with decisions 9, 2, and 28.

- **`begin`** keeps the session's state (text, checked form, model or its running rebuild, revision, what edits reached) and opens a transaction. One at a time, not nested: a second `begin` is refused.
- **Inside a transaction,** an edit is applied once the gate takes it and returns without starting a rebuild (section 3). Nothing is written to the document's file.
- **`commit`** waits for the current revision's rebuild, then saves the document in canonical form through `file::save`'s safe save, writing new fingerprints and solves only for what the session's edits reached (decision 28):
  - A reached feature that built gets its new fingerprint; a reached sketch, its new solve.
  - A feature no edit reached keeps its stored fingerprint, and a sketch no edit reached its stored solve. If its rebuild measures otherwise, or its re-solve moves it, that's `drift`, listed in the commit's problems and never written over: only `format` accepts drift (decision 31), naming each feature it accepts.
  - A feature that failed, or that a kernel fault stopped (section 6), keeps its stored fingerprint and is listed, and the document is still saved, as `fmt` saves it and as SolidWorks saves a part with rebuild errors. A reached feature whose fingerprint couldn't be written stays reached in the session until one is.
  - The commit is refused, and the transaction left open, if the file changed since the session read it (`conflict`, decision 2), if the canonical text would pass 16 MiB, or if the file can't be written (`io_failed`).
  - A commit whose document equals the one `begin` saw writes nothing.
- **`rollback`** ends the transaction and restores what `begin` kept: the text, byte for byte as it was (not rewritten in canonical form), the checked form, and what edits reached, exactly; and the model `begin` saw, the same one, not rebuilt, so its fingerprints and names are what they were, if there was one. If `begin` came while its revision was still rebuilding, and a rebuild started in the transaction (by a read of the current model, say; an edit starts none, decision 13) then superseded it, that model was never made: the rollback then starts a rebuild of the restored document, which the cache makes cheap (every step it finished before is a hit). So a session keeps its own models (the one `begin` saw, the current revision's, the newest it published), never relying on the engine's published model, which may be the transaction's. The revision is a new number whose state equals the one `begin` saw, and the restored model is that revision's: a read after the rollback names the new revision in `model.revision`, since a revision names a state. A rollback never touches the document's file. Rebuilds inside the transaction may have written cache entries (`.silico-cache/`): they stay, since they're keyed by their step and true for any document, and an edit made again hits them.
- **Outside a transaction,** each edit is its own transaction: begun, applied, committed, and saved at once (decision 1). Its result holds the commit's. If the commit is refused, the edit is undone whole and the session is as it was before it. An edit saved this way can't be undone by the API (decision 9), so `remove_feature` returns the feature it removed and its place, and `replace_text` the text it replaced (outside a transaction only), and the MCP tools' descriptions tell agents to edit inside a transaction.
- **After a commit** there is no undo in the API (decision 9). The committed states are the file's history, which is git's. An agent that wants to try something opens a transaction and rolls it back.

### A file changed outside the session (decision 2)

Agents may edit a document's text directly and then run `silico check` (ARCHITECTURE.md), so a file can change under a session.

- Before each command outside a transaction but `close`, `status`, `read_logs`, `cancel`, and reads of the published model, the session reads its file and compares its bytes with those it last read or wrote; inside a transaction, only `commit` reads it. Bytes, not times: a change within a file system's time resolution, or one that keeps the size, is still found.
- **Outside a transaction,** a change is reloaded through the gate, as the app will reload a file it watches: a new revision, and `"reloaded": true` in the command's envelope. If the gate refuses the new text, the session holds it and its problems, as `open` does. A change from outside is a hand edit: the session's edits didn't reach it, so its stale fingerprints are `drift` until `format` accepts them, as `silico fmt` does today.
- **Inside a transaction,** nothing is reloaded, and a `commit` that would write is refused as a `conflict`, naming the file (one whose document is the one `begin` saw writes nothing, so loses nothing, and ends the transaction). The agent rolls back (the next command outside the transaction then reloads the file) or rolls back and begins again from the file's new state. Nothing is merged, silently or otherwise.
- **An edit names the revision it was made against** (decision 12). An agent that read the text at revision 5, while the file was reloaded at revision 6, would otherwise overwrite what changed with `replace_text`. An edit whose `revision` isn't the session's is refused as a `conflict`, saying which revision the session is at.
- Outside a transaction, a file that's gone or can't be read is `io_failed` for every command that reads it (one grown past what Silico reads of a document is `invalid_input`), naming the file, with the cause "the session reads its file before each command to find changes made outside it" and the suggestion "put the file back at \"bracket.silico\", or close the session (roll back first) and open the file where it is now"; the session keeps its state. Inside a transaction, every command but `commit` runs on what the session holds, and a `commit` that would write refuses a file that's gone as a `conflict`, as it refuses one changed, and one it can't read as `io_failed`. `close` never reads the file, so a file gone or changed never keeps a session open.

## 5. Edits

As plan decision 3 recommends: both, from M4. Typed commands for the edits the bracket needs, which M5's UI then uses, and a command that replaces the whole text. Each goes through the gate: the edit is applied to a copy of the session's document and the copy is checked (`Checked::new`, the gate every write goes through). A bad edit is refused whole: the session's document, revision, and model are unchanged, and the refusal lists every error the gate found (the first 100 and how many). There is no partial edit.

- **`add_feature`** appends a feature to the timeline. Its `feature` is a feature as the document writes it, except:
  - `id` may be left out, and the core makes one. M4.2 adds the generator M2.1 planned: from the OS's randomness by default, seedable in tests only (not through the API, the Rust API or a request: decision 20). An ID is a value the document stores, chosen once; a replayed session (M4.9) passes the IDs its recording holds (decision 20).
  - `v` may be left out, for the feature type's current version.
  - `fingerprint` is refused: a commit writes it.
  - With A4, a sketch on a face may leave out `plane.x`. The face's name is looked up in the solids live at the sketch's place in the timeline (made by features before it, and consumed by none before it), and must be stable. The core then names the face's `default_x` (F1), which needs that model, so this edit waits for its rebuild; a name that finds nothing is refused as `reference_broken`, with candidates. The token is always written. A4's design settles the rest.
  - The result holds the feature as the document now holds it.
  - Element IDs inside a sketch (its points, lines, circles, arcs, constraints) are the client's: they refer to each other within the feature, so they're given with it, and the gate refuses any that repeat or aren't of the form.
- **`set_field`** sets one field of one feature, named by the feature's ID and the field's path (section 2: `extent.length`, `position.2`, `edges`, `constraints.g4h5j6k7.value`, `note`). The value is read as the document reader reads that field, exactly. It replaces the field's whole value: to add a circle to a sketch, set its `circles`. `id`, `type`, `v`, and `fingerprint` can't be set (a feature of another type is a new feature; a version changes by an explicit upgrade, later). `note` set to `null` removes it.
- **`remove_feature`** removes one feature and returns it, with its place in the timeline, so a client can put it back with `replace_text` (M4 has no insert). If others use it, the gate refuses the removal with each one's broken reference, naming it: SolidWorks asks whether to delete a feature's children too; the API makes the client remove them first, by ID.
- **`replace_text`** replaces the document's whole text, which goes through the gate as `silico check` puts a file through it, and, outside a transaction, returns the text it replaced (inside one, `rollback` restores it, so `before` is `null`). Text without the header's `naming` is refused, naming `naming`: the reader takes a missing field as scheme 5 only for documents saved before M4.0 (docs/ports/naming.md), and text an agent writes now isn't one.
- **What an edit reaches** (decision 28). A feature an edit reaches is one whose own values it changed (anything but `name`, `note`, and `fingerprint`), one it added, and every feature that uses one of those, directly or through others. A typed edit's reach is what it touched; `replace_text`'s is found by comparing the new document with the old by ID. An edit of a `name` or a `note` reaches nothing. `check` doesn't compare a reached feature's stored fingerprint with its rebuild (it was measured from other inputs; the commit writes its new one), and still reports drift for every feature no edit reached. A change reloaded from the file reaches nothing (section 4).
- **Not in M4:** inserting a feature before the end of the timeline, reordering, suppressing, and finer sketch edits (add one point, split a line). M5's UI needs them; they come with it.

## 6. Long work

### Running commands, and progress

In Rust every command returns a `Running` handle, `command::Running` (a name of its own: `pool::Pending` is the kernel request's). It has `wait`, `wait_timeout`, and `try_take`, as `recompute::Run` does, and `cancel` and `progress`, which neither `Run` nor `pool::Pending` has: M4.2 adds them. The recompute reports no progress today, so the progress below comes with M4.2 too. The app polls it each frame and never waits on it, MCP's server awaits it, and the CLI waits. A command that waits for a rebuild reports its progress: on MCP, a request that carries a `progressToken` gets `notifications/progress` with the steps done, the steps in the rebuild, and the step running:

```json
{"progressToken": 7, "progress": 3, "total": 9, "message": "f0000001 fillet"}
```

Progress is a diagnostic, not a result (section 10): which step finishes first depends on scheduling.

### Cancellation (decisions 10 and 34)

- **MCP's cancellation.** A client may cancel a request it sent (`notifications/cancelled`). The request stops its kernel and solver work through the pool's superseded path, as a newer generation's does, and gets no reply: MCP's rule is that a receiver should stop the work and not respond (specification 2025-06-18, *utilities/cancellation*; the same since 2024-11-05). In Rust, `Running::cancel` does the same.
- **`cancel`,** for clients that make calls at once and don't send MCP's cancellation, and for the app's stop button (decision 34). It names the command it means (`{"command": "check"}`) and stops it the same way if that command is running: the session's queued command, if it's the one running, and every published read of that name in flight. It's refused if no command of that name is running, so a cancel that arrives late can't stop the next queued edit. It answers at once, and the stopped command answers too, so a client waiting on it isn't left waiting: with a `cancelled` error (a new code, decision 16) if it left no trace, or with its real result if it had already done its work (an edit already saved).
- A stopped wait stops the rebuild it was waiting on. The session's revision stays; the next command that needs the model starts its rebuild again, and the cache has kept every step that finished.
- A cancelled edit either finished or left no trace, never half: cancellation can arrive after the work is done, so the client reads `status` to learn the revision.

### Faults reported once (A1)

A kernel fault (`worker_crashed`, `worker_timeout`, `protocol_error`, `resource_exhausted`, `internal`, and `worker_unavailable` if #89 merges; until then a worker that can't be had is `worker_crashed`, as it is on main) says nothing about the document. It's reported once a response, never copied onto the features it stopped: today's model holds a start failure on every sketch feature (AR1's pattern, which M3's review left to M4.1).

- **Kept as the revision's outcome** (decision 32). Crashes and timeouts aren't kept by the cache (a refusal that follows from the step's values is; recompute.rs), so a feature that reliably crashes the worker or runs past its timeout would otherwise be run again by every read, 60 seconds each. Instead the fault is the model's outcome for that feature and every feature that uses it, until a new revision, or `check` with `fresh`, tries again.
- **Beside the result, not instead of it.** A read answers from what the rebuild built and gives the fault once, in the envelope's `model.fault`, naming the feature whose request met it where one did (a fillet whose request crashed OCCT) and none where none did (a worker that can't be had). `check` lists the document's own problems as usual; the faulted features are neither built nor problems of the document. A command that needs a faulted feature's solid (its elements, a distance to one of them) is refused with the fault itself.
- **Saving around it.** A commit saves with the faulted features keeping their stored fingerprints, as failed features do. `status` says the rebuild is `faulted`.
- **New functions for it.** `command::check` and `command::format` return an error at the first kernel fault, so they can neither report one beside a result nor save around it. M4.2 adds session-level functions that do (the session's `check`, `commit`, and `format`), and leaves `command::check` and `command::format` as they are for the CLI until it becomes a thin client of the session's commands, in M4.2's last step.
- **The suggestion** for a fault that met the same feature twice running says so: try `check` with `fresh`, and if it repeats, report the document.

```json
{"code": "worker_crashed", "message": "the kernel worker crashed while building this feature", "feature": "f0000001", "elements": [], "elements_total": 0, "parameter": null, "cause": "the worker ended on signal 11 (SIGSEGV) during a fillet", "suggestion": "check with fresh to try it again; if the same feature crashes the worker again, report it with the document", "candidates": []}
```

### Limits

One table, every command's (A1), so `/break-it` tests them all at once. `version` returns them as data. A request over a limit is refused as `invalid_input`, naming the field, with the limit in the message and what to do in the suggestion, except where the table says otherwise. The values are decision 18's.

| Limit | Value | Commands | Past it |
|---|---|---|---|
| A document's canonical text | 16 MiB (`MAX_DOCUMENT_LEN`) | `open`, every edit, `commit`, `format` | `invalid_input`, naming `text` or the edit's field |
| A request's bytes | 64 MiB (`MAX_INPUT_LEN`) | all | `invalid_input`, no parameter |
| A request's nesting | 64 (`MAX_DEPTH`) | all | `invalid_input`, no parameter |
| A response's bytes | 128 MiB | all (`text` and `replace_text` are the largest) | `invalid_input`, naming the field that makes it: `text`'s `feature` reads one feature |
| Errors and warnings listed | 100 (`PROBLEMS_LISTED`), with the total | all | not refused: the rest are counted |
| Sessions open in one process | 16 | `open` | `invalid_input`, no parameter: close one (not `resource_exhausted`, which is a kernel fault, exit 2) |
| Published reads running in one session | 8 | every read of the `published` model | `invalid_input`, no parameter: wait for one to answer (each holds a thread and its session until it ends) |
| Elements a call lists | `limit`, 1 to 1,000 | `elements` | `invalid_input`, naming `limit`; the rest are read by the cursor |
| Elements a query returns | `limit`, 1 to 1,000; a tie at the cut is returned whole up to 1,000, or not at all | `query` | `invalid_input`, naming `limit` |
| Elements highlighted | 1,000 | `render` | `invalid_input`, naming `highlight` |
| A render's size | 1 to 4,096 pixels a side | `render` | `invalid_input`, naming `width` or `height` |
| A render | 30 s | `render` | `worker_timeout`, a kernel fault (decision 29) |
| Log events a read returns | `limit`, 1 to 1,000, and 1 MiB of text | `read_logs` | a read stops at 1 MiB and its cursor says where |
| A session's log buffer | 10,000 events and 16 MiB | `read_logs` | not refused: the oldest are dropped and counted |
| The export tolerance | 1e-5 to 1e8 mm (docs/ports/mesh-export.md) | `export` | `invalid_input`, naming `tolerance` |
| An export's triangles | 10,000,000 in all, counted on the mesh the worker made, before it's sent (decision 18; `silico_protocol::MAX_EXPORT_TRIANGLES`: the worker's check on its mesh, and the core's over every part in the 3MF) | `export` | `invalid_input`, naming `tolerance`: a coarser one makes fewer, or export fewer parts |
| An export's archive | 4 GiB, less a byte (a plain zip: no ZIP64), about 50 million triangles: a backstop the triangle limit keeps an export far below (10 million make about 0.9 GB) | `export` | `invalid_input`, naming `tolerance`, suggesting a coarser tolerance or fewer parts at once (a request's limit, not `resource_exhausted`, a kernel fault) |
| A kernel request | 60 s (`kernel::DEFAULT_TIMEOUT`) | every rebuild step, `describe`'s batches, the measures, `export` | `worker_timeout`, a kernel fault |
| A sketch solve | 300 s (`SKETCH_TIMEOUT`) | rebuilds | `worker_timeout` |
| A whole command | none | | the client cancels |

No command has a limit on its whole time. A refusal that depends on how fast the machine is would make one request succeed on one machine and fail on another; each request to a worker has its timeout, which is a kernel fault, never the document's.

### Files a command writes (decision 35)

`render`'s `to` and `export`'s `path` are the only paths a command writes besides the document's own (which only `commit` and `format` write) and the cache.

- **Never a document.** A path that ends in `.silico`, names a file a session of this process holds (by its path through links), or lies in a `.silico-cache/` directory is refused as `invalid_input`, naming the field. A render to `bracket.silico` would otherwise replace the committed document, the next command would reload it, the gate would refuse it, and the work would be gone.
- **The format's extension.** `to` ends in `.png`; `path` in `.3mf` (or `.step`).
- **Not over an existing file unless asked.** A file already at the path is refused, naming the field, unless the request gives `"replace": true`; then it's replaced, keeping its permissions, as `file::save` keeps them.
- **Whole or not at all.** The core writes the file, never a worker (the render worker returns the PNG's bytes; the kernel worker the mesh): to a new file beside it, renamed into place, as `file::save` does, so a write cut short leaves what was there and a reader never sees part of it. Inside the workspace, never through a link out of it (decision 26).

### `export` (M4.8)

As docs/ports/mesh-export.md settles it: each body meshed at the tolerance, the mesher's linear deflection (with FreeCAD's angle, `min(0.1, 5·tol + 0.005)` rad), joined at the edges its faces share, checked closed, manifold, oriented outward, with no degenerate triangle, and refused otherwise. Every edge's polygon and every joined vertex are within the tolerance, the f32 rounding counted against it, and no face is meshed coarser for its own tolerance in a way that matters: OCCT meshes a face no finer than twice its tolerance, so a face whose tolerance raised its deflection (twice its tolerance past the deflection asked: OCCT's own test) is meshed again with `ForceFaceDeflection`, and refused only if that places other nodes (compared by their bits, -0 as 0, in any order), naming it and a tolerance that works, one at which OCCT raises none of them. A raised face with the same nodes is taken (planes and cylinders always, having no nodes inside them; often cones, spheres, and tori, where a step count rounds the same), and the mesh written is always the first, FreeCAD's (the M4.8 decision's 2b, as Fable amended it, 2026-10-24). A face's interior is the mesher's: measured within the tolerance on planes, cylinders, cones, and tori, and up to 2.1 times it at a sphere's seam, as FreeCAD's is (the M4.8 decision, Fable's, 2026-10-24). Faces that bound no material (OCCT's INTERNAL and EXTERNAL) are left out, as FreeCAD's mass properties leave them out, and named in `left_out` (FreeCAD's export includes them, wound reversed: Silico leaves them out on purpose); written as `type="model"` in millimetres, one object a body, named by its feature, the archive's bytes the same every run. It reads the current model only. `silico export` is a thin client of it.

Request: the format (`3mf`; and `step` if decision 6 is taken), the path (inside the workspace, ending in the format's extension), whether to replace a file already there (section 6, *Files a command writes*), the features (`null` for every body), and the tolerance (the default is FreeCAD's 0.1 mm; the request always gives it).

## 8. Versioning

- **The API has one version number,** `"api": 1`, which `version` returns. Agents ask for it first; the MCP server's `initialize` reply names the build in `serverInfo`, as MCP asks, and the API's version is the `version` tool's.
- **Before Silico's first public release,** `api` stays 1 and the shapes may change under it, as the document format does (M2.1's D5), each change agreed with the maintainer through the protected snapshots below.
- **After it,** a change an existing client could misread (a field removed, renamed, retyped, or given another meaning; a code's meaning changed) bumps `api`. A field added to a result doesn't. A field added to a request doesn't either, if a request without it means what it meant before: the one place a request field may be left out.
- **What a change to a shape requires:** the command's snapshot and its example files change in the same commit, with the maintainer's approval (every crate's `tests/contract/` is protected), and this document's examples with them.

## 9. Transport and clients

### Transport (decision 7)

stdio only in M4: `silico serve` speaks MCP (JSON-RPC 2.0, one message a line) on its stdin and stdout, one client per process, as an MCP client starts it. No network listener, so nothing is exposed. A process holds several sessions (several documents) of its one client, sharing one pool, which is why M4.2 makes generations per client. A network transport, with authentication, waits until something needs it.

### Exact JSON both ways (decision 23)

An MCP SDK holds a call's `arguments` and a reply's `structuredContent` as `serde_json::Value`. The workspace's serde_json has `float_roundtrip` but neither `preserve_order` nor `arbitrary_precision`, so through a `Value` a reply's keys come out sorted, `0.000001` comes out `1e-6`, a `Measure` with more digits than an `f64` holds is rounded, and a request's number with more than 15 significant digits may be rounded rather than refused. With decision 23's recommendation:

- **The server reads and writes the JSON-RPC lines itself.** It reads each line from stdin, finds the method and ID, and hands a `tools/call`'s `arguments` to the core as their text (`serde_json::value::RawValue`, serde_json's `raw_value` feature), which Silico's own reader reads as it reads a document. It writes each reply line itself, with the envelope spliced in as the raw text Silico's writer made, as `structuredContent` and, as a JSON string of the same text, as `content`'s one text block. A JSON-RPC error's `data` is spliced the same way. An SDK, if one is used, supplies the protocol's types for the handshake (`initialize`, `tools/list`), never the path a command's JSON takes.
- **Tested:** on stdio, `structuredContent`'s bytes on the wire are the core's one-line form of that answer (section 2), and `content`'s text is the same bytes; a request carrying `0.1` reaches the core as exactly 100,000 nm, and one carrying `0.10000000000000000001` is refused for its decimals, not rounded.

### A tool's answer

- `structuredContent` is the envelope; `content` holds the same JSON as one text block, for clients that don't read structured content; `isError` is `true` when `ok` is `false`.
- `render`'s PNG is an image block of its own, and is never in `structuredContent` or the text block: base64 in text would put 70 to 200 KB of characters into an agent's context for one 800 × 600 view.
- A message that isn't JSON, isn't JSON-RPC, or names an unknown method or tool gets a JSON-RPC error, whose `data` is an envelope with `ok: false` and the error in the contract's shape, so even garbage gets a structured error (M4.9's `/break-it` catalog).
- **Progress and cancellation** are MCP's notifications (section 6), and `cancel` for clients that don't send them. `read_logs` is a tool, read when the agent asks, not MCP's logging notifications.
- Each tool's description says what an agent most needs: edit inside a transaction, read `current` after an edit, and that names come from `elements` and `query`.

### One command, every client

Each command is one MCP tool, with the same name and the same shapes. The CLI's commands open a session, run one command, and close it. The app (M5) runs the same commands off its UI thread, reading the published model for what it draws.

## 10. Determinism

Nothing in a result depends on time, randomness, `HashMap` order, or thread scheduling. A result is a function of the files the session read, the commands it ran, in order, and the model the envelope names.

- **Orders.** Features in timeline order. Elements by body in timeline order, then faces, edges, vertices, then name byte by byte; an entry's aliases in the element map's order. Errors in the order found: reading, then the gate, then each failed feature and each drifted fingerprint in timeline order (`command::Problems`). Candidates in the order M2.8 gives them. Warnings by feature in timeline order, then by their first element's ID. A distance's witness pair by its points' coordinates, never the kernel's list order. Export objects in timeline order. Every map is a `BTreeMap` or an `IndexMap`, and every object's keys are in schema order.
- **Counters, not clocks.** Session IDs count up within the process; revisions within the session.
- **IDs.** A feature ID the client doesn't give is random (M2.1): chosen once, it's then data, written in the file and returned in the result; a replay gives the IDs its recording holds (decision 20).
- **Concurrency.** A session runs its commands one at a time, in order. Sessions don't share generations, so one's work never changes another's results (MA2).
- **The published model.** Which revision a `published` read answers from depends on when it's asked; what it answers, given that revision, doesn't, and the envelope names the revision. `current` reads have no such dependence.
- **Kernel faults** depend on the machine (a crash, a timeout); a result that holds one says so in `model.fault`, and every other part of it is as without the fault.
- **Not results, and described so in their schemas:** progress (`status`'s `running`, `done`, and `steps`, MCP's progress notifications), logs (`read_logs`: times and the interleaving of threads), and a render's pixels and `png_bytes` (GPUs differ: plan decision 5; its camera is computed and deterministic). None reaches a name, a file, or another result.
- **The operating system's words.** An `io_failed` error's message quotes the system's reason ("No such file or directory (os error 2)"), which differs between platforms; its code and parameter don't.
- **Tested,** by extending the determinism sweep (`tests/determinism/`) to every command's result: the same commands on the same documents give the same bytes, run after run and on both checked platforms.

## 11. Open decisions

Each with its options, briefly, and the recommendation the maintainer approved on 2026-10-24, all of them as recommended. Decisions 1 to 7 are #50's, 9 and 10 the amendments' (A2, A3); 11 on are ones this design found the API forces, numbered on from the plan's, 29 to 34 added after round 1 of review and 35 after its verification. Already decided, and not reopened here: decision 8, the `naming` header (the maintainer, 2026-10-21); the face frame, F1 and F2 (Fable, 2026-10-22; the maintainer's veto open); `distance` and `angle` (Fable, 2026-10-23; the maintainer's veto open); mass properties precise (the maintainer's standing choice, 2026-10-09); an angle with a face whose surface isn't a plane refused (the recommended default; the maintainer's veto open); AR1's m + k (the M3 review).

**1. What a commit does, and what an edit outside a transaction does** (M4.2). The trade: (a) outside a transaction each edit is applied and saved at once, so the file always holds what the agent last did and git sees each step, but an edit saved this way has no undo but git or another edit; (b) outside a transaction, edits are applied but not saved until a save, as SolidWorks applies an edit at once and saves on Save, with its undo between, which is an open transaction by another name; (c) edits are refused outside a transaction, so every change is explicit, at the cost of two more calls for a one-line edit.
**Decided (recommended, approved 2026-10-24):** (a), #50's: a commit saves the document through `file::save`, a rollback never touches the document's file, so the file only ever holds committed states and git sees nothing half-done; outside a transaction, each edit is its own transaction, applied and saved at once; one transaction at a time per session, not nested. What (a) gives up is softened by `remove_feature` and `replace_text` returning what they removed, and by tool descriptions that tell agents to work in transactions. The app may hold a transaction open as its unsaved state, which is (b) for a person; M5 decides.

**2. A file changed outside the session** (M4.2). Merge the change, let the last writer win, or refuse.
**Decided (recommended, approved 2026-10-24):** outside a transaction the session reloads the file through the gate, found by comparing bytes before each command; inside one, the commit is refused as a `conflict`, naming the file, and the agent rolls back or begins again from the file's new state. Nothing merges silently.

**3. Edits as commands and as text** (M4.1). Text only, commands only, or both.
**Decided (recommended, approved 2026-10-24):** both, from M4: `replace_text` through the gate, and typed `add_feature`, `set_field`, and `remove_feature`, each naming what it touches by ID, which M5's UI then uses; each through the gate, so a bad edit is refused whole.

**4. How queries are written** (M4.4). A phrase language, or structured filters.
**Decided (recommended, approved 2026-10-24):** structured JSON filters, section 7's `query` shape, so a query means one thing and its errors name a field. A tie is never broken by name or position: a tie at the cut is returned whole, past `limit`, when it fits in 1,000 elements, and otherwise not at all, `tied` saying how many there are, so the agent narrows the filter.

**5. How renders are tested** (M4.6). Not the API's, but it decides that a render's pixels aren't a result (section 10).
**Decided (recommended, approved 2026-10-24):** as #50 recommends: tests read the ID buffer and check it against the projection by hand, never compare pixels with stored images; CI renders with a software rasterizer (Mesa's on the Linux runner), pinned in pixi.

**6. STEP export** (M4.8). In M4.8, or later.
**Decided (recommended, approved 2026-10-24):** as #50 recommends: STEP in M4.8, its header written from the document so its bytes are deterministic; `export`'s `format` then takes `step` beside `3mf`.

**7. Transport** (M4.9). stdio, a network listener, or both.
**Decided (recommended, approved 2026-10-24):** stdio only in M4, one client per server process, no network listener; several sessions in one process share one pool. MCP pinned at a revision with structured tool results and cancellation (2025-06-18 or later), which M4.9's study confirms.

**9. Undo after a commit** (M4.1, A2). An undo stack in the API, or none.
**Decided (recommended, approved 2026-10-24):** no undo stack in the API. Git and the file's history are the history of committed states; an agent that wants to try something opens a transaction. A second history would be a second source of truth. The app's undo (SolidWorks has one) is M5's to decide.

**10. MCP's cancellation** (M4.2, M4.9, A3). A cancelled request answered with an error, or not answered.
**Decided (recommended, approved 2026-10-24):** a request MCP cancels stops its kernel and solver work through the pool's superseded path and gets no reply, as MCP's cancellation rule says. (`cancel`, decision 34, is the other way in.)

**11. The response's shape** (M4.1). Bare results, with errors carried only as MCP's `isError` text; or one envelope.
**Decided (recommended, approved 2026-10-24):** one envelope for every command and every client: `ok`, the session's state, the model read, and either `result` or `errors` with `total` (section 2). A document's problems are a result; `ok: false` is a command that didn't do what it was asked.

**12. Edits name the revision they were made against** (M4.2). Decision 2 covers changes found between commands, but an agent that read the text before a reload would overwrite the reloaded change with `replace_text`. Options: a `revision` on every edit, on `replace_text` only, or none.
**Decided (recommended, approved 2026-10-24):** every edit carries the revision it was made against, required, and a stale one is refused as a `conflict`.

**13. When a rebuild starts, and who waits for it** (M4.2). A rebuild per edit, started at once, makes a run of edits in a transaction start and kill a rebuild each.
**Decided (recommended, approved 2026-10-24):** a revision's rebuild starts when a command first needs its model (section 3), not at the edit; a read of the current model waits for it and never answers from an older one; a read of the published model starts it and doesn't wait for it (decision 33); an edit inside a transaction neither starts nor waits; outside one it waits, since its save writes fingerprints.

**14. Single-element measures** (M4.5). #50's row lists an edge's length, a radius and diameter, and a vertex's position as measures. As commands of their own, each refusing what it doesn't apply to; or as fields of each element's entry.
**Decided (recommended, approved 2026-10-24):** fields of the entry (`length`, `radius`, `diameter`, `position`), `null` where they don't apply: one computation per number, so a measure and the element list never disagree (docs/ports/measure.md). `distance` and `angle` stay commands, as decided.

**15. How paths name a sketch's members, in requests and errors** (M4.2). Today the gate's errors name a sketch's members by place (`constraints.3.line`), and the place counts the file's order as read, which isn't the sorted order `text` shows after an edit, so an agent acting on a place can edit another member. (a) Requests and errors both by ID from M4.2, which changes the gate's `parameter` for sketch errors (not a protected contract; its tests change with it); (b) requests by ID, errors by place, the core translating an edit's refusal only; (c) both by place.
**Decided (recommended, approved 2026-10-24):** (a): a list of objects that have an `id` is indexed by ID, any other array by place, from 0, with no leading zeros, in requests and in every error, from M4.2. docs/design/m3.2-sketch-format.md's example of a gate error's field (`constraints.3.line`, in *The gate's rules for sketches*) then goes stale, and M4.2 updates it. Settled further on 2026-10-25 (§2, *Paths to a field*): requests take IDs only and a place there is refused; errors fall back to places for members with no usable ID; and an edit that repeats an ID is refused at the field it requested.

**16. New error codes** (contract changes, `error-codes.txt`, protected).
**Decided (recommended, approved 2026-10-24):** append `conflict` (in order after the last code on main; M4.2 doesn't depend on #89): a commit refused because the file changed outside the session, an edit made against a revision the session isn't at, or a cursor of another revision. Not a kernel fault. The alternative, `io_failed` with a message (what `file::save` gives a file changed since it was read today), leaves an agent unable to tell a conflict, which it fixes by rolling back, from a full disk. And append `cancelled`, for decision 34: the answer of a command `cancel` stopped. Not a kernel fault, not the document's. A renderer that can't be had needs no code if decision 29 puts rendering in a worker (`worker_unavailable`, #89's; `worker_crashed` until it merges).

**17. Warnings** (M4.2). ROADMAP.md's M4 brings a check's warnings (M3.2's D2 touching ends, and M3.3's agreeing redundant constraints, which it calls a warning) and `silico fmt --merge-touching`; #50 schedules neither.
**Decided (recommended, approved 2026-10-24):** warnings in M4.2, in `check`'s result, each in the error contract's shape, its code from a new protected list, `warning-codes.txt`: `ends_not_joined` and `constraints_redundant`. `--merge-touching`, an edit, waits for M5's sketch editing, where SolidWorks merges points, and ROADMAP.md says so.

**18. The limits' values** (M4.1, A1).
**Decided (recommended, approved 2026-10-24):** section 6's table, returned by `version`, with no limit on a command's whole time.

**19. What a tie is** (M4.4). #50 says "equal within the measure's tolerance". Equal within a relative tolerance isn't transitive (a chain of near values ties ends that aren't near), and an agent sees two different numbers called equal.
**Decided (recommended, approved 2026-10-24):** a tie is equal as written: the same number after the measure is rounded as results write it (an area to 6 places, a length to the nanometre). One rule, exact on what the agent reads.

**20. Feature IDs from the API** (M4.2). Always the client's; made by the core; or made by the core from a seed a session takes.
**Decided (recommended, approved 2026-10-24):** made by the core from the OS's randomness when the request gives none (M2.1), the client's when it does; a replayed session (M4.9) gives the IDs its recording holds. No seed in the API. A sketch's element IDs stay the client's (they refer to each other inside the feature).

**21. Opening a document the gate refuses** (M4.2). Refuse to open it, or open it with its problems.
**Decided (recommended, approved 2026-10-24):** open it, holding its bytes and problems, so an agent can mend it with `replace_text`, as SolidWorks opens a part whose rebuild fails.

**22. A session's bounds** (M4.2).
**Decided (recommended, approved 2026-10-24):** a file is open in one session a process; `close` is refused while a transaction is open; a client that goes away rolls back its transactions and closes its sessions. With decision 30's (a), every session in a process is one client's, so "use session s1" is advice to that client about its own session.

**23. Exact JSON across MCP, both ways** (M4.9). Requests: (a) let the SDK parse arguments into a `Value`: every valid value comes through exactly (a `Length` has at most 13 significant digits, an `Angle` 12, and up to 15 round-trip through an `f64` and serde_json's shortest printing), but a number with more digits than an `f64` holds is rounded rather than refused, and a key given twice is silently kept once; (b) the server reads JSON-RPC lines itself and hands the arguments' text (`RawValue`) to Silico's reader, which costs Silico its own framing for MCP's few methods, since rmcp's `CallToolRequestParam.arguments` is a `serde_json::Map` (or a fork of rmcp); (c) turn on serde_json's `arbitrary_precision` and `preserve_order` for the workspace, which keeps digits and key order in a `Value` but changes how every crate's serde_json reads numbers and orders keys (the CLI's protected check line among them). Replies: through a `Value` under (a), keys come out sorted, small decimals as exponents (`1e-6`), and a large `Measure` rounded, so `structuredContent` and `content`'s text would disagree; (b) splices Silico's own text into both; (c) keeps order and digits but has the same workspace cost.
**Decided (recommended, approved 2026-10-24):** (b), both ways: the server reads and writes the JSON-RPC lines itself, arguments to the core as raw text, the envelope spliced into the reply as raw text, as `structuredContent` and as `content`'s text, JSON-RPC errors' `data` too (section 9); an SDK for the handshake's types at most.

**24. The contract files** (M4.1).
**Decided (recommended, approved 2026-10-24):** section 8's table: a snapshot of each command's schemas, the envelope's, this document's examples named by what they show, and `warning-codes.txt` in `crates/silico-core/tests/contract/`, all protected; M4.9's `tools.json` checked equal to them.

**25. What `cache_clear` clears** (M4.3). #50 says "a document's cache", but the cache is the directory's (`.silico-cache/` beside the file, keyed by step, shared by every document there). Clear the whole directory's entries, or only those the document's current revision uses (which needs its keys, and leaves earlier revisions' entries).
**Decided (recommended, approved 2026-10-24):** the directory's entries, all of them, and only the files the cache made; an entry removed is only a miss.

**26. Where the workspace is enforced** (M4.2, M4.9). In the MCP server, or in the core's sessions.
**Decided (recommended, approved 2026-10-24):** in the core: sessions take an optional workspace root, which `silico serve` gives and the CLI doesn't, so the rule has one implementation.

**27. Key order** (M4.1). The error contract's files are in declaration order; the CLI's `check --json` line is sorted by key (serde_json's map), so Silico has two orders already.
**Decided (recommended, approved 2026-10-24):** the API writes keys in schema order, in M2.1's layout; the CLI's line keeps its protected contract until you approve moving it to schema order too.

**28. Fingerprints after an edit, and drift** (M4.2). Invariant 5 says drift "fails as drift and is never smoothed over". (a) A typed edit drops the stored fingerprints of what it touches and everything downstream, and a commit writes every fingerprint as rebuilt, as `fmt` does: simple, but a `note` edit on the first feature drops every fingerprint, and a commit silently writes over the drift of features no edit reached, so an OCCT change reaches nobody. (b) A commit writes new fingerprints and solves only for what the session's edits reached (a feature whose own values changed, by a typed edit or by `replace_text` compared by ID, a new feature, and everything that uses one); `name` and `note` reach nothing; a feature no edit reached keeps its stored fingerprint and, if its rebuild differs, is a `drift` problem of the commit; accepting drift is explicit, through `format` (decision 31), naming each feature it accepts. A change reloaded from the file is a hand edit and reaches nothing, so its stale fingerprints wait for `format`, as they wait for `silico fmt` today; ARCHITECTURE.md's "until the document is saved again (or `silico fmt` is run)" then reads "until `format` (or `silico fmt`) is run" for hand edits. (c) As (b), but a commit also accepts drift for features changed by a reload since the last save, which needs the session to keep the text it last saved and compare: hand edits are accepted by the next commit, and an agent can't tell them from a kernel change.
**Decided (recommended, approved 2026-10-24):** (b).

**29. Where `render` runs** (M4.6). `silico-core` can't depend on `silico-render` (wgpu), and #50's M4.6 says rendering is never on a thread a client waits on without a timeout; a GPU hang in the process can't be stopped. (a) A `Renderer` trait the client gives the core, as it gives a `Kernel`, implemented by `silico-render` in the client's process: no new process, the GPU context shared with the app's viewport, but a hang or a driver crash takes the session's thread or the process with it, and the timeout can only stop waiting, not stop the work. (b) A render worker process (a `silico-render` binary, through `silico-worker`, as the kernel and sketch workers are): a timeout that kills it, a crash that's `worker_crashed`, a missing GPU that's `worker_unavailable`, no new error code; it costs sending the meshes to the worker and a GPU context in each.
**Decided (recommended, approved 2026-10-24):** (b), with a 30-second limit a render (section 6). The worker returns the PNG's bytes and the core writes any file (decision 35). The app's viewport (M5) renders in its own process, as it must, and isn't a command.

**30. Several clients on one document in one process** (M4.2, hard to reverse). ARCHITECTURE.md's process diagram draws the egui UI and the MCP server in one process, but stdio gives each `silico serve` one client, and section 3 gives each session one client. (a) A session belongs to one client; clients share a document across processes through its file, which decision 2 already handles (the app reloads what an agent commits, outside its own transaction); ARCHITECTURE.md's diagram is corrected to show the app and `silico serve` as separate processes on the same core. (b) Sessions can be attached by several clients in one process: each transaction records the client that owns it, another client's edit or rollback during it is refused, and the MCP server can run inside the app, so a person watches an agent's edits live without a file round trip; it adds attach and ownership to every command's rules.
**Decided (recommended, approved 2026-10-24):** (a) for M4, which needs no ownership rules; (b) can come with M5 if live co-editing in the app is wanted, as an `attach` that leaves M4's shapes as they are.

**31. A `format` command** (M4.2). `check`'s drift says to save or run `silico fmt`, but with decision 28's (b) a commit doesn't accept drift, and a commit with no edits writes nothing, so an agent through MCP couldn't do either. (a) A `format` command: the session's document saved in canonical form with every fingerprint and solve as rebuilt, changed or not, drift accepted and named, refused inside a transaction; `silico fmt` its thin client. (b) A `commit` option that accepts drift. (c) Nothing: an agent runs `silico fmt` from a shell.
**Decided (recommended, approved 2026-10-24):** (a), with a `features` filter so an agent accepts only the drift it means, and the drift suggestion's wording (recompute.rs's `DRIFT` and `SKETCH_DRIFT`) names `format` beside `silico fmt`. Refusing `format` inside a transaction is for M5 to revisit if the app keeps its unsaved state as an open transaction.

**32. A kernel fault that repeats** (M4.2). Crashes and timeouts aren't kept, so a feature that reliably crashes the worker or times out would, read by read, cost a minute each, and keep every commit and every edit outside a transaction from saving. (a) Keep the fault as the revision's outcome for that feature and those that use it, tried again on a new revision or `fresh`; report it once beside the result (`model.fault`); a commit saves with those features keeping their stored fingerprints, as failed ones do; `status` says `faulted`. (b) As today: a fault is the command's whole answer, and the next command tries again.
**Decided (recommended, approved 2026-10-24):** (a). SolidWorks saves a part with rebuild errors; a fault is the kernel's, but its effect on what can be saved should be a failed feature's.

**33. Reading the published model** (M4.2, M5). If every read waits for the current revision and commands run one at a time, the app's pre-selection and Measure tool stall during a rebuild, or the app reads `Sessions::published` directly, a path no command offers. (a) Every read command takes `"model": "current" | "published"`, the envelope names the revision read, and the app uses only that; (b) reads always wait for the current revision, and the app keeps a Rust-only path to the published model. With (a), a published read that needs the kernel (`distance`, `angle`, `render`) would be superseded by the session's next rebuild if it ran under the session's generations; (a) needs them on a lane of their own.
**Decided (recommended, approved 2026-10-24):** (a): what the app can see, an agent can see, through the same command. Every solid a read can name is described as part of its rebuild, before the model is published, so element reads of a published model need no kernel; published `distance`, `angle`, and `render` run on the session's read lane, whose generation its rebuilds never advance; a published read doesn't wait for a rebuild, but takes as long as its own kernel work; `status` lists the ones running, and `cancel` can stop them.

**34. Stopping a long command without MCP's cancellation** (M4.2). A client that waits on one call can only cancel it from a second call made at the same time, so `cancel`'s real users are clients that make calls at once but don't send MCP's cancellation, and the app's stop button. (a) A `cancel` command that names the command it means and is refused if that isn't what's running (so a late cancel can't stop the next queued edit); it answers at once, and the command it stops answers with a new `cancelled` error if it left no trace, or with its real result if it had already done its work; (b) require clients to send MCP's cancellation, say so in the tools' descriptions, and give the app's stop button a Rust-only path (`Running::cancel`).
**Decided (recommended, approved 2026-10-24):** (a), with `cancelled` appended to `error-codes.txt` (decision 16).

**35. Files a command writes besides the document** (M4.6, M4.8). `render`'s `to` and `export`'s `path` could overwrite any file in the workspace, the open document included. (a) Refuse a path that ends in `.silico`, names a document a session holds, or lies in `.silico-cache/`; require the format's extension; refuse an existing file unless `"replace": true`; the core writes it, through a new file renamed into place. (b) As (a), but replace an existing file by default, as most tools' "save as" does after a prompt the API can't show. (c) Write only into a directory of Silico's own (`out/`), named by the core.
**Decided (recommended, approved 2026-10-24):** (a): an agent's typo never costs a file, and replacing one is said in the request.

## 12. Tests the design implies

For M4.2 on, each command's tests with its step. Expected values come from the design, from hand calculation, or from FreeCAD.

- **The examples, byte for byte** (#50's M4.1 row): every JSON block in this document is read by Silico's reader and written back by the API's writer to the same bytes; each equals its file in `commands/examples/`; each request block validates against its command's request schema and each result or error block against its result or the envelope's. A block that changes here and not in its file, or the reverse, fails.
- **The envelope:** every command, refused and not, gives exactly one envelope shape; a document's problems come in `result` with `ok: true`; the 101st gate error is counted in `total`, not listed; `model` is `null` exactly for commands that read none.
- **Sessions (M4.2):** two sessions on one pool, a new revision in one never drops or stops the other's work (the fake kernel's call record, and the pool's tests with launch logs, as M1's are); a long rebuild in one doesn't starve the other's queue; two sessions in one directory share one cache; a session dropped mid-rebuild leaves no partial state; IDs `s1`, `s2` in order, never reused; a file opened twice is refused naming the first session; a 17th session is `invalid_input`; a refused document opens with its problems, and edits but `replace_text` refuse until it's mended.
- **Off the caller's thread:** every command's `Running` handle returns before its file read, gate, rebuild, or save (a fake file system and kernel that block until released); `published` reads, `status`, `read_logs`, and `cancel` answer while a `current` read waits.
- **Rebuilds start lazily:** ten edits in a transaction start no rebuild (the fake kernel's record is empty), and the first `check` starts one, for the tenth revision.
- **Transactions (M4.2):** rollback restores the text byte for byte (a non-canonical file stays non-canonical), and the model's fingerprints and element maps exactly (the same model); a rollback after a failed rebuild restores the last good model; a commit with nothing changed writes nothing (the file's bytes and inode unchanged); a second `begin` is refused; `close` with a transaction is refused; a client that disconnects mid-transaction leaves the file as it was; a rollback whose `begin` came mid-rebuild, after a `check` in the transaction superseded that rebuild, starts one rebuild of the restored document served from the cache (the fake kernel's record shows no step it finished requested again).
- **Drift and reach (decision 28):** a `note` edit on the first feature, committed, writes no fingerprint; a pad's length changed writes the pad's, its pocket's, and its fillet's, and leaves an unrelated box's as stored; a box whose stored fingerprint is off by 1e-6 mm³ (a fake kernel's) and that no edit reached is kept as stored and listed as `drift` by the commit, and `format` then accepts it, naming it; a `replace_text` that changes one feature's value reaches exactly that feature and what uses it; a reached feature that failed stays reached until a commit writes its fingerprint.
- **Decision 2:** a file edited outside, outside a transaction, is reloaded (`reloaded: true`, a new revision); one edited inside a transaction makes the commit a `conflict` and writes nothing; an edit at a stale revision is a `conflict`; an edit that keeps the file's size and time is still found.
- **Edits:** each typed edit refused whole by the gate (the document, revision, and model unchanged), every error listed; `set_field` reads its value exactly (`0.1` is 100,000 nm) and refuses `id`, `type`, `v`, and `fingerprint`; a sketch member set by ID, and its refusal naming the same path, after members were added before it; removing a feature others use names each; `remove_feature`'s returned feature and index, put back with `replace_text`, give the document as it was; `replace_text` without `naming` refused; `add_feature` without an ID makes a valid one, and with one keeps it; a replayed session with recorded IDs gives the recorded document byte for byte.
- **Long work:** a cancelled `check` (MCP's way) stops its rebuild (the fake kernel's record shows the superseded path) and gets no reply; `cancel` naming `check` stops it and it answers `cancelled`, and naming a command that isn't running is refused (a late cancel after an edit is queued leaves the edit alone); a `cancel` of an edit already saved gets `stopped: false` and the edit answers with its real result; a published `distance` running while ten edits start and supersede rebuilds finishes with its answer; a cancelled edit is either whole or absent; a worker that crashes on one feature gives one `worker_crashed` in `model.fault`, naming that feature, not one per feature (AR1's pattern), while `check` lists the document's other problems; a second read of that revision runs nothing on the kernel; a commit saves around it; `check` with `fresh` tries it again; a worker that can't be had gives one `worker_unavailable` (`worker_crashed` until #89 merges) and no feature.
- **Limits:** every row of section 6's table, at its value and one past it, refused naming its field, or counted where the table says so; `version`'s limits equal the constants they come from.
- **M4.3:** `check` with `fresh` builds every step, ignoring the engine's kept results, solutions, and refusals as well as the disk's, and leaves entries a later rebuild hits; `cache_clear` removes every entry and nothing else (a stray file and a link out of the directory are left alone); clearing while another process rebuilds leaves no entry that's trusted half-written (M2.5's corrupt-entry tests).
- **M4.4:** a published model's `elements` and `query` run nothing on the kernel (the fake kernel's record); an element whose own name is unstable and an alias stable passes `"stable": true`; the entries' fields for a box (six faces, analytic areas, normals, centroids, `default_x` from F1's table) and a cylinder's side (its axis, radius, and diameter); `name`, `aliases`, and `stable` the same as the element map's, every one, an unstable name `stable: false`; the order holds across runs and platforms; the cursor pages through 32 elements two at a time and meets each once, and a cursor of another revision is a `conflict`; a second `elements` call on the same model runs no `describe`; "largest planar face facing +Z" finds the top by name, on a block with two equal tops returns both with `tied: {"count": 2, "included": true}`, and on 5,000 equal faces returns none with `included: false`; an unknown kind or type, and `facing` on edges, refused naming the field; `schema` equals the snapshot exactly, for the document and for each command; a torus face's `major_radius` and `minor_radius` (R 10, r 2, as M4.4's design tests), `null` on every other type; a cone face's `half_angle` −33.690067526 and `apex` (0, 0, 6) for `Part.makeCone(4, 0, 6)`, the sign kept, `null` on every other type, and a nearly cylindrical cone's `apex` `null`; each edge's `start` and `end` in `firstVertex()`/`lastVertex()` order, including an edge its faces use reversed; a degenerated edge's `type` `other`, `length` 0.
- **M4.5:** Fable's cases for `distance` and `angle` (`m4-measure-fable.md`, *Build and tests*), and the oracle cases there; mass properties equal to the fingerprint's, and to the analytic volume of a box with a hole.
- **M4.6:** a render worker that hangs is killed at 30 s as `worker_timeout`, and the session goes on; the result never holds the PNG's bytes; with `to`, the file is a PNG of the size asked; plus #50's key tests.
- **Files a command writes (decision 35):** `to` or `path` naming the open document, any `.silico` file, a file in `.silico-cache/`, a path without the format's extension, or a link out of the workspace is refused and nothing is written; an existing file is refused without `replace` and replaced with it; a write killed midway leaves the old file whole.
- **M4.7, M4.8:** each row's key tests in #50, plus their limits (section 6) and that each result's shape is its snapshot's.
- **Determinism:** the sweep extended to every command's result, byte for byte.
- **M4.9:** the `/break-it` catalog's garbage MCP calls, each getting a structured error; on stdio, `structuredContent`'s bytes on the wire equal the core's one-line form of that answer, and so does `content`'s text; a call carrying `0.1` reaches the core as exactly 100,000 nm and one with 20 significant digits is refused for its decimals; a key given twice in a call's arguments is refused; `tools.json` equal to the core's snapshots.
