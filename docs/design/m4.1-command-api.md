# M4.1 design: the command API

**Status: a draft for the maintainer.** Nothing is built from it until he approves it, as M2.1 and M3.2 were. M4.1 (docs/roadmap/m4-mcp.md, #50, with the amendments in `m4-plan-amendments.md`) designs every command the agent interface needs: each command's request, its result, and its errors as JSON; sessions; transactions; edits as commands and as text; a file changed outside the session; undo; cancellation; faults reported once; one table of limits; and how the shapes are versioned. The command API's shapes are the MCP tools' shapes, one to one, so the CLI and the app read the same ones. Each open decision is in section 11, with the plan's or the amendments' recommendation marked **Recommended, for Trevin:**, to approve or veto line by line. The body of this document is written as if each recommendation is taken.

Step numbers are #50's. If amendment A4 (sketches on faces) is taken, a step M4.5 is added after M4.4, and #50's M4.5 to M4.9 become M4.6 to M4.10. This document uses #50's numbers throughout and calls the added step A4's.

## Already decided

These are cited, not reopened:

- **ARCHITECTURE.md's invariants and Agent interface.** One headless core, many clients (invariant 3): the MCP server, the CLI, and the app do nothing the command API can't. The UI thread never blocks (invariant 4). Errors are structured (invariant 9): a stable code, the feature, the elements at fault and their total, the parameter, the cause, a suggestion, and candidates. Transactions: begin, commit, rollback.
- **The error contract** (`crates/silico-core/tests/contract/`, protected): the shape in `error-full.json` and `error-minimal.json`, every field always present, `null` when absent, `[]` for none; the codes in `error-codes.txt`, appended to, never renamed or removed.
- **The document format** (M2.1, M3.2, M3.6): strict JSON read by Silico's own reader, lengths and angles exact, canonical layout (M2.1's D7), IDs of 8 lower-case Crockford base32 characters, made by the command API from the OS's randomness through a generator tests can seed (M2.1, *How M2.1 is built*).
- **M4.0, the naming scheme in the header** (the maintainer, 2026-10-21; merged, #112): `"naming": 5`. Every name in this document is scheme 5's.
- **Measurement's `distance` and `angle`** (Fable, 2026-10-23, `m4-measure-fable.md`; the maintainer's veto open): their requests and results, used here exactly as given. Mass properties precise, from M1's `measure` (the maintainer's standing choice of accuracy over parity, 2026-10-09, as docs/ports/measure.md records it). An angle with a face whose surface isn't a plane is refused (the recommended default, docs/ports/measure.md; the maintainer's veto open).
- **The frame of a sketch on a face** (Fable, F1 and F2, 2026-10-22, and F1 revisited, `m4-face-frame-fable.md`, `-2.md`; the maintainer's veto open): `"plane": {"face": "<name>", "x": "+y", "reversed": false}`, the default x chosen once at creation, and `default_x` reported for each planar face. It belongs to A4, which is still a proposal; section 2's element entries and section 5's `add_feature` leave room for it, so the API doesn't preclude it.
- **AR1, a sketch's refusals reported once** (the M3 milestone review, #90): a sketch with no profile, swept by k features, gives its m refusals once, and one error for each sweep that names it: m + k.
- **3MF export** (docs/ports/mesh-export.md, merged, #113): what a printable mesh is, the refusals, the deterministic archive.

## 2. Shapes every command shares

### The response

Every command answers with one of two shapes. A command that ran:

```json
{
  "ok": true,
  "session": {"id": "s1", "revision": 4, "transaction": false, "reloaded": false},
  "result": {"base": 4}
}
```

A command that was refused or couldn't run:

```json
{
  "ok": false,
  "session": {"id": "s1", "revision": 4, "transaction": true, "reloaded": false},
  "errors": [
    {"code": "invalid_input", "message": "a transaction is already open in this session", "feature": null, "elements": [], "elements_total": 0, "parameter": "session", "cause": null, "suggestion": "commit or roll back the open transaction, then begin again", "candidates": []}
  ],
  "total": 1
}
```

- `session` is the session's state after the command: its ID, its revision (section 3), whether a transaction is open, and whether the session reloaded its file from disk before running the command (decision 2). It's `null` for a command that takes no session (`version`, `schema`, `open` that failed).
- `errors` holds every reason the command was refused, in the order found, each in the error contract's shape, the first `PROBLEMS_LISTED` (100) of them; `total` is how many there are, listed or not. One shape for one error and for a gate's hundred.
- A document's problems are not a refusal. `check` that finds a failed fillet ran: its problems are in its `result`. `ok: false` means the command didn't do what it was asked: a bad request, an edit the gate refused, or a kernel fault (a worker that crashed, hung, or can't be had), which says nothing about the document. That is the CLI's exit 1 against exit 2 (docs/cli.md), kept.

In the command reference below, each example is the `result` member, or one member of `errors`, as its envelope carries it.

### Layout and key order

- Every request and result is JSON in M2.1's canonical layout (D7): an object or array on one line when it holds no object at any depth, otherwise one member per line, indented two spaces; `, ` and `: ` between members on one line; LF, and no trailing newline (a response is a value, not a file).
- Keys are in schema order: the order each shape below gives them. Never sorted, never in a map's order.
- On a transport that needs one message a line (MCP's stdio), the same value is written on one line. That's the only difference: the same members, in the same order, with the same numbers.

### Numbers

As the document writes them (ARCHITECTURE.md, *Numbers in the file*), read exactly from their digits by Silico's own reader, never through a float:

- **Lengths** (a distance, a radius, a point's coordinates) are `Length`: millimetres, plain decimals, at most 6 places (`2.5`, `0.000001`). Computed lengths are rounded to the nanometre once, at the end (`Length::rounded`, as Fable's measurement decision does).
- **Angles** are `Angle`: degrees, at most 9 places.
- **Areas and volumes** are a fingerprint's `Measure`: mm² and mm³, 6 places (`780.365046`).
- **Directions** (a normal, an axis) are unit vectors of `f64`, each written as Rust writes it, the shortest decimal that reads back as the same `f64` (M3.2's D3), `-0` written as `0`.
- **Counts, revisions, cursors** are whole numbers.

A request's length with a seventh decimal, an angle with a tenth, or `-0` is refused as the document refuses them: `invalid_input`, naming the field.

### Names and IDs

- A feature is named by its ID (`k7f2qx3m`), never its display name, which needn't be unique.
- An element is named by its stable name in scheme 5's form (`m3tq8v0z.cut.Edge(G k7f2qx3m.box.Face6, G a91cw0de.cylinder.Face1)`), never by OCCT's index. A name that finds nothing is `reference_broken`, with candidates (M2.8), never a guess.
- A request names a field as the error contract's `parameter` does, dotted: `extent.length`, `position.2`. A member of a sketch's list is named by its ID, not its place (decision 15): `constraints.g4h5j6k7.value`.

### Requests are strict

A request is read as a document is: unknown keys refused, every field the shape gives required, `null` where the shape allows it and the client has nothing to give. A request a newer client sends to an older server fails loudly, naming the field the server doesn't know, rather than being half-understood.

### Element entries

`elements` and `query` return elements in one shape, every field always present, `null` where it doesn't apply. The fields M4.5's measures need are Fable's (`m4-measure-fable.md`, *Build*, 1); M4.4's design settles the rest within this shape. A box's top face, after the hole M2.1's example cuts in it:

```json
{"name": "k7f2qx3m.box.Face6", "feature": "m3tq8v0z", "kind": "face", "type": "plane", "area": 780.365046, "length": null, "position": null, "normal": [0, 0, 1], "centroid": [20, 10, 10], "start": null, "end": null, "midpoint": null, "straight": null, "axis": null, "radius": null, "diameter": null, "default_x": "+x"}
```

- `feature` is the feature whose solid the element is of; `kind` is `face`, `edge`, or `vertex`; `type` is the geometry's, as OCCT names it: for faces `plane`, `cylinder`, `cone`, `sphere`, `torus`, `bezier`, `bspline`, `revolution`, `extrusion`, `offset`, `other`; for edges `line`, `circle`, `ellipse`, `hyperbola`, `parabola`, `bezier`, `bspline`, `offset`, `other`; for vertices `point`.
- `area` (a face's), `length` (an edge's), `position` (a vertex's) are M1's precise measures (a relative 1e-9).
- `normal` is a planar face's outward unit normal; `centroid` a face's centre of area.
- `start`, `end` are an edge's end points; `midpoint` a straight edge's; `straight` whether an edge is straight (a line, or a degree-1 B-spline of two poles).
- `axis` is `{"point": [...], "direction": [...]}` for a cylinder, cone, sphere, torus, circle, or arc; `radius` a cylinder's, sphere's, circle's, or arc's; `diameter` twice the radius, for a circle or arc edge and a cylinder face.
- `default_x` is A4's: for a planar face, the axis token a sketch on it would take by default (F1); `null` otherwise. It goes if A4 isn't taken.

An entry holds an object only in `axis`, so a face of a cylinder is written one member per line:

```json
{
  "name": "m3tq8v0z.cut.Face(I a91cw0de.cylinder.Face1)",
  "feature": "m3tq8v0z",
  "kind": "face",
  "type": "cylinder",
  "area": 157.079633,
  "length": null,
  "position": null,
  "normal": null,
  "centroid": [20, 10, 5],
  "start": null,
  "end": null,
  "midpoint": null,
  "straight": null,
  "axis": {"point": [20, 10, -1], "direction": [0, 0, 1]},
  "radius": 2.5,
  "diameter": 5,
  "default_x": null
}
```

### Warnings

`check` reports warnings beside problems (ROADMAP.md's M4, which M3 deferred to here: M3.2's D2 warning for two curve ends at one place that aren't one point, and M3.3's agreeing redundant constraints). A warning is in the error contract's shape, so an agent reads one shape, with its code from a list of its own (decision 17): it never fails anything.

```json
{"code": "ends_not_joined", "message": "two curve ends are at one place but aren't one point, so the profile is open there", "feature": "s0000002", "elements": ["pb000003", "pb000007"], "elements_total": 2, "parameter": null, "cause": "the ends are 4e-8 mm apart, within FreeCAD's joining distance of 1e-7 mm", "suggestion": "share the point: make one curve end at the other's point", "candidates": []}
```

## 3. Sessions

A session is one open document, held between commands (M4.2's `command::Session`). Every client holds documents this way: MCP's tools, the app's windows, and the CLI, whose commands open a session, run one command, and close it in one process.

### Opening, holding, closing

- **`open`** reads the file (`file::read`: a regular file, no more than a document may be) and puts it through the gate. The session opens even if the gate refuses the document (decision 21): it then holds the bytes and the gate's problems, `open`'s result lists them, and the commands that need a checked document refuse until `replace_text` gives it one (SolidWorks opens a part whose rebuild fails; an agent must be able to open a broken file to mend it). With `"create": true`, `open` writes a new, empty document to the path (`{"silico": 1, "units": ..., "naming": 5, "features": []}`, in canonical form) and refuses if the file exists.
- **A file open once a process.** Opening a file a session of this process already holds (by its path through links) is refused, naming that session (decision 22). Two sessions saving one file would each see the other's saves as changes outside the session.
- **Paths** are relative to the workspace when the process has one (decision 26): `silico serve` is started in a directory and refuses any path outside it or through a link out of it (M4.9). The CLI has none, so `silico check ../part.silico` works as it does today.
- **`close`** ends the session. It's refused while a transaction is open (commit or roll back first), so nothing is dropped without the client saying so. A client that goes away (MCP's stdin closed, the app quit) rolls back every open transaction and closes its sessions: only a commit ever writes the document.
- **Session IDs** are `s1`, `s2`, ... in the order the process opened them, never reused within the process: a counter, not randomness.

### What a session holds

| Held | What |
|---|---|
| The path | As given, and as its links resolve |
| The file's bytes | As last read from the file or written to it: what decision 2 compares the file with |
| The document's text | The bytes the session's document is: the file's, until an edit; after one, the edited document in canonical form |
| The checked form | The gate's `Checked` for that text, or the gate's problems if it refused it |
| The revision | A whole number, 1 at `open`, one more for each change of the session's document: an accepted edit, a reload from the file, a rollback, a commit that writes. It never goes back and is never reused, so a result and an edit can say which state they're of |
| The model | The current revision's `Model`, or its rebuild, running in the background |
| The transaction | If one is open: the state `begin` saw (text, checked form, model, revision) |
| A kernel handle | The session's own handle on the shared pool, with its own generations (MA2, below) |
| Its logs | M4.7's bounded buffer of the session's `tracing` events |

### Rebuilds and the model

Every new revision starts a rebuild of it in the background (`Recompute::start`), superseding the session's previous rebuild if it's still running. A command that reads the model (`check`, `elements`, `query`, the measures, `render`, `export`, `commit`) waits for the current revision's rebuild and answers from its model, never from an older revision's (decision 13). The answer says which revision it's of, in its envelope. The app doesn't wait: it shows the newest model published (`Session::published`, the Rust API's, not a command), marked as older than the document while the rebuild runs.

### Per-client generations (MA2)

Today the pool's generations are global: `Kernel::advance` supersedes every older generation, whoever started it, so one document's new rebuild could drop another's work (the M2 review's MA2). M4.2 gives each session its own handle on the shared pool (`KernelPool::client`), with its own generations: a session's new revision supersedes only its own older work, never another session's. Workers stay shared, up to one a core (ARCHITECTURE.md's pool), so several documents rebuild in parallel. Generations are internal: no result carries one. The revision is what a client sees.

### One command at a time, per session

A session runs its commands one at a time, in the order they arrive, so a result never depends on how two of a client's requests interleave. Two commands answer at once even while another of the session's waits, because they only read: `status` and `read_logs`. Commands of different sessions run at the same time.

## 4. Transactions

As plan decision 1 recommends, with decisions 9 and 2.

- **`begin`** keeps the session's state (text, checked form, model or its running rebuild, revision) and opens a transaction. One at a time, not nested: a second `begin` is refused.
- **Inside a transaction,** an edit is applied once the gate takes it and returns without waiting for its rebuild (decision 13), so a run of edits doesn't pay for rebuilds of states it passes through: each new revision's rebuild supersedes the last. Nothing is written to the document's file.
- **`commit`** waits for the current revision's rebuild, then saves the document in canonical form with its fingerprints as rebuilt and its sketches as solved, exactly what `silico fmt` writes (`command::format`), through `file::save`'s safe save. A feature that failed keeps its stored fingerprint and is listed in the result's problems, and the document is still saved, as `fmt` saves it and as SolidWorks saves a part with rebuild errors. The commit is refused, and the transaction left open, if the file changed since the session read it (`conflict`, decision 2), if the rebuild met a kernel fault, if the canonical text would pass 16 MiB, or if the file can't be written (`io_failed`). A commit whose document equals the one `begin` saw writes nothing.
- **`rollback`** ends the transaction and restores exactly what `begin` kept: the text, byte for byte as it was (not rewritten in canonical form), the checked form, and the model, the same one, not rebuilt, so its fingerprints and names are what they were. If `begin`'s rebuild hadn't finished, it's started again. The revision is a new number whose state equals the one `begin` saw. A rollback never touches the document's file. Rebuilds inside the transaction may have written cache entries (`.silico-cache/`): they stay, since they're keyed by their step and true for any document, and an edit made again hits them.
- **Outside a transaction,** each edit is its own transaction: begun, applied, committed, and saved at once, as an edit in SolidWorks applies at once. Its result holds the commit's. If the commit is refused, the edit is undone whole and the session is as it was before it.
- **After a commit** there is no undo in the API (decision 9). The committed states are the file's history, which is git's. An agent that wants to try something opens a transaction and rolls it back.

### A file changed outside the session (decision 2)

Agents may edit a document's text directly and then run `silico check` (ARCHITECTURE.md), so a file can change under a session.

- Before each command but `status` and `read_logs`, the session reads its file and compares its bytes with those it last read or wrote. Bytes, not times: a change within a file system's time resolution, or one that keeps the size, is still found.
- **Outside a transaction,** a change is reloaded through the gate, as the app will reload a file it watches: a new revision, and `"reloaded": true` in the command's envelope. If the gate refuses the new text, the session holds it and its problems, as `open` does.
- **Inside a transaction,** nothing is reloaded, and `commit` is refused as a `conflict`, naming the file. The agent rolls back (the next command outside the transaction then reloads the file) or rolls back and begins again from the file's new state. Nothing is merged, silently or otherwise.
- **An edit names the revision it was made against** (decision 12). An agent that read the text at revision 5, while the file was reloaded at revision 6, would otherwise overwrite what changed with `replace_text`. An edit whose `revision` isn't the session's is refused as a `conflict`, saying which revision the session is at.
- A file that's gone, or can't be read, is `io_failed` for every command but `status`, `read_logs`, and `close`; the session keeps its state.

## 5. Edits

As plan decision 3 recommends: both, from M4. Typed commands for the edits the bracket needs, which M5's UI then uses, and a command that replaces the whole text. Each goes through the gate: the edit is applied to a copy of the session's document and the copy is checked (`Checked::new`, the gate every write goes through). A bad edit is refused whole: the session's document, revision, and model are unchanged, and the refusal lists every error the gate found (the first 100 and how many). There is no partial edit.

- **`add_feature`** appends a feature to the timeline. Its `feature` is a feature as the document writes it, except:
  - `id` may be left out, and the core makes one (M2.1: from the OS's randomness, through the generator tests seed). An ID is a value the document stores, chosen once; a replayed session (M4.9) passes the IDs its recording holds (decision 20).
  - `v` may be left out, for the feature type's current version.
  - `fingerprint` is refused: a commit writes it.
  - With A4, a sketch on a face may leave out `plane.x`. The core then names the face's `default_x` (F1), which needs the base's model, so this edit waits for its rebuild; the face's name is found in its feature's element map, or the edit is refused as `reference_broken`, with candidates. The token is always written.
  - The result holds the feature as the document now holds it.
  - Element IDs inside a sketch (its points, lines, circles, arcs, constraints) are the client's: they refer to each other within the feature, so they're given with it, and the gate refuses any that repeat.
- **`set_field`** sets one field of one feature, named by the feature's ID and the field's dotted path (`extent.length`, `position.2`, `edges`, `constraints.g4h5j6k7.value`, `note`). The value is read as the document reader reads that field, exactly. It replaces the field's whole value: to add a circle to a sketch, set its `circles`. `id`, `type`, `v`, and `fingerprint` can't be set (a feature of another type is a new feature; a version changes by an explicit upgrade, later). `note` set to `null` removes it.
- **`remove_feature`** removes one feature. If others use it, the gate refuses the removal with each one's broken reference, naming it: SolidWorks asks whether to delete a feature's children too; the API makes the client remove them first, by ID.
- **`replace_text`** replaces the document's whole text, which goes through the gate as `silico check` puts a file through it.
- **Fingerprints after an edit.** A typed edit drops the stored fingerprint of the feature it changes and of every feature that uses it, directly or through others: those were measured from other inputs, and the commit writes their new ones. So `check` inside a transaction reports no drift for what the session itself changed, and still reports it for every feature the edit doesn't reach. `replace_text` keeps the text as given, fingerprints and all, as a hand edit does: a stale fingerprint is `drift` until a commit writes it (ARCHITECTURE.md, *Fingerprints*). This is decision 28.
- **Not in M4:** inserting a feature before the end of the timeline, reordering, suppressing, and finer sketch edits (add one point, split a line). M5's UI needs them; they come with it.

## 6. Long work

### Rebuilds in the background, and progress

A rebuild runs off the caller's thread, always. In Rust every command returns a pending answer (`Pending`, like `recompute::Run`: `wait`, `wait_timeout`, `try_take`, `cancel`, `progress`); the app polls it each frame and never waits on it, MCP's server awaits it, and the CLI waits. A command that waits for a rebuild reports its progress: on MCP, a request that carries a `progressToken` gets `notifications/progress` with the steps done, the steps in the rebuild, and the step running:

```json
{"progressToken": 7, "progress": 3, "total": 9, "message": "f0000001 fillet"}
```

Progress is a diagnostic, not a result (section 10): which step finishes first depends on scheduling.

### Cancellation (decision 10)

MCP lets a client cancel a request it sent (`notifications/cancelled`). A cancelled request stops its kernel and solver work through the pool's superseded path, as a newer generation's does, and gets no reply: MCP's rule is that a receiver should stop the work and not respond (specification 2025-06-18, *utilities/cancellation*; the same since 2024-11-05). So there's no error code for it. In Rust, `Pending::cancel` does the same.

- A cancelled wait stops the rebuild it was waiting on. The session's revision stays; the next command that needs the model starts its rebuild again, and the cache has kept every step that finished.
- A cancelled edit either finished or left no trace, never half: cancellation can arrive after the work is done, so the client reads `status` to learn the revision.
- `status` and `read_logs` answer at once, so they aren't worth cancelling; cancelling one changes nothing.

### Faults reported once (A1)

A kernel fault (`worker_crashed`, `worker_timeout`, `protocol_error`, `resource_exhausted`, `internal`, and `worker_unavailable` once #89 merges) says nothing about the document. It's the command's error, reported once: `ok: false`, one error, naming the feature whose request met it where one did (a fillet whose request crashed OCCT) and no feature where none did (a worker that can't be had). It's never copied onto the features it stopped: today's model holds a start failure on every sketch feature (AR1's pattern, which M3's review left to M4.1), and `command::check` already returns only the first fault; every command does the same. The session keeps its state, and the next command tries again (the pool replaces a crashed worker).

```json
{"code": "worker_crashed", "message": "the kernel worker crashed while building this feature", "feature": "f0000001", "elements": [], "elements_total": 0, "parameter": null, "cause": "the worker ended on signal 11 (SIGSEGV) during a fillet", "suggestion": "run the command again; if the same feature crashes the worker again, report it with the document", "candidates": []}
```

### Limits

One table, every command's (A1), so `/break-it` tests them all at once. `version` returns them as data. A request over a limit is refused as `invalid_input`, naming the field, with the limit in the message and what to do in the suggestion, except where the table says otherwise. The values are decision 18's.

| Limit | Value | Commands | Past it |
|---|---|---|---|
| A document's canonical text | 16 MiB (`MAX_DOCUMENT_LEN`) | `open`, every edit, `commit` | `invalid_input`, naming `text` or the edit's field |
| A request's bytes | 64 MiB (`MAX_INPUT_LEN`) | all | `invalid_input`, no parameter |
| A request's nesting | 64 (`MAX_DEPTH`) | all | `invalid_input`, no parameter |
| Errors and warnings listed | 100 (`PROBLEMS_LISTED`), with the total | all | not refused: the rest are counted |
| Sessions open in one process | 16 | `open` | `resource_exhausted`: close one |
| Elements a call lists | `limit`, 1 to 1,000 | `elements` | `invalid_input`, naming `limit`; the rest are read by the cursor |
| Elements a query returns | `limit`, 1 to 1,000 (ties at the cut are all returned) | `query` | `invalid_input`, naming `limit` |
| Elements highlighted | 1,000 | `render` | `invalid_input`, naming `highlight` |
| A render's size | 1 to 4,096 pixels a side | `render` | `invalid_input`, naming `width` or `height` |
| Log events a read returns | `limit`, 1 to 1,000, and 1 MiB of text | `read_logs` | a read stops at 1 MiB and its cursor says where |
| A session's log buffer | 10,000 events and 16 MiB | `read_logs` | not refused: the oldest are dropped and counted |
| The export tolerance | 1e-5 to 1e8 mm (docs/ports/mesh-export.md) | `export` | `invalid_input`, naming `tolerance` |
| An export's triangles | 10,000,000 | `export` | `invalid_input`, naming `tolerance`: a coarser one makes fewer |
| An export's archive | 4 GiB (plain zip, no ZIP64) | `export` | as triangles |
| A kernel request | 60 s (`kernel::DEFAULT_TIMEOUT`) | every rebuild step, `elements`, the measures, `export` | `worker_timeout`, a kernel fault |
| A sketch solve | 300 s (`SKETCH_TIMEOUT`) | rebuilds | `worker_timeout` |
| A whole command | none | | the client cancels |

No command has a limit on its whole time. A refusal that depends on how fast the machine is would make one request succeed on one machine and fail on another; each request to a worker has its timeout, which is a kernel fault, never the document's.

### `query` (M4.4)

A structured filter over the entries (plan decision 4): a kind, a type, a direction a planar face faces within an angle, ranges of measures, an order, and a limit.

Request, "the largest planar face facing +Z":

```json
{
  "session": "s1",
  "feature": null,
  "kind": "face",
  "type": "plane",
  "facing": {"direction": [0, 0, 1], "within": 1},
  "measures": [],
  "order": {"by": "area", "descending": true},
  "limit": 1
}
```

- `kind` is required; `type`, `facing`, and `order` may be `null`; `measures` is a list of `{"measure": "area", "at_least": 100, "at_most": null}`, each a measure the kind has.

## 8. Versioning

- **The API has one version number,** `"api": 1`, which `version` returns. Agents ask for it first; the MCP server's `initialize` reply names the build in `serverInfo`, as MCP asks, and the API's version is the `version` tool's.
- **Before Silico's first public release,** `api` stays 1 and the shapes may change under it, as the document format does (M2.1's D5), each change agreed with the maintainer through the protected snapshots below.
- **After it,** a change an existing client could misread (a field removed, renamed, retyped, or given another meaning; a code's meaning changed) bumps `api`. A field added to a result doesn't. A field added to a request doesn't either, if a request without it means what it meant before: the one place a request field may be left out.
- **What a change to a shape requires:** the command's snapshot changes in the same commit, with the maintainer's approval (every crate's `tests/contract/` is protected), and this document's examples with it.

## 9. Transport and clients

### Transport (decision 7)

stdio only in M4: `silico serve` speaks MCP (JSON-RPC 2.0, one message a line) on its stdin and stdout, one client per process, as an MCP client starts it. No network listener, so nothing is exposed. A process holds several sessions (several documents), sharing one pool, which is why M4.2 makes generations per client. A network transport, with authentication, waits until something needs it.

- **Exact numbers across MCP.** An SDK that parses a call's arguments into `serde_json::Value` turns `0.1` into a float first. The server hands each call's `arguments` to the core as their text (`serde_json::value::RawValue`), and the core reads it with Silico's own reader, as it reads a document (decision 23).
- **A tool's answer.** `structuredContent` is the envelope; `content` holds the same JSON as one text block, for clients that don't read structured content; `isError` is `true` when `ok` is `false`. `render` adds the PNG as an image block, so a client shows it.
- **What isn't a tool call.** A message that isn't JSON, isn't JSON-RPC, or names an unknown method or tool gets a JSON-RPC error, whose `data` is an envelope with `ok: false` and the error in the contract's shape, so even garbage gets a structured error (M4.9's `/break-it` catalog).
- **Progress and cancellation** are MCP's notifications (section 6). `read_logs` is a tool, read when the agent asks, not MCP's logging notifications.

### One command, every client

Each command is one MCP tool, with the same name and the same shapes. The CLI's commands open a session, run one command, and close it. The app (M5) runs the same commands off its UI thread.

| Command | MCP tool | CLI | App (M5) |
|---|---|---|---|

`silico fmt` stays a one-shot of `command::format` and `file::save`, the functions `commit` saves with: it writes canonical form even when nothing was edited, which a commit doesn't. `silico check --json`'s line keeps its contract (`crates/silico-cli/tests/contract/check-line.json`); see decision 27 on its key order.

## 10. Determinism

Nothing in a result depends on time, randomness, `HashMap` order, or thread scheduling. A result is a function of the files the session read and the commands it ran, in order.

- **Orders.** Features in timeline order. Elements by body in timeline order, then faces, edges, vertices, then name byte by byte. Errors in the order found: reading, then the gate, then each failed feature and each drifted fingerprint in timeline order (`command::Problems`). Candidates in the order M2.8 gives them. Warnings by feature in timeline order, then by their first element's ID. A distance's witness pair by its points' coordinates, never the kernel's list order. Export objects in timeline order. Every map is a `BTreeMap` or an `IndexMap`, and every object's keys are in schema order.
- **Counters, not clocks.** Session IDs count up within the process; revisions within the session.
- **IDs.** A feature ID the client doesn't give is random (M2.1): chosen once, it's then data, written in the file and returned in the result; a replay gives the IDs its recording holds (decision 20).
- **Concurrency.** A session runs its commands one at a time, in order. Sessions don't share generations, so one's work never changes another's results (MA2).
- **Not results, and described so in their schemas:** progress (`status`'s `done` and `steps`, MCP's progress notifications), logs (`read_logs`: times and the interleaving of threads), and a render's pixels (GPUs differ: plan decision 5; its camera is computed and deterministic). None reaches a name, a file, or another result.
- **The operating system's words.** An `io_failed` error's message quotes the system's reason ("No such file or directory (os error 2)"), which differs between platforms; its code and parameter don't.
- **Tested,** by extending the determinism sweep (`tests/determinism/`) to every command's result: the same commands on the same documents give the same bytes, run after run and on both checked platforms.

## 11. Open decisions

Each with its options, briefly, and the recommendation this design is written to. Decisions 1 to 7 are #50's, 9 and 10 the amendments' (A2, A3); 11 on are ones this design found the API forces, numbered on from the plan's. Already decided, and not reopened here: decision 8, the `naming` header (the maintainer, 2026-10-21); the face frame, F1 and F2 (Fable, 2026-10-22; the maintainer's veto open); `distance` and `angle` (Fable, 2026-10-23; the maintainer's veto open); mass properties precise (the maintainer's standing choice, 2026-10-09); an angle with a face whose surface isn't a plane refused (the recommended default; the maintainer's veto open); AR1's m + k (the M3 review).

**1. What a commit does** (M4.2). A transaction could end in the session's memory, with saving a separate command, or end on disk.
**Recommended, for Trevin:** a commit saves the document through `file::save`, and a rollback never touches the document's file, so the file only ever holds committed states and git sees nothing half-done; outside a transaction, each edit is its own transaction, applied and saved at once; one transaction at a time per session, not nested. (SolidWorks applies an edit at once and saves on Save; the app can hold a transaction open as its unsaved state, which M5 decides.)

**2. A file changed outside the session** (M4.2). Merge the change, let the last writer win, or refuse.
**Recommended, for Trevin:** outside a transaction the session reloads the file through the gate, found by comparing bytes before each command; inside one, the commit is refused as a `conflict`, naming the file, and the agent rolls back or begins again from the file's new state. Nothing merges silently.

**3. Edits as commands and as text** (M4.1). Text only, commands only, or both.
**Recommended, for Trevin:** both, from M4: `replace_text` through the gate, and typed `add_feature`, `set_field`, and `remove_feature`, each naming what it touches by ID, which M5's UI then uses; each through the gate, so a bad edit is refused whole.

**4. How queries are written** (M4.4). A phrase language, or structured filters.
**Recommended, for Trevin:** structured JSON filters, section 7's `query` shape, so a query means one thing and its errors name a field; a tie is never broken by name or position: every tied element is returned, and `tied` says so.

**5. How renders are tested** (M4.6). Not the API's, but it decides that a render's pixels aren't a result (section 10).
**Recommended, for Trevin:** as #50 recommends: tests read the ID buffer and check it against the projection by hand, never compare pixels with stored images; CI renders with a software rasterizer (Mesa's on the Linux runner), pinned in pixi.

**6. STEP export** (M4.8). In M4.8, or later.
**Recommended, for Trevin:** as #50 recommends: STEP in M4.8, its header written from the document so its bytes are deterministic; `export`'s `format` then takes `step` beside `3mf`.

**7. Transport** (M4.9). stdio, a network listener, or both.
**Recommended, for Trevin:** stdio only in M4, one client per server process, no network listener; several sessions in one process share one pool. MCP pinned at a revision with structured tool results and cancellation (2025-06-18 or later), which M4.9's study confirms.

**9. Undo after a commit** (M4.1, A2). An undo stack in the API, or none.
**Recommended, for Trevin:** no undo stack in the API. Git and the file's history are the history of committed states; an agent that wants to try something opens a transaction. A second history would be a second source of truth. The app's undo (SolidWorks has one) is M5's to decide.

**10. Cancellation** (M4.2, M4.9, A3). A cancelled request answered with an error code, or not answered.
**Recommended, for Trevin:** a cancelled request stops its kernel and solver work through the pool's superseded path and gets no reply, as MCP's cancellation rule says, so no new error code.

**11. The response's shape** (M4.1). Bare results, with errors carried only as MCP's `isError` text; or one envelope.
**Recommended, for Trevin:** one envelope for every command and every client: `ok`, the session's state, and either `result` or `errors` with `total` (section 2). A document's problems are a result; `ok: false` is a command that didn't do what it was asked.

**12. Edits name the revision they were made against** (M4.2). Decision 2 covers changes found between commands, but an agent that read the text before a reload would overwrite the reloaded change with `replace_text`. Options: a `revision` on every edit, on `replace_text` only, or none.
**Recommended, for Trevin:** every edit carries the revision it was made against, required, and a stale one is refused as a `conflict`.

**13. Which commands wait for the rebuild** (M4.2).
**Recommended, for Trevin:** a command that reads the model waits for the current revision's rebuild and never answers from an older one; an edit inside a transaction returns once the gate takes it; outside one it waits, since its save writes the fingerprints; the app reads the newest published model without waiting.

**14. Single-element measures** (M4.5). #50's row lists an edge's length, a radius and diameter, and a vertex's position as measures. As commands of their own, each refusing what it doesn't apply to; or as fields of each element's entry.
**Recommended, for Trevin:** fields of the entry (`length`, `radius`, `diameter`, `position`), `null` where they don't apply: one computation per number, so a measure and the element list never disagree (docs/ports/measure.md). `distance` and `angle` stay commands, as decided.

**15. How an edit names a member of a sketch's list** (M4.2). By its place (`constraints.3.value`), as the gate's errors name it today, or by its ID.
**Recommended, for Trevin:** by its ID (`constraints.g4h5j6k7.value`): a place moves when a member is added before it, and lists are sorted by ID. The gate's errors keep naming places for now; moving them to IDs is a separate change to error messages, for later.

**16. New error codes** (contract changes, `error-codes.txt`, protected).
**Recommended, for Trevin:** append `conflict` (after #89's `worker_unavailable`): a commit refused because the file changed outside the session, or an edit made against a revision the session isn't at. Not a kernel fault. The alternative, `io_failed` with a message (what `file::save` gives a file changed since it was read today), leaves an agent unable to tell a conflict, which it fixes by rolling back, from a full disk. And for M4.6, a renderer that can't be had needs a code, decided with M4.6: `worker_unavailable` if rendering runs in a worker, otherwise a new one.

**17. Warnings** (M4.2). ROADMAP.md's M4 brings a check's warnings (M3.2's D2 touching ends, and M3.3's agreeing redundant constraints, which it calls a warning) and `silico fmt --merge-touching`; #50 schedules neither.
**Recommended, for Trevin:** warnings in M4.2, in `check`'s result, each in the error contract's shape, its code from a new protected list, `warning-codes.txt`: `ends_not_joined` and `constraints_redundant`. `--merge-touching`, an edit, waits for M5's sketch editing, where SolidWorks merges points, and ROADMAP.md says so.

**18. The limits' values** (M4.1, A1).
**Recommended, for Trevin:** section 6's table, returned by `version`, with no limit on a command's whole time.

**19. What a tie is** (M4.4). #50 says "equal within the measure's tolerance". Equal within a relative tolerance isn't transitive (a chain of near values ties ends that aren't near), and an agent sees two different numbers called equal.
**Recommended, for Trevin:** a tie is equal as written: the same number after the measure is rounded as results write it (an area to 6 places, a length to the nanometre). One rule, exact on what the agent reads.

**20. Feature IDs from the API** (M4.2). Always the client's; made by the core; or made by the core from a seed a session takes.
**Recommended, for Trevin:** made by the core from the OS's randomness when the request gives none (M2.1), the client's when it does; a replayed session (M4.9) gives the IDs its recording holds. No seed in the API.

**21. Opening a document the gate refuses** (M4.2). Refuse to open it, or open it with its problems.
**Recommended, for Trevin:** open it, holding its bytes and problems, so an agent can mend it with `replace_text`, as SolidWorks opens a part whose rebuild fails.

**22. A session's bounds** (M4.2).
**Recommended, for Trevin:** a file is open in one session a process; `close` is refused while a transaction is open; a client that goes away rolls back its transactions and closes its sessions.

**23. Exact numbers across MCP** (M4.9). Let the SDK parse arguments into floats (not exact: refused), turn on serde_json's `arbitrary_precision` (which changes how every crate's serde_json reads numbers), or hand the core each call's arguments as text.
**Recommended, for Trevin:** the arguments as text (`RawValue`), read by Silico's own reader.

**24. The contract files** (M4.1).
**Recommended, for Trevin:** section 8's table: a snapshot of each command's schemas, the envelope's, this document's examples, and `warning-codes.txt` in `crates/silico-core/tests/contract/`, all protected; M4.9's `tools.json` checked equal to them.

**25. What `cache_clear` clears** (M4.3). #50 says "a document's cache", but the cache is the directory's (`.silico-cache/` beside the file, keyed by step, shared by every document there). Clear the whole directory's entries, or only those the document's current revision uses (which needs its keys, and leaves earlier revisions' entries).
**Recommended, for Trevin:** the directory's entries, all of them, and only the files the cache made; an entry removed is only a miss.

**26. Where the workspace is enforced** (M4.2, M4.9). In the MCP server, or in the core's sessions.
**Recommended, for Trevin:** in the core: sessions take an optional workspace root, which `silico serve` gives and the CLI doesn't, so the rule has one implementation.

**27. Key order** (M4.1). The error contract's files are in declaration order; the CLI's `check --json` line is sorted by key (serde_json's map), so Silico has two orders already.
**Recommended, for Trevin:** the API writes keys in schema order, in M2.1's layout; the CLI's line keeps its protected contract until you approve moving it to schema order too.

**28. Fingerprints after a typed edit** (M4.2). Keep them, so `check` in a transaction reports drift for everything the edit reached, or drop what the edit made stale.
**Recommended, for Trevin:** a typed edit drops the stored fingerprint of the feature it changes and of every feature that uses it, directly or not, and the commit writes their new ones; drift is still reported for every feature the edit doesn't reach. `replace_text` keeps the text as given, as a hand edit does.

## 12. Tests the design implies

For M4.2 on, each command's tests with its step. Expected values come from the design, from hand calculation, or from FreeCAD.

- **The examples, byte for byte** (#50's M4.1 row): every JSON block in this document is read by Silico's reader and written back by the API's writer to the same bytes; each equals its file in `commands/examples/`; each request block validates against its command's request schema and each result or error block against its result or the envelope's. A block that changes here and not in its file, or the reverse, fails.
- **The envelope:** every command, refused and not, gives exactly one envelope shape; a document's problems come in `result` with `ok: true`; the 101st gate error is counted in `total`, not listed.
- **Sessions (M4.2):** two sessions on one pool, a new revision in one never drops or stops the other's work (the fake kernel's call record, and the pool's tests with launch logs, as M1's are); a session dropped mid-rebuild leaves no partial state; IDs `s1`, `s2` in order, never reused; a file opened twice is refused naming the first session; a 17th session is `resource_exhausted`; a refused document opens with its problems, and edits but `replace_text` refuse until it's mended.
- **Transactions (M4.2):** rollback restores the text byte for byte (a non-canonical file stays non-canonical), and the model's fingerprints and element maps exactly (the same model); a rollback after a failed rebuild restores the last good model; a commit with nothing changed writes nothing (the file's bytes and inode unchanged); a commit after edits writes what `silico fmt` would; a second `begin` is refused; `close` with a transaction is refused; a client that disconnects mid-transaction leaves the file as it was.
- **Decision 2:** a file edited outside, outside a transaction, is reloaded (`reloaded: true`, a new revision); one edited inside a transaction makes the commit a `conflict` and writes nothing; an edit at a stale revision is a `conflict`; an edit that keeps the file's size and time is still found.
- **Edits:** each typed edit refused whole by the gate (the document, revision, and model unchanged), every error listed; `set_field` reads its value exactly (`0.1` is 100,000 nm) and refuses `id`, `type`, `v`, and `fingerprint`; removing a feature others use names each; `add_feature` without an ID makes a valid one, and with one keeps it; a typed edit drops exactly the fingerprints of what it reaches (a pad's length changed drops the pad's, its pocket's, and its fillet's, and keeps an unrelated box's); a replayed session with recorded IDs gives the recorded document byte for byte.
- **Long work:** a cancelled `check` stops its rebuild (the fake kernel's record shows the superseded path) and gets no reply; a cancelled edit is either whole or absent; a worker that crashes mid-rebuild gives one `worker_crashed` error naming the feature that met it, not one per feature (AR1's pattern), and the next command succeeds; a worker that can't be had gives one `worker_unavailable` and no feature.
- **Limits:** every row of section 6's table, at its value and one past it, refused naming its field, or counted where the table says so; `version`'s limits equal the constants they come from.
- **M4.3:** `check` with `fresh` builds every step and leaves entries a later rebuild hits; `cache_clear` removes every entry and nothing else (a stray file and a link out of the directory are left alone).
- **M4.4:** the entries' fields for a box (six faces, analytic areas, normals, centroids, `default_x` from F1's table) and a cylinder's side (its axis, radius, and diameter); names the same as the element map's, every one; the order holds across runs and platforms; the cursor pages through 32 elements two at a time and meets each once; "largest planar face facing +Z" finds the top by name, and on a block with two equal tops returns both with `tied: true`; an unknown kind or type, and `facing` on edges, refused naming the field; `schema` equals the snapshot exactly.
- **M4.5:** Fable's cases for `distance` and `angle` (`m4-measure-fable.md`, *Build and tests*), and the oracle cases there; mass properties equal to the fingerprint's, and to the analytic volume of a box with a hole.
- **M4.6, M4.7, M4.8:** each row's key tests in #50, plus their limits (section 6) and that each result's shape is its snapshot's.
- **Determinism:** the sweep extended to every command's result, byte for byte.
