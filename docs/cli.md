# The `silico` command

Each command is a thin client of the core's commands (`silico_core::command`), which the app and MCP (`silico serve`) run too, so they all do the same thing: `check`, `fmt`, and `show` open each file as a session, run one command on it (`check`, `format`, `outline`), and close it, every file on one kernel pool and one sketch solver (docs/design/m4.1-command-api.md, section 9).

| Command | What it does |
|---|---|
| `silico check [--json] FILE...` | Reads each document, puts it through the gate, rebuilds it (solving each sketch from the coordinates its file stores), and compares each feature's stored fingerprint, and each sketch's stored points, radii, and reference values, with the rebuild: a difference is `drift`, and a sketch that doesn't solve is a problem of its own. Every problem goes on stderr. A kernel fault (a worker that crashed, hung, or couldn't be had) isn't the document's: the problems found beside it go on stderr, then the fault, its suggestion the worker's own and then to run `silico check` again to retry it, and the file couldn't be checked (exit 2). With `--json`, one line per file goes on stdout instead: `{"file", "ok", "problems", "total"}`, where each problem is an error in the core's error contract. A file that couldn't be checked gives `{"file", "ok": false, "error"}`, its error in the same shape (`io_failed` for a file that couldn't be read, `invalid_input` naming the parameter `path` for a name that isn't UTF-8, or the kernel fault). That line holds the fault alone: the problems found beside it, which stderr lists without `--json`, aren't in it (a question for the line's next change of shape). Both lines are a contract (`crates/silico-cli/tests/contract/check-line.json`). |
| `silico fmt [--check] FILE...` | Rewrites each document in canonical form with its fingerprints as rebuilt and its sketches as solved (points, circles' radii, and reference dimensions' values), and says which fingerprints and which sketches' solves it wrote. Canonical form includes the header's `naming` (the naming scheme, M4.0), so `fmt` adds it to a document saved before it; `check` doesn't ask for canonical form, so it finds nothing wrong with such a document, and `fmt --check` says `fmt` would rewrite it. With `--check`, writes nothing and says whether it would. A feature that didn't build keeps the fingerprint stored with it, and a sketch that didn't solve keeps what its file holds; each says why, and the file is still written (exit 1). It accepts every feature's drift (the `format` command with no features named). A kernel fault (a worker that crashed, hung, or couldn't be had) is saved around, as a failed feature is: each feature it stopped keeps what's stored with it, the rest is written, and the fault is said last, its suggestion the worker's own and then to run `silico fmt` again to retry it (exit 2), as the `format` command saves around one (decision 32). So with no kernel to be had at all, `fmt` still writes the file in canonical form, every fingerprint and sketch as stored. It never writes a file this user may not write (as the system says), one whose save would pass the 16 MiB a document may be (the fingerprints and solved sketches it writes count: exit 1, saying so; exit 2 if the rebuild met a kernel fault too, said after it), or one that changed while it was being rebuilt (`conflict`, exit 2). It writes through a symbolic link to the file it names, and keeps the file's permissions. A file with other names (hard links) is written in place, its old text kept beside it (`.NAME.fmt-PID`, the name cut short if the document's is near the 255 bytes a name may be) until the new is on disk: if `fmt` is killed mid-write, that file holds the document as it was. The file is grown to its new length before it's written, so a limit on a file's size stops the write before it changes. That copy needs the directory to be writable, as a rename does: a hard-linked file in a directory this user can't write isn't formatted. |
| `silico show FILE` | The document's outline (the `outline` command): one line per feature, with its values and fingerprint, then its note, for a sketch its points, curves, and constraints, a line each as the file writes them, and for a fillet or chamfer its edges, a line each; then the bodies. Needs no kernel. |
| `silico schema [NAME]` | The document's JSON Schema, exactly as `crates/silico-core/tests/contract/document-schema.json` holds it; or, given a command's name (`version`, `open`, `status`, `cancel`, `begin`, `add_feature`, `text`, `check`, `elements`, `query`, `schema`, `mass_properties`, ...), its request's and its result's schemas, `{"request", "result"}`, as its snapshot in `tests/contract/commands/` holds them, so a script reads the shapes of a call's arguments and of its result. Needs no kernel and no file. A name that's neither is exit 2, with the names it takes. |
| `silico textconv FILE` | Git's text conversion: the outline, if the file reads as a document; otherwise the file as it is (conflict markers, a half-made edit), so `git diff` still shows it. |
| `silico serve [--workspace DIR]` | The MCP server (docs/design/m4.9-mcp.md): MCP 2025-06-18, JSON-RPC 2.0 one message a line, on stdin and stdout, for one client, as an MCP client starts it; every command is a tool (`tools/list`), its answer the command's envelope exactly. Its documents are in the workspace, `DIR` or the current directory: every path a tool takes is relative to it, and none may lead out of it. The root of a disk (`/`) is refused as the workspace (exit 2), since some MCP clients start servers there. It starts one kernel pool, sketch solver, and render worker (without a render worker, `render` is refused, said on stderr). Nothing but MCP's messages goes on stdout; logs go to stderr (`SILICO_LOG`, as for every command). It runs until stdin ends, stdout closes, or SIGTERM, then cancels every call in flight and rolls back every open transaction (exit 0), an answer being written as stdin ends written whole first; a second SIGTERM while it ends exits at once (exit 1); stdin that can't be read is exit 2. `--workspace=DIR` is the same as `--workspace DIR`. |

`--` ends the options, so a file can be named like one. `check`, `fmt`, and `show` refuse a file whose name isn't UTF-8 as a file that couldn't be read (exit 2), as the session commands every client runs refuse it, since a response couldn't name it exactly: the refusal names the parameter `path`; `textconv` reads it. A file's name is shown as it is, unless it holds a character a terminal would act on or draw as nothing (a control, an invisible character, a space but the plain one), a quote, or a backslash: then it's shown quoted, with those escaped as an outline escapes a document's text (`"bad\u{1b}.silico"`). A JSON line holds the name itself.

**Exit codes:**
- 0: nothing wrong.
- 1: a document has problems, or (with `fmt --check`) isn't in canonical form, or a file is longer than a document may be.
- 2: the command couldn't run. That means a usage error, a file that couldn't be read or written, or whose name isn't UTF-8, a file that changed while `fmt` rebuilt it (run `silico fmt` again), or a kernel or sketch solver that couldn't start or failed for reasons that aren't the document's (a worker crashed or hung, or something ran short).

## `git diff` of a document

To diff the outline rather than the JSON, add this to the repository's `.gitattributes`:

```
*.silico diff=silico
```

and tell git how to convert (once per clone, or in your global config):

```bash
git config diff.silico.textconv "silico textconv"
```

An edit to one value then diffs as one line of the outline, and each feature's line stays the same unless that feature changes.
